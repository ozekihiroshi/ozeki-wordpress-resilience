# ADR 0004：単独導入の製品と共通バックアップ部品

日付：2026年10月18日。状態：採用。利用者が「そのように整理してやっていきましょう」と承認。

## 決定

両製品は別プラグインのインストール・有効化を必須としない。共通する処理は単一の保守元から版を固定して各配布物へ組み込む。利用者の環境で相手プラグインを自動インストールしない。Resilienceは平常時の収集・設定と、WordPress外で動く復元ツールを分ける。

共通化の対象はDBダンプ、圧縮、資産のサイズ・ハッシュ計算、S3転送と固定版取得など。WordPress管理画面、スケジュール、保持方針、必要資産の判定、サイト全体の整合性方針、復元・Evidence評価は製品の責任とする。認証情報の取得方針や権限の分離も共通部品の利用だけでは保証しない。

保存形式の共有は契約を定めて検証する。既存形式の読込み可能性と、Resilienceの復旧要件を満たすことは別に判定する。旧オブジェクトのVersion IDがない場合などに、移行だけで検証済みへ昇格させない。

## 理由

プラグイン間の必須依存は利用者の導入・更新を複雑にする。一方、処理を二重実装すると不具合修正や互換性の負担が増える。共通部品を同梱すれば、単独導入とコード再利用を両立できる。ただし各製品への更新取り込みと回帰試験は引き続き必要である。

## 現状と移行

M1は既存製品の固定コミットの内部DBダンパーとvendorを利用している。共通ライブラリとしての独立性・単独導入を達成した状態ではない。過去のM1証拠はそのまま保存し、移行後の実行は別の記録を作る。

初期は同一サイトでどちらか一方の運用を推奨する。配布前に二重スケジュール、保持削除の競合、クラス名衝突、異なる同梱版の混在を検証し、併用検知と移行案内を実装する。相手の自動停止・削除は行わない。

共通部品のリポジトリ名・パッケージ名・配布形態は未決。抽出単位を先に契約試験で確かめる。既存製品の廃止・リブランドは決定しない。

以前の「既存バックアップ製品を必須の供給元とする」案は本決定で更新する。既存形式の互換読込みは維持すべき候補だが、他方のプラグインの稼働は復元の前提にしない。
