Ozeki WordPress Resilience — Milestone 1: Independent Recovery

文書版数：1.0
作成日：2026年10月11日
作業方式：段階的実装・検証・証拠保存
対象：小規模企業案内サイト（モデルA）

1. プロジェクトの背景

Ozeki WordPress Resilienceは、WordPressサイトを利用する小規模企業、スタートアップ、個人事業者向けのサイバーレジリエンス基盤である。

従来のセキュリティ製品のように、攻撃を完全に防止することだけを目指すものではない。

サーバへの侵入、データ破壊、ランサムウェア、障害などによって本番WordPressが完全に失われても、事業に必要な情報資産と復旧能力を維持することを目的とする。

本プロジェクトの基本原則は次のとおり。

本番環境の侵害・完全喪失を想定する。

復旧に必要な資産と権限を本番環境から独立させる。

バックアップの存在と復元可能性を区別する。

復旧能力を測定可能な証拠で評価する。

導入・運用の簡便性を重視する。

小規模事業者が継続できる低コスト構成を目指す。

技術的な測定結果と推定・仮説を混同しない。

2. Milestone 1の目的

今回の開発範囲は、Independent Recovery（独立復旧）の実証に限定する。

検証すべき命題は以下である。

元のWordPressサーバに一切アクセスせず、外部に保存されたRecovery Bootstrap、Recovery Asset Manifest（RAM）、Recovery Setを使って、別のクリーンな環境へWordPressを復元できること。

対象は、企業案内用の模擬WordPressサイト1件とする。

初期目標：

RPO：24時間以内

RTO：24時間以内

復旧方式：Cold Standby

復旧操作：手動を許容

費用：定常的な追加クラウド費用500円/月以下を研究目標とする

RPO・RTOおよび費用目標は、達成が保証されているものではない。必ず測定値と区別する。

3. 既存プラグインとの関係

既存製品：

Ozeki Database Backup for S3
https://wordpress.org/plugins/ozeki-database-backup-for-s3/

既存プラグインは独立したWordPressプラグインとして維持する。

Ozeki WordPress Resilienceは、その機能を利用する上位システムとして設計する。

次の制約を守ること。

既存プラグインを新製品へ統合しない。

既存プラグインの公開済み機能を無断で変更しない。

ソースコードを調査し、実際に利用できる機能と制約を確認する。

必要な連携方法を検討し、既存機能を利用できる場合は再実装しない。

既存プラグインの改修が必要と判断した場合は、理由、対象箇所、互換性への影響を文書化し、改修前に報告する。

既存プラグインについて、DBバックアップ、メディアバックアップ、S3オブジェクト管理、チェックサム、履歴管理の実装を重点的に調査する。

既存プラグインの実装内容を確認する前に、推測で連携コードを作成しないこと。

4. 作業上の安全制約

以下を厳守する。

実運用中のWordPressサイトを停止・破壊しない。

実運用DBを初期化・削除・変更しない。

既存S3バケットのオブジェクトを削除しない。

本番用AWS認証情報を実験用コードやログに記録しない。

個人情報や実顧客データを模擬サイトへコピーしない。

本番環境のDNSを変更しない。

実課金が発生するクラウドリソースの作成・変更は、対象と概算費用を提示して承認を得る。

既存リポジトリの変更を勝手に破棄しない。

Gitの強制pushや履歴破壊を実行しない。

疑わしい環境や不明な認証情報を発見した場合は、作業を停止して状況を報告する。

5. 作業フェーズ

本タスクは次の6フェーズに分割する。

各フェーズの成果物を作成し、検証結果を確認してから次の段階へ進む。

Phase 0：既存環境と資産の調査

目的

作業対象のリポジトリ、WordPress環境、既存バックアッププラグインの実装と制約を把握する。

実施内容

作業ディレクトリとGitの状態を確認する。

既存プラグインのソースコードとREADMEを調査する。

DBバックアップの生成形式を確認する。

メディアバックアップの保存形式を確認する。

S3のキー構成、メタデータ、バージョン管理の利用状況を確認する。

SHA-256等の完全性検証方法を確認する。

WP-CLIによる操作可能範囲を確認する。

RAM生成に利用できる情報を洗い出す。

復旧に不足する資産と情報を特定する。

成果物

docs/m1/00-environment-inventory.md

docs/m1/01-existing-backup-capabilities.md

docs/m1/02-gap-analysis.md

目的

本番環境を使用せず、独立復旧を検証できる再現可能な模擬サイトを用意する。

実施内容

WordPress、PHP、DBのバージョンを固定する。

投稿と固定ページを用意する。

画像とPDFを登録する。

テーマと必要最小限のプラグインを配置する。

ダミーの問い合わせフォームを用意する。

検証用の基準データを設定する。

復元前後を比較できる検査項目を用意する。

Dockerなどの隔離された環境を優先する。

6. Evidenceの管理ルール

Evidenceを次の3種類に分類する。

E1：Declaration

WordPressまたはバックアッププラグインから申告された事実。

E2：Observation

外部環境で資産の存在・取得可能性・完全性を確認した事実。

E3：Verification

独立した復旧環境で実際に復元・動作確認した事実。

各証拠には、最低限以下を記録する。

証拠ID

証拠種別

対象資産またはRecovery Set

実施日時

実施主体

検証方法

検証範囲

結果

関連ログ

E1だけでE3相当の復旧成功を宣言しない。

証拠がない場合は未検証と記録する。

7. 成功判定

以下の条件をすべて満たした場合に、Milestone 1の基本実証を成功とする。

AC01：元サーバへのアクセスなしで復旧できる。

AC02：BootstrapとRAMを独立して取得できる。

AC03：必須復旧資産をすべて取得できる。

AC04：DBの基準データが復元される。

AC05：メディアの完全性検査に成功する。

AC06：主要ページと機能が動作する。

AC07：E1、E2、E3の証拠を区別して保存する。

AC08：復旧手順を再実行可能な形で記録する。

RPO 24時間、RTO 24時間は別途達成判定する。

復旧の成立と性能目標の達成を混同しないこと。

8. 実装上の原則

機能を増やさず、実験目的に必要な範囲へ限定する。

既存プラグインの実装を尊重する。

標準的な技術を優先する。

余分な外部依存を増やさない。

特定のクラウドサービスに固定しすぎない。

可能な限り自動テストを作成する。

復旧手順は人間が読んで実行できるようにする。

将来の製品化を妨げる設計は避ける。

ただし、将来の機能を先回りして実装しない。

AI分析、高度なPEM、完全自動復旧、マルチクラウド、自動DNS切替は今回実装しない。

10. Codexへの作業進行指示

最初の実行ではPhase 0のみを行うこと。

まだRAM生成コードや復旧処理を実装しない。

最初に、作業対象となるリポジトリ、既存プラグインの実装、既存の環境設定、利用可能な試験環境を調査する。

Phase 0の終了時に、次の内容を報告すること。

確認したリポジトリとGitの状態

既存バックアッププラグインの実装概要

現時点で再利用できる機能

復旧に不足する資産・機能

実験環境の構築候補

想定リスク

Phase 1で実施する具体的な作業

判断・承認が必要な事項

Phase 0の調査結果を確認するまでは、Phase 1以降の実装を開始しないこと。

また、作業が進行できない場合は、確認できた事実、未確認事項、実行したコマンド、発生したエラーを具体的に報告すること。

推測で成功したことにしたり、未実施の試験を完了として記録したりしないこと。

12. 最終目標

本プロジェクトで最初に証明すべきことは、機能の多さではない。

「本番WordPressを完全に失っても、独立して残された資産と手順から、企業サイトを再構築できる」という事実を、再現可能な実験と証拠によって示すことである。

これをMilestone 1の最優先事項とする。
