# M1時間・費用の測定方法

測定対象は、模擬本番停止から独立復旧の主要機能が使えるまで。実装・設定準備時間と、復旧中の作業・待機時間を混同しない。

- 想定障害：模擬本番source、source-db、previewを停止する直前のUTC時刻を記録。
- 復旧開始：別ホストdmのBootstrap取得開始。
- 復旧終了：初回独立復元のDB・全メディア・HTTP検査がすべて成功した時刻。
- RTO：復旧終了−想定障害時刻。復旧中の失敗・再試行・待機も含む。
- RPO：想定障害時刻−バックアップDB取得時点。取得時点の幅があるため、収集開始を用いた保守的な上限を併記する。
- 再現性：初回に使用したものとは別のDockerボリューム・ネットワークで2回目の復元を行う。
- 検知待ち：この実験では障害を手動で宣言して直ちに復旧するため、監視による検知待ちは含まない。
- 人的時間：チャット・コマンド実行中の経過時間だけでは実作業時間を厳密に分離できない。正確な人時を測定済みとしない。

容量は実際に発行したS3オブジェクトのサイズから算出する。Versioningの旧版も課金対象だが、本実験の本体資産は新キーへ条件付きPUTで一度だけ保存する。失敗結果不明のPUTや検査用オブジェクトは別記録とする。

東京S3 Standard単価は0.025 USD/GB-month、PUT等0.0047 USD/1000回、GET等0.0037 USD/10000回。公式価格APIの2026-10-15公開値を参照する。S3から同一リージョンEC2への取得と、EC2からローカルへの外向き転送は別の経路として集計する。無料枠は保証に含めない。

24時間以内というRTO目標は今回の範囲で達成した。取得開始時刻から停止までの経過も24時間以内だった。ただしRPO値は復元可能なスナップショットの古さを表し、継続更新中のデータ損失を実測した値ではない。定期バックアップの運用保証でもない。収集はuncoordinatedであり、実運用のDB・メディア同時整合は後続課題。

初回のRTOには取得開始まで・復元開始までの操作待ちを含む。障害宣言前のIAM修正・収集・プログラム準備を含めない。監視の検知待ち、OS・Dockerの導入時間、DNS公開は対象外。2回目は取得済みの同じ資産を使った復元の再現性試験である。

## 費用の分離

- **定常保管の概算**：1セットを1か月保持すると、0.45666GiB × 0.025 USDで約0.01142 USD/月。十進GBで保守的に丸めても約0.0123 USD/月。既存バケット内の他データは含まない。
- **今回の保存・取得要求の概算**：成功PUT12回で0.0000564 USD、主要な成功GET23回で0.00000851 USD。設定閲覧、CLIの追加要求、AWS管理画面操作などはこの計数に含まない。失敗要求も含む請求額全体の確定値ではない。
- **今回の転送**：dmからWSLへの復旧資産本体は約0.490GB、別途プロトコル・メタデータ転送がある。同一リージョンS3からEC2への取得とEC2からインターネットへの転送は分ける。EC2外向き転送の適用単価・無料枠消費・請求額は未測定。
- **計算資源**：既存EC2を中継・取得に使い、新規EC2/EBSは作成していない。既存EC2料金の按分は未測定で、無料と扱わない。ローカル復旧はDB512MiB・WordPress768MiB・proxy64MiBのメモリ上限で実行した。実CPU時間や最大メモリ使用量は計測していない。
- **事故対応費**：今回は模擬試験であり、担当者人件費、待機、DNS、メール、侵害調査の費用を算定していない。復元の短い実行時間だけから事故対応費を推計しない。

無料枠・為替・税を前提に総額を断定しない。500円/月という研究目標は保管部分では十分小さいが、総費用としては未判定。日々のフル保存、旧Versionの蓄積、保持期間、実行環境の共通化を設計し、請求明細と照合する必要がある。
