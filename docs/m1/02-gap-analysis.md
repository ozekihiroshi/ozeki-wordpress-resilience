# Phase 0 不足機能と次フェーズの計画

調査日：2026年10月17日  
状態：Phase 0の調査結果。以下の実装案は未着手。

## 開発判断

既存バックアップ製品を変更せず、その出力と内部機能を評価して利用する方針を維持する。DB・メディアの生成、ハッシュ検証、内部復旧セットを新製品で全面再実装する必要はない。新製品はサイト全体の資産、独立した復旧入口と権限、復元手順、証拠・評価を補う。

内部RecoveryManifestと製品全体のRAMは役割が異なる。既存の厳密な形式を維持し、上位RAMが参照する構成を推奨する。これは設計案であり、スキーマ実装はPhase 2で決める。

## 連携方式の選択肢

A案は、公開版相当のbackup/mediaコマンドで生成した資産を上位で固定する。内部API依存は減るが、セットの対応付けと外部収集を新たに整備する必要がある。

B案は、0.3.0の調査コミットに固定し、外部アダプターからRecoveryCollector・RecoveryPipeline等を呼ぶ。既存の状態管理とマニフェストを活用できるが、公開APIの安定性は未保証。DB接続・WordPress固有情報を渡す収集側と、WordPressなしで動く復旧側を分離する必要がある。

推奨はB案の契約をPhase 2前に評価すること。既存コードのコピーや改修は現時点では不要と判断する。安定した呼出しが成立しない場合に改修理由と互換性影響を報告する。

## Phase 1の具体案

1. Dockerデーモンの起動方法とWSL警告を確認し、専用環境を利用できる状態にする。
2. 新プロジェクト用Git管理を整備する。秘密情報・ダンプ・作業ファイルを追跡対象から外す。
3. WordPress、PHP、DB、バックアッププラグインの版とイメージを固定し、再現可能な環境定義を作る。
4. 模擬本番と復旧先で別のネットワーク・ボリューム・DB資格情報を使う。外部送信は模擬サイトの目的に限定する。
5. 投稿、固定ページ、画像、PDF、独自設定、ダミーフォームを作る。実顧客データは使用しない。
6. DB検査値、メディアハッシュ、期待URL、ログイン、フォームの期待結果を定義する。フォームの成功は外部への実メール配送を必要条件としない案とする。
7. docs/m1/03-test-environment.mdと04-baseline-data.mdに起動・停止・再現方法と基準データを記録する。

Phase 1ではS3書込みや課金リソース作成を前提にしない。Phase 3の前に保管先、Versioning、権限、料金見込みを具体化して承認を受ける。

## 利用者に確認する事項

今回の調査結果を確認のうえ、Phase 1を上記のWSL＋専用Docker環境案で開始してよいか。使用版と内部APIの最終採用は、環境・契約確認に基づいて明示する。

Phase 0で既存プラグインを変更していない。新プロジェクトもRAM生成コード、復旧処理、模擬環境の実装には進んでいない。
