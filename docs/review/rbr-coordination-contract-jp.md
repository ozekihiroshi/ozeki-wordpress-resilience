# 同時編集・保持権限・WordPress保存入口：具体仕様 v0.2

2026年10月22日。**設計のみ・未実装・未実証**。[英語主仕様](rbr-coordination-contract.md)／[前仕様](rbr-storage-contract-jp.md)。前仕様の未決定事項を具体化します。S3先行原本を正常とする前提、常設別EC2なし、旧Restoreの承認条件を維持します。

## 採用する構成

- 同時編集：S3上の連番の世代枠に、条件付きで一度だけ完成目録を書き込む。
- 保持：初期構成では通常サイトに保持変更権限を渡さない。期限が足りない原本だけ、同じ内容の保護付きコピーを自動保存する。
- 保存操作：対象3ページではブロックエディターの「更新／公開」と画像選択をそのまま使い、内部の保存経路を変更する。別画面で二度保存させない。
- 構成：既存WordPress・PHP・DBとS3。別EC2、Lambda、DynamoDB、毎日の署名や承認は不要。ただし下記のDB反映条件を満たせる環境であることは必要で、対応確認は未実施。

## 1. 同時編集の確定

世代1、2、3…に対応するキーを用意し、それぞれ完成目録そのものを保存します。世代Nの次はN+1です。目録には親世代の固定Version ID・ハッシュ、操作ID、変更内容のハッシュ、原本の固定版、保持期限を含めます。

S3の`If-None-Match: *`を付けた作成を必須とします。二人が同じN+1を確定しようとしても先に成功した一方だけが確定します。原本の準備は並行して構いません。負けた側は原稿を残して競合を表示し、新しい内容を確認してから保存し直します。初版では別ページ同士の変更でも自動マージしません。

- 応答消失時は、同じ世代枠を読む。同じ操作ID・ハッシュなら成功結果を回収する。
- 別操作なら競合。N+2へ勝手に飛んで競合を回避しない。
- 確認できなければ結果不明を維持する。無条件の再送はしない。
- 次世代を示すキャッシュは補助情報。復旧時には列挙した連続世代と親参照を確認し、欠番・不明な版・保留情報を無視して最大番号だけを選ばない。
- 世代番号は確定順であり、時刻や「正常性の強さ」ではない。権限を盗んだ攻撃者による新規登録を、この仕組みだけで防げるとはしない。

これは時間切れで所有者を交代する分散ロックを使わない方式です。条件付き作成を対象prefixのポリシーでも強制し、削除・削除マーカー作成を通常権限では認めません。前世代への参照をたどるため、保持する世代の祖先目録も保持します。初版は自動削除なしなので、履歴圧縮は後の課題です。

### WordPressへの反映順も守る

S3で順番が決まっても、古い処理が後からWPを上書きしてはいけません。そのため初版は、S3確定後のWP反映が未解決の間、次の正式保存を待たせます。

反映時は専用状態行をInnoDBのトランザクションでロックし、同じDB接続で対象ページ・関係の変更と適用済み世代を更新します。S3通信や画像転送は短いDBトランザクションの外で行います。画像はS3保存後に準備し、確定ページで使うまでは準備中として扱います。

接続喪失後に古いSQLを勝手に再接続・再実行することを禁止する反映経路が必要です。失敗した処理を再開する際は、世代とWPの対応・内容を再確認します。単に一定時間たったからロックを無視する方式にはしません。

任意のプラグインの保存フック・外部送信・ファイル・キャッシュまでDBの巻戻しで元に戻せるとはしません。対応する反映処理を限定し、後処理の失敗も表示します。この条件を満たさない環境で「保護できている」と表示しないことを導入条件にします。

## 2. 保持延長権限は標準では不要にする

保持延長の専用権限を細かく設けるより、初版では**保持条件が足りない原本を新しい保護付き格納先へ再保存する方式**に絞ります。

新規導入用の設定案は、バージョニング・ガバナンスObject Lock・デフォルト36日・自動削除なしです。製品の最低保護期間は35日で、1日の差は処理時間の余裕です。既存の35日バケットの設定は変更しません。

保存操作に最大1時間の締切Tを設け、全参照先の保持期限がT＋35日以上であることを確認してから確定します。締切後は不明な確定結果を照合し、必要な保護を再計算します。時刻差や保持結果が不明なまま成功扱いにはしません。確定目録自身の実際の保持条件も確認し、異常ならWP反映を止めます。

| 原本の状態 | 自動処理 |
|---|---|
| 必要期限を満たす | 固定Version IDをそのまま再利用 |
| 必要期限が不足 | 固定版を取得・ハッシュ照合し、新しいキーへ同じバイト列を保存。新しい保持期限を確認 |
| 取得・保存・保持確認に失敗 | 前の完成世代を維持し、今回の確定を止める |

コピー後も論理的な原本ID・版・由来は同じで、S3上の格納先だけを区別します。以後の保存は新しいコピーを再利用できるので、毎回すべての画像を複製するわけではありません。更新のない日は処理不要です。容量は増える可能性があり、表示します。

通常サイトに必要なのは、対象prefixへの条件付き新規保存、固定版取得、保持情報の読取り、照合に必要な限定一覧・読取りです。保持変更・保護回避・削除・Legal Hold変更・バケット設定変更は与えません。利用者指定の保持上書きも許可せず、設定したデフォルト保持を使います。具体的なIAM文書は実装段階で作成・検証します。

復旧用読取り権限と管理・整理権限は別に保管します。将来の保持延長アダプターは選択肢ですが、初版に必要ありません。署名承認期限の自動延長も行いません。ロック期限後も自動削除しませんが、管理者に対する永久ロックを意味するとは説明しません。

## 3. 通常の更新ボタンでS3先行保存する

初期対応は対象3ページのブロックエディターです。「更新／公開」→S3原本保存→世代確定→WP反映と進み、途中状態を表示します。通常保存の追加承認は要求しません。

実体はプラグインの保存調整APIとします。操作ID・親世代・本文・関係・公開状態を受け、サーバ側で認証、nonce、編集権限、対象ページ、容量を確認します。エディターだけの制御にはしません。

- 対象ページへのコアREST更新は`rest_pre_dispatch`で調整APIを通らないものを拒否する。内部の反映処理からのみ書き込む。
- `rest_pre_insert_page`は入力検査の補助に使う。書込み後の`save_post`でS3へ送る方式は採らない。
- 自動下書き・リビジョンは未保護として保存できるが、公開中の本文や共有メタ情報を先に変更しない。
- タイトル・slug・画像・代替文・メニュー・関係・ゴミ箱移動も制御対象。本文だけ保護して済ませない。
- クイック編集・一括編集など未対応の既知入口は対象資産に限り画面とサーバで拒否する。無関係なページの通常編集は妨げない。
- Classic Editor、XML-RPC、WP-CLI、インポート、独自プラグインによる直接書込みは初期対応外。直接SQLや任意のプラグインコードまで通常のWPプラグインで封じ込めるとはしない。対象経路を表示し、差異があれば次回保護保存前に知らせる。

画像は一時領域で受信・形式検査し、S3の原本保存を確認してから正式なWP添付ファイルへ登録・サムネイル生成します。画像単体のS3受理と、画像を使用するサイト世代の完成は別です。アップロードのフィルターは補助検査であり、それだけで全経路を保護したとは扱いません。

既存メディアを使う場合は、管理者が承認した初期基準の方針に従い、保存操作の中で現時点の原本として登録します。過去のアップロード時点に保護していたことにはしません。保護外のページと共有する画像メタ情報も、保護経路で更新するか、保護用資産を分けます。

長引く保存は操作番号付きの処理中表示にし、画面から継続できます。ブラウザを閉じてもS3確定済みの記録は残り、管理画面を開いた時に再開します。無アクセスでもWP-Cronが必ず完了させるとは約束しません。

## 利用者に残る作業

初回に3ページとS3を設定し、既存素材の初期基準を了承し、復旧用アクセスを別途保管します。その後は通常の更新・公開操作です。人の判断を求めるのは、編集競合、未対応の内容、認証などの失敗、侵害疑いの申告、復旧後の公開です。毎日の署名、保持延長作業、別ホスト管理は増やしません。

この文書で設計方式を選定しました。対応するWordPress環境での保存経路・DB接続喪失・S3競合・権限の検証はこれからで、今回実施していません。
