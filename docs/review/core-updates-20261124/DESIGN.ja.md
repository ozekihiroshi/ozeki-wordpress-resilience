# 日常更新の保存漏れを直す方針

main `4053e1d` から分離した `codex/update-preservation-contract` で作業中。
本番反映、公開、WordPress.orgへの送信は今回行わない。

## 原因と修正範囲

初回保存には含まれる情報が、日常履歴の項目や変更通知に揃っていなかった。
本文の保存成功だけでは、関連する情報の保全まで確認できなかった。

| 情報 | 修正 |
|---|---|
| 記事パスワード・投稿者 | 保存と適用で項目を共有。空のパスワードと記録欠落を区別し、投稿者の表示情報も保存する。認証情報・権限は持ち込まない。実際の保存結果と再開時の一致確認にも項目を加える。 |
| カテゴリ・タグ | 未使用の分類、祖先、削除、記事への割当を含む確定状態を記録する。新版の記事詳細履歴から分類の写しを適用する処理はやめ、二重の解釈を残さない。 |
| 記事をごみ箱へ移動・復元した際のコメント | 操作完了後の状態と、WordPressが親記事に持つ復元用メタデータを記録する。ごみ箱解除時に元のURL名へ戻す情報も含める。コメントの適用は既存の検査を使う。 |
| 基本設定 | サイト名、トップページ・投稿一覧ページ、タイムゾーン、一覧件数と必要な関連値に限定。準備済みのソフトウェアや運用設定を維持する既存の適用規則は変えない。 |

基本設定のキーは `blogname`、`show_on_front`、`page_on_front`、
`page_for_posts`、`timezone_string`、`gmt_offset`、`posts_per_page`。
任意のプラグイン設定を取り込む仕組みではない。

既存の永続キュー、書込みロック、固定バージョンの読み戻し確認、正式履歴番号を使う。
取得失敗は未完了として残し、S3確定の失敗では凍結した内容を保持して再開する。
同じリクエスト内の変更は完了状態にまとめ、既に確定した同一状態の重複記録を避ける。

## 互換性と移行

健全な保存元と、準備済みの復旧先を新版に揃える。未完了の保存を解消し、
編集を止めて保存元で新しい初回保存を作成する。これを移行の起点とする。
検証・レビュー完了前に本番へ反映しない。

新しい原本・全体保存・独立した索引には、新版を必要とする形式名を付ける。
既存の原本・履歴と旧版で凍結済みのキューは書き換えず、旧形式の解析も維持する。

旧初回保存には、その時点のパスワードが含まれる。一方、その後の旧記事履歴には
パスワード変更が含まれない。その履歴を選んだ場合は、**復旧先を書き換える前に**
新しい初回保存が必要なことを案内する。該当する旧記事の個別復旧も同様。
過去のパスワードの推測や、複雑な公開確認待ちの移行管理は追加しない。

## 確認方法

不具合を再現した合成データを再利用し、各操作後のWordPressの保存値・
匿名閲覧時のパスワード要求を比較する。再保存後は別の新規WordPressへ再復旧し、
元の保存オブジェクトのハッシュが変わっていないことも確認する。

旧形式の読み取りと、変更していないrc.21による新しい原本・全体保存・索引の拒否を確認する。
提出済みZIPは変更しない。既存のキュー失敗・再開確認に加え、項目欠落、
古い分類の再適用、許可外の設定を検出する小さな契約確認を追加する。
結果は別記録とし、この設計文書だけで確認完了とはしない。
