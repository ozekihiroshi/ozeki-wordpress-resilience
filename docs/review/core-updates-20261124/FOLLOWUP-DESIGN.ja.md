# 仮説確認後の修正設計（実装前）

2026-11-24。対象は `codex/update-preservation-contract`、開始点 `629c245`。
この文書は修正設計であり、確認結果は別記する。2026-11-24の利用者指示により、公開前の候補版間の保存データ互換性は保証しない方針へ更新。
本番・既存原本と履歴・提出済みZIP・タグ・研究側の未コミット変更を保全する。

## 共通原因

記事や添付の本体を保存する入口だけでは、別操作による変更や、それに伴って変化する関連情報を捕捉しきれない。また、現在状態だけを復旧しても、次の通常操作が参照する状態情報が古いままなら利用結果が変わる。

修正の単位は、対応する操作の完了後に意味が成立する情報のまとまりとする。任意のメタデータをすべて戻す、未知の原本不足を見逃す、復旧先の設定を初期化する、といった対処は行わない。

## 修正対象

### 1. 予約を経由する公開状態

- 保護済み記事がpublishからfuture、draft等へ移っても、本文と公開条件を記録する。
- WordPressの予約公開が通常の記事保存フィルターを通らない経路を、完了済み操作として捕捉する。Cronには編集者のログインがないため、管理画面の権限検査を単に外して共用する実装にはしない。
- 最初から未公開の下書きを無条件に保全する機能とは分ける。初回保存に含まれた予約記事、予約公開により対応対象になった記事も検証する。
- 復旧先へのCron設定・予約実行の移植は行わない。非公開状態と日時を戻すことと、自動実行を引き継ぐことを区別する。
- 失敗時には完了を装わず、既存の永続キューで未完了を追跡し再開可能にする。

### 2. 投稿者表示と記事の引継ぎ

- プロフィール表示名変更とユーザー削除時の記事引継ぎを、本文保存とは独立した完了操作として保全する。
- 記事と投稿者の対応、表示名等を一緒に扱う。認証情報・役割・権限の復活は目的としない。
- 既に復旧用の権限なし投稿者を作成している場合は、表示情報を復旧点へ合わせる。復旧先の管理者などの準備済みアカウントは上書きしない。
- 新規復旧先と以前に復旧した環境で同じ結果になることを確認する。

### 3. コメントの状態遷移

- 本体に加え、WordPressがゴミ箱・スパムから戻すために使う既知の承認状態と時刻を記録する。
- 状態変更の途中ではなく、付随情報まで確定した操作を捕捉する。
- メタデータの存在だけでなく、解除による削除も適用する。古い初回保存の承認状態を残さない。
- 親記事のゴミ箱移動・復元と、コメント単体の操作を区別しつつ、共通の適用契約を使う。

### 4. 添付画像の削除

- 添付本体の削除に伴う、対応する記事のアイキャッチ参照と添付へのコメント等の削除を一体として反映する。
- 全記事を対象とするWordPressの一括メタデータ削除では記事IDが渡されないため、個別IDの通知だけに依存しない。
- 本文に古い画像URLが残っていても、正式に削除した画像と確認できる場合は記事の通常保存を妨げない。一方、削除の根拠がない原本不足は引き続き検出する。
- 削除を識別する情報は、新しい初回保存・再保存にも引き継ぐ。ローカルの一時的な記憶だけで判定しない。
- 既存復旧先に以前のファイルが残る問題は、新規復旧で画像が再配置される問題とは分ける。準備済みファイルを一括削除せず、適用前に残存を検出し、安全に準備し直す案内を行う方針とする。

## 記録形式と互換性への影響

コメントの完全な操作状態と、既知の画像削除を区別する情報は現在の日常記録だけでは表現できないため、記録契約の追加・改訂が必要である。

新しい記録を旧処理が部分的に読んで成功扱いにすることは避ける。未公開の `owr-core-updates-1` を含め、対応版を識別できる形式・検査を用いる。具体的な形式名は実装時に決定するが、同じ形式名の意味だけを黙って変更しない。

- 既存S3原本・正式履歴・Checkpointは書き換えない。新しい記録を追記する。
- 公開前の候補版間の保存データ互換性は保証しない。既存の一般形式を読める場合も、不足した承認状態や削除根拠を推測して完全な記録扱いにはしない。未公開core-updates-1は新しいcore-updates-2と区別し、対応しない形式は適用前に拒否する。
- 保存元と復旧先の双方を対応版へ揃える。従来の方針どおり、健全な保存元から新しい初回保存を作り移行起点とする。
- 新しい初回保存だけで解消できる現在状態と、過去の削除根拠が存在しない問題は別である。旧い参照切れは自動的に「削除済み」と認定しない。
- 提出済みrc.21は新形式を復旧できない。黙って不完全復旧するのではなく、適用前の拒否を確認する。

この影響を実装前に報告する。公開済み・提出済み成果物への上書きは行わない。

## 先に固定する合格基準

既存の各仮説確認スクリプトを回帰確認の起点とし、次の期待結果を修正前に固定する。

| 経路 | 必須結果 |
| --- | --- |
| publish→future→draft | 復旧先で古い公開状態へ戻らない。本文と日時・公開条件が一致 |
| 時刻到来による予約公開 | 標準の公開処理による結果が正式履歴から戻る |
| 投稿者名変更・削除引継ぎ | 記事を再保存しなくても表示名・対応が一致。新規/既存復旧先で一致 |
| コメントのtrash/spamと解除 | 承認済み・承認待ちの双方を正しく戻す。古い承認情報を残さない |
| 親コメント完全削除 | 返信のつなぎ直しを維持 |
| 添付説明・代替テキスト変更 | 現在合格している保存・復旧を維持 |
| 添付完全削除 | 本体、対応する参照、関連コメントが一致。新規復旧先へ画像を再配置しない |
| 削除画像への本文URLが残る記事保存 | 既知の削除は通常保存可能。根拠のない欠損は未完了として検出 |
| 既存復旧先の残存ファイル | 無関係なファイルを削除せず、残存を成功として見逃さない |
| 保存失敗・再開 | 凍結した操作を取り違えず、未完了を隠さない |
| 復旧後の通常操作・再保存・再復旧 | 状態・値・関係・必要な削除根拠が維持される |
| 互換性 | 旧原本不変、旧形式読取り、新形式を旧版が適用前に拒否 |

仮説を無制限に追加せず、今回再現した問題と直接関係する境界に限定する。実S3とブラウザの確認範囲は、模擬S3・標準APIの結果と区別して記録する。
