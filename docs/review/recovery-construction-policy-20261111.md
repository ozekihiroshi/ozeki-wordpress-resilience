# 保存と復旧の不整合から見直す構築方針

2026年11月11日。開発・確認・公開判断のための文書。

**今回の修正を、製品全体の確認完了とは扱わない。** 指摘箇所の修正、同じ原因が及ぶ範囲の確認、公開の判断を分ける。利用者に約束した情報が残り、復旧先で使え、その後も保全を続けられることを共通の合格基準とする。

本書は、rc.8への審査指摘からrc.9・rc.10、その後のACF・WP-Members確認までを対象とする。研究段階の計画を再開するものでも、新機能や大規模な再設計を要求するものでもない。現行製品の対応範囲を守るための構築・確認方針である。

## 問題が続いた構造

今回の事実から、次の弱点が認められる。

1. **保存側と復旧側が、同じデータの扱いを十分共有していなかった。** 初期標準値だけを見ると数値でも、通常の編集画面では真偽値になる。版情報を数値とみなすことも、実際に保存される内容と一致しない。
2. **値を戻すことと、使える状態を戻すことを分けて見てしまった。** 選択肢や入力条件、必要な標準設定がなければ、値が存在しても編集・利用できない。
3. **処理終了や代表値の一致を、広い成功の根拠にしすぎた。** 同じプロセス内での成功では次の起動を確認できず、標準項目だけの試験では追加・編集後の定義を確認できない。

これは、今回の2箇所だけ直せば他の対応データも正しい、と結論できる構造ではない。一方、他のすべての対応データに同じ不具合が存在すると確認したわけでもない。共通の基準で確認範囲を揃え、事実で判定する。

## 今後の構築方針

### 守る単位を、利用に必要なまとまりで定義する

アダプターごとに、保全する値、意味を決める定義、関連する情報、必要な導入済みソフトウェアを対応付ける。会員なら会員値と項目定義、表ならセルと必要な表示設定、ACFなら値と定義・フィールド参照をひとまとまりとして扱う。

対応表には、正常な保存形式、空・未選択・削除の意味、復旧先での扱い、確認方法を記す。保存処理、復旧規則、試験、利用者向け説明が同じ対応表を参照する。共有する実装を増やすこと自体を目的とせず、まず扱いの食い違いをなくす。

### 実際の操作が作るデータを基準にする

初期値だけでなく、通常画面での新規作成、編集、解除・空欄、定義変更で生成されるデータを確認する。実際の保存データを、個人情報や秘密を含まない回帰試験用データとして残す。試験の都合で型を整えたデータだけを使わない。

管理画面、RESTなどについて、製品が対応すると説明する保存経路を明示する。一つの経路の成功を、他の経路の成功として扱わない。入力検証と権限・nonce確認はそれぞれ必要であり、片方で代替しない。

### 安全な選択的適用と、正常な情報の復旧を両立する

認識した正常な対応データは、利用に必要な定義とともに復旧する。正常な値を落として処理が完了しても不合格とする。不適合・未対応の情報は原本に保持し、適用しない理由を示す。この二つを同じ「未適用」で済ませない。

不足する規則の対処として、不明な設定をすべて通すことはしない。拒否する型の試験に加え、通常操作で得た正しいデータが通る試験を対にする。原本の保存と復旧先への適用は引き続き分ける。

### 情報資産を復旧する原則を維持する

WordPress本体、テーマ、プラグインは信頼できる配布元から別途準備する。S3から旧環境の実行ソフトウェアを自動配置して補わない。動作に必要な標準設定は信頼できる導入済み版から得て、認識された保存設定を適用する。

既存原本・正式履歴・Checkpointを書き換えて修正を成立させない。保存形式を変更する必要が生じた場合は、実装前に理由、互換性、既存資産への影響を報告する。本書作成時の会員項目修正に保存形式の変更はない。その後のACF定義独立保全では、新履歴・復旧点の識別子を追加した。既存原本を変更しない互換性と確認結果は[取り込み記録](acf-definition-history-20261111.md)を参照。

## 共通の合格基準

| 段階 | 確認すること |
|---|---|
| 保存 | 通常の対応操作から保存され、未処理ではなく正式な履歴に確定する |
| 初回復旧 | 新しい環境に、値・必要な定義・関係が揃う。正当なID・URLの置換は意味の一致で比較する |
| 復旧後の利用 | 新しいリクエストで起動し、利用者が表示・編集・ログイン等、そのデータの用途に沿った操作を行える |
| 再保存 | 復旧先で別の保全領域を準備し、変更・解除・空欄などを保存できる |
| 再復旧 | 別の新しい環境で、変更結果が使える状態に戻る。欠落、重複、型や意味の変化がない |
| 復旧経路 | Baseline、Baseline＋正式履歴、Checkpointの適用結果を区別して確認する |
| 保全と失敗時 | 元の資産を変更しない。失敗時にどこまで適用されたか判別でき、成功表示で隠さない |

証拠には、対象ソースまたはZIP、連携版、操作経路、入力の種類、比較結果を記す。単体試験、CLIでの実環境確認、HTTPフォーム操作、ブラウザ操作を区別する。Plugin Checkの通過は、この一巡の動作確認の代わりにはならない。

## 今回の最終差分確認

確認対象は `main` の `96ad6e2` に対する `17f6e98`。製品変更は `RecoveryRules.php` の会員項目の復旧規則のみで、試験コードと実画面由来の試験データを加えた3ファイルの差分である。

- フラグは初期値と編集値の両方を受け取るが、不正な値・配列は拒否する。
- 項目型ごとの選択肢・入力条件を適用し、未知の設定は引き続き除外する。
- 保存処理、既存原本、正式履歴、保存形式、実行ソフトウェアを復元しない原則は変わらない。
- 追加回帰試験は既存の `application-rules.php` に含まれ、既存CIの実行対象になる。新しいCI実行が既に完了したという意味ではない。
- 前回の実行結果と差分を再照合し、今回の差分について追加の修正事項は見つからなかった。これは製品全体の公開判定ではない。

## 公開判断の前に確認すること

1. **方針と対応範囲を確認する。** 本書の合格基準が、製品の約束と一致するかを確認する。「今回の不具合が直った」を公開判断の根拠のすべてにしない。
2. **対応データごとの確認表を作る。** 上の未完了範囲を、具体的な操作・値・必要な定義・関係に分け、既存証拠と照合する。確認済み、不足する証拠、実際の不具合、設計上の対象外を区別する。
3. **不足する確認の順序を決めて実施する。** まず会員の登録・状態変更・削除・パスワード変更など利用継続に関わる操作、その後に他の対応データの不足を埋める。既存証拠で足りる試験は繰り返さない。全バージョン・任意拡張の無制限な組合せを新しい必須条件にはしない。
4. **公開可否の判定を残す。** 正常な対応データが失われる、使えない、権限が変わる、既存資産を壊す、失敗を成功と表示する問題は解消して再確認する。残す制限は、製品の約束に含まれるかを先に判断し、単なる免責で済ませない。
5. **新しい公開候補を別途確認する。** マージ後のソースから別の候補ZIPを作り、Plugin Check、導入・更新、重要な復旧操作、同梱文書・対応ソースの整合を確認して、送信前に報告する。公開判断と送信は別の段階として扱う。

差分確認を通過した修正と本書はmainへ取り込むが、それを公開承認や全体の確認完了とは扱わない。新候補の作成・再提出は行わない。次の作業は不足する確認の一覧と優先順を具体化することであり、直ちに公開することではない。
