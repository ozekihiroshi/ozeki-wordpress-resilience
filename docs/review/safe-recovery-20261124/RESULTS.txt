1. Recovery application boundary
Archived originals are unchanged. Whole-site and individual article application use
RecoveryContent. Executable HTML is filtered. Unrecognized shortcodes are readable
text; supported table/form references remain available. Code examples do not run
shortcodes. Source block instructions do not execute: stored presentation HTML is
used, or an instruction without stored HTML is shown as text for review.
CF7 input/mail placeholders are handled separately from WordPress shortcodes.
Archived mail attachment paths are not activated. TablePress cells, navigation URLs,
comments and supported metadata are included in the application review.

2. Temporary files
Each recovery owns a random private directory outside the web root. Normal completion
and ordinary failure clean its known files only. Failed rollback retains evidence;
an admin notice reports abandoned workspaces. Files belonging to the caller are not
deleted. Interrupted upload replacement removes its temporary file during rollback.
Tests cover ownership, active lock detection, retained evidence and abandoned state.
An OS kill during actual DB/file replacement has not been exercised.

3. Routine media checks
Unchanged access rules with no pending work avoid binary reconciliation and S3 calls.
Changes target affected attachment paths. Scope includes destination bucket/prefix/
region/owner. Explicit recheck forces reconciliation. The hint is local WP state,
not a new S3 record format. Metadata enumeration still occurs; this is not an O(1)
index or a large-site performance certification.

4. Markdown
The original Markdown stays byte-identical. Recovered rendered content is filtered
before the normal WordPress shortcode stage. Code examples remain text. This does
not modify the upstream Markdown plugin or claim safety of every external renderer.

Compatibility / limits
No S3 schema or existing original/history rewrite. An older implementation can read
the same records but does not gain these application safeguards.
Static block visual HTML survives, but block editor structure is flattened. Dynamic
blocks without stored presentation are not reconstructed. Review before release:
this is a deliberate execution boundary, not identical feature restoration.
The full roundtrip used plugin APIs and stored/rendered content assertions. It did
not include human browser operation, real SMTP delivery, real AWS latency/permissions,
or destructive OS interruption. Individual restoration uses the shared sanitizer but
its complete admin workflow still needs a dedicated end-to-end check.
Prepared destination software is neither installed nor initialized by recovery.
Do not interpret this checkpoint as completion of every external-plugin safety path.
