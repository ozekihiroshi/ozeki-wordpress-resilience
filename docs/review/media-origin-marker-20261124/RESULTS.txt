Recovery provenance and media access boundary — 2026-11-24 JST

Base: main 219fe0d. Work branch: codex/recovery-media-origin-boundary.
No production deployment, rc.19 ZIP/tag replacement, WP.org submission or email.

Cause
rc.19 marks recovered attachments with _ozeki_resilience_m1_origin_url so their
presentation can retain the execution boundary. FileScope's attachment metadata
allowlist did not recognize this own provenance key. Recovery placed 12 files as
public, but the next MediaAccess::current classification treated them as held.
The 39 held originals remained privately retained; the observed defect was a
classification disagreement introduced by our metadata, not permission granted
by that metadata. The uncorrected test stopped before recapture.

Fix
Recognize exactly _ozeki_resilience_m1_origin_url as access-neutral metadata.
Do not permit all keys with a Resilience prefix and do not override unknown keys,
private attachment status, inherited held/unknown conditions or directory guards.
This is a FileScope correction; archive formats, originals and history do not change.

Regression first
Extended the existing tests/file-scope.php before changing production code.
RED: public file scope changed after adding only our provenance marker.
GREEN: identical file scope with the marker; public remains public; inherited held
and unknown states, directory guards, private status and unknown metadata continue
to restrict placement. Both ordinary unknown keys and a lookalike Resilience key
are covered. Existing media-access.php and attachment-contract.php also pass.

Integration method
Use the same fixed-version community initial Baseline and formal history through 76.
Dedicated dm Docker sites, internal network only; trusted software prepared separately.
Install the unchanged rc.19 ZIP, then overlay only corrected FileScope.php in the test
sites. This is verification of the working fix, NOT a claim that rc.19 already includes it.
Source originals are a hash-verified read-only fixed-version copy. Resave uses a fresh
random prefix in the existing isolated S3 bucket through a scoped host broker; source
credentials are not supplied to the trial WordPress. No source writes or deletions.
Normal WordPress APIs/hooks and internal HTTP checks are used, not browser automation.
