# S3先行原本保存・Rule-Based Reconstruction：仕様と移行計画

2026年10月22日。main `f5ebf8ca74a50e469741b67f36d6dfa4e9200b6e`（PR #10マージ後）の静的調査。開始時の作業ツリーはクリーン。英語の詳細評価を主とし、この日本語版に結論と仕様をまとめます。実装変更・追加試験・本番調査・S3操作は行っていません。

## 採用する前提と構成

**正常運用の登録手順でS3へ先に保存したものを正常な原本とする。** この前提そのものを無侵害判定の課題へ戻しません。後からその原本と利用関係を失わず、新しいWordPressへ再投入できることを製品の責任にします。

標準構成は「現在のWordPress＋Resilience＋S3」。常設の別EC2、外部Controller、SSH、systemd、root権限は標準の必須条件にしません。障害時に利用者・保守技術者が新しいWordPressとResilienceを用意します。S3への復旧用アクセスは、失ったサイトの外に残します。

平常時：編集・アップロード → S3原本保存 → 本文・画像・関係を束ねた世代確定 → WordPress反映。
復旧時：新しいWordPress → S3接続・世代選択 → 計画 → 再構築 → 必須情報の検査 → 人が公開承認。

## 現在できていることとの違い

| 分類 | 対象 | 現状と扱い |
|---|---|---|
| そのまま使える小さな部品 | SHA-256、固定Version ID・サイズの照合 | 保存した版を識別する処理として再利用。保存サービス全体の導入が完成している意味ではない |
| 変更して再利用 | 本文の構造化、画像処理、リンク関係、欠落一覧 | 現在は保存済みWPからPythonへ抽出し静的HTMLを生成する。保存前の入力、独立資産ID、PHP主体の処理へ対応が必要 |
| 変更して再利用 | PHP保存ヘルパー | 認証・任意サイトの設定を呼出し側が用意する必要がある。現状は保持期間にも35日等の制約がある |
| 変更して再利用 | RAM・目録・進捗・管理画面 | 識別・完全性・失敗記録の考え方を残し、Profileと新しい作業記録へ適合させる |
| 研究・拡張として保持 | DB一式復元、Docker隔離、署名台帳、SSH/systemd、watchdog | 既存機能・証跡は削除しない。初期製品の標準利用に全部を要求しない |
| 新規開発 | S3先行保存の入口 | **現行は後から抽出する方式で、先行保存は未実装** |
| 新規開発 | Profile・資産ID・世代管理 | 原本と関係情報を束ね、完成した版を選べる契約が必要 |
| 新規開発 | 新WordPressへの再投入 | 新IDへの対応付け、再実行・中断再開、メディア登録、ページと関係の生成が必要 |
| 新規開発 | 通常／復旧モードの画面・凍結と隔離 | 現在のプラグイン画面は主に通知・外部状態表示。抽出・再構築の操作画面ではない |

最終ZIPの新規導入・更新成功は、これら新規機能の実装済み証拠ではありません。静的プレビューで確認したのは、素材の独立性・対応する表示・欠落報告です。

## 骨格となる保存仕様

- 原本は独立した資産IDを持つ。旧WordPressの数字のIDを恒久IDにはしない。
- 本文、画像原本、親子・リンク・使用位置・メニューの関係、再構築設定を別々に版管理する。
- サイト世代の目録が、それらの固定版を組み合わせる。必要な素材がそろうまで完成世代にはしない。
- 更新は新しい版、削除は新しい世代での不掲載として記録する。保護中の旧原本を消さない。
- Profileは定義済み規則を選ぶデータ。任意PHP、シェル、秘密情報、旧options全体を持ち込まない。使用できるテーマ等は新しいプラグイン側の許可範囲で制限する。
- 通常サイトの権限から保護済み原本・保持設定・利用保留の管理権限を分ける。具体的な接続方式は次の設計判断であり、今回IAMを変更しない。

S3とWordPressを一つのトランザクションにできた扱いにはしません。予定 → 原本保存 → 世代確定 → WP反映を分けます。S3保存後にWP反映だけ失敗したら、その原本を使って再開します。結果不明なら照合してから再試行し、二重保存・二重ページ作成を避けます。S3へ保存できない間は、保護された保存・公開の完了を表示しません。

自動下書きはローカルの未保護状態として許容する初期案です。最終保存・公開との境界を表示します。REST、CLI、外部インポートなど未統合の更新経路を保護済みと扱わない方針を、実装前に確定します。

## 原本保護・侵害疑い・保持期間

侵害疑いの申告後は正常系列への追加を保留し、以後の取得物を隔離します。高度な侵害自動検知は初期製品の前提ではありません。利用保留の記録も元WordPressの外に残し、復旧時に選んだ古い目録だけでは保留情報を隠せない設計が必要です。照会・権限・認証の具体方式は未確定の設計項目です。

同じ画像を再利用するたびにコピーする必要はありません。ただし、**新しい世代が参照する古い原本を先に失効させない**ことが必要です。原本・Profile・目録の保持を連動させます。保持延長の担当権限、保留中の保存、期限後整理は明示的に設計し、現行の35日設定やS3資産は今は変更しません。

既存サイトは、その時点の内容を初期基準として明示的に採用する導入手順が必要です。後から採取したものを「過去のアップロード時の原本」とは記録しません。既存Backup for S3の素材も、将来取り込む場合は別の由来として扱います。

## 承認と製品境界

旧Restoreの署名・期限・root所有台帳の条件はそのまま残します。新しいRBRの標準構成にその運用を必須として持ち込むことはしませんが、旧承認を無効化したり迂回したりもしません。新契約では正常原本の登録、サイト世代の完成、再構築検査、公開承認を区別します。毎日の外部署名作業を前提にしない方式を、これから仕様として承認する段階です。

Backup for S3は独立したバックアップ・通常復元製品のままです。Resilienceの必須依存にせず、今回共通部品や保存済みバックアップを変更しません。

## 移行順序

1. **保存契約を確定**：資産ID、Profile、世代、必要な会社情報、保存失敗と再開、保留情報、保持方針。
2. **最小の一続きの処理**：会社案内・サービス・連絡先とPNG/JPEGをS3へ先行保存し、手動準備した新WPへ再投入。固定のクリーンなテーマ、追加機能プラグインなしを初期案とする。
3. **操作と再開を統合**：設定、通常保存の状況、復旧接続、世代選択、計画、進捗、欠落、公開判断を画面から扱う。
4. **事故対応として完成**：凍結・隔離、利用保留の照会、保持・競合・不明結果の扱いを整える。ここまで満たす前に「侵害時に使える製品」とはしない。
5. **必要に応じて拡張**：対象形式・編集経路・ホスティング、任意の外部Controller。常設別EC2を標準へ戻さない。

現在のPython/Docker処理をボタンで包むだけでは、外部環境依存が残ります。既存のデータ規則と検査の考え方を再利用し、WordPressで動く処理へ作り直す方向を推奨します。既存コードと証跡は参照・比較用に保持します。

## 費用・負担と未確定事項

常設復旧EC2・SSH/systemd管理の負担を標準構成から外せます。一方、S3の原本保持・更新版・リクエスト・復旧時転送、保存時の待ち時間、例外対応の負担は残ります。原本の長期保持で保管量が増える場合もあり、すべての費用が必ず下がるとは見積もりません。

現段階で月額や工数の日数は未測定です。先行保存と再試行、新WPへの投入と再開が大きな開発箇所です。共有ホスティングの制限、認証方式、保存入口の網羅範囲、参照原本の保持、Profileと利用保留の権限を確定すれば、限定した実装見積もりに進めます。これらを理由に追加サーバを先に用意しません。
