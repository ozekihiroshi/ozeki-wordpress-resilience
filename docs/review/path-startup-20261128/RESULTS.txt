2026-11-28: 作業領域の境界判定と設定移行失敗の影響範囲

今回取り込む修正
1. SiteSnapshotとRecoveryWorkspaceが同じrealpath・ディレクトリ境界判定を使用する。
   WordPressと同じ文字列で始まる隣接ディレクトリを誤って拒否しない。
   WordPress内部と直接のシンボリックリンクを拒否する従来の条件は維持する。
2. 設定移行失敗時に、無関係な投稿・ユーザー・分類・REST操作まで止める全体ガードを撤去する。
   Resilienceの起動だけを止め、WordPressの通常の権限確認は維持する。
3. 正常移行では保護設定、初回保存の確認状態、未完了保存を維持する。
   移行が必要という理由だけでは保全中断の記録を作らない。
4. 起動に失敗して保全できない場合だけ、DBに中断の可能性を記録する。
   再試行の成功、無効化・再有効化では消さない。別リクエストが記録した中断も読み直す。
   再試行成功後は保護オフとし、未完了保存・停止中の変更の確認、新しい初回保存、
   明示的な保護開始を案内する。削除するのはローカルの初回保存確認マーカーであり、S3原本ではない。
5. 初回保存の成功後に中断マーカーを解除するが、それだけでは保護をオンにしない。

方針の訂正
開発途中では、移行開始時に中断マーカーを作り、正常移行でも初回保存を要求していた。
これは移行実施と保全中断を混同した過剰な動作だったため撤回した。この文書はその最終方針を示す。
中断マーカーは「変更が実際に失われた証拠」ではなく、保全しないまま通常操作を許可した可能性の記録。
新しい初回保存はその時点の状態を保全するもので、停止期間中の全変更履歴を後から再現するものではない。

English summary
Successful identifier migration preserves existing protection, baseline readiness and pending work.
Only a failed preservation startup records an interruption. A successful retry or plugin reactivation
does not erase it. Fresh reads account for a failure recorded by a concurrent request; both completion
orders were checked with separate PHP processes and actual MariaDB locks. A delayed failure is acted
on at the next startup, not by retroactively cancelling a running successful request.
Unrelated WordPress operations keep their core permission checks. Failure to persist the interruption
itself is explicitly reported; durability through a database write outage is not claimed.
The shared workspace path check fixes sibling-prefix rejection without introducing a web-root fallback.
The actual-S3 restart evidence predates the final successful-migration refinement; its unchanged admin
action path passed, with the test-transport limitations described above. No release artifact or review
submission is produced by this source merge.
