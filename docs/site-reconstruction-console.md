# Multi-material reconstruction console

This console belongs to `owr-site-materials-v1`, separately from the retained three-page signed console. It reuses fixed-version receive, request-derived Q and the shared WordPress projection CLI. No old three-page receipt, fixture generation, source database or signature approval is substituted for the selected material generation.

## Setup and operation

Use the existing guarded dedicated editor enrollment. Configure an external `tools/site-reconstruction-worker.py --config /private/recovery.json` beside the editor worker. Reuse `transport`, `work` (the existing writer journal/object scope), `bridge` and `prefix`; add `recovery_work` (a private dedicated folder outside WordPress), `target_label`, `wordpress_image` and `database_image`. Images must be locally present pinned `sha256:` IDs. Do not place credentials or runtime configuration in the web-writable bridge.

For experimental S3, recovery uses its own reader transport ledger under `recovery_work/reader`; it never shares the writer transport journal. The worker reads up to the newest 50 journal records and verifies committed material generations through the configured storage adapter. It publishes the fixed receipt, Q digest, asset summary and jobs at `bridge/reconstruction/status.json`; WordPress reads it and writes only small selected-generation requests under `reconstruction/requests`. Arrange the same restricted shared-directory permissions as the editor bridge. First run the worker so these directories exist. The worker must have Docker access; WordPress does not invoke Docker or a shell.

In WordPress open **S3先行編集 → 素材世代から再構築**. Select an immutable generation, review its fixed Version ID, Q digest and material list, then choose **選択世代を専用復旧先へ再構築**. Results include the selected generation, Q, verification outcome, reconstructed IDs and private target identifiers. Reads do not alter source content. Only administrators can read or enqueue, and WordPress REST cookie/nonce authentication applies. A stale report (over 120 seconds) or changed Q/profile refuses requests.

The worker fetches and verifies the selected generation again immediately before calling `site-reconstruct-private.py`, which reuses the dedicated target builder and `site-wordpress-apply.php`. It creates a new internally networked WordPress/DB pair, checks pinned images and no default network route, disables Cron and outbound application effects, applies as drafts, checks the expected logical state and idempotent replay. Successful private targets are retained for operator inspection. No public port, DNS change or production overwrite is accepted. The protected source may continue to exist during this test but its DB is never an input to reconstruction.

## Failure and lifetime boundaries

An identical generation/Q/profile request maps to one job. Repeated clicks do not create additional targets. A failed or interrupted job is not automatically retried; inspect the private execution log, bundle and `target-*/resources.json` first. A restarted worker marks a previous running job interrupted. It does not infer success or delete resources. There is no retry/cleanup UI yet. Verified jobs can expose the private content snapshot described below. The dedicated test harness removes only its own target resources after verification.

Target DB/files currently use private temporary Docker storage. These are inspectable disposable recovery targets, not durable production installations; restarting/removing them can discard reconstructed state. Cold runtime bootstrap, external-host placement, live theme preview/public activation, a durable deploy target and loss of the generation-reference journal remain separate operational work. Runtime images come from the local cache. The report contains a Q digest and material summary, not the full expected document. Older than 50 journal records require operator-side selection tooling.

Storage integrity/retention checks and new-schema signature refusal remain unchanged; no automatic signature integration or approval renewal is added. Invalid/expired material generations are displayed as ineligible. This feature introduces no cloud PUT operations: it reads existing generations and creates isolated local targets.

## Bounded catalog reuse

The worker now caches only the verified catalog summary in its private recovery directory, keyed by storage context and the full fixed receipt. It reuses the summary for at most 3,600 seconds and never beyond the generation protection deadline. Clock rollback invalidates the cached age. The screen exposes the original check time and protection deadline separately from report freshness. A fresh heartbeat does not claim a fresh S3 check. Unchanged catalogs perform no S3 GETs; new or expired entries receive full verification.

Execution always fetches the selected fixed generation and all its materials anew through the existing receive function, including retention, hashes and request-derived Q, immediately before target creation. The previous consecutive duplicate receive is removed; cached catalog data never authorizes execution by itself. Changes or loss of retention after catalog creation still block reconstruction. Signature policy is unchanged.

An unassisted live-S3 browser trial passed all 43 checks with the corrected enabled-button wait. Both seven-material and four-material selected generations matched Q. The unchanged seven-generation catalog measured 0.115 seconds with zero storage GET calls in this environment; this is a warm-cycle measurement, not a cold-start or network SLA. All 38 related regression tests passed. First-time/expired catalog checks and long reconstruction work can still delay report updates; the 120-second stale-report refusal remains. See [evidence](../evidence-public/site-reconstruction-catalog-cache-validation.json).

## Private reconstructed-content preview

After successful reconstruction, the external worker runs `site-preview-export.php` inside that exact private target. It reads the target DB and attachment bytes, checks them against the verified materials, and exports a content snapshot. It never renders the old source DB. The snapshot is bound to the job, generation and Q and stored outside the web root in the private bridge. A preview export failure is reported separately and does not discard a successful reconstruction.

In **素材世代から再構築**, choose the preview button for a verified job. The administrator sees reconstructed titles, body text, images and internal links. Pages are presented as sections; internal links navigate within the snapshot. The display explicitly identifies the generation, Q and capture time. It does not expose a target port, publish drafts, change DNS, or activate themes, forms or external integrations. This is a snapshot of reconstructed content, not a live theme/site preview. It remains viewable after the temporary target stops and does not certify the target is still running. Earlier completed jobs without an exported snapshot do not automatically gain a preview.

Preview JSON requires the same administrator capability and REST authentication as the console and is returned with no-store caching. The iframe has an empty sandbox, CSP denying scripts, forms and external resources, and embedded verified image bytes. The operator must keep the bridge outside publicly served directories. Payloads are bounded at 128 MiB; large previews may be unavailable due to server/browser memory limits. Cleanup/expiry of stored preview files is still an operator task.

Preview validation: 58 dedicated browser checks passed, including actual target text and decoded images, internal link navigation, both generations, anonymous/subscriber denial and unchanged source content. Storage used a persistent S3 double. The asynchronous-button wait and toolbar-scroll corrections were test-harness issues; final verification required no assistance. [Evidence](../evidence-public/site-private-preview-validation.json).

### Experimental S3 preview verification

The real-S3 browser run passed all 58 checks without browser assistance. It edited company text, added a post and page, registered and replaced an image, then resumed the same committed generation after an injected worker exit. The latest seven-material and original four-material generations each reconstructed from their fixed S3 objects and matched the selected Q. The administrator preview displayed actual target text, decoded image bytes and a working internal page link. Anonymous and subscriber requests were refused. Generation, Q, verified result and preview identity were independently compared after the run. Trial targets were removed; S3 evidence remains retained. This run used repository code, not a newly frozen ZIP.

An earlier run was incomplete. WSL attempted S3 IPv6 connections that timed out, while IPv4 TCP connected in about 0.05 seconds. The underlying host IPv6 routing cause remains unconfirmed. A process-local test helper preferred IPv4 for S3 and SSH authorization; no OS, production or plugin networking configuration was changed. The original uncertain PUT and its journal were retained, not resent. The successful run used a new generated-data prefix.

That failure also exposed an adapter defect: a newly created adapter directory lacked an operations journal until its first successful read or write, so restarting after an early read failure failed to load the journal. New stores now persist their empty journal immediately. An existing missing or uncertain journal still fails closed and is never silently reset. Nine offline adapter guard tests and fourteen reconstruction worker tests passed. These adapter and environment findings are separate from the earlier browser timing corrections. [Live-S3 evidence](../evidence-public/site-private-preview-live-s3-validation.json).

## Installing the private-preview build

Update both the WordPress plugin ZIP and the matching external operator kit. The plugin displays the preview; the kit exports it from the verified private target. Preserve the private worker configuration, generation journals, bridge requests/reports and preview files outside the replaceable program directory. Installation does not enroll a site or start reconstruction automatically. Existing successful jobs without a snapshot need operator handling; installing this build does not recreate their targets or backfill previews.

The S3 adapter journal initialization correction is included in the operator kit. It does not repair or reset existing missing/uncertain journals. The WSL IPv4 preference used in the dedicated live trial is an environment workaround and is not installed by either ZIP. Keep the original unsuccessful trial records. For actual public deployment, durable target storage, live theme validation and explicit publication remain separate work.

ZIP lifecycle verification exposed a preview switch race: the visible old iframe could be inspected before the new generation loaded. The UI now hides the previous snapshot, replaces its sandboxed frame, and reveals it only on load, bound to the selected generation. A request sequence rejects late responses. This UI defect is separate from the S3 adapter initialization fix and WSL networking issues. The browser harness waits for the loaded selected-generation marker. The first ZIP/trial remains recorded as incomplete.

The subsequent lifecycle trial found a harness-only stale-element reference while the UI replaced its iframe. The wait now samples visibility and generation atomically in one browser script. This does not relax any Q, permissions or content assertions.
