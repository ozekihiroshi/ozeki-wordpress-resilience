# 研究成果・保留課題の分類と次の検討順位

更新日：2026-11-06

作業種類はエビデンス整理。状態は既存文書・コード構成の確認完了であり、新たな実装受入や動作試験ではない。分類と検討順位を研究用ブランチへ残すことを今回の完了条件とする。製品完成への寄与は、独立した復旧資源の保全という目的に必要な研究と、現行製品の完成条件に含めない研究を分け、開発範囲の拡散を防ぐこと。

## 確認基点と読み方

- 保管先：`archive/research-before-wordpress-org`。旧研究を現在の製品仕様として扱わない。
- 公開側の比較基点：ローカルmainの `599b3077f0aebf3b99d07dfa38725ffef858fa15`。以下の取込み状況はこの版の[README](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/599b3077f0aebf3b99d07dfa38725ffef858fa15/README.md)と関連資料に基づく。GitHubの最新状態や稼働環境を今回新たに監査したものではない。
- 過去の試験は対象ビルド・環境・操作の範囲で読む。実S3、模擬障害、ブラウザ、ZIP導入更新の結果を同一視せず、現行版で全試験を再実行したとは扱わない。
- 「取込み済み」は機能・設計の継承を含み、研究コードの無変更移植を意味しない。「役割を終えた」は削除指示ではない。

## 1. 基本製品へ取り込まれた成果

| 成果 | 現行製品での位置づけ・境界 |
| --- | --- |
| 原本と付随情報の分離保存 | 独立原本、固定版参照、再取得・照合後の正式履歴確定。無害性の保証ではない |
| Baseline・独立Checkpoint・指定時点復旧 | 初期取得は管理者が信頼するWordPress状態から、通常Checkpointは保全済みS3資産と正式履歴から作成。未記録の現行状態を混入させない |
| GFS・保持・削除・残存資源からの復旧 | 基本製品に実装され、専用範囲での実削除、管理画面・定期経路、復旧の記録がある。任意の環境や長期反復の保証へ拡張しない |
| 保存状態・未確定・再開・復旧結果表示 | 保存失敗や未確定を可視化し、明示的に再開。復旧の自動巻戻しや無条件の自動再開ではない |
| 標準投稿・固定ページ・画像・コメント | 対応する保存・変更・削除と関連情報の再構築。あらゆるメタデータや更新経路を保証しない |
| 対応プラグイン | Markdown Documents、CF7／Flamingo、WP-Members、TablePressの所定範囲。バージョン・適用規則の条件付き |
| ACF無料版 | 公開側へ取込み済み。投稿・固定ページの基本15型。値・定義・フィールドキーを分離し、未知情報は自動適用せず保持。PROは対象外で対応予定もない |
| AWS標準認証・IAMサンプル・利用ガイド | 標準構成の導入・運用条件として整理。試験用の認証補助を製品依存にしない |

根拠：[研究段階の検証索引](../releases/product-evidence-index.md)、公開側の[ACF無料版の範囲](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/599b3077f0aebf3b99d07dfa38725ffef858fa15/packages/markdown-m1/docs/acf-free.md)と[ACF検証範囲](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/599b3077f0aebf3b99d07dfa38725ffef858fa15/packages/markdown-m1/docs/acf-free-verification.md)。

重要な差：現在の公開側は、信頼できるWordPress・テーマ・プラグインを別途準備し、保存した旧テーマ／プラグインコードを復旧時に展開・実行しない。旧研究のソフトウェア収録・復元試験を現行製品の保証に読み替えない。

## 2. 将来のオプション候補

| 候補 | 残す価値 | 再採用前に決めること |
| --- | --- | --- |
| 独立署名・USB保管 | 保存側と署名・照合の信頼起点を分ける | 現行資源の署名対象、鍵の管理者・保管場所、紛失／侵害時の扱い、自動処理との両立 |
| Pushover・独立監視 | 保存失敗・未確定やシステム停止の見落としを減らす | WordPress内の失敗通知か、WordPress停止中も検知する外部監視か。最小イベント、宛先・資格情報の管理 |
| 可読文書の抽出・静的プレビュー | WordPressの再構築前でも原本を利用する補助手段 | 現行のS3分離原本から必要な範囲だけを扱えるか。既存の取得・閲覧で足りるなら追加しない |

USB・署名とPushoverの検証結果、鍵の配置、未確認事項は[保留研究記録](usb-signing-pushover-held-research-ja.md)を参照。過去の署名鍵は手元PCに置き、USBは暗号化バックアップと公開信頼情報の持出しに使用した。日次保存は署名せず承認待ちとなり、署名は別操作だった。USBだけに鍵を置く構成や、非抽出型ハードウェア署名装置の実証ではない。

可読文書・プレビューは[抽出研究](../guides/portable-content-extraction.md)と[プレビュー研究](../guides/portable-preview.md)を参照。旧抽出経路にはWordPressの起動を要する部分もあり、侵害された元環境を安全に解析する手段とは扱わない。一般サイトの完全な表示や無害化は保証しない。

現在の鍵・トークンの残存、有効性、媒体保管、通知サービス・タイマーの稼働状態は今回未確認。過去の試験成功や「保留」という分類を、現在の安全性確認・停止確認と同一視しない。

## 3. 現行製品への開発経路として役割を終えたもの

| 研究経路・成果物 | 今後の扱い |
| --- | --- |
| DB・サイトファイル一式の取得と復元 | 情報資産再構築とは別方式。参考実装・過去の証拠として残す。別製品への移植済みとは扱わない |
| Pythonワーカー、SSH補助、共有bridge、専用Docker再構築 | 現行製品の必須構成へ戻さない。必要な知見だけ個別に評価する |
| 専用編集画面、限定ページ向けコーディネーター | 標準編集画面との連携へ移行した旧試作として保管 |
| 外部キュー凍結・再配送、全更新経路の停止制御 | 専用構成の研究。現行製品の不足や未達条件に数えない |
| 取込み前のACF試作、旧ZIP・旧README | 履歴・比較用。最新実装の説明や再配備用に使わない |

根拠：[旧経路と移植候補の棚卸し](../legacy-transfer-inventory.md)、[外部更新元の制御](../guides/wordpress-external-writers.md)、[旧キュー復旧](../guides/queue-recovery.md)。各資料の未達事項は当時の方式に対するもので、現在の基本製品へ自動的に引き継がない。試験用Docker・アカウント・ブラウザ等の問題は試験環境の運用で扱う。

## 4. 次に検討する順位

1. **通知が必要な失敗を絞る。** 保存失敗に管理者が気づけない問題か、元サーバ停止中にも検知したい問題かを区別する。既存表示・運用で不足する具体例と最小構成が説明できれば設計判断を終える。実装再開や送信の承認ではない。
2. **独立署名で守る境界を決める。** USBという道具から始めず、保存側侵害後にも独立して残す確認基準を定義する。署名対象・鍵の管理場所・自動化の必要性を決め、その後に保管方式を比較する。
3. **原本の直接利用に不足があるか判断する。** 復旧エンジンなしで必要な情報を利用する目的に対し、現行ファイルの取得で足りるか確認する。足りなければ抽出・一覧・プレビューの最小範囲を検討し、汎用サイト生成へ広げない。

これらは必須の開発予定でも、現行製品の公開を妨げる欠陥一覧でもない。採用時には完成目的との関係、実際の復旧への影響、環境固有の問題か、複雑化せず対応できるかを説明する。

次の実装は、その時点の公開mainを確認して別の研究ブランチを作り、必要な成果だけを移す。この研究アーカイブ全体をmainへマージしない。今回は文書の保存だけとし、追加試験、製品コード・設定・S3資産・公開済みZIPの変更やリリース公開は行わない。
