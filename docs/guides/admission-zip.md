# 初回取得・日次接続・担当者確認の固定ZIP受入（試作版）

対象は0.1.0-dev.1の開発候補です。WordPressプラグインZIPと外部処理を含むdevelopment kitは別配布です。プラグインのインストールだけでは外部処理・鍵・サービスは配置されません。

## 整理した実装

- 導入前検査・担当者確認を初回取得入口へ接続。ロック取得後と書込み停止直前に再検査し、条件不足なら取得を開始しません。
- 日次処理の `tick_admitted` は取得結果の検証と保存前再検査を行います。保存完了と署名承認待ちは別状態です。結果不明を勝手に再送しません。
- 初回用の短期確認と日次用の最長7日の担当者確認を分離。技術的な鮮度・構成は毎回再検査し、確認期限は自動延長しません。
- 確認状態は既存報告・SSH・systemd・WordPress読取り専用画面で確認できます。OS再起動の試験結果は別の証拠を参照し、ZIP試験で繰り返しません。

## 検証方法

`build-release.py` で新しい出力フォルダへ生成し、manifestとSHA256を固定します。旧候補ZIPは上書きしません。`run-deployment-zip-lab.py --operator-review --distribution <配布フォルダ> --old-zip <既存候補ZIP> --output <新規試験フォルダ>` は、ZIPから展開したコードで既存のWordPress受入試験を実行します。

新規導入と既存候補からの上書き更新を、ネットワーク隔離したWordPress/MariaDB/Chromiumで検査します。実際のPlugin_Upgrader、無効化・再有効化、配布全ファイル一致、非既定設定・Cron・wp-config・要求記録・外部報告・SQLite履歴の不変を確認します。担当者確認の表示、権限、POST拒否も確認します。

初回取得・日次処理の専用fixtureから実際のローカル保存待ち記録・確認原本を生成し、状態一式のハッシュを比較します。保存先はローカル代替であり実S3を使用しません。保持検査用コピーは元の絶対パスを含むため、そのコピーを新しい運用領域として再開できることや台帳移行まで保証しません。外部設定とコードは別配置で、展開による設定上書きを拒否します。

同じ0.1.0-dev.1という版数でも旧・新ZIPのハッシュで区別します。正式版間の移行とは呼びません。最終試験後の結果文書・証拠は固定ZIPの外に保存し、ZIPを黙って作り直しません。

## 残課題と分類

本番スケジュールへの適用、確認原本の署名・失効台帳・ロールバック対策、長期無人の棚卸し更新、担当交代・鍵更新・別媒体更新の統合運用は未達です。従来入口をすべて新ゲートへ移行したとは扱いません。管理画面の正常表示は無感染や本番復旧の保証ではありません。

環境障害、試験基盤の不備、製品不具合は別記します。既知のWebDriver起動問題は根本原因未確定であり、今回成功しても解決済みにはしません。72時間観測、実S3保存・署名・復元、正式公開は今回の受入範囲外です。

初回ZIP試験では保存・更新・保持が成功しましたが、目視確認で試験用転送状態の定義不足を発見しました。製品画面は正しく未確認を表示していました。試験基盤へ対応するhealthファイルと定義を追加し、ブラウザでも未確認表示がないこと・受渡し成功表示を必須化しました。初回ZIPと結果は保持し、修正した試験を含む別ZIPで再検証します。
