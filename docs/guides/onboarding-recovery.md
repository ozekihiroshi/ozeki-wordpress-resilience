# 導入から日次取得・承認・隔離復元まで（試作版）

2026-10-21。基準はPR #5マージコミット `0b10e54`、0.1.0-dev.1。正式リリース・本番適用許可・72時間観測の合格を意味しない。操作主体は外部処理担当、サイト担当、署名担当、復旧担当。兼務しても権限と保管場所を分ける。

## 操作の順序と受渡し

|順序|担当・操作場所|入力と既存入口|進める条件・結果|
|---|---|---|---|
|1 本体導入|サイト担当・WordPressのプラグイン画面|[固定ZIPの新規導入/更新](admission-zip.md)|設定と履歴を保持。インストールだけでは取得は起動しない|
|2 外部配置|外部処理担当・専用Linuxホスト|[設定計画](external-deployment-plan.md)のplan→generate→[systemd配置](generated-systemd-lab.md)|対象は棚卸し/検査/監視/報告経路。鍵・所有者・固定コマンドを確認。取得や署名サービスまで生成されるわけではない|
|3 導入前検査|検査側・WordPressの読取り専用画面|収集profile、inventory、report、health|取得成功・5分未満・設定一致。未確認項目を正常扱いしない|
|4 担当者確認|担当者の保護領域|[確認の明示発行](recurring-capture-review.md)。確認10項目、workspace、構成と対象のハッシュを結び付ける|日次用は最長7日。変更・期限切れ・失効時は再確認。復旧セットの署名承認とは別|
|5 取得と保存|外部取得側|[日次API tick_admitted](daily-capture-admission.md)へ保護されたファイルパスとbackendを渡す|ロック後/停止直前/保存前の検査。整合性と停止解除確認後のみ保存。storage_completeとawaiting_approvalを確認|
|6 独立承認|署名担当・保存元とは独立した保管場所|候補文書、固定Version ID、保持証拠を確認し署名。日次approveへ独立文書/公開鍵のハッシュを渡す|署名検証・固定版再読取りに成功してapproved。まだ復元検証済みではない|
|7 隔離復元|復旧担当・隔離先|既存recovery workerへrequest-id、day、trustを指定|承認済みのみ開始。署名/固定版/内容を再検証し、隔離WordPressの内容・HTTPを確認|
|8 結果確認|日次状態と読取り専用画面|workerが復元結果を日次台帳へ登録|restore_verifiedと後片付けを確認。本番再公開・無感染の保証ではない|

日次取得のAPIは開発者向けで、生成されたsystemd設定から起動する本番CLIを完成させたものではない。既存低水準tickや署名省略へ置き換えない。長期無人の棚卸し更新、本番の取得backend・配置・運用鍵の統合は残課題。

## 失敗時

- 検査不足・失効：取得/S3保存を開始しない。現状の日次台帳はunknownとして保持する。入力を直しても台帳を消して再実行しない。
- PUT結果不明：受領と固定版を照合し、明示的なreconcile条件を満たす場合のみ進める。自動再送しない。
- 署名不一致：承認待ちを維持し、復元を開始しない。署名・独立ピンを確認する。
- 復元失敗/途中停止：元の結果と所有資源を調査し、既存のinspect-interrupted/cleanup-reviewed手順を使う。結果登録のみの再試行と復元再実行を区別する。
- 状態報告停止：表示は過去の情報。表示正常への回復とバックアップ承認を混同しない。

## 今回追加する接続試験

以前の取得判定付き実取得試験は承認待ちまで。今回は同じ生成資産を独立の試験署名、既存approve、recovery worker、実隔離復元、結果登録へ渡す。既存の取得fixture・復元処理を再利用し、新たなバックアップ実装を作らない。

```sh
python3 -B tools/run-onboarding-recovery-lab.py --execute-lab --output /home/ozeki/.local/share/owr-onboarding-new-run/result.json
```

出力先は未使用のLinux私有領域を指定。Dockerと既存lab/m1/images.envのイメージが必要。実WordPress/MariaDBと生成投稿/メディアを使用し、保存はローカル固定版アダプターで代替する。署名鍵は専用試験用で、保存元の台帳外で生成して署名後に破棄する。同一プロセス/ホストの権限分離を安全性の証明にはしない。

棚卸し根拠と保持応答はfixture。実SSH棚卸し・AWS権限・Object Lockの再試験ではない。復元では取得workspaceを利用不可にし、固定版ストアから再取得する。復元DBはnetwork none、WordPressはそのネットワーク名前空間を共有し、公開ポート・元サーバーマウント・AWS資格情報を与えない。これは生成データの隔離試験であり実マルウェアの安全な実行を保証しない。

確認項目：条件不足時の取得/PUT拒否、重複日次枠、保存完了と承認待ちの分離、未承認復元拒否、不正署名でGETしないこと、承認後も復元未検証、実復元後の結果自動登録、同一要求で再取得/再復元しないこと。72時間観測の台帳・鍵・資産は使用しない。

## 問題の分類

環境の既知観測空白は維持する。以前のWebDriver起動原因は未確定で、今回ブラウザを使わない試験の成功を解決証明にしない。試験fixtureの問題は製品不具合と分け、発生時は初回の結果も残す。製品の残課題は上記の本番接続・長期運用・独立信頼情報の運用。

## 初回試験の診断

初回は署名検証、資産取得、隔離WordPressの投稿/メディア/HTTP 200、復元資源削除まで成功したが、日次結果登録が `pending / KeyError` となった。代替アダプターのGET記録に `retention` がなく、既存の結果登録が要求する保持証拠を満たさなかったことが原因。これは今回接続用に再利用した試験fixtureの不足。実S3アダプターや製品の検査を変更せず、fixtureに保存時と一貫した保持情報を記録するよう修正した。初回の台帳と復元結果を保持し、別の新規領域で再試験する。保持情報は引き続き模擬値である。

## 検証結果

別領域での再試験は全8項目成功。実隔離WordPressの投稿・添付ファイル・メディアハッシュ・HTTP 200と復元資源削除を確認し、日次状態は `restore_verified`、結果登録は `recorded`。同じ復元要求の再投入はGET/PUT/再復元を増やさない。日次取得判定の既存7回帰試験も成功。[結果](../../evidence-public/onboarding-recovery.json)／[初回失敗](../../evidence-public/onboarding-recovery-initial.json)。本番コードの変更なし。試作版と既存ZIPを維持し、72時間観測の評価とは分ける。

実SSH棚卸しと実験S3を接続した追加試験も完了。[実経路と検証範囲](onboarding-ssh-s3.md)。前回ローカル代替の証拠と区別して保存。
