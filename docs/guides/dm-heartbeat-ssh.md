# dmでの専用SSHによる生存記録の受信

2026-10-19。watchdog配置先はdmに確定。WSLから実際のdmへ、生成した専用試験のheartbeatを送って検証した。既存のFTP・MySQL・SSH設定は変更せず、サービスの再起動も行っていない。

## 配置と権限

|場所|配置内容|
|---|---|
|手元WSL|`~/.local/share/owr-heartbeat-dm/id_ed25519`：配送専用秘密鍵、モード0600。バックアップ署名鍵とは別|
|手元WSL|同ディレクトリの `known_hosts`：既存管理接続で確認したdmのホスト公開鍵を固定|
|手元WSL|`sender.json`：ホスト・ポート・専用ユーザー・鍵のパス・heartbeatのパス|
|dm|`owr-heartbeat`：受信専用ユーザー。パスワードログインはロック|
|dm|`owr-watchdog`：生存記録を読み、自身の台帳へ記録するユーザー。ログインシェルなし、パスワードロック|
|dm|`/opt/owr-heartbeat/tools/`：管理者所有のプログラム|
|dm|`/etc/owr-heartbeat/receiver.json`：固定された受信先と対象ID。管理者所有|
|dm|`/var/lib/owr-heartbeat/incoming/heartbeat.json`：受信ユーザーが更新し、watchdogは読取りのみ|
|dm|`/var/lib/owr-watchdog/`：watchdog専用の状態・試験通知。受信ユーザーから読書き不可|

秘密鍵はdmへ転送していない。管理用 `ssh dm` の鍵を定期配送には使用しない。専用鍵のauthorized_keys行に `restrict` と固定コマンドを設定し、SSH要求は `heartbeat` のみ許可する。プログラム・設定・authorized_keysは受信ユーザーが変更できない。SSHデーモンの設定変更・reload、新しい待受ポートの追加は不要だった。

新規ユーザーと受信入口は配置済みで、専用鍵による手動送信ができる。常設の送信タイマー、dm上のwatchdogタイマー、実通知経路はまだ有効化していない。試験の通知はdm内の専用受信箱へ保存した。

## 受信条件

`tools/heartbeat-ssh.py receive` は管理者が指定したディレクトリへだけ保存する。入力は最大4096バイトで、項目はformat・monitor_id・completed_at・undelivered・open_incidentsの5つに限定する。重複JSONキー、別対象、追加項目、不正な整数、タイムゾーンなしの日時、5秒を超える未来日時を拒否する。受信プロセスにはCPU・メモリ・入力待機時間の上限を設ける。

保存は排他ロック下で一時ファイルに書き込み、同期してから原子的に置換する。過去の記録への巻戻しと、同じ完了時刻で内容が異なる記録は拒否する。同一記録の再送は受領するが、ファイルと完了時刻を更新しない。破損した既存記録を発見した場合は停止して管理者確認を求め、黙って上書きしない。

応答のSHA-256を送信内容と照合する。転送失敗時もローカルのheartbeatを残すので、再送できる。受信側の古い記録を削除して停止を隠す処理はない。

## 通常監視との接続

通常監視の外側の設定へ、次の項目を追加すると監視完了後にSSH配送する。

```json
{
  "heartbeat_ssh_config": "/home/ozeki/.local/share/owr-heartbeat-dm/sender.json"
}
```

これは既存 `monitor.json` に追加する一項目で、ファイル全体の置換例ではない。`monitor_id` と `heartbeat_file` を送信側設定と揃える。今回の対象は `isolated-queue-lab`。別のサイトへ切り替えるときは受信側の対象も管理者が別途設定する。

手動で現在の記録を再送する場合：

```bash
python3 tools/heartbeat-ssh.py send \
  --config "$HOME/.local/share/owr-heartbeat-dm/sender.json"
```

このコマンドだけを繰り返しても生存時刻は新しくならない。通常監視の完了が止まれば、転送だけ動いていても停止と判定される。通常監視が失敗した場合は新しいheartbeatを作らず、SSH配送が失敗した場合は処理を非0終了する。完了時刻は実際の監視完了時に取得するよう補強した。

## 実際のdmでの検証

専用SSH往復で以下を確認した。

- 正常受領・同一内容の再送・通常監視完了後の配送。
- 古い記録、同時刻の内容違い、別対象、未来時刻、上限超過の拒否。
- 任意シェルコマンド、SFTP要求、リモートポート転送、未登録鍵、ホスト鍵不一致の拒否。
- dmの別ユーザーwatchdogが、実際の更新停止を検知し、新しい完了記録で解消すること。
- 受信ユーザーがコード・設定・watchdog台帳を書き換えられず、watchdogが受信記録を書き換えられないこと。

試験では停止判定を15秒へ短縮した。実運用の15分設定での常時稼働・再起動後の起動・実メール/プッシュ到達は別途確認する。

前後のSSH・vsftpd・proftpd・MySQLについて、稼働状態・PID・稼働開始時刻と、対象の主要設定ファイルのハッシュが一致した。FTP/MySQLへの接続や `demand` DBの操作は行っていない。この確認は既存業務への無影響を裏付ける範囲を示すもので、すべての業務処理の試験をしたという意味ではない。

## 運用上の境界と取り消し

SMTP・Google認証情報のコピー、Postfixの変更・撤去、IAM変更、メール/プッシュの外部送信は行っていない。受信ユーザーと専用鍵は今後の運用に使うため残した。不要になった場合は、まず管理用接続でこのユーザーのauthorized_keysだけを退避して専用鍵を失効させる。既存の管理用SSH鍵や他ユーザーの設定は変更しない。履歴を残したうえで専用ユーザー・ディレクトリを整理する。

SSH鍵の漏洩時はこの入口で虚偽の生存記録を送られる可能性がある。固定コマンドは操作範囲を制限するが、監視元そのものの侵害まで健全性を保証しない。署名鍵・SMTP認証情報・watchdogの台帳を受信側から分離する設計は維持する。
