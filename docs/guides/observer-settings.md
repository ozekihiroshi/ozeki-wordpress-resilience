# 独立watchdogの通知設定を管理画面から反映する

Resilience → 独立watchdogで、通知先・接続設定名・対象警報・有効状態・Pushoverの再通知間隔と期限を設定する。通常の通知設定とは別に保存する。秘密鍵・APIキー・SMTPパスワードは引き続き外部観測ホストで管理する。

## 利用者の操作

1. 外部管理担当者から許可済みの接続設定名を確認する。Pushoverの「受信者」は表示名であり、実際の受信先は外部の接続設定で決まる。メールは許可されたアドレスから選ぶ。
2. 「設定候補を保存」。この時点では稼働中の通知先を変更しない。初回は外部既存の宛先が自動入力されないため、必要な宛先・対象警報を照合して登録する。
3. 新しい外部状態を取得した画面で「外部側へ反映を要求」。古い報告・未接続・同時編集の競合時は要求を拒否する。
4. 画面を再読込みし、同じ設定版の「反映済み」を確認する。要求受付・転送完了だけでは反映済みと表示しない。最新報告が古くなった場合も反映を未確認として扱う。
5. 拒否された場合は理由を確認する。外部側の既存通知を継続する。競合なら最新状態で再要求し、許可条件違反なら候補または外部の許可設定を修正する。

対象は監視停止・生存記録不正・監視側の通知異常。外部ポリシーの既定では3種類すべてに少なくとも1つ有効な通知先が必要。個別通知先の無効化は可能だが、必須警報を無通知にする変更は拒否する。WordPressから監視周期・停止期限・外部ポリシー・秘密情報は変更できない。

## 切替時に保持するもの

- 切替時点の既存警報は旧宛先の設定で取り込んでから、新しい設定へ原子的に切り替える。
- 未配送、再試行時刻、送信回数、結果不明、確認待ちreceipt、確認・取消処理を保持する。結果不明を自動再送しない。
- 旧ルートの宛先と資格情報を固定する。接続設定を後で更新しても過去の警報を別宛先へ送り直さない。
- 旧ルートが無効でも、そのルートで発生した警報の解消・取消は旧ルートで処理する。
- SSH応答喪失時の同一要求再送は重複適用しない。SQLiteの切替後に停止しても、次回は同じ設定版を照合して完了を記録する。
- 設定処理が失敗しても通常の監視と旧設定での通知を継続する。処理自体の異常は管理画面へ報告する。

## 外部管理担当者の初期設定

現在は専用環境で実装・検証した開発版。本番への配置・実通知は未実施。

1. `examples/watchdog-observer/observer-settings-policy.example.json` を参考に、外部観測ホストで許可済み接続設定、許可メール宛先、必須警報を定義する。PHPやSSH受付ユーザーからこのファイルと資格情報を読めないようにする。通知資格情報は観測実行ユーザー所有0600。メール資格情報の形式は既存SMTP手順に従う。
2. 専用SSH受付ユーザー `owr-settings-inbox` を作り、受付ディレクトリを同ユーザー所有、観測ユーザーが所属する読取グループ、2750にする。受付DBは0640。受付ユーザーには観測の私有状態・通知キー・コードの書込み権限を与えない。観測ユーザーは受付DBを読取り専用で開き、処理結果を私有stateへ保存する。
3. endpoint設定にサイトIDと固定の受付DBパスだけを指定する。専用公開鍵のauthorized_keysは次の形式とし、パスワード、TTY、転送もsshd側で禁止する。

```
restrict,command="/usr/bin/python3 /opt/owr/observer-settings.py receive --config /etc/owr/observer-settings-endpoint.json" ssh-ed25519 <公開鍵>
```

4. WordPress側に専用要求ディレクトリを作る。Webユーザー所有・専用relayグループ・2770とし、relayだけにSSH秘密鍵0600を許可する。状態を読むSSH鍵とは別に用意する。known_hostsは信頼できる経路で取得した公開鍵を `owr-notification-<site_id>` で固定する。
5. wp-config.phpへ `define('OWR_OBSERVER_REQUEST_DIR','/var/lib/owr-observer-requests');` を追加する。既存のOWR_OBSERVER_STATUS_FILEによる状態取得も必要。
6. relay.example.jsonとservice/timer例を環境に合わせる。専用SSHの送信は1回1要求。初回に空の要求ディレクトリでexchangeを実行すると、空の受付DBを作成して疎通を確認できる。生存記録の状態転送タイマーも継続する。
7. 観測設定に `configuration` オブジェクトを追加する。その内容はcontrol.example.jsonの各フィールドで、delivery_stateは既存alerts.stateと同じ、site_idはadmin_site_idと同じにする。control.stateは例のように既存観測の書込許可ディレクトリ内を使う。別の場所ならsystemdのReadWritePathsも追加する。
8. 既存観測を接続する際は、既存の配送DBが初期化済みであることを確認する。新しい設定を候補ファイルへ保存し、観測実行ユーザーで `python3 /opt/owr/observer-settings.py enable --config /etc/owr/observer-with-settings.json` を実行する。この明示的な初回操作はconfigurationの追加だけを許可し、既存の生存記録・警報・配送DBを変更しない。サービスの設定ファイル参照を同じ候補へ切り替える際は短い保守時間内で行う。stateを削除して接続し直してはいけない。
9. 観測定期処理が受付を処理し、反映結果と稼働中設定版を公開状態へ載せる。設定受付の異常時も独立通知は旧設定で継続する。timerを有効化する前に手動で一往復を確認する。

## 管理画面から独立通知先へテスト送信

画面末尾で、反映済み・有効な通知先ごとにテストできる。設定候補と外部の稼働中設定版が一致し、外部状態が新しい場合だけ受付する。専用SSHには通知先ID・設定版・要求IDを渡し、通知キーや任意の宛先・本文は渡さない。外部側でも設定ハッシュと版を照合し、途中で設定が変わった要求は送信しない。固定本文・通常優先度で送信し、Pushoverの緊急繰返し通知は作らない。

1. 通知先のテストボタンを押す。初期表示は受付であり、配送成功ではない。
2. 要求転送・観測処理・状態取得の各定期処理後に再読込みする。要求IDと設定版を付けた最新20件を確認できる。
3. 「サービス受付」は通知サービスの受付結果。iPhoneなど端末での受信は別に確認する。「配送拒否」「一時失敗」「結果不明」は自動再送しない。「未送信」は期限・設定版・有効状態・頻度を確認する。必要な修正と端末確認の後、新しい要求として再テストする。

テストの期限は5分。同じ通知先は管理画面・外部処理の両方で60秒間隔に制限する。通常警報を先に処理し、テストの実送信は1周期1件まで。同一要求の再転送は再送信しない。送信前に開始を永続化し、その後停止した場合も結果不明として再送を抑止する。既存警報の未配送・確認待ちreceipt・解消処理とは別の台帳を使う。

状態取得が古いときは過去の結果として表示する。外部のテスト処理自体の異常も表示する。受付上限1000件は設定変更と共有するため、満杯時は管理担当が台帳を確認する。今回の検証は専用環境の模擬通知先を使用し、本番配置・実サービスへの通知は行っていない。

## 上限・運用上の注意

候補通知先は10件、要求1件は4KB、ローカル待機は100件、外部受付は1000件。設定変更要求は24時間、テスト送信要求は5分で期限切れとなる。外部受付と処理台帳は自動削除しないため、長期運用の保管・アーカイブ手順は別途必要。共通配送処理の旧ルートを含む上限は400件で、上限超過時は切替を拒否し旧設定を維持する。未配送やreceiptを残したままstateを消して解消しない。

変更の成功は「設定の反映」であり、通知先の実受信を保証しない。管理画面の独立通知状態と実機での受信を確認する。WordPressが侵害された場合も外部の許可条件は変更できないが、許可範囲内の変更要求は可能。さらに厳格な運用では外部承認の追加が必要で、この版には独立した人手承認フローは含まない。
