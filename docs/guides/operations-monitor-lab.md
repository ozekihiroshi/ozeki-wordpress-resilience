# 日次バックアップの監視と試験通知

専用環境で、日次台帳・承認期限・復元試験記録を読み取り、異常の発生と解消を試験用の運用担当受信箱へ通知する。監視は保存や署名承認を実行せず、既存の台帳を変更しない。本番メール・Slack等への送信、タイマーの有効化はまだ行わない。

## 初期判定

|項目|専用環境の初期値・判定|通知後の対応|
|---|---|---|
|取得漏れ|毎日03:00 JSTから2時間後までに `awaiting_approval` / `approved` に到達していない日|保存処理と容量を確認。unknownは証拠を照合してからreconcileする|
|署名承認待ち|保存完了イベントから24時間経過|独立した運用担当が対象と保持証拠を確認し、既存の承認手順を実施|
|承認期限切れ|承認記録の期限、または未承認候補の承認可能期限に到達|期限を書き換えず、復元を止めて独立再審査・再承認を行う|
|復元試験失敗|復元プロセスの非正常終了、タイムアウト、成功報告の欠落・不完全|今回のログと専用コンテナを確認し、新しい出力先で再試験|
|復元未完了|開始から35分経っても終了記録がない|監視対象プロセスの中断や残存コンテナを確認|
|監視元の読取り失敗|台帳・承認記録・復元台帳が欠損、不正、読取り不能|監視元を修復。以前の異常を正常扱いしない|

保存失敗・状態不明は猶予前でも通知する。開始日以前の未取得を遡って作らない。取得漏れは日ごとに残るため、翌日の成功で昨日の未取得を隠さない。承認期限もセットの日ごとに判定し、新セットの承認で古い期限切れを消さない。履歴の監視対象からの除外・担当者による確認済み操作は今後の仕様対象。

## WSLでの設定例

`operations-monitor-lab.py` は1回だけ実行して終了する。JSON設定を独立した監視用フォルダに作り、絶対パスを指定する。以下の `/home/ozeki` は使用者に合わせる。

```json
{
  "site": "isolated-queue-lab",
  "start_day": "2026-10-19",
  "hour_jst": 3,
  "capture_grace_seconds": 7200,
  "pending_seconds": 86400,
  "restore_timeout_seconds": 2100,
  "daily_state": "/home/ozeki/.local/share/owr-daily-s3-lab-20261019",
  "restore_journal": "/home/ozeki/.local/share/owr-monitor-lab-20261019/restore-journal",
  "monitor_state": "/home/ozeki/.local/share/owr-monitor-lab-20261019/state",
  "test_inbox": "/home/ozeki/.local/share/owr-monitor-lab-20261019/operator-inbox"
}
```

復元台帳のディレクトリは事前に作成する。空なら「記録済みの失敗なし」であり、「復元済み」ではない。復元試験そのものの実施漏れや定期実行間隔はまだ判定しない。

```bash
python3 tools/operations-monitor-lab.py --config /absolute/path/monitor-config.json
```

終了コード0は未解決異常・未送信通知なし、2は対応対象あり。設定不正や監視DBの障害は非0で終了する。監視用状態は再実行のたびに同じフォルダを使う。設定変更には新しい監視用状態フォルダが必要で、新規通知になる。監視・復元台帳・受信箱は保存元から書き換えられない運用担当側へ配置する。この専用試験の同一WSLユーザー配置はOS権限分離の証明ではない。

## 復元試験の開始・終了記録

[固定版取得・隔離復元](approved-daily-restore.md)の実行例で、入口を `tools/monitored-restore-lab.py` に変更し、`--journal /absolute/path/restore-journal` を追加する。`--lab-image` はラッパー側で専用イメージへ固定するため省く。他の `--approved-*`、`--output`、`--execute-lab` は同じ。

開始を永続化してから専用ランナーを起動する。非0終了・30分のタイムアウト・成功報告の検査失敗を `failed` とする。42ケースの完全な合格、対象セット一致、隔離復元確認、コンテナ削除確認が揃った場合だけ `succeeded` にする。ログは出力報告と同じ場所の `.log`。SIGKILL等で終了記録が書けなければ、監視が35分後に未完了として検知する。失敗時はコンテナ削除を確認済みとみなさず、ログに記載された今回のリソースだけを確認する。

失敗は同じセットの後続成功で解消する。再試験の開始だけでは解消しない。元の承認記録や取得時点の `retrieval.json` を成功状態に書き換えない。既存の成功実測を監視へ引き継ぐ場合は、検証した元報告のハッシュと出典を付けて履歴として登録し、新しい復元試験を実施したと表示しない。

## 配送と障害時の運用

通知はSQLiteのoutboxへ先に永続化する。異常ごとの発生・解消時にだけ通知を生成し、再発には新しいイベントIDを付ける。受信箱はイベントIDをファイル名にしたJSONで、原子的に保存してから受領済みとする。送信済み・未送信の状態は再起動しても維持する。送信先の停止や受領応答の喪失では未送信を残し、次回実行で同じIDを順番に再送する。通知本文へ生ログ・認証情報・署名URLは載せない。

`undelivered > 0` は通知経路の障害。ディスク容量・フォルダ権限を確認し、同じ設定で再実行する。outboxや監視DBを削除して解決扱いにしない。受信箱ファイルは試験用通知であり、人が読んだことを示さない。

本番導入前には実通知先・担当者・配送アダプター・再通知/エスカレーション・監視プロセス自体の停止を検知する外部監視・履歴の終了条件を決める。今回は実通知先への送信、常駐化、自動署名、自動復元、本番S3変更は行っていない。

## 実測結果（2026-10-19）

監視・通知24件を含むPython契約180件に合格。4種類の異常の同時検知、解消・再発、配送失敗・受領後の中断・再送、監視元破損、復元プロセスの異常終了・タイムアウトを専用試験で確認した。既存の承認済みセットも読み取り専用で観測し、異常なし・日次台帳変更なしを確認した。過去の42ケースの復元報告を検証して履歴登録したもので、今回S3取得・復元を再実行していない。[実測記録](../../evidence-public/operations-monitor-lab.json)。
