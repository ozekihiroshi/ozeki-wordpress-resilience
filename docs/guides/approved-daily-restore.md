# 承認済み日次セットの固定版取得と隔離復元

対象は専用実験セット `AWS-82e377a986a42ce5`。日次の[未署名保存・独立署名承認](daily-s3-approval.md)で保管した三資産を、既存の署名と独立ピンで検証して復元する。再取得用の新しい署名やバックアップを作る処理ではない。

## 復元開始前の必須条件

1. 運用担当が選んだ信頼情報フォルダ、セットID、文書SHA-256、公開鍵SHA-256を明示する。日次台帳やダウンロードした文書から公開鍵の選択先を決めない。
2. 独立承認記録、署名、ピンの有効状態、承認期限、サイト・セット・公開鍵・文書ハッシュを照合する。失敗ならS3読取りも開始しない。
3. `OwrM1RecoveryReader` だけで三資産を明示的なVersion IDから取得する。最新オブジェクトを取得しない。保存側communityへの接続、PUT、DELETE、署名鍵へのアクセスは不要。
4. 全資産のハッシュ・サイズ・35日保持・変更されていないLast-Modified・DB/ファイル/キューのチェックポイント・処理コードのハッシュを照合する。
5. アーカイブの全メンバーを展開前に検査する。絶対パス、上位ディレクトリへの遡及、リンク、特殊ファイル、重複パス、ファイルとディレクトリの衝突、上限超過を拒否する。最大20,000エントリ、単一ファイル128MiB、展開後合計512MiBの専用試験上限を設定する。

これらが全部通った後でのみ、取得した資産を専用コンテナの復元処理へ渡す。署名検証だけでコードが無感染だとは認定しない。

## 専用環境の動作

DBコンテナはDockerの `--network none`。WordPress・キューブローカー・ワーカーはそのネットワーク名前空間を共有し、外部通信経路と公開ポートを持たない。S3への通信はホストの取得処理だけが行い、署名URLやAWS認証情報は復元先へ渡さない。

検証済み資産でDBとキューを復元する。ファイルは今回新規作成した `owr-consistency-...` コンテナの `/var/www/html` の中だけを空にして展開し、全ファイル一覧とSHA-256を署名対象のアーカイブと比較する。取得元やホストのサイトフォルダは消さない。

キューは停止状態で復元し、DBの完了台帳とファイルの効果を照合してから専用ワーカーを再開する。未処理ジョブの再配送、ACK喪失ジョブの重複効果防止、衝突ジョブの隔離を確認する。外部決済・メール等への配送は行わない。

## 実行例

WSL Ubuntu-24.04と `owr-external-lab:local` イメージを使う。結果ファイルと読取り受領記録は毎回新しいパスを指定する。既存署名・ピン・独立承認記録は変更しない。

```bash
python3 /mnt/d/workspace/ozeki-wordpress-resilience/tools/run-wordpress-consistency-lab.py \
  --execute-lab --lab-image owr-external-lab:local \
  --approved-trust "$HOME/.local/share/owr-daily-s3-operator-lab/AWS-82e377a986a42ce5/approved-trust" \
  --approved-set-id AWS-82e377a986a42ce5 \
  --approved-document-sha256 dbf4a3a41a6c5a31881d8168ff9d18cd6d952875f82406cffe013230a52ee707 \
  --approved-key-sha256 02d0b3e07a27e766530bc709c9b2e4058f758c0dca851eefb05c161303b42834 \
  --approved-read-receipts "$HOME/.local/share/owr-approved-restore-lab/AWS-82e377a986a42ce5/NEW_READ_DIRECTORY" \
  --output /mnt/d/workspace/ozeki-wordpress-resilience/.local/NEW_RESTORE_RESULT.json
```

保存系の `--s3-lab`、`--s3-resume-set`、`--daily-s3-stage` との併用は拒否する。実験用バケット・プレフィックスと生成サイトのみを扱う入口であり、本番サイトを指定する汎用コマンドではない。

## 証拠と障害時の扱い

- `operations.json`：固定Version IDを指定した3回のGET受領記録。
- `retrieval.json`：署名・三資産・アーカイブの検査結果。取得時点の記録なので、ここだけでは復元成功と判定しない。
- 完了した統合試験の結果：全ケースの合格と `resources_removed=true` を確認する。
- `restoration.json`：統合試験の完了後に記録する復元完了証拠。元の承認記録は履歴として変更しない。

署名・承認期限が切れたら停止する。期限を書き換えたり署名検証を省略したりしない。取得失敗・保持の短縮・資産不整合でも復元へ進めない。復元途中で失敗した場合はログと今回のコンテナ名を確認し、同じ本番サイトへ再実行するような扱いをしない。専用環境の再試験は新しい結果・受領記録パスで行う。S3への書込みがないので、再試験によるバックアップ版の増殖はない。

## 範囲

新しい日次バックアップの起動、S3への追加保存・削除、IAM変更、本番署名鍵の使用、本番サイトへの復元・再公開は含まない。署名側と取得側は同一WSLユーザー内の専用試験であり、別PC・OS権限による強制分離の証明ではない。疑似感染や実マルウェアの実行試験も行わない。

## 実測結果（2026-10-19）

専用環境42ケース、Python契約156件が合格。承認済みセットの既存署名を再利用し、実S3から3回の固定版GETだけで取得した。全3,972ファイルの一覧・ハッシュ、DB/キューのチェックポイント、キュー再配送・重複効果防止・衝突隔離を確認した。公開ポートなし・外部通信経路なしを確認し、試験コンテナは削除済み。[実測記録](../../evidence-public/approved-daily-restore.json)。元の承認記録と取得時点の証拠は維持し、復元完了を別に記録した。
