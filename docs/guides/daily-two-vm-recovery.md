# 生成・取得を別VMに分けた障害回復試験

この試験は日次状態報告の生成・受渡しを対象とします。新しいバックアップ・署名・復元は実行しません。
本番向けサービス例を変更せず、60秒周期で実行します。

## 構成

|生成VM|取得VM|
|---|---|
|専用Ubuntuカーネル・独立ディスク|別のUbuntuカーネル・独立ディスク|
|試験用の台帳・証拠のコピー|台帳は配置しない|
|publisherとSSH読取り用ユーザー|relayとWeb読取り用ユーザー|
|公開用報告とSSHホスト鍵|受信報告と取得用SSH秘密鍵|

VM間の専用ネットワークで、固定コマンド・ホスト鍵固定の実SSHを使用します。
管理用経路を別に設け、試験用NICだけを切断してもVMの稼働状況を確認できます。
外側のQEMU実行コンテナは外部ネットワークなし、CPU・メモリ制限付きです。
Windows・WSL・Docker本体や既存72時間観測の環境は再起動しません。

## 検証する障害と判定

|操作|障害中の判定|回復時の判定|
|---|---|---|
|試験用NIC切断|取得側が転送失敗を記録。失敗が続いても最後の報告のハッシュを保持。生成側は更新継続|NIC復帰後に新しい報告を取得|
|生成VMだけを停止|取得VMは動き続け、転送失敗と前回報告を保持|生成VMを起動するとpublisherが自動起動し、取得が回復|
|取得VMだけを停止|生成VMは動き続け、報告を更新|取得VMを起動するとrelayが自動起動し、最新報告を取得|

両VMのBoot IDを比較し、停止した側だけのOSが起動し直したことを確認します。
OS起動後にサービスの手動startは行いません。
障害前後の復元結果・後片付け履歴と、元データのバイト列が変わらないことも確認します。
各VMではサービスのユーザー・権限制限と、不要な台帳・秘密鍵が存在しないことを検査します。

取得VM自体が停止すると、そのVM内の取得処理や管理画面から停止を報告することはできません。
その検知には別ホストのwatchdogが必要です。今回、外部通知の配送は検証していません。
また、SSH接続失敗だけでは「通信断」と「相手OS停止」を判別できません。
画面向けの状態はどちらも転送失敗となり、原因は独立した稼働確認と照合して判断します。

## 再現と記録

`lab/two-vm/` に再現スクリプトがあります。
既存の `owr-systemd-vm:lab` イメージ、固定したUbuntuイメージ、
生成データ試験 `owr-recovery-cleanup-20261020-v2` を使用します。

```sh
export OWR_TWO_VM_OUTPUT="$HOME/.local/share/owr-two-vm-new-unique-trial"
python3 lab/two-vm/start.py
python3 lab/two-vm/exercise.py
python3 lab/two-vm/cleanup.py
```

新規出力先だけを使ってください。途中失敗した場合は `events.json` と各VMのログを確認し、
結果不明のままsetupを再実行しません。設定済み環境や他のホストへ流用するスクリプトではありません。
cleanupは記録されたコンテナとマウント先・ホスト名を照合します。失敗時にVMが既に停止している場合は、
その状態を調べて専用資源だけを撤去します。

生の出力には使い捨てのSSH秘密鍵・起動用seed・VMディスクが含まれます。Gitへ登録しないでください。
公開用結果は [検証証拠](../../evidence-public/daily-two-vm.json) にまとめます。
試験用ネットワークはQEMU stream backendで接続し、VM再起動後の接続を再確立できる構成です。
その仕様は[QEMU公式ドキュメント](https://www.qemu.org/docs/master/system/invocation.html)を参照しています。

## 検証の限界

2台は独立したVMですが、同じ物理PC上です。
物理機器の故障、ホスト電源断、別データセンター、実WAN、パケット遅延・複雑な通信劣化、本番への配置は未検証です。
今回の障害注入は日次状態報告用の試験であり、72時間観測の空白やバックアップ保存の失敗とは別に記録します。
新たなWordPressブラウザ試験は含めず、WordPressが読む受渡し状態・報告本体・ハッシュを実通信で確認します。
