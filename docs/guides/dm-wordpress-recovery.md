# dmでのWordPress表示・機能確認

実施日：2026年10月18日。正常な既知のM1模擬資産を対象に、S3固定版から復元した専用DBを使って別サーバーdmでWordPressの表示・機能を確認した。

## 結果

- コード・メディア・構成の5資産をS3からVersion ID指定で再取得し、返却Version ID・サイズ・SHA-256を照合。
- コア、テーマ、プラグイン、メディアを専用ディレクトリへ展開。絶対パス・親ディレクトリ参照・リンク・特殊ファイルを拒否し、既存ファイルを上書きしない。保存された構成は照合・保管のみで、旧環境の設定をそのまま適用していない。
- メディア全5ファイルのサイズ・ハッシュ・パスが基準と一致。
- WordPress内部16項目に合格。DB基準データ、fixture ID、メディア一覧の3項目を元基準と厳密比較して一致。
- HTTP14項目に合格。主要4ページ、日本語・絵文字、内部リンク、画像・PDF、フォームのnonce拒否と正常受付、管理者ログイン、プロフィールを確認。
- MySQL・vsftpd・nginxは最後にactiveを確認。demandの接続・参照・更新は行っていない。FTP業務の転送やデマンドアプリ自体の機能試験は未実施。

## 実行環境

| 項目 | 内容 |
| --- | --- |
| WordPress | 7.0.2 |
| 検証用PHP | Ubuntuパッケージの8.1.2-1ubuntu2.26 |
| DB | 既存MySQL 8.0.46、専用DB owrrecoverylab20261018 |
| テーマ | Twenty Twenty-Five 1.5 |
| 復元したバックアッププラグイン | 0.3.0（固定資産に含まれる版） |
| 実行場所 | dmの ~/.local/owr-db-lab/site-20261018-001 |
| HTTP | 127.0.0.1:18081、PHP内蔵サーバー。検証専用 |

標準PHP 7.2を変更せず、APTでUbuntuのPHP 8.1 CLI・必要拡張パッケージを取得し、dpkg-deb -xで専用領域へ展開した。システムへのパッケージインストールやalternatives変更は実施していない。専用php.iniを使用し、システムのPHP追加設定ディレクトリを読み込まない。取得パッケージのハッシュは専用領域のpackages.jsonに保存した。

既存MySQLクライアント設定をPHPのparse_ini_fileで読む方法は、パスワードの特殊文字で失敗した。既存ファイルやパスワードは変更せず、同じ資格情報を専用の非公開JSONへ移し、PHPから読む方法に修正した。初期のエラーログは失敗の記録として残す。秘密情報を含むファイルはGitへ登録しない。

## 既存業務との分離

- transient systemd serviceをubuntuユーザーで実行。既存Webサーバー設定やFTP・MySQLサービスの再起動なし。
- MemoryMax 384MiB、CPUQuota 25%、TasksMax 16、RuntimeMaxSec 1200。HTTP試験後のメモリ観測は44,576,768 bytes（約42.5MiB）。ピークや業務無影響を保証する測定ではない。
- NoNewPrivileges、PrivateTmp、ProtectSystem=strict、ProtectHome=read-onlyを設定。書込み許可は専用サイト領域。SSH・AWS設定ディレクトリをサービスから不可視にした。
- IPAddressDeny=any、IPAddressAllow=localhostを設定し、DBへは専用ユーザーでUnixソケット接続。外部公開ポートやファイアウォールは変更しない。
- 同じ制限の検査サービスからEC2メタデータ宛TCP接続が失敗することを確認。メタデータの資格情報取得は実施していない。最初の検査起動はsystemdの引数展開で失敗したため、PHP検査ファイルに切り替えて確認した。
- WordPress側でも外部HTTP、メール、cron、自動更新、ファイル編集・追加を停止。これは検疫・検証用設定であり、本番の更新停止を推奨するものではない。
- PHPルーターはドットパス、wp-config、uploads内PHP等を拒否。これは悪意あるコードを安全に実行するためのサンドボックスという意味ではない。

## DBの変更範囲と現在の状態

この段階では専用DB内の模擬管理者owradminのパスワードをランダム値へ更新し、WordPressログインに伴うセッション等の更新が生じる。従って、前段の全行一致はWordPress起動前の観測として保持する。起動後のDB全体が元SQLと同一という主張はしない。基準ページと設定・メディアの確認は別途合格している。

資格情報・新しいsalt・管理者パスワードはdm専用領域にだけ保存。確認用HTTPサービスowr-dm-lab-http-20261018は試験終了後に停止した。サイトファイル・専用DB・非公開検証記録は残している。現在、確認用Webページは公開していない。

再試験時は同じservice-properties.jsonに基づく制限付き一時サービスで専用PHPを起動し、verify.phpとverify-http.pyを使用する。PHP内蔵サーバーを既存nginxの設定へ組み込んだり、0.0.0.0で公開したりしない。停止対象は今回の専用サービスだけとする。

## この実証の範囲

元WSLホストとは別のdm上で、既存MySQLと専用PHPを使って既知の正常なサイトを動作させられた。ソフトウェア環境が元環境と完全一致したという意味ではなく、PHP・DBバージョンの違いを記録した上で機能を検証した。

今回も作業者は同じで、AWS IAMロールの分離と独立した真正性検証は未達・未検証。感染疑いの資産を共用dmで実行してよいことの証明ではない。次は復旧権限と信頼情報の独立性を整える。侵害を模擬する実行・破壊試験は別の専用環境で行う。
