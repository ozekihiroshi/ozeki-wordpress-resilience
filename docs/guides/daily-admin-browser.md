# 日次バックアップ管理画面のブラウザ検証

対象は試作版の「Resilience → 日次バックアップ・復元」です。
既存72時間観測とは別のWordPress・MariaDB・Chromiumを使います。
外部通信できないネットワーク名前空間に配置し、公開ポートは設定しません。
本番データ、署名鍵、AWS権限を使いません。

## 試験データと操作

既に検証済みの生成データの台帳を専用領域へ複製し、
「途中停止後の後片付け確認済み」と「別要求での復元成功」を表示します。
「途中停止・結果不明」「後片付け未完了」は、追加の表示専用JSON行で検査します。
この行は故障や削除を再実行した結果ではなく、画面試験用の明示的な模擬状態です。

Chromiumで実際にログインし、WordPressのサイドバーメニューから画面を開きます。

- 未ログイン時はログイン画面へ移動する。
- 管理者は日次状態と復元・後片付け履歴を確認できる。
- 編集者にはメニューを表示せず、直接URLでも状態情報を表示しない。
- 専用ページ内に保存・復元・削除のフォームやボタンがない。
- ブラウザからのPOSTは405で拒否され、再読込みしても状態は変わらない。
- 未取得・更新停止・対象サイト不一致を正常状態として表示しない。
- 通常幅1440pxと狭い幅390pxで表示する。狭い画面の表は必要に応じて横スクロールする。

前後で、複製した台帳・証拠ファイル、WordPressのResilience設定とCron設定、
外部要求ファイルを比較します。ログインに必要なWordPressセッション記録はこの比較の対象外です。
通知・watchdog設定とWordPress管理画面の初回処理を済ませてから比較します。
未初期化の管理画面を経由するとCronに差分が発生したため、項目ごとのハッシュとCronフックを採取しました。
追加されたのはWordPress本体の `wp_scheduled_delete`、`delete_expired_transients`、
`wp_update_user_counts`、`wp_scheduled_auto_draft_delete`、`wp_update_comment_type_batch` でした。
Resilience設定は変わっていません。試験の初期化と検証対象の操作を分離しています。
試験後は作成したコンテナと匿名ボリュームを削除します。

## 実行ファイル

- `tools/run-daily-browser-lab.py`：専用環境の起動・状態ファイル切替・不変性検査・後片付け。
- `lab/notification-admin/daily-browser-test.py`：Chromiumの画面操作・権限・スクリーンショット。

既存の専用復元試験データとローカルDockerイメージを前提とした開発用ランナーです。
出力先は毎回新規にし、成功済みの領域を使い回さないでください。
SeleniumサーバーのWebDriver APIへPython標準ライブラリで接続するため、
コンテナへPython版Seleniumを追加インストールする必要はありません。

最初の準備で試験スクリプトの引用符の誤りを構文検査が検出しました（資源作成前）。
最初の環境試験ではPython版Seleniumがないことを検出し、
既存のブラウザ試験と同じWebDriver API方式に修正しました。
いずれも試験ツール側の課題であり、プラグインや72時間観測の障害ではありません。

最初の目視確認では、390px幅の表が細かく折り返されて読みにくいことを確認しました。
製品側の表に最小幅760pxとキーボードでフォーカスできる横スクロール領域を追加しました。
ページ全体は横にはみ出さず、表内を横に移動して後片付け欄まで確認できます。

表示修正後の試験で、管理者から編集者へ切り替えるログイン待機が1回タイムアウトしました。
当時はログインエラー本文を採取しておらず、過去の原因は断定できません。
入力欄の明示クリア、ログインページのキャッシュ回避、失敗時のエラー採取を試験へ追加しました。
この単発記録をプラグインの障害や環境障害と断定せず、後続試験の結果とは別に残します。

本番導入・状態報告の定期更新・ホスト間転送は、このブラウザ検証の対象外です。
