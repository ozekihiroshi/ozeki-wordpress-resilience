# 実WordPress更新経路と整合性判定の専用試験

対象は外部通信と公開ポートのない、毎回新規作成するWordPress / MariaDB。実サイト、AWS、既存の復元環境へ適用するツールではない。

## 制御する境界

`lab/consistency/route-prepend.php` をPHPの `auto_prepend_file` に設定し、WordPressの読込みより前に共有ロックを取る。コーディネーターは新規受付を停止してから排他ロックを待ち、その後MariaDBの全体読取りロックを保持する。PHPは終了コールバックを含むリクエスト終了まで共有ロックを保持する。

**停止中はGETを含めPHPによる画面表示も503になる。** GETや読取り用エンドポイントも、プラグインやWordPress初期化がDB・ファイルを更新する可能性があるため、今回の初期方式では例外にしない。CLIのPHPファイル実行は終了コード3で拒否する。静的ファイルの配信は対象外。

単にMUプラグインの初期化フックだけで止める方式では、先にロードされる設定・ドロップイン等を覆えない。この試作はサーバー側PHP設定も必要であり、通常のWordPressプラグインを有効化するだけで全経路を止められると表示してはならない。

## 実際に使う経路

| 経路 | 正常時の更新確認 | 停止中 |
| --- | --- | --- |
| 管理画面 | Cookie認証と実フォームのnonceで `wp-admin/post.php` から公開投稿 | 503、更新なし |
| REST | Cookie認証とREST nonceで標準投稿API | 503、更新なし |
| メディア | 標準RESTメディアAPIで実ファイルをアップロード | 503、ファイル作成なし |
| Ajax | `admin-ajax.php` の標準カテゴリー追加処理 | 503、更新なし |
| cron | `wp_schedule_single_event` で登録し、実 `wp-cron.php` から投稿する試験フック | 新規実行は503、開始済み処理は完了待ち |
| CLI | PHPファイルからWordPressを読み込み実投稿 | 終了コード3 |
| PHP終了処理 | Ajax試験フックが登録する終了コールバックで実DB更新 | コールバック完了まで取得開始を待機 |
| DB直接接続 | 前段試験でDML、新経路試験でDDLを試行 | MariaDB読取りロックによる待機とタイムアウト |

管理画面は試験用MUプラグインでクラシック編集画面に設定する。cron・終了処理用のコールバックと認証後のnonce取得用ページは試験補助であり、本番へ配布する機能ではない。通常の投稿・メディア・カテゴリー処理はWordPress標準の処理を呼ぶ。

加えてXML-RPC、コメント送信、admin-post、async-upload、ログイン、updateの入口へ停止中にリクエストし、WordPress処理に入る前の503拒否を確認する。この追加6入口は受付拒否の試験であり、正常時の更新処理をそれぞれ最後まで実行したという意味ではない。

## 判定器への接続

`tools/wordpress-route-lab.py` が実測から `owr-capture-consistency-v1` の観測を作り、既存の `capture-consistency.py` に渡す。

- 独立した期待更新元一覧: `php-http`、`php-cli-file`、`database-direct`。
- PHP設定の有効性、HTTP各経路の拒否、CLI拒否、排出完了、DBロック取得を確認する。
- 受付済みPHP処理の世代番号、サイト全ファイルの取得前後ハッシュ、tar内ファイルのハッシュを比較する。
- DBダンプ・tarの終了コード、サイズ、SHA-256を記録する。
- 保持中の所有トークンとコーディネーター生存、正常解除応答を確認する。テーブルエンジンも検査する。
- 標準メディアのDB参照が取得ファイルに含まれることを確認し、ダンプを別の空DBへ復元して参照を再確認する。

`consistent` は、この専用環境の宣言済み更新元についての取得整合性だけを意味する。署名承認・保持証明・本番復旧許可とは別で、`production_recovery_approved` は常にfalse。

直接ファイル変更を実際に発生させた観測は `inconsistent`、期待一覧に未登録のSSH更新元を追加した場合と停止範囲の確認が欠けた観測は `unverified` にする。後者は証拠の欠落を注入する判定試験であり、すべての未対応プラグインを実行したという意味ではない。

## 範囲の限界

`scope_complete` は `isolated-lab-controlled-php-v1` という閉じた試験構成内だけの値。ホスト管理者による `php -r`、`-n`、設定上書き、SSH、デプロイ、外部キュー、別ストレージ、任意プラグインが起動する子プロセスは未網羅である。特に `php -r` にはauto_prepend_fileが適用されない。本試験のHTTPクライアント・観測・初期設定に限ってこの管理経路を使用し、通常更新元と区別する。

DBロックは直接ファイル更新を防がない。ハッシュ比較だけでは、停止制御を迂回して変更後に元へ戻す操作を保証できない。本番用に範囲を宣言する前に、これらの経路を停止・権限制約する外部制御と、漏れがある場合の拒否が必要。今回の合格を本番サイトにコピーしてはならない。

プロセス強制終了後の残存マーカー、独立した監視・所有者失効判定も引き続き未完了。[先行試験の失敗時の扱い](wordpress-consistency-lab.md)を参照。

## 実行

```bash
cd /mnt/d/workspace/ozeki-wordpress-resilience
python3 tools/run-wordpress-consistency-lab.py --execute-lab --routes --output .local/wordpress-routes-new.json
```

先行10ケースに実更新経路の試験を追加する。引数なしでは作成しない。ランダム名の専用コンテナと匿名ボリュームのみを終了時に削除する。元のサイトやAWSは使用しない。

詳細観測はローカル出力に保存する。公開用記録では全ファイル一覧や認証用情報を載せず、判定・件数・ハッシュと検査結果を示す。
