# WordPress / MariaDB 取得停止の専用試験

この試験は新規のWordPressとMariaDBをDocker内に作成し、実際の投稿・ファイル書込みを使って停止・待機・解除を検証する。既存サイト、dm、AWS、署名鍵を使用しない。汎用プラグインへ統合する前の実アダプター試作である。

## 停止の順序

1. コーディネーターの所有ロックを排他的に確保し、一意トークン付き停止マーカーを作る。
2. 更新入口はマーカーを確認し、共有ロック取得後にも再確認する。停止中のHTTPは503、CLIは終了コード3で拒否する。
3. コーディネーターが排他ロックを待つ。既存の更新処理はDBとファイルの両方を終えるまで共有ロックを保持する。
4. 排他ロック取得後、専用MariaDB接続で `FLUSH TABLES WITH READ LOCK` を保持する。DBへの直接書込みも待機することを別接続で確認する。
5. 別接続でDBをダンプし、メディアを取得する。DB参照と実ファイルのSHA-256を照合する。正常解除後、別の空DBへダンプを実際に読み戻し、取得したメディアとの参照一致も確認する。
6. 所有トークンによる解除要求を受け、DB接続・排他ロックを解放し、自分の停止マーカーだけを削除する。実際に再投稿し、再開を確認する。

新規受付の停止と進行中処理の完了は別イベントとして記録する。正常解除応答がない取得は成功扱いにしない。二重実行は他の所有者のマーカーを削除しない。

## 失敗・期限

排出待ちには期限があり、超過すると取得へ進まず解除する。DBロック待ちにもセッション単位の期限を設ける。準備完了後は更新しない固定リースを使い、リース切れ・親プロセスの標準入力切断でもfinallyで解除する。取得失敗時も親がfinallyで解除を要求する。

これはOS停止・SIGKILLを含む万能な自動復旧ではない。コーディネーターを強制終了するとDB接続とflockは解放されるが、停止マーカーが残り、新規書込みを拒否し続ける場合がある。この試験では環境を廃棄して再作成する。実サイト用には、独立監視による所有者失効確認と、誤った解除を防ぐ管理者手順が必要。

## 実行方法

WSL Ubuntuで、既に `lab/m1/images.env` に記録されたイメージがローカルにあることを前提とする。自動ダウンロードはしない。

```bash
cd /mnt/d/workspace/ozeki-wordpress-resilience
python3 tools/run-wordpress-consistency-lab.py --execute-lab --output .local/wordpress-consistency-new.json
```

引数なし／helpでは環境を作らない。出力先は新規ファイルを指定する。試験用秘密値は毎回生成し、パーミッション600の一時envファイルで渡す。結果に秘密値やSQL本文を出さない。

各実行はランダム名の専用コンテナだけを作成する。DBは `--network none`、WordPressはDBのネットワーク名前空間を共有し、ループバック通信のみ。ホストへのポート公開もない。実行終了時には作成したコンテナとその匿名ボリュームだけを削除する。Dockerデーモンの停止・prune・既存ボリューム削除はしない。プロセス自体が強制終了した場合の残存資源は別途管理対象になる。

## 適用範囲と未達

制御対象は `lab/consistency/writer.php` を通る専用HTTP・CLI更新処理。実際のWordPress API、MariaDBトランザクション、ファイル書込みを利用するが、通常の管理画面・REST・cron・外部キュー・SSH・デプロイ・任意プラグインがこのゲートを通ることまでは実装していない。自動cronとファイル更新は試験環境で無効化する。

DB読取りロックは直接DB更新を止めるが、別プロセスによる直接ファイル変更までは止めない。したがって実サイト全体の `scope_complete=true` や整合性合格へ自動変換しない。前段の `capture-consistency.py` への正式な証拠アダプター、全更新経路の棚卸し、実サイトの停止時間帯、独立監視は次の統合課題である。保存元の侵害耐性やマルウェア除去の証明でもない。

結果: [実測記録](../../evidence-public/wordpress-consistency-lab.json)。成功結果は全試験と専用資源の削除が完了した場合にのみ出力する。
