# 独立watchdog：通常警報とテスト送信の統合試験

専用環境で `watchdog-observer.py observe` を実行し、実際のwatchdog状態機械、通常警報のoutboxと配送台帳、独立設定の受付・テスト配送、公開状態を一連の処理として検証する。通知プロバイダーのみ模擬実装に置き換え、実Pushoverへは送らない。前段のiPhone実機試験とは別の検証である。

## 処理順と画面表示

1. 監視対象の生存記録を取得し、設定変更要求を処理する。
2. watchdogと監視ホストの状態を判定し、発生・解消イベントを永続化する。
3. 通常警報の配送・確認照会・取消を処理する。
4. テスト要求を処理する。実送信は1周期1件まで。同一要求は再送しない。
5. 通常警報とテスト結果を別々に公開し、管理画面が取得する。

テストの「サービス受付」は通常警報の成功を保証しない。今回、独立通知設定画面にも通常警報の配送異常を明示する表示を追加した。詳細は「Resilience → 通知」で確認する。

|停止・異常|期待する挙動|
|---|---|
|要求転送停止|ローカル要求を保持。外部の結果が届くまで結果待ち。成功と表示しない|
|転送後に観測処理停止|受付DBを保持。公開報告の日時と結果を更新しない|
|配送ロック占有|通常配送失敗とテスト処理異常を報告。送信ボタンを無効化し、要求を未処理で保持|
|ロック解除・再起動|未処理の通常警報とテストを処理し、完了済み要求は再送しない|
|結果取得停止|管理画面は最後に取得した履歴を保持。5分を超えた報告は古い履歴と明示し、テストボタンを無効化|
|テスト結果不明|通常警報のreceiptは保持。テストの自動再送はしない|
|通常警報失敗・テスト成功|両方の状態を併記。テスト成功で通常警報異常を隠さない|
|停止中に要求が5分超過|再開後は未送信として記録し、古いテストを送信しない|
|監視対象復旧|通常警報の解消・receipt取消を継続。取消は既存の照会予定時刻に従う|

## 再現方法

WSL Ubuntuから実行する。既存の専用Dockerイメージが必要。

```sh
python3 -m unittest discover -s tests -p test_observer_runtime_integration.py
python3 tools/run-observer-runtime-lab.py /tmp/observer-runtime-ssh.json
python3 tools/run-notification-admin-lab.py --output /tmp/observer-runtime-ui
```

実SSH試験では外部通信を遮断した2コンテナを使用する。監視対象コンテナ全体の停止・再起動、ホスト鍵不一致、古い生存記録、通常警報とテストの同時処理、観測コンテナ再起動後の重複抑止を確認する。試験終了時に、この試験が作成したコンテナとネットワークだけを削除する。

WordPress試験は専用WordPress・MariaDB・ブラウザーで行い、実際の観測関数から出力された配送停止・復旧結果を管理画面に渡す。報告の鮮度切れと要求期限切れは、専用試験データの時刻を変更して境界を検証する。取消試験は専用配送台帳の照会予定時刻を到来済みにする。長時間停止や実サービスの待ち時間を実測した結果とは扱わない。

## 適用範囲

これは専用環境の検証。本番サーバー、dmの既存FTP・MySQL、既存監視設定、実通知先は変更しない。systemdの常設配置・運用開始を意味しない。通常警報とテストの台帳は削除・統合せず、既存の重複抑止・旧通知先のreceiptを維持する。

検証結果：統合8件、watchdog回帰9件、実SSH19項目、WordPress画面166項目が合格。[検証記録](../../evidence-public/observer-runtime-summary.json)。
