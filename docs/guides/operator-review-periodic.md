# 担当者確認の定期報告と表示回復

既存 `preflight-relay.tick` の `review_file` 設定を使用します。棚卸しから毎回新しい検査結果を生成し、原本の担当者確認を読み、状態要約を付加します。既存 `preflight-transfer.serve/pull` が要約だけを制限付きで受け渡し、WordPressの読取り専用画面で確認します。新しい監視・通知サービスは追加しません。

## 接続と操作

- 生成側：profile_file / inventory_file / connection_file / workspace に加え、担当者管理の日次用 review_file を指定します。入力と出力のパスを分けます。
- 受取側：既存のreport_file / health_file とWordPress定数を使用します。原子的置換後も読めるよう、表示用ディレクトリのグループ継承等を設定します。WordPressから書き込めない配置にします。
- 期限切れ・失効：原本を定期処理が再評価して報告。画面でも期限を判定します。期限内表示だけで実行を許可しません。
- 再確認：外部の担当者用発行処理で新しい記録を作り、履歴を保管して参照を切り替えます。次の報告・転送で期限内へ回復します。日次の失敗台帳の解消とは別です。
- 原本がない・不正・報告更新停止の場合は、未取得・不正・現在の有効性未確認として扱います。自動延長は行いません。

## 今回の専用試験

`python3 -B tools/run-operator-review-periodic-lab.py --output /new/lab/directory`

ネットワークなしのWordPress/MariaDB/Chromiumと新しい試験ディレクトリを使用します。外部試験プロセスが2秒周期で既存の報告生成・転送処理を実行します。棚卸し事実と転送路は生成データ／プロセス内transportです。実SSH・別ホスト・systemdの運転試験ではありません。

検証する連続した状態：期限内 → 実時間の短縮期限切れ → 明示再確認で期限内 → 明示失効 → 再確認で期限内。期限切れは試験用原本の期限を5秒先へ設定し、実際の時計で期限を越えるまで待ちます。実運用の7日経過試験を意味しません。

各場面でWordPressの表示、POST405、editor閲覧拒否、操作フォームなし、秘密値の非表示を確認します。表示中も報告が更新され、担当者確認原本は定期処理によって変わらないことを検査します。発行と切替は試験内の明示操作であり、定期ループに更新権限を付与する設計ではありません。

試験用表示ディレクトリは専用WordPressのGID33を継承し、原子的に置換した報告の0640権限を維持して読み取れるようにします。この配置設定は試験基盤の準備事項です。本番・既存観測のディレクトリは変更しません。

環境・試験基盤・製品の評価は分けます。既存の原因未確定ブラウザ問題は、この成功によって原因確定・解決扱いにしません。AWS・通知・署名・復元・72時間観測の保存セットへの追加操作はありません。

結果：5場面すべて成功、定期報告50回更新。ブラウザ確認中も各場面3～4回の更新を確認し、その間の担当者確認原本のバイト列は不変。POST405・editor拒否・読取り専用・非露出も各場面で確認。再確認後の画面を目視確認済み。専用コンテナと周期処理は終了済み。実SSH、systemd、別ホストでの運転は今回の合格範囲に含みません。新たな製品不具合・環境障害は確認せず、試験表示ディレクトリのグループ継承を準備中に補完しました。

次段階の実SSH・systemd・専用VM再起動試験は[こちら](operator-review-systemd.md)に分けて記録します。
