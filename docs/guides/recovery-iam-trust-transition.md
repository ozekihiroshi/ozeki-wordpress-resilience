# 復旧権限と信頼情報を分離する移行手順

更新日：2026年10月18日。設定変更前のレビュー資料。AWS変更、署名鍵の生成、本番への署名検証必須化は未実施。

## 調査結果

- 保存元と復旧先は共有ロールを使用している。dmからIAM GetRole / ListAttachedRolePolicies / ListRolePoliciesはAccessDenied。復旧専用ロールの存在も確認できず、「存在しない」とは判断しない。
- 対象S3はVersioning Enabled。Object Lock設定は存在しない。保持耐性があるとは判定しない。
- dm上のanchorは別ホストへ複製された期待値である。署名・独立管理された検証鍵・失効情報は未実装で、真正性はunverifiedを維持する。

## 境界を三つに分ける

| 主体 | 保持するもの・権限 | 持たせないもの |
| --- | --- | --- |
| 保存元community | 対象範囲への資産保存。既存業務の権限は別途棚卸し | 復旧専用ロール取得、保護対象の固定版削除、信頼情報の署名鍵・変更権限 |
| 復旧取得側dm | 固定Version IDでの取得、署名・期待値の検証に必要な公開情報 | 対象資産の書込み・削除、署名秘密鍵 |
| 独立した管理環境 | 検証鍵の信頼根拠、レビューした復旧情報への署名、失効・鍵更新記録 | 本番サーバーからの自動承認依頼を無条件に署名する仕組み |

署名は「特定の管理主体がこの組合せを承認した」ことを示す。バックアップが無感染であることやサイトが復旧できることを自動で証明しない。

## 1. 管理者による現状の取得

IAM管理権限をcommunityやdmへ追加して調査を簡便化しない。管理者のAWSコンソールまたは指定されたSSOプロファイルで調べる。

AWSコンソールでは、共有ロールとOwrM1RecoveryReader（存在する場合）の次を保存する：信頼ポリシー、全インラインポリシー、全アタッチ済み管理ポリシーの有効版、Permissions boundary、関連instance profile。S3のbucket policy、Versioning、Lifecycle、暗号化、Object Lockも確認する。OrganizationsのSCP等はアカウント管理者に確認する。

CLIの場合は[読み取り専用エクスポート](../../tools/export-recovery-iam-review.py)を使用する。実行例の値は実環境に置き換える。出力先の親ディレクトリを事前に用意し、.local以下へ保管する。内容はインフラ構成情報なので公開しない。

```sh
python3 tools/export-recovery-iam-review.py --profile ADMIN_SSO \
  --writer-role EXISTING_WRITER_ROLE --reader-role OwrM1RecoveryReader \
  --bucket YOUR_BUCKET --owner YOUR_ACCOUNT_ID --region ap-northeast-1 \
  --output .local/iam-review-20261018.json
```

エクスポートは選択したロールとバケットだけの調査であり、SCP、他の委任経路、dmの業務が実際に呼ぶAWS APIまで自動網羅しない。completeは要求したAPIの取得完了であり、安全性の合格ではない。

## 2. 復旧専用ロールへ切り替える前の条件

1. dmのFTP・MySQL自体の稼働に加え、SSM、ログ転送、定期ジョブ等が使うAWS権限を確認する。共用業務は2027年3月末まで維持する。
2. OwrM1RecoveryReaderの信頼先はEC2サービス。communityの共有ロールをAssumeRole元として許可しない。EC2信頼だけではdm限定を意味しないため、ロールをEC2へ渡すiam:PassRoleとinstance profile付替え権限の管理主体も確認する。
3. 既存の[復旧専用ポリシー](../../examples/m1/recovery-reader-policy.json)を起点に固定版GETのみを許可し、対象プレフィックスの変更・削除を拒否する。タグ・保持情報変更やバケット設定変更、KMS、追加の委任経路は全ポリシーのレビュー後に具体化する。
4. 必要な運用権限だけを専用ロールへ引き継ぐ。既存ロールの全ポリシーを複製しない。元のinstance profileを記録し、接続経路が維持できる時間帯に切り替える。
5. 共有ロール自体を復旧専用へ変更しない。共有ロールへreaderのDenyを追加すると保存元にも作用する。
6. 切替後は新しい主体名と固定版GETを確認する。切替前の資格情報がキャッシュされる可能性を考慮し、旧資格情報も失効・期限切れを確認するまでは分離完了と扱わない。

EC2のinstance roleは同じホスト上のアプリケーションが共有する。dmで同じ共有ロールから別ロールをAssumeRoleするだけの構成は、その共有ロールを持つcommunityにも経路を与えるなら分離にならない。既存業務と両立できなければ独立した取得環境を使う。

## 3. 信頼情報の独立管理

利用者は署名鍵を手元PCで管理し、別媒体に復旧用コピーを置く方針を選択した。鍵生成と別媒体へのコピーは未実施。秘密鍵をGit、community、dm、同じ復旧アーカイブへ入れない。手元PC案でも同一担当者・端末侵害という残る制約を明示する。

署名対象は、サイトID・セットID・発行時刻・有効期限・世代番号、Recovery Set / RAM / Bootstrapのbucket・key・Version ID・サイズ・ハッシュ、署名鍵IDを含む承認記録とする。バイト列を固定して署名し、復旧側は独立経路で配布した検証鍵の指紋と照合する。公開鍵や期待ハッシュを取得元のアーカイブに入れただけでは信頼の起点にならない。

対象セットの署名前に、独立取得結果と既知の復元結果をレビューする。汚染検査未実施ならその状態も記録し、正常性を過大に承認しない。dmでの検証と実行は分け、未検証のBootstrapコードを先に動かさない。

検証は署名不一致・未知の鍵・失効・期限切れ・別サイト・別セットを拒否する。古い正当な署名の再提示に備え、独立保管された最新の承認世代と失効情報を確認する。災害時に古い正常セットを選ぶ場合は、明示的な再承認として記録し、黙って期限や世代の検査を外さない。

鍵紛失・漏えい・更新、別担当者への引継ぎ、別媒体からの復旧を手順化し、実際のコピー保管と復旧試験が済むまで「独立保管完了」としない。署名済み情報は新しい承認記録として追加し、過去のM1証拠のauthenticityを後から書き換えない。

## 4. 破壊耐性と試験

Versioningのみでは削除権限を持つ主体から固定版を守れない。保存主体のオブジェクト版削除、Lifecycle・Versioning・bucket policy・鍵・ロールの変更経路を確認する。署名は改ざん検知を補うが、資産の削除や読み出し不能を防がない。

Object Lockは現バケットへ直ちに適用しない。保持期間、費用、管理者の解除能力、既存データへの適用範囲を決める。Governanceのbypass権限や、Complianceの保持期間中の削除制限を理解した上で、まず使い捨ての専用資産で試す。Bucket単位の設定変更は既存用途への影響を確認する。

受入試験：

- 復旧専用主体で固定版GET成功、サイズ・ハッシュ一致。
- 保存主体から復旧ロール取得が拒否される。PassRole・profile付替え・SSM等の他ホスト制御経路もレビューする。
- PUT/DELETE等の拒否試験は専用canaryだけで行う。成功してしまっても業務データを損なわない対象を用意し、既存固定版を試験で削除しない。
- 署名内容・鍵・サイト・世代・期限・失効の否定試験が失敗側で閉じる。
- 保存元停止後に別管理の信頼情報から固定版を取得し、元サーバーの認証に依存せず復旧できる。

## 現在の保留理由

現在のEC2ロールにはIAM閲覧権限がなく、既存業務の権限と移行対象を確定できない。利用者の最新回答により、IAMの確認・設定はAWSコンソールで行う。署名鍵は手元PC＋別媒体の方針。既存ロールの全ポリシー内容と別媒体の実際の保管は未確認。IAM変更や鍵生成を実施済みとは報告しない。

参考：[EC2でのIAMロール利用](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_switch-role-ec2.html)、[S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)、[Object Lockの運用上の注意](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html)。

## AWSコンソールで今行う確認

1. AWSコンソールで対象アカウントへ入り、IAM → ロール → 現在の共有ロールを開く。
2. 「許可」から、アタッチされたポリシー名と各JSON、有効な管理ポリシー版、インラインポリシー、Permissions boundaryの有無を確認する。「信頼関係」のJSONも確認する。JSONはアクセスキーやパスワードを含まないが、アカウントID等の構成情報を含むため公開しない。
3. IAM → ロールでOwrM1RecoveryReaderを検索し、存在すれば同じ項目を確認する。既存ロールを削除・上書きしない。
4. EC2 → インスタンス → dmの「セキュリティ」で現在のIAMロールを記録する。この段階ではIAMロールを変更しない。
5. S3 → 対象バケット →「アクセス許可」のbucket policyと、「管理」のLifecycleルールを確認する。対象プレフィックスに期限切れ削除・旧版削除が適用されるかを見る。設定は変更しない。

まず共有ロールのポリシー一覧と、復旧専用ロールの有無を共有すると、必要な確認を絞れる。名前だけでは権限分離を認定できないため、移行前にはJSONも確認する。パスワードやアクセスキーの送付は不要。

ローカルの .local/iam-console-20261018/ に実バケット名を反映したreader-policyとEC2信頼ポリシーを準備した。これらは既存M1の最小構成案で、全ポリシー・運用影響レビュー前に共有ロールへ追加しない。最終適用内容は上記確認後に確定する。

### 復元入口への必須ゲート統合

`tools/run-independent-recovery.py` は信頼ディレクトリ・承認記録・署名・期待サイトID・セットIDを必須とする。独立配布した検証コードで署名と承認ハッシュ、失効、期限、世代、対象、anchor/Set/RAM/Bootstrapを検査してからDocker操作を始める。展開済みBootstrapの全ファイルを署名対象アーカイブと照合し、追加ファイル・リンクも拒否する。拒否時には復元先作成も行わない。検証をスキップするオプションはない。

`--verify-only` は検証だけで終了する。今回の承認済みM1セットはこの新しい入口で合格した。通常復元への接続はDockerを代替した自動テストで確認し、実DBを使う完全復元は今回再実行していない。従来の未署名の派生データを作る `test-shared-core-recovery.py` は作業開始前に停止する。派生セットを正式に発行・独立承認した後に新しい入口を利用する。

検証と実行の間にローカルファイルを書き換えられない、管理された復旧環境を前提とする。同じOS権限やrootを持つ攻撃者を防ぐ仕組みではない。任意の古いスクリプト・手動SQL投入をOS全体で禁止するものでもない。dmで過去に実施した手動復元を遡って保護したとは扱わない。マルウェア検査・実行隔離・保存資産の削除耐性は別の要件として残る。

ゲート統合の自動回帰試験は15件合格。Pythonの最適化実行（-O）でも拒否条件が無効化されないことを含めて確認した。正常な通常モードはDocker代替コマンドへ到達し、異常系はDocker呼出し・復元先作成のいずれも行わないことを検証した。
