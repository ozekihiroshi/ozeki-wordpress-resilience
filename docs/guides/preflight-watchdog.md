# 導入前検査の独立watchdog

## 今回追加する範囲

以前の日次状態報告watchdog試験は、日次バックアップの生成・取得処理が対象です。導入前検査の別VM試験は、結果の受渡しと管理画面表示まででした。今回初めて、導入前検査の報告・更新記録を独立watchdogへ接続し、警報と回復通知の経路を確認します。通知基盤自体は既存の `watchdog-observer.py` を再利用します。

新規部分は `tools/preflight-watchdog-probe.py` です。WordPressや検査サービスのリクエストから監視を呼ばず、独立した監視プロセスが検査側と受渡し側へ固定コマンドSSHで問い合わせます。

## 検査側・受渡し側の配置

それぞれのホストへ専用の読取りユーザーを作り、公開報告・更新記録だけを読めるグループへ所属させます。非公開状態・SSH秘密鍵・DB資格情報を読ませず、報告への書込み、sudo、Docker権限を与えません。

プローブ設定例（検査側。受渡し側ではmonitor_idを別名にする）：

```json
{
  "monitor_id": "preflight-source",
  "site_id": "example-site",
  "config_sha256": "プロファイルの64桁ハッシュ",
  "report_file": "/var/lib/owr-preflight-web/report.json",
  "health_file": "/var/lib/owr-preflight-web/health.json"
}
```

独立監視側の公開鍵をroot管理のauthorized_keysへ登録します。

```text
restrict,command="/usr/bin/python3 -B /opt/owr/tools/preflight-watchdog-probe.py --config /etc/owr/watchdog-probe.json" ssh-ed25519 公開鍵
```

sshdは当該ユーザーの公開鍵認証のみ、TTY・転送を禁止します。独立監視側のknown_hostsには別経路で検証した鍵を `owr-notification-preflight-source` の別名で登録します。設定は [独立watchdog手順](watchdog-observer.md) のobserve構成を使用し、monitor_id、SSH接続先、専用状態ディレクトリーを分けてください。公開報告の形式・サイト・設定版・時刻の組が一致しない場合は異常として返します。

## 判定

- 検査側は元の検査時刻を返します。SSH接続が成功した時刻で上書きしません。
- 受渡し側は更新記録が確定した検査時刻と受渡し処理時刻の古い方を返します。転送だけ動いても検査停止を隠しません。
- 受渡し失敗・形式不正・時刻逆転はinvalidとして検知します。更新記録が進まない場合は確定時刻が古くなり停止として検知します。
- 検査停止・受渡し停止は観測時刻の期限超過として検知します。
- SSH自体が到達不能の場合は、到達性と進捗を別々に監視します。
- 検査が正常に実行されても、対象サイトの未確認項目が解消したとは限りません。watchdogは導入可否の承認ではありません。

監視の猶予は実行周期・通信時間・許容する検知遅延に合わせます。専用試験では更新60秒・期限100秒・監視約3秒を使用します。実運用の標準値確定とは分けます。別監視機から両ホストのSSHへ到達でき、時刻が同期していることが前提です。

## 専用試験

新しい生成データ・2台のUbuntu VMを使用し、両VMの外側の監視プロセスで実SSHを実行します。通知先は専用ローカルHTTP受信先です。通信断、検査サービス停止、受渡しサービス停止、通知受信先の503、回復、監視プロセスの再起動を試します。時刻を加工しません。WordPressの再配置・画面試験や以前の日次バックアップ試験を繰り返すものではありません。

同じ物理ホスト上の論理分離であり、物理ホスト全体の障害耐性を証明しません。Pushover実機や本番メールへの送信、72時間観測への変更は行いません。既存の監視基盤の再利用なので、一般的な通知機能を一から追加する変更ではありません。

## 結果

[専用試験の記録](../../evidence-public/preflight-watchdog.json)：処理23項目と単体7件が合格。警報4件と回復通知4件をローカルHTTP受信先で確認し、監視再起動後の重複はありませんでした。今回の試験で新しい環境・試験ツール・プラグインの障害は発生していません。以前の試験で記録したタイムアウトの原因解明を意味するものではありません。

通知種別は既存の `heartbeat_invalid`（通信断後の受渡し失敗記録など）と `monitor_stopped`（更新停止）を使います。対象は `preflight-source` / `preflight-receiver` で区別します。今回、管理画面の新設や実機プッシュ通知は追加していません。
