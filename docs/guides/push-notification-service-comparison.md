# 重要警報のプッシュ通知サービス比較

調査日：2026-10-19。重要警報はプッシュ、詳細・履歴はメールという方針は採用済み。サービス選択は以下の推奨案であり、契約・購入・実通知・アダプター実装は未実施。

## 結論

現在の大関さん中心の少人数運用には、**Pushoverを最初の実機試験候補**とする。確認操作と繰返し通知をサービス側で扱え、dmからHTTPSで送信できる。既存のGoogleメールと通知サービスを分けられ、dmにメールサーバーや新しい受信用ポートを設ける必要がない。確認状態も外向きのAPI照会で取得する設計にする。

予備担当への自動引継ぎや当番表を最初から必要とする場合は、**PagerDuty Freeを優先して再評価**する。単に費用の高い将来候補ではなく、現在でも選べる有力な代案である。

製品としてのOzeki WordPress Resilienceは特定のサービスの契約を必須にせず、通知先を交換できる構造とする。最初の導入先の選択と、プラグイン全体の依存関係を分ける。

## Pushoverで試す構成

- 通常監視側とdmのwatchdogから、外向きHTTPSでPushoverへ直接送信する。dmの警報をcommunity経由で中継しない。
- Google SMTPによる詳細メールとプッシュは、送信待ち・再試行・成功失敗の記録を分ける。メールの先頭イベントが失敗しても重要プッシュを進められるようにする。
- 事件ID、発生・解消イベントID、送信先、サービス側のreceipt、確認日時を永続化する。API受付、端末での表示、人による確認を同一視しない。
- 確認操作は「担当者が気付いた」という記録であり、障害解消やバックアップの署名承認として扱わない。
- 監視停止、取得漏れ、復元試験失敗、承認期限切れを重要警報とする。単なる承認待ちはまずメールとし、警告を出す時刻は別途定義する。
- 通知内容はサイトの別名、事象、時刻、事件ID、対応の要点に絞る。バックアップ本体、署名鍵、認証情報、個人情報を送らない。メールも生ログの無制限添付を避ける。
- サービスの資格情報は監視側とdmで分離できる範囲を確認し、WordPress保存元やGitに配布しない。

緊急通知は、試験案として60秒間隔・30分で期限を設定する。Pushoverの仕様は再通知間隔の最小30秒、期限の最大3時間、再通知回数の上限50回。無期限に繰り返せるものではない。期限切れでも未確認なら事件を継続中として残し、別担当への連絡や次の通知を行うかを運用規則で決める。[API仕様](https://pushover.net/api)

解消した事件の繰返し通知は停止する。送信応答が失われた場合の二重送信はreceiptの保存だけでは完全には防げないため、不明状態を記録し、無制限な再送を避ける。確認照会・取消については[receipt API](https://pushover.net/api/receipts)に合わせる。

## 残る停止検知の範囲

dmは通常監視側の停止を検知するが、dm自身の停止をdmだけで通知することはできない。これを補うには、別の外部サービスへdmから生存記録を送り、途絶を外側から検知する仕組みが必要。今回のサービス選定だけでこの検知が完成したとは扱わない。

Googleメールとプッシュサービスを分けても、受信端末の電源・通信やモバイルOSの配信基盤には依存する。集中モード・消音・夜間でも必ず鳴るとは保証せず、実機で確認する。

## 次の試験と採用条件

1. 受信端末がiPhoneかAndroidか、受信担当と予備担当の有無を確認する。
2. 専用環境に通知先を交換できるアダプターと、メールとは独立した配送状態を実装する。まず模擬受信先で検証する。
3. Pushover試用で、画面ロック・バックグラウンド・夜間設定・集中モード・一時的な通信断の挙動を実機確認する。
4. 確認による再通知停止、解消時の取消、未確認期限切れ、APIタイムアウト・429・5xx、再起動後の再開を確認する。重複や通知の大量発生を抑える。
5. Google SMTP障害時にもプッシュが進むこと、プッシュ障害時にもメール記録が進むことを確認する。既存の事件・未配送記録を移行時に失わない。
6. 結果を記録し正式採用を決める。その後に定期実行と実宛先を有効にする。

今回は比較と設計の更新のみ。dmのFTP・MySQL・Postfixや常駐サービスの設定変更、通知サービスへの登録・送信は実施していない。
