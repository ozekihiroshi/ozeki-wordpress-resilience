# 独立watchdog：Pushover・iPhone実機試験の準備と手順

2026-10-19。これは実行前の手順書。今回の作業では資格情報の読出し・コピー、サーバー配置、タイマー起動、実通知を行っていない。前段の専用環境試験は模擬プロバイダーによるもので、実機受信の証拠にはしない。

## 今回の構成案

専用WordPress管理画面 → 専用SSH受付 → 独立観測処理 → Pushover → iPhone。
独立観測処理 → 公開状態 → 専用読取りSSH → WordPress管理画面、で結果を戻す。

既存のdmはwatchdogの配置先として扱う。dm自身とそのwatchdogを監視する「独立観測側」は別ホストに置く。初回の実機試験では手元WSL Ubuntuを独立観測側にする案。WSLの停止・PCのスリープもあるため、常設の独立監視が完成したとは評価しない。実際の配置、接続名、パスは次回の準備作業で確認する。

既存の自動試験は外部通信できないコンテナと模擬通知先を使う。その試験を実キーに置き換えて実行しない。実機用には専用WordPress・DB・要求ディレクトリ・受付DB・観測state・配送DBを用意し、必要なSSH通信と観測側からPushoverへのHTTPS/DNSが使える構成にする。既存サイト・既存監視のDBを流用しない。

## 必要な設定

|項目|準備内容|
|---|---|
|iPhone|以前受信できたPushoverアカウントでログイン。OSの通知許可、集中モード、Pushoverのquiet hoursを確認|
|Pushover資格情報|以前用意したAPI TokenとUser Keyを再利用可能。保存場所と使用者を確認し、秘密値はチャット・Git・WordPressへ渡さない|
|独立観測側の資格情報|Linuxの絶対パス、実行ユーザー所有0600。SSH受付ユーザーやWordPressから読めない場所|
|接続設定名|例 `independent_push`。外部policyのprofilesに登録。実キーを管理画面に入力しない|
|サイトID|WordPress通知設定のsite_idを、受付・relay・公開状態・状態取得側で一致させる。監視対象probeの識別子とは混同しない|
|WordPress|`OWR_OBSERVER_REQUEST_DIR` と `OWR_OBSERVER_STATUS_FILE`。管理者権限が必要|
|SSH|要求受付用、状態読取り用、dmの生存記録読取り用を用途別に設定。固定コマンド・ホスト鍵検証を維持|
|外部観測設定|admin_site_id、public_status_file、configurationを設定。configuration.delivery_stateとalerts.stateを一致させる|
|通信・時計|独立観測側から `https://api.pushover.net/1/messages.json` へTLS検証付き接続。各実行環境の時刻を同期|

最小の外部policy例（パスは実行環境に合わせる）。既存policyへ適用する場合は、他の通知先を削除する置換ではなく必要なprofileを追加する。

```json
{
  "profiles": {
    "independent_push": {
      "transport": "pushover",
      "credentials_file": "/etc/owr/independent-pushover.json"
    }
  },
  "required_kinds": ["monitor_stopped", "heartbeat_invalid", "notification_delivery_failed"]
}
```

資格情報ファイルの形式は `{"token":"API_TOKEN","user":"USER_KEY"}`。秘密値はエディター等で設定し、コマンド引数やログへ出さない。管理画面の「受信者」はPushoverでは表示名であり、実宛先はこのUser Keyで決まる。現アダプターはdevice指定に対応していないため、同じユーザーの他の有効端末にも配信され得る。[Pushover公式API](https://pushover.net/api)

接続の詳細は[独立通知設定](observer-settings.md)、[状態の管理画面表示](observer-admin-status.md)、[外部観測配置](watchdog-observer.md)に従う。既存配送設定には資格情報の固定コピーがあるため、元の秘密ファイルを差し替えるだけで稼働中通知先が変わるとは扱わない。設定版の更新・反映を通して切り替える。

## 実施順序

1. **試験場所を確認する。** 専用WordPressのURL、独立観測側、監視対象dm、実行ユーザー、各設定ファイルの絶対パスを記録する。既存Pushover登録のやり直しは不要。秘密値を表示せず、資格情報の所有者・権限・形式を確認する。
2. **経路を接続する。** 専用SSH受付と状態取得、独立観測処理を配置する。初回は手動実行とし、自動タイマーは有効化しない。既存設定への接続では既存stateを消さず、enableによる明示的な移行手順を使う。
3. **余分な警報を防ぐ。** 監視対象の生存記録が新しく、観測結果が正常で、専用配送DBに未配送・確認待ちの警報がないことを確認する。observeはテスト送信専用コマンドではなく、通常警報も処理する。古い生存記録を更新したように偽装したり、既存台帳を削除して試験を進めない。異常があれば先に原因を解消する。
4. **管理画面で通知先を登録する。** Resilience → 独立watchdogで、表示名「実機試験用iPhone」、方式Pushover、接続設定名 `independent_push` を指定。有効にし、3種類の必須警報を選択して候補保存する。
5. **反映を確認する。** 「外部側へ反映を要求」→要求転送→外部観測処理→状態取得→画面再読込みの順に進め、同じ設定版が反映済みになったことを確認する。APIキーやダミー資格情報が混在したまま進めない。
6. **テストを1回要求する。** iPhoneを手元に置き、「独立watchdogのテスト送信」を押す。要求IDと設定版、要求時刻を控える。受付表示の時点では受信成功ではない。
7. **処理結果を戻す。** 要求転送→独立観測処理→状態取得を順に実行する。要求の有効期限は5分なので、その範囲で処理する。再読込みし、同じ要求IDの「サービス受付」を確認する。公開報告が模擬実行や古い状態でないことも確認する。
8. **iPhoneと照合する。** 現実装のタイトルは `OWR lab: notification_test`。本文のevent_idは管理画面の要求IDからハイフンを除いたもの。サイトID・時刻・event_idを照合し、受信時刻を記録する。本文の `resolved` は通常優先度を選ぶための現実装上の値で、実際の障害が解消した通知ではない。
9. **重複がないことを確認する。** 同じ要求のまま処理・状態取得をもう一度行い、iPhoneへ追加通知が来ないことを確認する。新しいテスト要求を追加する場合は60秒以上空ける。

手動処理のコマンド形は次のとおり。各コマンドは対応するホスト・専用ユーザーで実行し、山括弧を実際の設定パスに置き換える。observeは実通知を起こし得るため、準備確認後の実機試験段階で実行する。

```text
python3 /opt/owr/observer-settings.py exchange --config <要求転送設定の絶対パス>
python3 /opt/owr/watchdog-observer.py observe --config <独立観測設定の絶対パス>
python3 /opt/owr/observer-status.py pull --config <状態取得設定の絶対パス>
```

## 合格条件と結果の読み方

- 新しい外部報告に、要求ID・設定版と一致した「サービス受付」が表示される。
- iPhoneで同じevent_idの通知を受信する。端末の受信確認は人が記録する。
- 同じ要求の再処理で追加送信されず、既存通知設定・未配送記録が保持される。

今回のテストは通常優先度0。緊急通知の繰返しや確認用receiptを使わないため、iPhoneで読んでも管理画面が自動で「本人確認済み」へ変わる機能ではない。通知音等は端末設定に従う。[Pushover公式API](https://pushover.net/api)

|状態|次の確認|
|---|---|
|反映待ち・テストボタンなし|設定版の一致、外部状態の鮮度、SSH、受付ディレクトリの接続|
|結果待ち|要求転送・観測処理・状態取得のどこまで完了したか|
|未送信|5分の期限、設定変更、有効状態、60秒の頻度制限|
|配送拒否|資格情報、宛先、Pushover側の応答を秘密値なしで確認|
|一時失敗・結果不明|自動再送しない。まずiPhoneの履歴を確認し、必要なら後で新しい要求を作る|
|サービス受付だが未受信|User Keyのアカウント、他端末、iPhoneの通信・通知設定・quiet hours。受付だけで合格にしない|
|古い報告|状態取得経路を修復する。履歴を現在の成功とは扱わない|

記録項目：試験日時、専用サイトID、配置場所、設定版、要求ID、管理画面結果、iPhone受信時刻、重複有無、既存状態維持、残課題。キー・トークン・資格情報ファイルの内容は記録に含めない。

初回はこの1往復を合格にしてから、定期実行や端末通信断などの追加試験へ進む。実機試験が終わっても既存の監視は停止しない。新設した試験用定期処理がある場合だけ停止対象を確認し、試験記録は保持する。

## 実施結果：2026-10-19

実機試験は合格。専用WordPress → 実SSH受付 → WSLのテスト配送処理 → 実Pushover → iPhone受信、および実SSHによる結果取得 → 管理画面表示を確認した。

- 要求ID：`a1c3cfea-e62a-4b4a-848f-de72da989a28`、設定版1。
- Pushover受付：`accepted`。管理画面のスクリーンショットと公開状態、私有配送台帳のIDが一致。
- iPhone受信：利用者が受信成功を確認。
- 同一要求再処理：プロバイダー呼出し0回、既存記録に変更なし。再検証で実通知を追加していない。
- テスト配送記録1件、通常警報の配送記録0件。

今回は独立watchdogのテスト配送コントローラーを使う専用実行構成で、dmの監視・通常警報配送は接続していない。画面のホスト監視状態は未観測として扱う。常設監視、PC停止への耐性、定期サービスの起動は合格範囲に含めない。試験用ワーカーとローカル転送は起動から2時間で終了し、DB・コンテナは記録を保持する。
