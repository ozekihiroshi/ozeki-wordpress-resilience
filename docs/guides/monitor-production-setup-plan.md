# SMTP実設定・別ホストwatchdog導入計画

2026-10-19の初期計画。後続作業ではdmが配置先に確定し、[専用SSHの実装・実測](dm-heartbeat-ssh.md)まで完了。本書の以下の未実施記述は計画整理時点の履歴。今回は設定項目と導入手順の整理。SMTP接続、実メール送信、SSH接続、サーバー設定変更、常設タイマーの有効化は行っていない。[実装・専用試験の結果](monitor-email-scheduling.md)を前提とする。

## 初期の配置案

|役割|配置案|決定状況|
|---|---|---|
|バックアップ元|community上の対象サイト|既存。今回の導入で変更しない|
|通常監視|現在の台帳・復元記録がある手元PCのWSL|初回導入案。PC停止中は監視も止まる|
|停止監視watchdog|別ホストのdm|確定。専用SSHの実装・実測済み。常設タイマー・実通知は未設定|
|通常通知のSMTP|利用者が指定する既存SMTPサービス|未定|
|停止通知のSMTP|通常通知と異なるSMTPサービスまたは独立したリレー|未定。同一サービスなら共通障害が残る|
|受信担当|大関さんの確認可能なメールボックス|具体的なアドレスは未定|

`dm`は既存の復旧用環境でもあるため、監視用の専用Linuxユーザー・ディレクトリ・ユニットを追加する案とする。FTP、MySQL、`demand` DB、既存アプリ、EC2のIAMロールを変更する必要はない。保存元communityへwatchdogを置くと、保存元の障害・侵害と同時に停止するおそれがあるため、初期配置案には含めない。

通常監視をWSLに置く場合、スリープ・シャットダウンも停止通知の対象になる。日常的にPCを停止するなら、通常監視と必要な台帳も常時稼働する運用ホストへ移す計画が必要。台帳の移行は今回の初期配置とは別作業とし、空の台帳で正常扱いにしない。

## 決める情報

通常通知用とwatchdog通知用で、次の項目をそれぞれ記入する。

|項目|必要な内容|扱い|
|---|---|---|
|サービス名|契約先・メールサービス名|最初に確認。サービス確定後、公式手順で利用条件を照合する|
|SMTPホスト|送信用サーバーのFQDN|設定の `delivery.host`|
|ポート・TLS方式|提供元が指定する組合せ|`smtp_starttls` または `smtp_tls`。平文への切替なし|
|認証方式|ユーザー名＋パスワード、専用パスワード、または認証不要リレー|現実装はSMTP login方式。OAuth専用サービスには追加実装が必要|
|送信元|実際に送信を許可されているアドレス|`delivery.from`。サービス側の送信元・ドメイン認証条件も確認|
|宛先|運用担当の受信アドレス|`delivery.to`。現実装は1アドレス。複数担当なら管理済み配信先または追加実装を検討|
|認証ファイル|配置先だけを決める|秘密値は手元で入力。チャット・Gitへ貼らない|
|配送経路の独立性|通常通知と停止通知が同時に停止しないか|別認証情報だけではSMTPサービス自体の障害を分離できない|

受信側についても、迷惑メールを含めて到着確認できる担当、休日等の確認方法、停止通知が来た際の連絡先を決める。同じ受信メールボックスを使えば、そのメールサービスが停止するリスクは共通に残る。

配置先は次を確定する。

|項目|確認事項|
|---|---|
|watchdogホスト|`dm`を使うか、別の常時稼働ホストを使うか|
|管理経路|初期設定に利用するSSH接続名。dmなら既存の `ssh dm` は管理作業用|
|実行ユーザー|watchdog専用の非特権ユーザー。既存DB・FTPの実行ユーザーと分離|
|起動方式|サーバーでは専用ユーザーを指定したsystemサービスを初期案とする。ログインなし・再起動後にも動くことを試験|
|時刻同期|両ホストの時刻同期。現在の未来日時許容差は5秒|
|通信|通常監視側→受信ホストのSSHと、それぞれのSMTPへの送信経路|
|容量|小さなJSON・SQLite・ログ用の空き容量、ログ整理方針。バックアップ資産は転送しない|

## 別ホストへ生存記録を届ける方式（SSH実装済み）

初期案は、通常監視側からwatchdogホストへ **SSHでheartbeatだけを送る方式** とする。watchdogホストから手元PCへ接続する必要がなく、PC側に受信用ポートを開けずに済む。

```text
WSLの通常監視 ──SMTP──→ 通常通知
    │ 監視処理の完了後にheartbeatを作成
    └──専用のSSH接続──→ dmの受信処理 ──→ heartbeat.json
                                             │ 読取り専用
                                   dmのwatchdog ──別SMTP──→ 停止通知
```

実装条件：

1. 管理用の `ssh dm` を定期配送に流用せず、heartbeat受信だけに限定した専用SSH鍵・専用受信ユーザーを用意する。バックアップ署名鍵とは別物。
2. SSHホスト鍵を管理経路で確認して固定する。受信側は固定コマンドに制限し、シェル・PTY・ポート転送などは許可しない。
3. 受信コマンドは入力サイズ上限、JSON形式、対象 `monitor_id`、タイムゾーン付き完了時刻、数値項目を検査する。送信側に保存パスを指定させない。
4. 受信した完了時刻をそのまま保存する。受信日時に書き換えない。同じ古いheartbeatの再送で監視が生きているように見せない。
5. 受信処理は同じファイルシステム内で一時ファイルへ保存・同期してから原子的に置換する。並行受信を直列化し、古い記録で新しい記録を巻き戻さない。同一内容の再送は受領可能にする。
6. 受信ユーザーが変更できるのはheartbeatの受信領域だけ。watchdogのプログラム、設定、SMTP認証ファイル、通知台帳を変更できない権限にする。watchdogユーザーはheartbeatを読み取る。
7. 転送失敗でも既存の有効な受信記録を削除しない。次回に再送し、古いままならwatchdogが期限超過を通知する。転送だけが動いても完了時刻は更新しない。

専用SSH送受信と権限制限は[dmで実装・検証済み](dm-heartbeat-ssh.md)。常設の定期配送・実通知経路はまだ有効化していない。 生存記録の経路断も停止警報になるため、警報だけでPCの故障と通信障害を断定しない。

SSH認証は送信元を認証するためのもので、通常監視ホストが侵害された場合の虚偽heartbeatまで防ぐ保証ではない。バックアップの署名検証・独立した信頼情報とは役割を分ける。

## ファイル配置案

|配置先|パスの例|内容|
|---|---|---|
|通常監視側|`~/.config/owr/monitor.json`|通常監視・SMTP設定|
|通常監視側|`~/.config/owr/smtp-credentials.json`|通常通知用の認証情報。Linux上で所有者のみ読取り|
|通常監視側|専用ユーザーの `.ssh/`|heartbeat配送専用鍵・固定したホスト鍵|
|dm|`/opt/owr/tools/`|管理者が配置するプログラム。受信ユーザーから変更不可|
|dm|`/etc/owr/watchdog.json`|対象ID・受信ファイル・状態保存先・別SMTP設定|
|dm|`/etc/owr/watchdog-smtp-credentials.json`|watchdog実行ユーザー所有、モード0600|
|dm|`/var/lib/owr-heartbeat/incoming/heartbeat.json`|専用受信処理が更新、watchdogが読取り|
|dm|`/var/lib/owr-watchdog/`|watchdogのSQLite台帳。受信ユーザーはアクセス不可|

現在のSMTP実装は認証ファイルの所有者と実行ユーザーが一致していることを検査する。親ディレクトリの権限も合わせる。watchdog入口は `monitor-runtime-lab.py`、依存ファイルは `monitor-delivery.py` と `operations-monitor-lab.py`。Python・CA証明書とLinux標準機能を使い、Docker・WordPress・MySQL・S3アクセス権限はwatchdogに不要。

既存のsystemd例はWSLの `/mnt/d/...` とユーザーサービス向けであり、サーバーへそのままコピーしない。サーバー用には実行パス、`User`、設定ファイル、書込み先を明示したサービスを別途作る。

## 導入順序と合格条件

|順序|作業|確認する結果|
|---|---|---|
|1|SMTPサービス・送信元・宛先・ホストを確定|上記の空欄を埋める。秘密値はローカル配置|
|2|専用環境でSSH送受信とサーバー用ユニットを実装|不正入力・古い記録・並行受信・転送失敗・権限越境を拒否|
|3|dmの読み取り中心の事前確認|稼働条件、OS/Python、時刻同期、空き容量、既存業務との分離を確認|
|4|専用ユーザー・ディレクトリ・認証情報を配置|管理用権限と定期処理の権限を分ける|
|5|通常・停止通知をそれぞれ指定宛先へ送信試験|SMTP受付だけでなく、担当者が受信箱で到着確認。既存の大量警報を一括送信せず、専用試験データを使う|
|6|heartbeatの手動送受信|完了時刻が維持され、dmのwatchdogが読める|
|7|watchdogを先に起動し、通常監視・配送を起動|初回heartbeatと通常監視の繰返しを確認|
|8|通常監視の専用タイマーを止める|既存業務を止めずに、15分＋次回watchdog実行までに停止通知|
|9|通常監視を再開する|新しい記録により解消通知。同じ古い記録では解消しない|
|10|heartbeat配送だけを止める／通常通知SMTPを試験設定で失敗させる|前者は更新停止、後者は通知未配送を別経路で検知。復旧後の再送も確認|
|11|ログインなしの稼働・再起動後の起動方法を確認|既存業務に影響するサーバー再起動は別の作業枠。未実測なら未達として記録|
|12|運用担当の確認と記録|連絡先、復旧手順、計画停止、監視自身の外部確認方法を確定して常設化|

初期値は通常監視5分、watchdog1分、更新なし15分。メール配送やネットワークの所要時間もあるため、実メールの到着時刻を厳密に16分以内と保証するものではない。短縮した専用試験の結果と、初期値での確認を区別して記録する。

## 設定変更・停止・残る範囲

現実装はwatchdog設定全体を台帳に固定している。初回は専用の新しい状態保存先を使う。以後、SMTP宛先を含むwatchdog設定変更は、既存ディレクトリのままでは拒否される。旧台帳の未配送通知を確認・記録し、新しい状態保存先で開始する切替手順が必要で、新規警報が再通知される可能性もある。台帳を削除して合わせない。状態を維持した設定移行機能は未実装。

計画停止でも現在は警報が出る。通知抑制を希望する場合は、対象・期間・自動解除の運用を別途設計し、watchdogを恒久停止する運用にしない。SMTP受付後の応答喪失では同じMessage-IDで再送され、重複する場合がある。

dm自体の停止、dmと通常監視が共有する障害、受信メールサービスの停止をすべて今回の構成だけで解消するものではない。watchdog自身については別の外部稼働監視を利用する方針とし、監視先サービス・通知経路は未定。既存業務への導入、本番SMTP接続試験、別ホスト試験はこの計画の後に実施する。
