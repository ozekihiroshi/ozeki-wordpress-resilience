# キューの復旧・再配送方針（専用環境 v1）

WordPressのDB・ファイルとキューを一組として復旧する。キューだけを新しい状態に戻したり、古いDBへ新しいキューを自動的に混ぜたりしない。対象は専用環境の単一ワーカーと、DB・決定的なファイル書込みだけを行う固定ジョブ。

## 取得と復旧

1. ワーカーを停止し、ブローカーの投入・ACK・配送を凍結する。受付拒否は成功ではない。投入元は同じIDで再試行できるよう要求を保持する必要がある。
2. 共通チェックポイントIDをキューとWordPress DBへ記録する。WordPressの更新受付を止め、進行中処理の完了を待ち、DBロックを保持する。
3. DBダンプ・サイトファイル・SQLite backup APIで取得したキューを一組にする。サイトID、チェックポイント、固定ハンドラーのSHA-256、全資産のSHA-256をマニフェストへ記録する。停止リースを失った取得は採用しない。
4. 復旧前に形式・サイト・ハンドラー・全資産ハッシュ・キュー内のチェックポイントと対応ジョブを検証する。復旧先ではワーカーを停止したまま三資産を復元する。復元DBのチェックポイントとファイルを確認し、同じチェックポイントで解除してからワーカーを起動する。

凍結状態はキューDBに永続化する。ブローカーを再起動しても自動で配送を再開しない。異なる解除トークンは拒否する。途中失敗時は停止を維持し、確認後に再開する。

この試験は破棄専用の隔離コンテナへ上書き復元している。本番導入では空の復旧先を使い、汚染ファイルが上書き復元後に残ることを避ける必要がある。

## ジョブ状態と再配送

| 状態 | 復旧後の扱い |
| --- | --- |
| pending（未処理） | 同じID・同じ内容で配送する |
| 実行済み、ACK未到達 | 復元DB内のジョブ台帳で重複を判定し、二度目の投稿を作らずACKする |
| done | 完了記録を保持し、自動再投入しない |
| quarantined | 自動再試行せず、原因と部分更新を調べる |
| 未対応形式・ジョブ | 復旧セットの検証で拒否する |
| 同一IDで別内容 | 投入時に拒否する。既存DB台帳との衝突も実行失敗として隔離する |

配送は at-least-once を前提とする。ACKまでの通信断では同じジョブが再配送され得る。固定ジョブはDB台帳と投稿を同じトランザクションで扱い、ファイル名と内容をIDから決定する。全てのアプリケーションで「必ず一度だけ実行」を保証する方式ではない。実行失敗は隔離し、安全な後続ジョブは進める。

メール・決済・Webhookなど取り消せない外部作用は未対応。外部サービス側の冪等性キー、結果照会、手動照合の方針が決まるまで自動再配送の対象に含めない。

## 復旧時点と記録の保持

復旧対象はチェックポイント時点まで。取得後に受け付けたジョブはこのスナップショットから回復できない。投入元の永続記録との照合や、別途設計する配送ジャーナルが必要であり、RPOゼロとはしない。古いDBと新しいキューを混ぜて補うこともしない。

この実装はdone・quarantinedの記録を削除しない。将来の削除条件は、保持中の最古の復旧セットと最大再配送期間の双方を越え、他の復旧セットがそのIDの重複防止記録を必要としないこと。35日保持だけを理由に台帳を即日削除しない。容量制御とジャーナル保管は本番適用前の課題。

## 検証範囲と信頼

`--external` の専用WordPress/MariaDB試験に、凍結・ACK喪失・三資産復旧・再配送・世代違い・破損・隔離を追加した。実行コマンドは[外部更新経路の手順](wordpress-external-writers.md#再実行)と同じ。新しい出力ファイルを指定する。

制御APIは外部通信のない試験ネットワーク用で、認証は未実装。Redis/SQS/RabbitMQ等のアダプター、多重ワーカー、汎用ジョブ、管理者による迂回を検証したものではない。スキーマ移行機構もなく、新規専用環境で実行する。

マニフェストのハッシュは資産の組合せと破損の検証であり、独立署名ではない。本番のS3固定Version ID・保持証拠・独立署名への組込みは未実施。保存元が侵害された際の健全性や本番復旧承認を、この試験結果だけで認定しない。
