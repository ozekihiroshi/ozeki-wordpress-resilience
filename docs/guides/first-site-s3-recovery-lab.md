# 2資産の取得から実S3・署名・隔離復元まで

この手順は開発用の専用環境と生成データだけを対象とする。一般サイト向けの導入完了や、感染していないことを保証する試験ではない。既存の3資産・72時間観測、Backup for S3、共通部品は変更しない。

## 接続した契約

`owr-first-site-capture-v1` の `consistent`、停止解除確認、設定ハッシュ、取得試行ID、DB/filesの容量・SHA-256、`queue.state=absent` と根拠を検査する。未完了・解除不明・混在・欠落はPUT前に拒否する。取得結果の原本は変更せず、別の `owr-protected-first-site-set-v1` に取り込む。

既存実験用S3アダプターを使い、保存元my-ssm-roleと復旧用OwrM1RecoveryReaderで役割を分ける。権限の範囲を変えず、実験用 `sites/isolated-queue-lab/sets/AWS-<一意ID>/` 内に新しいセットを作る。これは保管用名前空間であり、実際の取得元 `generated-first-site` は署名文書内で別に記録する。キューの空ファイルを捏造しない。

保存はDB・files・署名文書・署名の4オブジェクト。それぞれ固定Version IDで読み戻し、サイズ・SHA-256・GOVERNANCE保持35日以上を確認する。署名は最長7日で失効し、保持期限を超えない。保持を確認したことと、管理者にも削除できないことは別である。今回Object Lockの削除耐性試験を繰り返したとは扱わない。

## 試験署名と復元前検証

専用operatorディレクトリを保存処理の外に作り、別Pythonプロセスで使い捨て試験鍵を生成・署名する。秘密鍵は処理後破棄し、公開鍵ハッシュ・承認文書ハッシュ・署名文書と署名の固定版ロケーターを保持する。本番鍵・USB・既存観測の信頼情報は使わない。

同じWSLユーザーが双方を実行するため、ホストやOSアカウントの侵害に対する独立性を実証する構成ではない。本番では保存元から到達できない署名環境と信頼情報の保管を必要とする。ここでの署名は保管整合性の試験承認であり、マルウェア検査や本番再公開の承認ではない。

独立保管したpinから署名文書と署名を固定版取得し、公開鍵・署名・対象・期限・設定ハッシュを検証する。その後、両資産の固定版・保持・ハッシュ・取得試行の一致を確認する。どちらかが失敗すれば復元へ進まない。tar内の不正パス・リンク・特殊ファイル・重複・展開容量も拒否する。

新しいMariaDB/WordPressコンテナにDBとファイルを復元し、通常投稿、標準添付参照、メディア内容、HTTP 200と投稿表示を確認する。DBはnetwork none、WordPressはそのネットワーク名前空間を共有し、ポート公開なし。試験後は自分で作ったコンテナとボリュームだけを削除する。

## 実行と失敗時

前提はWSLのDocker、固定した試験イメージ、既存実験S3、community/dmへの専用SSH接続。IAMを自動変更しない。実データを指定する引数はない。

```sh
python3 tools/run-first-site-s3-lab.py --execute-lab \
  --output "$HOME/.local/share/owr-first-site-s3-lab/new-result.json"
```

出力先の親フォルダを先に0700で用意する。既存の出力名を再利用しない。今回のPCでは既存のプロセス限定ネットワーク補助を使ったが、プラグインの導入要件とは別の環境設定である。

`<出力名>-private/s3-receipts/operations.json` にPUT開始・応答Version ID、GET結果を記録する。通信結果不明・途中失敗では、自動再送や新規セットを作り直す操作をしない。台帳とS3固定版を照合してから続行方法を決める。この入口は自動再開CLIをまだ提供しない。途中の成功は `s3-result.json` のstagesに残り、全体passedは隔離復元成功後にのみtrueとなる。

取得原本、SQL、wp-config.php、署名pinなどprivateフォルダ全体をGitへ追加しない。使い捨てでもDB認証情報を含む。公開用集計だけを保存する。35日保持のS3試験オブジェクトはこの試験で削除しない。

## 残る課題

一般サイトへの接続、独立署名環境の配備、設定承認の運用、結果不明時の再開CLI、日次処理や管理画面への2資産契約の接続は未完了。WordPressプラグインを有効化するだけでこの処理が実行されるわけではない。既存配布ZIPや公開タグは変更していない。

## 実測結果（2026-10-20）

[公開集計](../../evidence-public/first-site-s3-recovery.json)に8実接続ケース、新規ゲート6テスト、既存取得14テスト、既存三資産ゲート11テストを記録。4オブジェクトを固定版保存し、署名不正時の取得拒否、実取得・隔離復元・HTTP表示、専用資源削除を確認した。初回は再利用した異常系試験でTimeoutExpiredとなり期待理由に達せず中断した。成功扱いにはせず、S3送信0・解除済みの原本を保管。往復専用の正常取得入口へ分け、停止期限を緩めず検証した。

### 初回タイムアウトの追跡結果

原因未確定としていた件を[別のローカル調査](first-site-timeout-investigation.md)で追跡した。停止確認の60秒待ちを再現し、未読出力とexec終了の待ち合わせ条件を3回再現。取得側を修正して元の異常系を再検証した。S3の追加保存はしていないため、上のS3集計は修正前のソースでの実測として残す。
