# 担当者確認の管理画面（読取り専用）

WordPress管理画面の「Resilience → 導入前検査」に「担当者確認（日次運用）」を追加しました。既存のmanage_options権限とGET限定の制限を再利用します。更新・失効・取得・署名を実行するボタンはありません。

表示内容は、期限内／期限切れ／失効済み／再確認が必要／未取得／不正、確認日時、有効期限、再確認理由です。期限は表示時にも判定するため、受信後に期限を迎えた記録を期限内として表示し続けません。時刻はタイムゾーン付きで表示します。

自動再検査の失敗は担当者確認の失効と区別します。確認が期限内でも、報告が5分以上古い、転送失敗・停止・世代不一致の場合は現在の有効性が未確認と明示します。表示は取得や復旧の許可ではありません。

## 接続

既存の外部 `preflight-relay.py` 設定に任意の `review_file` を追加します。値は担当者が管理する日次用確認ファイルへの絶対パスです。外部処理から読める権限で、WordPressや自動検査処理には更新権限を与えません。設定がない旧配置は「未取得」表示を維持します。

外部処理は既存の棚卸し・検査結果と確認記録から表示用 `operator_review` を生成し、既存の報告・転送状態ファイルの経路で渡します。担当者名、確認項目の根拠、秘密や署名鍵、元の確認ファイルをWordPressへ送りません。PHPは形式と理由コードを制限し、未定義値や任意のメッセージを表示しません。

読み込み不能・不正な確認は不正表示、見つからない確認は未取得表示にします。これにより棚卸し報告そのものを過去の成功のまま残すことを避けます。

担当者確認の更新・失効は[外部手順](recurring-capture-review.md)で行います。定期転送の設定変更・本番配置は今回自動実施していません。原本の変更は次の報告受信まで画面に反映されないため、画面の鮮度・転送状態を併せて確認してください。取得入口は表示用要約を信頼せず原本を再検査します。

## 専用検証

`python3 -B tools/run-operator-review-admin-lab.py --output /new/lab/directory`

既存の専用WordPress/MariaDB/Chromium環境を再利用し、生成した報告で期限内・期限切れ・失効・再確認・古い情報・未取得を検証します。管理者表示、editor拒否、POST405、操作フォームがないこと、報告ファイルのハッシュ不変を確認します。外部通知・AWS送信・72時間観測の台帳変更はありません。

試験基盤の初回失敗：既存UIフィクスチャがsrcの旧来の一部だけをコピーしており、PreflightWatchdogAdmin.php不足で有効化に失敗。コピー対象を現在のsrc全体へ修正しました。ブラウザ起動前に原因を特定した事象であり、以前の原因未確定ブラウザ問題の解決を意味しません。

検証結果：Python21件（集約5・報告7・転送9）、PHP11件、実ブラウザ6場面が成功。各場面で状態表示・非露出・読取り専用・POST405・editor拒否を確認し、全場面で報告ファイルのハッシュ不変を確認。期限内画面を目視確認済み。試験コンテナは終了時に削除。新たな環境障害は確認していません。製品の表示機能は実装済み、本番への設定反映は未実施です。

継続更新の検証は[定期報告と表示回復](operator-review-periodic.md)を参照してください。
