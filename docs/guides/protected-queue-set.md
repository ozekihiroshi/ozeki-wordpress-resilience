# 三資産の固定版・保持証拠・独立署名（専用環境）

DB・サイトファイル・キューを共通チェックポイントで取得し、固定Version IDと保持証拠を含む一つの文書に署名する。全資産の検証が済むまで、DB投入・ファイル展開・キュー配送へ進まない。

## 新しい復旧セット形式

`owr-protected-queue-set-v1` を追加した。既存の `owr-protected-candidate-v1` と実サイト用パイロットは変更していない。旧セットを三資産の整合取得済みセットとして読み替えない。

| 資産 | ファイル名 | 内容 |
| --- | --- | --- |
| database | database.sql | チェックポイントとジョブ台帳を含むDBダンプ |
| files | wordpress-files.tar.gz | 同じ停止区間で取得したサイトファイル |
| queue | queue.sqlite | 同じチェックポイントで凍結したキュー |

各資産について、バケット・リージョン・キー・Version ID・サイズ・SHA-256・保存側識別子・復旧側識別子・保持モード・最終変更日時・保持期限・照合日時を署名文書へ含める。共通チェックポイント、サイト、セットID、ハンドラーのハッシュ、署名の有効期間と連番も結び付ける。

`latest` やVersion IDなしへのフォールバックは行わない。保存成功のVersion IDが空または`null`なら中止する。保存後は復旧側の取得経路で同じ版を読み、サイズとハッシュを照合してから署名対象にする。

## 信頼情報と検証順序

手元の独立した信頼ディレクトリに、公開鍵、そのハッシュ、承認文書ハッシュ、サイト／セット、最低連番、失効状態、想定する保管先・識別子を置く。署名文書と署名ファイル自身の取得先も、独立側で固定Version IDとハッシュを保持する。ダウンロードしたデータから信頼ディレクトリを選ばない。

1. 独立側の取得情報から `recovery-set.json` と `recovery-set.sig` の固定版を取得し、保持証拠とハッシュを確認する。
2. 承認文書ハッシュ、公開鍵ハッシュ、RSA-SHA256署名、対象サイト・セット、連番、有効期間、承認範囲を確認する。
3. 三資産が過不足なく存在すること、保存側と復旧側の識別子が異なること、35日以上のGOVERNANCE保持と署名期限を満たすことを確認する。
4. 指定Version IDで三資産を再取得する。返却された版、サイズ、ハッシュ、保持モード・期限、復旧側識別子を再照合する。署名時より保持期限が短縮されていたら拒否する。
5. 三資産のハッシュとキュー内のチェックポイント、対応ハンドラーを共通取得記録と照合する。全件合格したバイト列だけを復元へ渡す。
6. 復元後のDBチェックポイント・ジョブ台帳・ファイルの照合を経てキューを再開する。

署名は `storage_integrity_candidate_only` の承認であり、マルウェア除去済みや本番復旧承認を意味しない。`production_recovery_approved` はfalse、`malware_cleanliness` はunverifiedのまま。

## 実装

- `tools/protected-queue-set.py`: 保存後の照合、署名対象の生成、固定版エンベロープ取得、復元前の検証ゲート。PUT/GETは注入する転送アダプターを使う。
- `tools/protected-queue-lab.py`: ローカル模擬ストアと試験専用RSA鍵で正常系・拒否系を実行する。
- `tools/wordpress-queue-recovery-lab.py`: 検証済み取得バイト列を実際の隔離WordPress/MariaDB・キュー復元へ渡す。署名検証の失敗を握り潰して復元する経路はない。

## 初期の模擬試験の範囲

S3部分はPythonのローカル版管理ストアを使う契約試験。実AWS API、Object Lockによる削除拒否、IAMの強制力、KMS、AWSから返る日時・ヘッダーの正規化は今回の実測対象ではない。保存側／復旧側の識別子は試験用で、実IAMの分離を証明しない。

RSA署名・検証はOpenSSLで実行する。鍵はWSLホスト側の一時ディレクトリへ生成し、復元コンテナへマウントしない。終了時に一時鍵と模擬ストアを破棄する。本番鍵、USB、既存S3バケットは使用しない。ホスト管理者から署名鍵を保護することまで実証したものではない。

専用WordPress/MariaDBの三資産は実データを取得・復元する。実行は既存の[外部更新経路の手順](wordpress-external-writers.md#再実行)の `--external` を使い、新しい出力ファイルを指定する。取得後に投入されたジョブの扱い、外部作用の制限は[キュー復旧方針](queue-recovery.md)を引き継ぐ。

## 実AWS接続時の要件

既存の実サイト専用転送処理を流用して本番へ送信することはしない。専用S3アダプターで実際のVersion ID・Object Lock応答・実行ロールを確認し、この契約形式へ正規化する必要がある。試験専用バケットと権限で、署名文書・署名自身の保持も含めた往復試験を行う。本番への接続は、その実測と独立保管・鍵運用の確認後に扱う。

## 実測結果

[実測記録](../../evidence-public/protected-queue-set.json): 専用環境51ケース（今回追加14ケース）とPython契約103件に合格。署名検証済みの固定版からDB・ファイル・キューを復元し、未処理分の配送とACK喪失時の重複防止まで確認した。試験コンテナ・匿名ボリューム・一時署名鍵は削除済み。

## 実S3アダプターの追加

実験バケット・ロールを固定した専用アダプターと`--s3-lab`を追加した。[設定と実行手順](real-queue-s3-lab.md)。上記51ケースの記録は模擬S3の結果のままとし、実AWSでの結果と混同しない。

後続の[実S3往復試験](real-queue-s3-lab.md)で、専用アダプター接続と分離ロールによる取得・署名検証・隔離復元まで実測済み。上記の模擬試験記録はそのまま保存する。本番運用への接続は別途扱う。
