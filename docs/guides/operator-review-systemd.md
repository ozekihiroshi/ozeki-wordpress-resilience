# 担当者確認のSSH転送とsystemd運用（試作版）

既存の `preflight-relay.py` が担当者確認の要約を報告に載せ、`preflight-transfer.py` が固定ホスト鍵・専用鍵・forced commandを用いたSSHで取得します。WordPressは取得済みの報告を読取り専用で表示します。新しい転送プロトコルや自動承認は追加しません。

## 配置

生成したpublisher設定に `review_file` の絶対パスを追加します。確認ファイルは担当者が明示的に発行し、報告サービスから書き換えられないディレクトリへ配置します。サービスには読取り権限のみを与え、秘密鍵・確認の原文・確認者名・証拠参照はWordPressへ転送しません。

既存のpreflight publisher/receiverサービスを利用します。systemdのUser、NoNewPrivileges、ProtectSystem、ProtectHome、PrivateTmpとReadWritePathsを維持し、確認ファイルを書込み許可範囲に含めません。サービスのenableは自動起動、start/stopは現在の実行状態を制御します。停止は確認の失効や期限延長を意味しません。

## 停止と再開

報告の更新が止まり鮮度上限を超えると、画面は「現在の有効性は未確認」を表示します。過去に有効だった確認を現在の安全性の保証として扱いません。再開後はSSH取得・再検査・報告転送が正常に終わったことを確認します。期限切れ・失効の場合はサービス再起動で解除せず、担当者が必要な再確認を実施します。

## 専用試験

`python3 -B tools/run-operator-review-systemd-lab.py --output <新しい非公開出力フォルダ>` は既存の生成設定・3VM systemd試験を再利用します。生成側、取得側、独立watchdogを専用Ubuntuゲストへ配置し、実SSH転送、310秒以上の停止、再開、3ゲストのOS再起動、WordPress管理画面を検証します。確認ファイルのバイト列が維持され、サービスに書込み権限がないことも確認します。

生成された棚卸し宣言は試験担当処理が起動・再開・再起動前に更新します。これは限定した試験構成の再観測であり、確認期限の自動更新ではありません。長期無人運転の棚卸し更新方式をこの試験だけで合格とはしません。

VMは同一WSL物理ホストを共有し、WordPressブラウザ試験への最終受渡しには9p共有を使用します。別物理ホストの故障独立性、本番適用、S3取得・保存・復元、72時間観測の合否は試験範囲外です。

結果は `evidence-public/operator-review-systemd.json` を参照してください。環境障害、試験基盤の不備、製品の不具合を区別して記録します。以前のブラウザ起動問題は原因未確定のまま扱います。

初回試行は実SSH棚卸し・転送・DB/ファイル不変の検査まで成功しましたが、試験コードがrootで確認発行時の作業領域検査を行い、領域所有者との不一致で拒否されました。実際のpublisherは所有ユーザーで成功しており、試験の発行呼出しを同じ所有ユーザーへ修正しました。初回のfailure.jsonは非公開試験出力に保持し、製品障害や環境障害に混同しません。

検証結果：実SSHで有効な要約を転送し、systemdの60秒周期更新・重複起動拒否・権限制限を確認。316秒の実停止後に現在の有効性未確認を表示し、再開後に回復しました。3台のゲストOSはBoot IDが変わり、自動起動後に報告・管理画面が回復。通常・停止・再開・再起動の4場面で担当者確認原本不変、POST405、editor拒否、読取り専用を確認しました。観測ホストのBoot IDは不変です。
