# SSH・外部キュー・管理された子プロセスの停止制御

対象は使い捨ての専用WordPress / MariaDB環境。実サイト、community、dm、AWS、通常のSSH設定は変更しない。

## 制御方式

WordPress側のPHP受付停止とMariaDB読取りロックに加え、外部更新を専用実行サービスへ集約する。実行サービスは既存の共有ロックを取得し、停止マーカーを再確認してから、固定されたジョブだけを実行する。子プロセスの終了までロックを保持する。新規受付が止まった後、コーディネーターが排他ロックを取得できることを処理完了の条件とする。

### SSH

専用のOpenSSHサーバーをループバック上に起動する。試験用のホスト鍵・認証鍵を毎回生成し、固定したホスト公開鍵で接続を検証する。既存の秘密鍵やSSHエージェントは利用しない。

`owr-operator` はroot権限・Docker操作権限を持たず、サイトディレクトリとwp-config.phpへ直接アクセスできない。SSHの `ForceCommand` で専用クライアントに固定し、`write ID`、`deploy ID`、`slow ID` だけを受け付ける。利用者の文字列をシェルに展開せず、パスやSQLも受け取らない。

シェル、任意の `php -r`、scp、SFTP、TTY、ポート転送を許可しない。`deploy` は制御経路を検証する固定のファイル更新ジョブであり、Git・rsync・任意デプロイスクリプトの対応完了を意味しない。

### 外部キュー

WordPressとは別コンテナに、HTTPとSQLiteを使う試験用の永続キュー、および単一ワーカーを起動する。キュー・ワーカーはDBの隔離ネットワーク名前空間を共有するが、外部通信もホストへのポート公開もない。ワーカーには実サイトのファイルボリュームやDB認証情報を渡さず、固定ジョブの実行サービスへ接続するUnixソケットだけを共有する。

ワーカーは先頭ジョブを読み取り、実行サービスが `done` を返した後にだけACKして削除する。停止中の `fenced`、実行失敗、通信失敗ではACKしない。キューサーバーの再起動にも未処理ジョブを保持する。処理成功後にACKだけ失われた場合を想定し、DBの一意ジョブIDで再配送を重複実行しない。同じIDを違う処理に使う場合は拒否する。

これはRedis、SQS、RabbitMQ等の製品別アダプターではない。単一ワーカー向けの試験契約であり、複数ワーカーの予約期限、順序、デッドレター、監視、本番用認証は未実装。

停止対象はWordPressへのジョブ適用であり、停止中もキューへの新規投入は可能。キューのDB自体は今回のWordPress復旧セットに含めない。本番では未適用ジョブの別保管・再配送と、復旧した世代に対する再実行方針を定義する必要がある。

### 子プロセス

固定ジョブは実際に別のPHPプロセスを起動してファイルを書き、親が終了を待ってからWordPressの投稿・ジョブ記録をコミットする。外側の実行サービスがロックを保持するため、子の `php -r` 自体にPHP受付フックが効かなくても、取得開始はその処理完了を待つ。

実行サービスは時間上限を持ち、超過時はジョブのプロセスグループを終了して回収する。今回実証するのは既知の子を待つ固定ジョブであり、任意の二重fork・別セッション化・デーモン起動まで回収できる保証ではない。任意の外部コマンドを許可リストへ追加する前に、プロセスの生存範囲と失敗時の部分更新を別途評価する。

## 取得判定

期待更新元は、先行の `php-http`、`php-cli-file`、`database-direct` に、`ssh-forced-command`、`external-queue`、`managed-child` を追加する。

全受付の停止・進行中ジョブと子の完了を確認してから、サイト全ファイルとDBを取得する。受付世代、取得前後とtar内のハッシュ、テーブルエンジンと構成、所有トークン、キューの保留状態を確認する。別DBへダンプを復元し、メディア参照と外部ジョブのファイルハッシュを照合して既存判定器へ渡す。

`consistent` は `isolated-mediated-writers-v1` という専用構成内だけの結果。ワーカー稼働の確認が欠ける観測、未登録の特権更新元、取得中のリース喪失は `unverified` とする。ワーカー停止を実際に確認できても、登録済み制御の確認が欠けた状態を自動で成功に繰り上げない。

## 保証しない範囲

- root、Docker管理者、サーバー外からのボリューム操作など、制御自体を変更できる権限。
- 任意のSSHシェル、SFTP、既存デプロイ、登録されていないワーカー・子プロセス・外部ストレージ。
- ジョブ失敗による任意アプリケーションの部分更新を、自動的に修復すること。
- 強制終了後の停止マーカーについての独立監視・安全な所有者失効判断。

本番に適用する際は実際のアカウント、権限、ジョブ、ストレージを棚卸しし、迂回経路を制約する必要がある。管理者の悪意や保存元侵害を、この停止機構だけで防げるとは扱わない。保存先の保持・権限分離・独立署名は引き続き別の防御となる。

## 再実行

WSLで先行の固定イメージから試験用イメージを作る。パッケージ取得のネットワーク利用は構築時のみ。

```bash
cd /mnt/d/workspace/ozeki-wordpress-resilience
BASE_IMAGE=$(sed -n 's/^OWR_WP_IMAGE=//p' lab/m1/images.env)
docker build --pull=false --build-arg BASE_IMAGE="$BASE_IMAGE" \
  -t owr-external-lab:local -f lab/consistency/ExternalLab.Dockerfile lab/consistency
python3 tools/run-wordpress-consistency-lab.py --execute-lab --external \
  --lab-image owr-external-lab:local --output .local/external-new.json
```

引数なしでは環境を作らない。指定したローカルイメージのIDを記録し、先行19ケースも含めて検証する。試験コンテナと匿名ボリューム、試験用SSH鍵は終了時に削除する。再利用用のローカルイメージは残る。既存コンテナを停止したり、Docker全体をpruneしたりしない。
