# 日次バックアップ・隔離復元の管理画面（試作）

WordPress管理画面の **Resilience → 日次バックアップ・復元** を開きます。
管理者権限（`manage_options`）が必要です。保存・承認・復元・後片付けを実行するボタンはありません。

## 表示する情報

- 最新30日次記録：総合状態、保存完了、署名承認、復元結果。
- 最新30復元要求：要求ID、日付、処理状態、結果、結果登録、後片付け。
- 後片付け：記録なし、未完了、確認済み、復元処理で資源削除済み、記録不整合。
- 報告の観測時刻、予定枠の保存未確認、未取得・形式不正・5分以上の更新停止。

途中停止を後片付けしても元の「結果不明」は残ります。
後続要求が成功しても旧要求の履歴は表示されます（最新30件の範囲）。
「後片付け確認済み」は成功や本番再公開の許可ではありません。
通常復元の資源削除表示は、台帳に固定された結果ファイルのハッシュも照合します。
報告が古い場合は前回記録として表示し、現在の正常性を判断しません。

## 専用環境での接続

1. 外部処理側で、既存の二資産用日次台帳から必要な項目だけを書き出します。
   出力先は台帳とは別で、Web公開ディレクトリの外に用意します。

   ```sh
   python3 tools/daily-admin-status.py \
     --state /path/to/dedicated-daily-state \
     --site-id generated-first-site \
     --output /path/to/status/daily.json
   ```

2. WordPressが読める専用ファイルとして配置します。WordPressにはファイルの読取り権限だけを与えます。
   Dockerでは状態フォルダを `/status:ro` としてマウントしてください。
   台帳・署名鍵・バックアップ本体をWordPressへ渡す必要はありません。
3. `wp-config.php` に配置先と対象IDを指定します。

   ```php
   define('OWR_DAILY_STATUS_FILE', '/status/daily.json');
   define('OWR_DAILY_SITE_ID', 'generated-first-site');
   ```

4. プラグインを有効化し、上記の管理メニューを開きます。
   状態ファイルは外部側で更新します。ページを開いてもエクスポートや復元処理は起動しません。
   定期生成・別ホストからの取得は[定期更新・SSH受渡し](daily-status-periodic.md)で専用環境向けに実装しています。実際の導入先には未配置です。

エクスポートは既存台帳を読取り専用で開きます。入力の存在しない台帳は新規作成しません。
出力は許可項目だけです。信頼情報のパス、署名鍵、認証情報、DB内容、詳細例外は含めません。
PHP側も形式・対象ID・時刻・件数・サイズ・値を検査し、未知項目を表示しません。
JSONは最大64KiBで、シンボリックリンクは読みません。

## 検証と制限

専用のWordPress/MariaDBを外部通信・公開ポートなしで起動し、
生成データの日次台帳を別の試験領域へ複製して試験します。
管理者表示、編集者403、未ログインのログイン要求、POST拒否、
未取得・古い報告・対象違い・未来時刻・過大入力・文字列注入を確認します。
表示前後で元の試験用台帳・証拠ファイルのハッシュが変わらないことも確認します。

初回試験で、描画時にPOSTを拒否するとヘッダー送信済みでHTTP 200になる実装上の問題を発見しました。
画面読込みフックで拒否するよう修正しています。これは環境障害ではありません。

この画面はローカル状態の表示で、侵害されたWordPressや外部ホストへの独立した証明ではありません。
本番配置と実行操作UIは別の作業です。定期更新・SSH受渡しは専用環境で検証済みです。通常幅・390px幅の実ブラウザ表示は[ブラウザ検証](daily-admin-browser.md)で確認しました。
既存の72時間観測、Backup for S3、共通部品を変更しません。
