# 状態報告・定期転送を含むZIPの導入と更新

この配布物は `0.1.0-dev.1` の試作版です。同じ版番号の候補があるため、ZIP名だけでなく同梱 `manifest.json` のSHA-256で識別します。公開版への自動更新は今回の対象ではありません。

## 配布物と役割

- `ozeki-wordpress-resilience-0.1.0-dev.1.zip`：WordPressへ導入する管理画面。日次バックアップ・隔離復元、生成側・取得側watchdog、転送状態を表示します。
- `owr-development-kit-0.1.0-dev.1.zip`：外部取得・監視・転送コード、systemdの設定例、仕様、試験。WordPressへアップロードするZIPではありません。

WordPress用ZIPには外部サービス、AWS SDK依存一式、秘密鍵、既存台帳を含めません。外部ホストの準備は[systemd導入ガイド](observer-status-systemd.md)と[定期転送](observer-status-relay.md)を参照してください。

## 新規導入

1. 専用WordPressの「プラグイン → 新規プラグインを追加 → プラグインのアップロード」でWordPress用ZIPを選び、有効化します。
2. 外部サービスは開発キットを専用コードディレクトリへ展開して配置します。依存環境・実行ユーザー・SSHホスト鍵固定・権限は上記ガイドで設定します。
3. `wp-config.php` の日次報告・watchdog報告・転送状態ファイルのパスとサイトID、monitor IDを対応させます。WordPressには報告ファイルの読取りだけを許可します。
4. 「Resilience」の日次状態と「生成・取得の独立監視」で更新時刻、警報・回復履歴、転送状態を確認します。未設定の状態は正常扱いになりません。

## 既存候補からの更新

1. ZIPのハッシュを確認し、WordPress DB、wp-config.php、外部設定・台帳・未配送記録を別に保全します。署名秘密鍵をプラグインフォルダへ置かないでください。
2. WordPressのZIPアップロード画面で既存プラグインの置換を選びます。同じ開発版番号でも内容は異なるためハッシュで判断します。削除・再インストールを更新手順にしません。
3. 外部コード更新は担当サービスを停止し、別のコードディレクトリにキットを展開して切り替えます。`/etc/owr`、状態・鍵・報告・配送台帳を新しい空ディレクトリで置換しないでください。
4. systemdの設定例を既存設定と比較し、パス・実行ユーザー・読書き範囲を維持して反映し、daemon-reloadと再起動を行います。WordPressの更新だけで外部サービスは更新されません。
5. 設定版、通知先、日次結果、警報・回復履歴、未配送件数を更新前と比較し、新しい報告の取得後に停止表示が回復することを確認します。

## 検証の区分

`tools/run-status-zip-lab.py` はネットワーク隔離した専用WordPress/MariaDB/Chromiumで、実際のPlugin_Upgraderによる新規導入・既存ZIP置換・無効化と再有効化を検証します。管理画面の読取り専用性、編集者の拒否、設定・Cron・wp-config・要求ファイル・生成済み外部台帳を比較します。ブラウザのZIPアップロード操作そのものや、本番外部サービスのコード切替を自動検証するものではありません。

試験は生成した警報・回復履歴を使用します。OS再起動とsystemdの実時間停止・再開は別の[VM検証](observer-status-systemd.md)で扱います。72時間観測、実S3保存、実端末通知の合格とは別です。

初回比較の失敗はWordPressが編集者ダッシュボード初訪問で追加する `wp_scheduled_auto_draft_delete` だけでした。標準の下書き初期化を比較前に済ませ、Cron比較を除外せず再検証します。プラグインの設定消失ではありません。

旧候補の置換直後には、WordPressの `WP_Upgrader::init()` が `wp_delete_temp_updater_backups` を追加する差分も確認しました。プラグイン設定は変化なし。標準更新処理の初期化も比較前に完了させ、Cronを含む完全一致で確認します。失敗試行の記録は残します。
