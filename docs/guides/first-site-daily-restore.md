# 承認済み日次セットの隔離復元（専用環境）

`first-site-daily-restore.py` は、独立保管した署名文書と信頼情報を検証し、二資産をS3の固定Version IDから取得して、新しいWordPress／MariaDBへ復元する開発用入口です。生成試験データだけを対象にします。

保存元サーバー、取得時の作業フォルダ、日次台帳、保存側のDB認証情報は復元の入力にしません。S3への追加保存、再署名、本番の上書きも行いません。

## 入力を用意する

日次セットを承認した担当者が、別管理する次の情報を指定します。

- 信頼情報ディレクトリ：`pin.json`、`public.pem`、`approved.json`、`approved.sig`
- 対象セットID
- 承認した文書、公開鍵、取得設定の各SHA-256
- 未使用の復元結果ディレクトリ

今回の署名文書は独立したローカル保管先から読みます。S3から取得するのはDBとファイルです。この日次セットの署名文書・署名自体はS3へ送信していません。最新版の一覧検索や、保存側から通知された未知の公開鍵による自動承認は行いません。

## 実行する

WSLのリポジトリルートで、各プレースホルダーを独立保管した実値に置き換えて実行します。秘密鍵は不要です。

```bash
python3 tools/first-site-daily-restore.py --execute-lab \
  --trust "/独立保管先/対象セット" \
  --output "/新しい復元作業先/試行ID" \
  --set-id "AWS-対象識別子" \
  --config-sha256 "承認した取得設定のSHA256" \
  --document-sha256 "承認した文書のSHA256" \
  --key-sha256 "独立保管した公開鍵のSHA256"
```

1. 信頼情報を試行用に固定し、文書と公開鍵のハッシュ、署名、対象、期限、取得設定を検証します。不正ならS3へアクセスしません。
2. 読取り専用ロールでDBとファイルの明示的Version IDを取得し、ハッシュ、サイズ、保持期間、取得時の組合せを再検証します。
3. アーカイブの安全なパス・メンバー形式・展開量と、署名されたファイル一覧ハッシュを確認します。二資産が揃うまで復元処理へ渡しません。
4. 新しいランダムDB認証情報と専用Dockerコンテナを作ります。DBは `network=none`、WordPressはその通信空間だけを共有し、ホストのポート公開・保存元マウント・AWS認証情報の渡し込みは行いません。
5. 投稿、標準添付参照、画像ハッシュ、HTTP 200と投稿表示、WP-Cron停止と外部HTTP遮断を確認します。
6. この試行のコンテナ・匿名ボリュームを除去して確認し、結果と取得物・読取り受領・信頼情報のコピーを残します。

`result.json` の `passed=true` は、上記の生成データ復元と後片付けが確認できた場合だけです。途中失敗時はfalseを維持し、エラー種別を記録します。`isolation.json` には試行専用の資源名と確認結果が残ります。同じ出力先への再実行は拒否します。未完了処理や資源がないかを調査してから、必要な場合だけ別の試行先を指定してください。

## 評価の範囲

本試験は、承認済み二資産の日次セットからの復元です。保存時の承認記録を上書きせず、復元結果を別の証拠として保持します。[日次状態への明示登録](first-site-daily-status.md)で復元観測を追記できます。[自動登録ワーカー](first-site-auto-recovery.md)を使うと、復元終了後の登録と登録のみの再試行を行えます。

生成データのDocker隔離試験であり、実マルウェアを安全に実行できることや、感染していないことの証明ではありません。本番再公開は承認しません。実サイト用アダプター、別ホストでの信頼情報運用、署名更新・失効、管理画面統合は別途必要です。
