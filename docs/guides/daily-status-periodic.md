# 日次状態報告の定期更新とSSH受渡し（試作）

外部側の **生成プロセス** と、WordPressホスト側の **取得プロセス** を別々に動かします。
どちらもバックアップ・署名・復元・後片付けは実行しません。
WordPressは読取り専用ファイル2個だけを参照します。

1. 生成側が毎分、既存の二資産用台帳から許可項目だけを `daily.json` に書き出す。
2. WordPress側の専用ユーザーが毎分、固定コマンドのSSH接続で取得する。
3. サイトID・要求ごとのnonce・形式・時刻・サイズ・前回報告との順序を検査し、原子的に差し替える。
4. 受渡しの結果を `transfer.json` に保存する。転送失敗時は前回の報告本体と観測時刻を変えない。

## 管理画面の表示

|表示|意味|
|---|---|
|取得成功|今回の受渡しを確認。バックアップや復元を新たに成功させた意味ではない|
|転送失敗・応答不正|SSH失敗、応答の不正、古い版への巻戻しなど。前回報告を保持|
|生成側の更新失敗|台帳の読取りなどで生成処理が失敗|
|生成側が5分以上未更新|SSH応答はあるが報告本体の観測時刻が古い|
|受渡し処理が5分以上未更新|WordPress側の取得プロセス停止など。現在の状態は不明|
|照合不能|受渡し記録のハッシュと報告本体などが一致しない|

2ファイルの差替えはそれぞれ原子的です。同時に切り替わる保証はなく、
途中停止や切替瞬間の不一致を「成功」と表示しないようハッシュで照合します。
更新停止の判定には両ホストの時計が正しいことが必要です。
WordPress自体が停止した場合の外部警報は既存の独立watchdogの役割です。

## 配置と権限

`examples/daily-status-transfer/` に設定例とsystemdサービス例を置いています。
パス・サイトID・ホスト名は導入先に合わせて変更してください。
`/opt/owr/tools/` にはこのリポジトリのtoolsを配置し、schemasも同じアプリケーションルートへ配置します。
コードと設定ファイルは管理者所有とし、Webユーザーが変更できないようにします。

- 生成用ユーザー：元の台帳・証拠は読取り。公開用報告ディレクトリだけ書込み。
- SSH受信用ユーザー：公開用報告だけ読取り。元の台帳・秘密鍵は読めず、報告は書けない。
- WordPress側の取得用ユーザー：専用SSH鍵を所有し、状態表示ディレクトリだけ書込み。
- WordPress用ユーザー：状態表示ディレクトリは読取りのみ。SSH鍵・取得設定は読めない。

報告ディレクトリは所有者書込み・共有グループ読取り（例：2750）、
報告ファイルは0640、SSH秘密鍵と取得設定は取得用ユーザーの0600とします。
秘密鍵と台帳をWeb公開ディレクトリに置かないでください。
`publish.json` の出力先は元の台帳ディレクトリと分けます。

SSH受信用ユーザーの `authorized_keys` は専用の公開鍵に限定し、次の強制コマンドを指定します。

```text
restrict,command="/usr/bin/python3 /opt/owr/tools/daily-status-transfer.py --config /etc/owr/daily-status-read.json serve" ssh-ed25519 PUBLIC_KEY
```

SSHサーバー側でもパスワード認証・TTY・ポート転送・エージェント転送を無効にします。
受信用ユーザーに通常のSSH鍵やパスワードでログインできる経路を追加しないでください。
強制コマンドは `daily-status-read` 以外を拒否します。リクエストでパスや実行コマンドは指定できません。

ホスト鍵は管理者が独立した方法で確認して登録します。取得時の自動承認はしません。
known_hostsの名前は `owr-daily-サイトID` です（例：`owr-daily-generated-first-site`）。
既存の通知転送用鍵・設定とは分けてください。

## 起動確認・定期運転・停止

設定とディレクトリを準備した後、それぞれの専用ユーザーで単発確認します。

```sh
python3 /opt/owr/tools/daily-status-transfer.py --config /etc/owr/daily-status-publish.json publish
python3 /opt/owr/tools/daily-status-transfer.py --config /etc/owr/daily-status-relay.json relay
```

終了コード0は今回の成功、2は生成・受渡しで確認した失敗です。
設定不正や重複起動などは非0で終了します。エラーの詳細や認証情報をWeb側には転送しません。
設定不正で記録更新自体ができない場合も、前回記録が5分を過ぎると停止表示になります。

WordPressの `wp-config.php` に次を追加します。

```php
define('OWR_DAILY_SITE_ID', 'generated-first-site');
define('OWR_DAILY_STATUS_FILE', '/var/lib/owr-status-web/daily.json');
define('OWR_DAILY_TRANSFER_FILE', '/var/lib/owr-status-web/transfer.json');
```

管理画面の **Resilience → 日次バックアップ・復元** で受渡し状態を確認します。
その後、生成ホストにはpublisher、WordPressホストにはrelayのサービス例を配置し、
設定内のUser/Groupとパスを合わせてから `systemctl daemon-reload`、
`systemctl enable --now サービス名` を実行します。
サービスは `--interval 60` のループを実行します。OSロックにより二重起動を拒否します。
WP-Cronやサイトへのアクセスには依存しません。

停止は `systemctl disable --now サービス名` です。台帳・報告・鍵は削除しません。
再開は `systemctl enable --now サービス名` です。失敗状態は次の成功した受渡しで解消します。
サービス停止中も前回報告は残り、5分後に現在の状態が不明であることを表示します。

## 検証範囲

独立した2コンテナの内部ネットワークで、実SSH・専用生成データを使って検証しています。
1秒の試験周期で3回の実更新、重複拒否、ホスト鍵不一致、前回報告保持、
生成失敗、修復後の再取得、任意コマンド拒否、ユーザー別の読取り・書込み制限を確認します。
本番ホストや既存72時間観測のサービスには配置していません。
追加の専用試験では、WSLのsystemdユーザーサービスから2秒周期のCLIを動かし、
実際に生成・取得を両方停止して5分以上測定しました。
時刻を書き換えず、停止中の報告本体・受渡し記録・生成側報告が変化しないことも確認しています。
Chromiumの管理画面で、正常→受渡し停止→取得側だけ再開（生成側未更新）→両方再開（正常）を確認しました。
以前の復元検証・後片付け結果も表示に残っています。

再現手順は新規出力先を指定して `python3 tools/run-daily-systemd-lab.py --output /home/USER/専用の新規試験記録先` です。
既存の生成データ試験 `owr-recovery-cleanup-20261020-v2` と、事前取得済みDockerイメージを必要とします。
試験は専用コンテナ・内部ネットワーク・一時ユーザーサービスを作り、終了時に削除します。
記録先には検証結果・systemdログ・画面画像を残します。既存出力先は再利用しません。

この試験のsystemdユニットはコンテナ用の停止処理を持つ試験専用構成です。
`examples/` の本番向けUser/Group・ProtectSystem等のハードニング設定をそのまま検証したものではありません。
同一PC上の試験であり、別物理ホスト・OS再起動・本番への常駐配置は未検証です。
詳細は `evidence-public/daily-systemd.json` に記録しています。

別のWordPress環境で、実SSH取得報告を用いた表示も検証します。
5分の期限超過・失敗表示の組合せは時刻と状態の注入による試験であり、
5分間の実停止を測定した証拠ではありません。上記の追加systemd試験では実時間による停止も別途確認しました。
ローカルファイル・SSHの信頼に基づく表示であり、独立署名付きの復旧承認とは異なります。


本番向けsystemd例の権限制限とOS再起動後の自動起動は、後続の独立VM試験で確認しました。設定を補強した結果と導入時の所有者・権限は[本番向けsystemd手順](daily-status-systemd-production.md)を参照してください。既存72時間観測のホストは再起動していません。
