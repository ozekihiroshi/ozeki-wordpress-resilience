# 途中停止した隔離復元の確認と後片付け

生成データ専用のローカルCLIです。日次保存・署名承認は変更しません。
ワーカーと同じWSLユーザー、同じDockerホスト、同じ状態ディレクトリで操作します。

1. `retry-registration --request-id OLD_ID` で確定結果の有無を確認します。
   完了済み結果が登録待ちなら、まず登録を再試行します。取得・復元は再実行しません。
2. `inspect-interrupted --request-id OLD_ID` で対象コンテナ、匿名ボリューム、
   結果ファイルのハッシュと `plan_sha256` を確認します。この操作は資源を削除しません。
3. 確認したハッシュを `cleanup-reviewed --request-id OLD_ID --plan-sha256 HASH`
   に渡します。確認後に状態が変わっていれば拒否します。
4. `reviewed_closed` と `resources_removed: true` を確認し、新しいIDで `run` します。

各コマンドの先頭は次の共通形式です。

```sh
python3 tools/first-site-daily-recovery-worker.py --state /path/to/dedicated-state COMMAND
```

新規要求には `run --request-id NEW_ID --day YYYY-MM-DD --trust /path/to/independent-trust`
を指定します。閉じた旧IDを再利用しても復元しません。

## 削除の条件と保存する記録

要求ごとのランダムな所有トークン、名前、Dockerの不変IDを照合します。
外部へのネットワーク、公開ポート、bind mount、特権、名前付きボリューム、
他コンテナと共有するボリュームがあれば拒否します。
同じワーカーの実行中はロックで拒否します。
WordPress側を先に、DB側を後に削除し、匿名ボリュームの消失も確認します。
Dockerの検査失敗を「資源なし」とは扱いません。

`result.json`、署名・取得記録、復元対象ファイル、失敗・不明の結果は残します。
`cleanup-progress.json` と `cleanup-review.json` に後片付けを記録し、
日次状態は `recovery_reviewed_closed` になります。復元成功を意味しません。
削除途中の失敗は閉鎖しません。再検査して新しいハッシュで明示的に再開します。
孤立したボリュームが残る場合は自動削除せず、手動調査が必要です。

## 適用範囲・検証

所有トークン導入前の旧要求は自動削除対象にしません。
復元資源が作られる前に止まり所有記録がない要求も自動解放しません。
同じOSユーザーによる記録・Dockerの改ざんへの独立証明ではありません。
管理画面、別ホストからの指示、一般の本番環境への適用は未実装です。

専用環境で実Dockerコンテナ2個と匿名ボリュームを残してプロセス終了を注入し、
確認・削除・記録保持・新規要求の固定S3取得2件・署名検証・隔離復元・自動登録を確認しました。
途中停止はsleep実行中の試験資源で注入しており、SQL取り込み途中の強制停止を実証したものではありません。
追加PUTは0です。既存72時間観測の資源・台帳は使用していません。
初回の試験ツールのイメージ設定名誤りは資源作成前に失敗しました。
その記録を保持し、資源なしを確認して閉鎖した後、修正版を別領域で検証しました。
