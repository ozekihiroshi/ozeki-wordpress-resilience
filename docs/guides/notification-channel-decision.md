# 通知方式の検討：Googleのメールとプッシュ

2026-10-19。ユーザーから、community-energy.jpのメールはGoogleにあり、community側には設定済みとの情報を受領。既存のcommunityの認証情報やPostfix設定は今回読取り・コピー・変更していない。具体的なGoogleの契約・認証方式・送信許可設定は未確認。

## dmにはメールサーバーを置かず送信できる

既存のSMTPアダプターは外部SMTPへ直接TLS接続するため、dmにPostfixを新設したり、communityのPostfix環境を丸ごと複製したりする必要はない。Googleはアプリ等からの送信方法としてSMTPリレーやGmail SMTPを案内している。[Google公式](https://support.google.com/a/answer/176600?hl=en)

採用時は、Google側で許可する送信元、送信先、認証方式、必要ならdmの送信元IPを確認する。通常パスワードをコピーすれば使えるとは判断しない。現実装はSMTP login方式または認証不要の信頼されたTLSリレーを扱い、OAuth専用方式には追加実装が必要。communityとdmで資格情報を分けても、同じGoogleサービスを使えばサービス障害の影響は共通に残る。

既存Postfixを廃止する場合は、アプリ・cron・OS通知などが利用していないかを調べてから別作業として実施する。heartbeat導入のために撤去する必要はない。

## 採用方針：重要警報はプッシュ、詳細・履歴はメール

2026-10-19にユーザーがこの方針を採用。重要警報はプッシュ、詳細・履歴はメールへ分ける。Pushoverを最初の専用環境試験に採用。アダプターと宛先別配送を試作し、確認照会・取消を模擬試験で検証した。実機確認とWordPress管理画面への組込みは未実施。利用者が通知サービスを選ぶ方針とし、[実装範囲・登録手順](pushover-notification-lab.md)を参照。候補・費用・推奨構成は[プッシュ通知サービス比較](push-notification-service-comparison.md)を参照。

|場面|初期の通知案|
|---|---|
|監視停止、バックアップ取得漏れ、復元試験失敗|スマートフォンへのプッシュ＋メール|
|承認待ち|まずメール。対応期限が近づく/過ぎたらプッシュ|
|期限切れ、メール配送経路の障害|プッシュ。メール経路が使えれば記録メールも送る|
|復旧・解消|元の警報と同じ経路で解消を通知し、繰返し警報を止める|

「APIやSMTPが受け付けた」「端末に通知が出た」「担当者が確認した」は別の状態として扱う。重要警報には確認操作、未確認時の再通知、一定時間後の別担当への連絡を設ける。深夜の通知、集中モード、端末の電源断・通信断も含めて実機で試す。

## 候補の比較

|候補|適する運用|導入前に確認する点|
|---|---|---|
|Google経由のメール|履歴・詳細を読み返す、既存の受信箱を使う|迷惑メールや受信遅延、人が見たかどうかはSMTP受付だけでは分からない|
|Slack|既に日常的に使うチームで警報と対応相談をまとめる|モバイルアプリと通知設定が必要。デスクトップ利用状態や通知設定によって遅延し得る|
|専用プッシュサービス（例：Pushover）|少人数の運用担当へ重要警報を届ける|アプリ導入と認証情報管理、費用・端末での挙動を確認。緊急通知には確認までの再通知機能がある|

Slackは一般性の問題より、担当者が日常的に利用し、必要な通知を受け取れる設定になっているかで選ぶ。Slackを現在使っていないなら、警報のためだけに新しいワークスペース運用を始めるより、専用プッシュの方が目的に合う可能性がある。Slackはモバイルへの即時通知や遅延の設定を提供している。[Slack公式](https://slack.com/help/articles/360025446073-Guide-to-Slack-notifications)

Pushoverの緊急優先通知は、再通知間隔・期限と確認の記録を扱える。採用する場合は同一事件の再送で緊急通知を増殖させないよう、サービス側のreceiptとこちらのイベントIDを結び付ける必要がある。[Pushover API](https://pushover.net/api)、[確認記録API](https://pushover.net/api/receipts)

## 次に決めること

1. 最初の実機試験はPushoverを推奨。予備担当への自動引継ぎを最初から必要とする場合はPagerDuty Freeを優先して再評価する。正式採用は試験後に決める。
2. 受信するスマートフォンのOSと、担当者・予備担当者。
3. Googleメールの送信方法（SMTPリレー等）と専用の送信元・宛先。秘密値は端末側へ直接配置する。
4. 重要度・確認期限・夜間対応・通知の抑制期間。

今回は専用SSHの実装・検証を先行した。新規サービス契約、Google管理設定、実メール・Slack・プッシュの送信、既存Postfixの撤去は行っていない。
