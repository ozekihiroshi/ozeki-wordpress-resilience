# dmの既存MySQLを使う検証専用DBの準備

更新日：2026年10月18日。利用者は既存MySQLの利用を許可し、demandには触れないことを条件とした。

## 今回の確認結果

- MySQLサーバー・クライアント：8.0.46（Ubuntuパッケージ）。管理接続と専用ユーザー接続の両方で確認済み。
- /var/lib/mysqlの保存先：ルートファイルシステム約118GB、空き約58GB。
- sudo経由のパスワードなしroot接続：Access denied。既存認証の変更・リセットは行っていない。
- サーバー既定はutf8mb3 / utf8mb3_general_ci。変更せず、専用DBだけutf8mb4 / utf8mb4_unicode_ciで作成した。専用名の未使用と作成権限を事前確認した。
- 利用者の明示許可を得て既存MySQL管理設定を内容非表示で使用し、専用DB・ユーザーを作成した。mysqladmin用グループを一時クライアント設定へ読み替え、元設定は変更していない。一時管理設定はメモリ上のファイルシステムで使用後に削除した。

## 作成対象と権限

| 対象 | 作成結果 |
| --- | --- |
| DB | owrrecoverylab20261018 |
| ユーザー | owrlab20261018@localhost |
| 接続 | dm内のUnixソケット。リモート接続用ユーザーは作成しない |
| DB既定値 | utf8mb4 / utf8mb4_unicode_ci。実サーバーの対応を確認して作成 |
| 許可 | 専用DBに対するSELECT, INSERT, UPDATE, DELETE, CREATE, DROP, ALTER, INDEXのみ |
| 上限 | MAX_USER_CONNECTIONS 2を初期値とする。CPUやディスクI/Oの隔離を保証するものではない |
| 秘密情報 | ランダム生成し、dm上の専用ディレクトリ0700・クライアント設定0600へ保管。Git・コマンド引数・ログへ出さない |

DB名にはGRANTのパターンと紛らわしいアンダースコアやパーセントを用いない。GRANT OPTION、FILE、PROCESS、グローバル権限、他DBの権限を付与しない。CREATE USER/DBの前に専用名の衝突をメタデータで確認する。既存の同名資産は再利用・上書きしない。IF NOT EXISTSで衝突を隠さない。

## 作成後の検証

1. 専用資格情報で接続し、DATABASE()が専用DB、CURRENT_USER()が専用ユーザーであることを確認する。
2. 管理接続で専用ユーザーのGRANTとロール割当てを確認し、専用DB以外への許可がないことを確認する。demandへの接続やSELECTを試す否定試験は行わない。
3. 専用DBにだけ小さなInnoDB検査テーブルを作成し、utf8mb4の日本語・4バイト文字の書込みと読込みを確認する。検査テーブルは専用ユーザーで削除する。
4. テーブル作成・削除が専用DB内に限定されることを確認する。MySQL全体の設定変更、サービス再起動、既存ユーザー変更、FLUSH PRIVILEGESは行わない。
5. 作成前後のサーバー稼働状態と空き容量を記録する。業務DBのデータ照合は実施しない。

## 復元先の誤指定防止

手順3の実データ復元は今回の作業範囲に含めない。実装時は専用DB名・専用ユーザー・ローカルソケットを固定し、別名指定を拒否する。資格情報ファイルの所有者と権限、接続後のDATABASE()/CURRENT_USER()を確認してから取り込む。管理者資格情報を復元処理に渡さない。

mysqlの既定DB指定だけではSQL内のUSEや完全修飾名を制限できないため、専用ユーザーのDB限定権限を必須とする。mysql --forceは使わずエラーで停止する。通常の既知の試験ダンプのみを対象とし、不審なSQLやコードを共用サーバーへ投入しない。SQLの事前確認と容量・負荷上限を次段階で定める。

## 接続確認で使うSQL（データは読まない）

```sql
SELECT VERSION(), @@character_set_server, @@collation_server;
SELECT CURRENT_USER();
SHOW GRANTS FOR CURRENT_USER;
SELECT SCHEMA_NAME FROM information_schema.SCHEMATA
 WHERE SCHEMA_NAME = 'owrrecoverylab20261018';
SELECT User, Host FROM mysql.user WHERE User = 'owrlab20261018';
```

上記は許可された管理接続でのみ実施する。管理接続の方法が確定するまで作成処理を進めない。

## 実施済みの結果

- 専用DBとlocalhost専用ユーザーを作成。上記8種類のDB内権限のみを付与し、グローバル権限・GRANT OPTION・ロール割当ては付けていない。mandatory_rolesも空であることを確認。
- MAX_USER_CONNECTIONSは2で作成。接続数を意図的に超過させる試験は未実施。
- utf8mb4の日本語・4バイト文字をHEX比較で確認。CREATE/INSERT/SELECT/UPDATE/ALTER/INDEX/DELETE/DROPを専用の小さなテーブルで検証。
- 検査テーブル削除後、専用DBのテーブル数は0。実バックアップの復元はまだ行っていない。
- demandへの接続・テーブル参照・更新は行っていない。既存ユーザー変更、全体設定変更、MySQL再起動も行っていない。
- 最後にmysqlサービスactive、空き約58GBを確認。業務アプリの機能試験や厳密な性能影響測定をしたという意味ではない。

資格情報はdmの `~/.local/owr-db-lab/client.cnf`（0600）、専用ディレクトリは0700。秘密情報を含まない作成検証記録は同ディレクトリのverification.json（0600）に保管。Gitには資格情報を含めない。

[固定した復元先の事前チェック](../../tools/check-dm-lab-db.py)をdmの専用ディレクトリへ配置した。次のコマンドはデータを書き込まず、専用DB・ユーザー・サーバーUUID・限定権限を確認する。

```sh
ssh dm 'python3 .local/owr-db-lab/check-target.py'
```

正常チェックは成功し、別DB名を引数指定した場合は接続前に失敗することを確認済み。このチェックは独立した信頼の起点やSQLインポート機能ではない。次段階の復元処理には同じ接続制約を組み込み、事前チェックだけ実行して別の接続で取り込む構成にしない。

MySQL 8.0で専用DBの基本操作を確認したことと、MariaDB由来のM1ダンプを互換復元できることは別である。ダンプの事前確認と実復元は手順3で検証する。

## S3固定版からのDB復元結果（2026年10月18日）

準備完了後、次段階のDB復元まで実施した。上記の「実バックアップの復元はまだ行っていない」は準備時点の記録である。

- dm上の既存anchorを起点に、Recovery Set・RAM・database.sql.gz・Bootstrapの4点をS3からVersion ID指定で新規取得。返却Version ID、サイズ、SHA-256を照合した。
- 対象は正常なM1模擬資産。DB圧縮サイズ21,303 bytes、展開後105,175 bytes。SQL36文、12テーブル、178行。
- 事前にSQLを解析し、許可した12テーブルへのDROP/CREATEとリテラルVALUESのINSERT、限定したセッションSETだけであることを確認。USE、他DB指定、クライアントコマンド等を許容しない構造で検査した。
- 専用ユーザーだけを使い、実際に取り込む同じ接続でDB名・ユーザー・サーバーUUID・権限・空DBを確認。LOCAL INFILEと自動再接続を無効化し、エラーを無視せず実行した。
- 専用接続のロック待ち上限を5秒とし、実行プロセスには60秒の上限を設定。MySQL全体の設定は変更していない。これらは共用サーバーのCPU/I/Oを完全に隔離するものではない。
- 取り込みと初回照合クエリは約1.078秒。エンドツーエンドの復旧時間やRTOではない。
- 全12テーブルの行数・全178行の全カラムを元SQLと比較し一致。基準投稿・固定ページ4件の記録も一致。シリアライズ済み設定値は復元後の文字列が元SQLと完全一致。
- 初回の比較はJSON_ARRAYが日時に小数秒を付ける表現差で失敗した。初回結果を残し、読取りクエリで各カラムを明示的にCHARへ変換して再照合した。データ変更や再取り込みは行っていない。
- 最後にMySQL active、空き約58GB、専用権限の維持を確認。demandへのアクセス、既存サービス再起動、既存ユーザー変更なし。FTPの業務機能試験は行っていない。

[公開用集計](../../evidence-public/dm-database-restore.json)。dm上の詳細結果は `~/.local/owr-db-lab/restore-20261018-001/verified-result.json`。初回照合失敗は同ディレクトリのrestore-result.json、固定版取得の記録はdownload-verification.jsonに保存。取り込みに使用したrestore.pyも同ディレクトリにあり、固定した既知資産専用の実験コードである。非空DBを拒否するため、そのまま再実行して上書きしない。

専用DBには検証済みデータを残している。WordPressのコード・メディアは起動・復元しておらず、ブラウザーでの機能確認は次段階。IAM分離と真正性は引き続き未達・未検証であり、感染後の安全な復旧を実証したという意味ではない。
