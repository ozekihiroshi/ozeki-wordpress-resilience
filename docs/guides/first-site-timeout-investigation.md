# 取得中タイムアウトの切り分けと修正（2026-10-20）

## 結論と分類

環境のせいと推定して終了する問題ではなかった。専用環境の添付欠落試験で `TimeoutExpired` を再現し、ファイル転送中の停止確認 `docker exec … php` が60秒待っていることを計測した。確認処理は小さな停止マーカーを読むだけだが、アダプターはその間、別のexecが出すアーカイブの読み取りを止めていた。

Docker 29.1.3の専用コンテナで、「出力が未読のまま出力プロセスが終了する」条件を作ると、別のexecが3/3回タイムアウトした。残りの出力を読むと3/3回とも復帰した。未読出力があってもプロセスを終了させない比較は3/3回成功、出力を読み続ける比較も3/3回成功した。単なるCPU・メモリ不足という説明より、この待ち合わせ条件を根拠とする。

同種の終了イベント処理の待機は[Mobyの報告 #53614](https://github.com/moby/moby/issues/53614)にもある。この報告を原因確定の代用にはせず、上のローカル再現・復帰・比較を実施した。Docker内部のスタックを初回の失敗時に取得したわけではないため、初回と上流報告の内部実装が完全に同一であることまでは証明していない。

分類は「Docker実行時の挙動に依存する、取得アダプターの待ち合わせ上の問題」。WordPressプラグイン本体の受入失敗とは分けるが、外部取得機能の修正対象であり、環境の備忘録だけで済ませない。Dockerの更新・再起動・待機上限延長は行っていない。

## 再現の経過

- 元の連続7ケースは修正前の再試験では成功した。
- 添付欠落を最初の取得にした単独試験で、同じ60秒のTimeoutExpiredが発生した。失敗扱い・停止解除済み。php/heldの工程名、実時間、例外位置を記録した。
- プロセス観測付きの再試験では3回、さらに10回とも欠落検出が成功した。間欠的であり、全試行失敗する問題ではない。
- 上記の小さな終了イベント比較で、待ち合わせ条件を3回再現した。
- 調査時の専用コンテナのmemory.eventsは上限到達・OOMとも0、cpu.statのthrottledは0。再現した時点のメモリPSIも0。I/O負荷は存在したが、単独の原因だと断定できる証拠はない。

## 修正

1. `bounded-process-stream.py` で、制御側が停止確認している間も別スレッドが出力を読み続ける。ホスト側の匿名一時ファイルへ保管し、読み取り側の待機でDockerの出力処理を止めない。
2. 一時保管の書込みは設定容量以内で打ち切る。期限・プロセス異常・I/O失敗は成功扱いにせず、終了時に一時ファイルを閉じる。保存元には一時アーカイブを作らない。
3. ホスト側では取得結果に加えて一時保管分が必要になるため、停止前に `2 × max_bytes + reserve_bytes` の空き容量を確認する。実際の一時保管は資産ごとに作り、処理後削除する。
4. 停止確認の次回時刻は確認の「完了」から0.5秒後とする。従来は開始時刻から計算していたため、確認に0.5秒以上かかると直後にまた確認を呼び、転送を妨げた。時計制御テストで旧実装20回の呼出しを再現し、修正後は6回以下という条件を満たした。
5. 取得結果の `timings` に工程別の回数・合計・最大時間、タイムアウト時の `timeout` に工程名・制限秒・実時間を残す。コマンド文字列・認証情報・標準出力・標準エラーは記録しない。

総停止期限、保持・署名条件、添付欠落を成功扱いしない条件は緩めていない。原本の失敗記録を成功で書き換えない。

## 検証と再実行

[公開集計](../../evidence-public/first-site-timeout-fix.json)に結果とソースハッシュを保存する。過去の取得・S3集計のハッシュは当時のソースの記録として残す。今回S3への再保存や本番サイトへの適用は行わない。

```sh
python3 tools/run-first-site-timeout-lab.py --execute-lab --mode single --repeats 3 \
  --output "$HOME/.local/share/owr-first-site-timeout/new-single.json"
python3 tools/run-first-site-timeout-lab.py --execute-lab --mode sequence \
  --output "$HOME/.local/share/owr-first-site-timeout/new-sequence.json"
```

出力先の親フォルダを0700で用意し、既存名を使わない。処理が終わる前に再実行しない。診断用のevents.jsonlはCPU/メモリ/I/OのPSI、工程時間、専用コンテナの遅延時プロセス状態を記録する。private配下の生成SQL・ファイルには試験資格情報があるので公開しない。

72時間観測の既存コード・日次セット・信頼情報、共通部品、Backup for S3、公開ZIPは変更しない。

## 修正後の実測

取得契約17テスト、外部一時保管4テスト、既存2資産署名ゲート6テストが成功。取得17・一時保管4は最適化実行でも成功。実WordPressの添付欠落単独3回と元の連続7ケースが期待どおり完了し、停止解除・専用資源削除を確認した。新しい読み取り方式による終了条件の比較も3/3回正常で、確認コマンドは約0.49–0.52秒で戻った。
