# 生成設定を使った専用環境への配置検証

対象は設定生成→担当者による未設定項目の補完→棚卸し→導入前検査→独立watchdog→WordPress表示。既存の取得・通知・SSH・画面処理を再利用し、設定形式から運転までの接続を確認する。これは本番向け自動インストーラーではない。

## 専用試験の実行

WSL Ubuntuで、既存の試験用Dockerイメージを用意したリポジトリから実行する。

```sh
python3 -B tools/run-generated-deployment-lab.py --output /home/ozeki/.local/share/owr-generated-deployment-NEW
```

出力先は未作成の専用ディレクトリを選ぶ。生成したDBパスワード・SSH鍵を含む私有領域のため公開しない。runnerは固有名のコンテナ・内部ネットワークだけを作成し、終了時にそれらを除去する。失敗記録・設定・検証証拠は出力先に保持する。試験は既存の72時間観測へアクセスしない。

## 配置の順序と手作業の対応

1. `plan`と`generate`を実行して新規bundleを作る。計画が成功してもproduction_readyはfalseのまま。
2. 計画のdirectoriesとfilesを専用ホストへ配置する。実行用ユーザーとSSH受信ユーザーを分け、コードは読取り専用マウントとする。
3. 棚卸し対象のPHP実行パス・専用DB接続・SELECT専用アカウントを下書きへ設定する。プロファイルと試験環境の宣言票を配置する。実ホストからの観測結果と宣言票を同一視しない。
4. 6経路それぞれの鍵を作り、作成元で取得したホスト公開鍵を計画の別名で固定する。計画のssh_endpointsをauthorized_keysの固定コマンドへ対応付け、shell・転送を無効にする。
5. **watchdog起動前に通知先を補完する。** この試験では既存smtp_test受信処理をobserverのループバックだけで動かす。alertsを省略した下書きではCLIは起動できない。実運用では選んだ通知先の実送信を別途確認する。
6. publisher、receiver、observer、observer report pullを計画のargvで1回ずつ実行する。DBとファイルの不変性、報告のsite/config/monitor対応、WordPressからの鍵読取り・報告書込み拒否を確認する。
7. 生成したwp-config.fragment.phpの定義を専用WordPressへ反映し、同じ絶対パスへ報告を読取り専用で接続する。既存の実ブラウザ試験を再利用する。
8. publisher/receiverを周期実行し、棚卸しSSHを止める。取得失敗の報告・画面表示、再開後の回復を確認する。更新時刻を書き換えて失敗・回復を作らない。

## 意図的な専用環境差分

- 設定ファイルの配置先、サイトID、monitor ID、表示定義は生成値を使用する。
- 専用イメージのPHPパス、生成DBのホスト名・認証、ローカル通知先は明示補完する。
- 専用コンテナ内のグループ33で設定読取りと表示ファイルの通過権限を構成する。本番ではホストごとのグループ/ACL設計が必要。この簡略構成をそのまま本番へ転用しない。
- 周期は試験用に60秒から2秒へ短縮する。systemd導入・OS再起動は今回の追加受入範囲ではなく、既存の専用VM試験の記録と区別する。
- 生成WordPress型テーブル・ファイルを棚卸しし、別の実WordPressで管理画面を検証する。実サイト全更新経路の確認、S3保存、署名・復元、本番適用の合格ではない。

## 初回試行で見つかった点

1. Docker既定アドレスプール不足でネットワーク作成前に停止。環境問題。既存runnerの空きサブネット探索を再利用し、既存ネットワークを削除せず対処した。
2. 通知設定下書きを補完せずwatchdog CLIを実行して停止。導入試験手順の不足。製品が必須設定の欠落を拒否した結果であり、通知処理のバグや環境問題とは扱わない。ローカルSMTP設定を明示補完する手順へ修正した。

3. WordPress画面の正常判定で停止。受渡し側のhealthはokだったが、最初の試験は画面の実判定を記録していなかったため原因未確定として保持する。試験の複数行PHPをDocker envへ渡す形式に問題を見つけ、単一行化と読取り診断を追加した。修正後の成功だけで以前の失敗原因を断定しない。

4. v4では定義・読取りが正常で、画面の実判定がinconsistentであることを記録。周期公開中にreportとhealthの世代が異なる状態を観測した。製品はこれを成功扱いせず反映途中と表示する。ブラウザ試験はinconsistentだけ最大15秒の再読込みを行い、収束までの標本を保存するよう変更。持続する不整合は試験失敗となる。

5. v5では正常表示・権限・読取り専用を通過し、実通信断の取得失敗も記録したが、次のブラウザセッションの管理者メニュー確認で停止した。最初の失敗時の画面遷移を保存できていないため根本原因は未確定。ログイン前のcookie分離、メニュー待機、各場面の標準出力・エラーと成功記録の即時保存を追加した。環境原因やプラグイン原因と断定しない。

最終専用試験は合格。[検証結果](../../evidence-public/generated-deployment.json)と[回復画面](../../evidence-public/generated-deployment-recovered.png)、[watchdog画面](../../evidence-public/generated-deployment-watchdog.png)を保存。実ブラウザの3場面で匿名・編集者の拒否、読取り専用・POST405・狭い幅の表示、watchdogの表示も確認。以前の失敗記録は削除しない。
