# 無人日次運用の担当者確認（試作仕様）

担当者の運用条件確認と、毎回の自動再検査を分離します。既存の初回用確認 `owr-first-capture-review-v1` は変更せず、日次用に `owr-recurring-capture-review-v1` を追加します。専用試験限定です。

## 期限

- 担当者確認：発行時から最長168時間（7日）。初期値168時間、1～168時間を指定可能。期限と同時刻で失効し、猶予はありません。
- 棚卸し、取得報告、検査結果、転送状態：毎回5分未満。古い成功結果を代用しません。
- 自動再検査は担当者確認を更新・延長しません。担当者確認が期限内でも技術的な検査不合格は解除できません。
- 確認は取得を進めるための運用条件の確認です。バックアップセットの独立署名承認、マルウェア不存在、本番復旧許可を意味しません。

7日は今回の試作の保守的な上限です。検知されない変更が7日間安全という保証ではありません。

## 毎回自動で確認すること

既存の取得・日次入口で、サイトロック取得後、更新停止直前、取得後、保存先の接続前検査後に最新入力を読み直します。容量・作業場所の権限、未終了処理・結果不明PUT、対応構成、報告世代の一致、取得・転送の成功、期限、確認対象のハッシュを検査します。データ取得中は既存の停止・処理完了待ち・整合性・解除確認を維持します。

報告時刻やnonce、正常範囲のファイル件数・容量・テーブル数の変化では担当者確認を失効させません。ただし容量上限や対応条件を外れた場合は自動検査で停止します。棚卸しは observed_at だけを除いた内容を確認記録へ結び付けます。実ホストのDB名・接頭辞・エンジン、ファイルルート、WordPress構成、PHP版・OS種別も別途結び付けます。報告にはこれらの原文を追加せず、項目群ごとのSHA256だけを持たせます。

## 担当者の再確認が必要な条件

|条件|扱い|
|---|---|
|確認期限切れ、明示失効 status=revoked、確認記録の削除|停止。新しい確認が必要|
|設定の変更（担当者、保存先、保持、権限参照、信頼参照、停止条件等を含む）|設定ハッシュ不一致で停止|
|棚卸しの確認対象または実ホスト構成の変更|確認範囲の不一致で停止。PHP更新も再確認対象|
|作業場所の変更|確認記録のworkspace不一致で停止|
|更新経路追加、手動の権限変更、鍵・保存先変更、侵害の疑い|担当者が即時失効し調査。自動検出できると仮定しない|
|通信失敗、古い報告、一時的な容量不足|自動検査で停止。確認期限と範囲が有効なら、原因解消そのものは新しい担当者確認を要求しない|
|停止解除不明、結果不明保存、未解決日次枠|台帳の調査が必要。新しい確認だけで再開できない|

日次枠の失敗は既存仕様どおりunknownとして保持し、自動再試行しません。一時的な問題が回復して判定が通るようになっても、そのことだけで失敗枠を再送しません。

## 発行・更新の手順

1. 現在の外部設定、最新の棚卸し・報告・転送状態を確認します。初回仕様の10項目を再確認し、根拠を confirmations.json に記録します。
2. 担当者が、保護された外部ホストで次のコマンドを明示的に実行します。cronには登録しません。

```sh
python3 -B tools/recurring-capture-review.py \
 --profile /private/profile.json --inventory /private/inventory.json \
 --workspace /private/capture-work \
 --report /private/report.json --health /private/health.json \
 --confirmations /private/confirmations.json --reviewed-by lab-operator \
 --valid-hours 168 --output /private/reviews/review-002.json
```

3. 発行された期限と確認対象を点検し、日次入口の admission.review が新しいファイルを参照するよう外部配置手順で切り替えます。処理途中の部分書込みを避け、既存記録を履歴として保管します。ツールは既存出力を上書きせず、配置・サービス再起動・通知は行いません。
4. 失効する場合は外部の管理された手順で有効ファイルをstatus=revokedに切り替えるか、参照を解除します。次の再検査で拒否します。期限短縮や停止も同様に担当者管理です。実行済みのPUTや進行中の転送をさかのぼって取り消すものではありません。

確認ファイルの署名認証や改ざん耐性のある失効台帳は未実装です。所有者限定の外部領域で、保存元・WordPress・自動検査プロセスから更新できない権限構成にする必要があります。旧記録への不正な巻戻しを防ぐ暗号学的仕組みはありません。自動実行が書き換え可能な確認記録を信頼してはいけません。

## 実装範囲と未達

担当者確認の期限・範囲・失効、明示発行、既存取得／日次入口での再検査を実装しました。期限前通知、管理画面からの更新、権限配置の自動設定、署名付き確認・失効台帳、失敗枠の再開操作は今回の対象外です。新しいホスト報告はreview_scopeを含む必要があり、古い報告は日次用確認では拒否します。初回用の5分確認は従来どおり利用できます。

## 検証

ネットワークなし・コード読取り専用の専用Docker、生成データ、模擬時計とローカルS3代替で16件成功。翌日相当の新報告で確認を再利用、期限境界、古い報告／棚卸し、失効、構成変更、確認欠落、明示発行と上書き拒否、日次の成功／失効時PUT0件を確認しました。日次試験は実取得コアと生成バックエンドを使い、AWS送信はありません。7日間の実時間運転を行った結果ではありません。

環境・試験基盤：新たな障害なし。既存ブラウザ問題の原因未確定は別管理。
製品：回帰試験で今回追加した確認対象の原文露出を検出し、項目群のハッシュだけを出力する方式へ修正。既存の非露出試験を含めて再確認。確認の更新方式が未実装だった課題を、限定された外部運用方式として実装。本番適用・強い失効管理等は未達です。72時間観測やその欠測は変更していません。
