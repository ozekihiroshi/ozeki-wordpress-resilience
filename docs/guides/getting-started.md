# 利用開始ガイド

更新：2026年10月19日。まずREADMEの「検証済みの範囲」と「未達」を確認する。現段階は開発者と運用担当者が環境を設定するパイロットであり、一般利用者向けのインストーラーは未完成。

## 用意するもの

| 用途 | 初期構成 |
| --- | --- |
| 保存元 | 対象WordPressと対象DBを特定できる環境 |
| 外部保管 | 専用S3バケット、VersioningとObject Lock、35日デフォルト保持 |
| 独立取得 | 保存元とは別の復旧ロール。固定版を読む権限と保持情報の読取り |
| 署名 | 保存元・復旧サーバーから分離したPC、公開ピンと鍵の管理 |
| 隔離復元 | 新規DB・ボリューム、外部通信とメールを遮断した試験環境 |
| 別媒体 | 暗号化鍵バックアップと独立公開ピン・固定版取出し情報を保管する媒体 |

長期アクセスキーをWordPressへ設定する方式は採用しない。今回の環境ではEC2ロールを使用した。別のホスティングで同じ認証方法が使えるとは限らない。

## 読む順番と確認ポイント

1. [取得記録](initial-live-stream-capture.md)で対象資産・秘密情報の扱い・容量を確認する。DBとファイルを同時点に揃える仕組みは次の開発段階。
2. [正式S3設定手順](production-storage-setup.md)でバケットとIAMを設定する。実環境名入りJSONは今回専用。他サイトでは所有者・バケット・prefix・ロールをレビューして作り直す。
3. 専用試験データで保存・固定版読取り・保持・拒否動作を確認する。バケット設定の読取り成功だけでは、固定版の読取り権限があるとは限らない。
4. [実データ保存・署名の記録](protected-candidate-publication.md)で、保存受付と独立取得、保管候補と本番復旧承認の違いを確認する。
5. [S3起点の隔離復元](signed-s3-candidate-restore.md)で署名ゲート・内容確認・終了後停止・USB読戻しを確認する。

今回完了した操作を、初心者向けの一括再実行手順として扱わない。[ツール一覧](../../tools/README.md)に従い、まずオフライン検査か読取り専用の署名検証を使う。

## 状態の読み方

| 状態 | 意味 |
| --- | --- |
| 保存受付済み | S3が版を返した。独立取得・保持確認はまだ別 |
| 保管内容検証済み候補 | 必須資産の固定版・ハッシュ・保持を確認。整合性や無感染の認定ではない |
| 候補への署名済み | 独立ピンで承認内容を確認できる。対象・期限・世代・範囲に制限あり |
| 隔離復元・基本動作確認済み | 試験範囲で復元できた。全業務機能・再公開は別の判断 |
| 期限切れ・未確認・失敗 | 検証を省略しない。原因を調べ、独立した再評価を行う |

## 困った場合

- AccessDenied：どのロール・操作・Resourceで失敗したかを確認。GetObjectVersionとGetObjectRetentionはバケット設定読取りとは別の権限。広範な管理者権限を追加する前に対象を確認する。
- 署名期限切れ：S3保持が続いていても承認更新が必要。日付だけを編集せず、新世代の承認・署名・独立ピン配布を行う仕組みを整える。
- 送信結果不明：新しいPUTを繰り返さない。受付記録・対象キー・版を独立側で確認する。
- 古い手順と状態が違う：READMEと[現在の計画](../spec/10-operationalization-plan.md)を入口に、各実験記録の日付・対象を確認する。

感染が疑われるコードを今回の共有Dockerホストへ安易に投入しない。悪性コード専用の隔離・再構築試験は未達である。
