# 日次バックアップ運用の専用環境試作

対象は `isolated-queue-lab` の生成データのみ。実WordPress／MariaDB／キューと実RSA署名を使い、保存先は模擬版管理ストアとする。実S3往復は[別の実測](real-queue-s3-lab.md)に記録済みだが、この日次コーディネーターにはまだ接続していない。本番サイト、正式S3、独立管理する本番秘密鍵へは接続しない。

## 日次の契約

- 日本時間03時を日次境界とする。`--hour-jst` で専用環境の時刻を指定できる。初回開始前に決め、既存台帳の途中では変更しない。
- OSタイマーが起動するたびに最新の実行対象日を求める。同日の完了済み処理は再実行しない。停止期間後は最新日の取得だけを行い、過去の欠測を成功で埋めない。時計が過去へ戻ったら停止する。
- WSL内LinuxファイルシステムにSQLite台帳とOSファイルロックを置く。同一状態ディレクトリでプロセスを排他する。複数PC・複数状態ディレクトリ間の排他は未対応。状態ディレクトリを変えて再試行してはならない。
- 実行IDごとに新しい作業ディレクトリ・結果ファイルを作る。三資産の一貫した取得、模擬35日保持、独立署名、固定版取得、隔離復元、再配送、試験資源の除去を含む51ケースを満たしたときだけ `success` とする。
- 台帳はローカル実行管理情報であり独立したRoot of Trustではない。署名・保持の判定は既存の復元前ゲートが担当する。ローカル管理者による台帳改ざんの検出は今回の範囲外。
- 日次の本番候補は、保存完了と独立承認完了を別段階にする必要がある。今回の自動署名は使い捨ての試験鍵に限る。本番鍵を保存サーバーや日次ジョブへコピーしない。

## 専用環境での実行

Ubuntu-24.04のDockerと既存 `owr-external-lab:local` イメージを使う。状態ディレクトリはWSL内に置く。引数なし・helpでは試験を起動しない。

```bash
python3 /mnt/d/workspace/ozeki-wordpress-resilience/tools/daily-backup-lab.py tick \
  --execute-lab --state-dir "$HOME/.local/share/owr-daily-lab-20261019"
python3 /mnt/d/workspace/ozeki-wordpress-resilience/tools/daily-backup-lab.py status \
  --state-dir "$HOME/.local/share/owr-daily-lab-20261019"
```

`state.sqlite` に状態遷移、実行ID、結果ファイル、結果ハッシュを保存する。実行フォルダの `worker.log` は管理者だけが読む。今回は外部通知を送らず、標準出力のJSONと終了コードで監視へ接続する。完了は0、失敗・結果不明・欠測・同時実行中は2。JSON破損など予期しない例外も非0になる。

## 失敗時の判断

| 状態 | 意味 | 操作 |
| --- | --- | --- |
| `success` | 全ゲートと隔離復元・後片付けが完了 | 同日の再起動は処理を省略。結果と台帳を保管 |
| `failed` | Docker等の事前確認で停止。ワーカー未起動 | 原因を直した後、同じコマンドへ `--retry-failed` を追加。新しい試行IDで記録 |
| `unknown` | ワーカー開始後の失敗、結果欠落、強制終了 | 自動再実行を禁止。翌日も停止。ログ・元の結果・残存する専用コンテナを確認 |
| `busy` | 別プロセスが同じ台帳を使用中 | 起動元を確認。ロックファイルを削除して解除しない |
| `missing_days` | 初回対象日以降に取得成功のない日 | 欠測として残す。RPO逸脱を運用担当へ報告し、過去の取得成功を捏造しない |

実行中のコーディネーターが強制終了した場合、次の台帳アクセス時に残った `running` を `unknown` に変更する。子ワーカーは動いている可能性があるので、先にプロセスとログを確認する。ワーカーは30分を上限とし、タイムアウト時には自身が起動したプロセスグループを停止する。残存Dockerコンテナは実行ログの `owr-consistency-...` と照合してから個別に扱う。Docker全体の削除・pruneはしない。

終了通知だけ失われ、元の実行フォルダに全51ケース成功・後片付け済みの結果が残っている場合は、以下で証拠を再検査できる。ワーカーは再実行しない。

```bash
python3 /mnt/d/workspace/ozeki-wordpress-resilience/tools/daily-backup-lab.py reconcile \
  --state-dir "$HOME/.local/share/owr-daily-lab-20261019" --day YYYY-MM-DD
```

証拠が不完全なら解除されない。台帳削除や成功への手編集は禁止。未完了セットの部分再開・放棄承認は今後のアダプター設計であり、現段階では診断して停止する。実S3の結果不明PUTも自動再送しない原則を維持する。

## タイマー接続例と未達

`examples/daily-lab/` にsystemdユーザータイマーの例を置く。毎時コーディネーターを呼び、日付の重複排除は台帳が行う。起動漏れ後も最新日のみ取得する。今回は例の配置だけで、タイマーのインストール・有効化はしていない。WSL停止中はタイマーも動かないので、常時稼働する運用環境の代用にはならない。

日次の実S3接続、独立担当による署名承認、承認期限更新とUSB配布、実通知、空き容量の基準、保存期限後の管理者整理、本番サイトへの適用は未実施。専用試験の模擬ストア・試験秘密鍵は試験終了時に破棄されるため、このコーディネーター自身は長期バックアップ製品ではない。
