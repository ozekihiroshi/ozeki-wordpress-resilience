## 方法

communityのwp-rescueとwp-rescue-dbが対象。取得前の空き容量は約14GB・使用率87%まで改善していたが、初回アーカイブの置場には使わなかった。

経路は「対象コンテナの標準出力 → community上のgzip -1 -n → SSH → WSLの専用領域」。DB、ファイル、実行イメージを順次処理し、サーバー側で.sqlや.tar.gzの一時ファイルを作らない。gzipは低いCPU優先度で実行した。低圧縮レベルは負荷を抑えるためであり、最大圧縮率を測ったものではない。

- DB：MariaDB標準のmariadb-dumpを使用。対象DBはwp_rescueに固定。--single-transaction、--quick、--skip-lock-tables、--hex-blob、utf8mb4、--no-tablespacesを指定した。対象の12テーブルがすべてInnoDBであることを先に確認した。
- DB認証：既存コンテナ環境の資格情報をコンテナ内で使用し、パスワードを引数・ログ・チャットへ出していない。
- WordPress：/var/www/html全体をtarの標準出力へ出す。wp-config.phpを含むため、実データは秘密情報を含む保護対象として扱う。
- 実行環境：WordPressとMariaDBの使用中イメージIDを固定し、docker image saveの標準出力を圧縮。別アプリのイメージ・コンテナは取得していない。
- 外部設定：既知のPHP uploads.ini（114bytes）と、非秘密の構成台帳を別途保存した。共有Traefik全体の設定は取得せず、復旧側の入口を別途構成する。

既存共通PHPダンプ部品は一時ファイルを作成する方式のため、今回の容量測定では使っていない。製品の標準取得方式へ統合する際は、共通部品のストリーム契約または標準CLIアダプターとして整理し、既存製品を無断で変更しない。

## ローカル保管と失敗時の扱い

原本は `/home/ozeki/.local/share/owr-captures/wp-ceri-link-20261018T073750Z` に保存した。ディレクトリ0700、ファイル0600。Gitや公開証拠、USB、S3へ実データをコピーしていない。これはファイルシステムのアクセス制限であり、別途パスワード暗号化したアーカイブではない。

各ストリームはWSLの.partialへ書き、送信元とgzip両方の終了コードを確認する。非ゼロ終了・容量制限超過・整合性失敗は成功扱いにせず、不完全なファイルを残して調査する。1ストリーム4GiBの安全上限と、開始前5GiB以上のローカル空き容量条件を設けた。今回すべて正常終了した。

取得スクリプト・詳細manifest・SHA-256は専用領域に保存した。公開するのは容量・検証結果等の集計で、DB・設定・サイトファイルは含めない。
