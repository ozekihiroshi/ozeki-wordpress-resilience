# 専用バケットでのObject Lock試験

状態：専用バケットでGovernance保持の比較試験に合格。準備手順と実測結果を以下に記載。既存のceri-link-resilienceは未変更。

## 1. コンソールで専用バケットを作る

- バケット名候補：`ceri-link-resilience-lock-lab-121426368082`（まだ存在・利用可能性を確認していない。重複する場合は別名を決め、ポリシーの対象も合わせる）。
- リージョン：東京 ap-northeast-1。汎用バケット。
- オブジェクト所有者：ACL無効の既定設定。
- パブリックアクセスをすべてブロック：有効。
- バージョニング：有効。
- デフォルト暗号化：SSE-S3。
- Object Lock：有効（作成画面の詳細設定等）。不可逆性の確認を読む。
- **デフォルトの保持期間は無効のまま**。対照実験のため、保持なし版と明示的に保持を付けた版を同じプレフィックスに作る。バケット単位で1日保持を付けると、保持なし対照を作れなくなる。
- Lifecycle、レプリケーション、バケットポリシー、Legal holdは設定しない。

有効化後はObject Lockを無効化したりVersioningを停止したりできない。小さな使い捨てデータのみを置く。実際にロックされるのは保持を設定した各オブジェクト版であり、バケット機能を有効にするだけでは全データの保持を保証しない。

## 2. バケット作成を確認してから試験権限を追加

EC2に付いているロールを付け替えず、専用バケットだけを対象に一時的な追加ポリシーを使う。保存側には試験用プレフィックスの削除とPutObjectRetentionもAllowする。これにより、単なる削除権限不足とObject Lockによる拒否を比較できる。既存の復旧バケットへの権限は変えない。

- my-ssm-roleへインラインポリシー `OwrObjectLockLabWriterTest` を追加。内容は `.local/object-lock-lab-20261018/writer-test-policy.json`。
- OwrM1RecoveryReaderへインラインポリシー `OwrObjectLockLabReaderTest` を追加。内容は同ディレクトリの `reader-test-policy.json`。
- 公開テンプレートは `examples/object-lock-lab/`。実バケット名入りは非公開領域に用意済み。

保存側にGovernance bypassは許可しない。バケットの設定変更・削除、IAM管理権限も追加しない。これはObject Lockの機構を確認するための試験用権限であり、実運用のwriterに削除や保持変更を付ける推奨ではない。

## 3. 実行する試験

新規UUID付きobject-lock-probes/配下の数KB以下のテキストだけを使う。STSで主体・アカウント、S3でVersioning/Lock有効・デフォルト保持なし・Lifecycleなしを確認してから開始する。必須の観測が得られなければ停止する。PutObjectには明示的なSHA256 checksumを指定する。

1. 保持なし対照を保存しVersion IDを記録する。dmで固定版取得とハッシュ一致を確認後、保存側でその固定版を削除する。成功が必要で、削除権限が機能している証拠とする。
2. 別キーを保存し、Governance・24時間の保持をPutObjectRetentionで設定する。成功応答だけでなくGetObjectRetentionのモード・期限を読み戻す。これで保持変更のAllowが機能していることも確認する。設定前の無保護期間があるため、この手順は小さな試験データ専用で、本番保護方式には採用しない。
3. そのVersion IDの削除がAccessDeniedになることを確認する。
4. 同じ版の保持を1時間へ短縮する要求がAccessDeniedになることを確認し、元の24時間の期限が変わっていないか読み戻す。
5. bypassヘッダー付きの版削除も拒否されることを確認する。これはbypass禁止のポリシー試験であり、手順3の通常削除拒否と証拠を分ける。
6. Version IDなしの通常削除は成功して削除マーカーが作られ得る。成功しても保持失敗と判定せず、dmから元の固定Version IDを取得して内容一致を確認する。
7. 試験用の別内容を同じキーへ上書きし、新版のVersion IDが異なることと、保持中の旧固定版をdmから取得できることを確認する。新しい版は自動保持されないため、本番の保持設定課題として区別する。

各操作の直前直後のVersion ID・サイズ・ハッシュ・保持期限・エラー種別を非公開証拠に残し、集計だけ公開する。ロック版の存在とdmの取得可否を毎回確認する。Governanceを回避できる管理者に対する保護やComplianceモードの試験ではない。

## 4. 後片付けと判定

保持中の版を削除するためのbypass権限は追加しない。試験データは保管し、保持期限を過ぎた後に利用者の指示で専用オブジェクト版と削除マーカーを整理する。期限経過だけでは自動削除されない。通常は微小量のストレージ・API利用だが無料とは扱わず、作成したバケットは管理対象に記録する。予約タスクは今回作成しない。

試験が完了したら、追加した2つの試験用ポリシーを取り外す手順を案内する。既存の他用途ポリシーは変更しない。検証合格でも、本番バックアップへの保持適用、保持期間の業務判断、別管理主体・別アカウント、保持変更権限の統制、暗号鍵喪失対策は別途必要である。

参考：[AWS Object Lockの運用・制約](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html)、[Object Lock設定](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-configure.html)。


## 実測結果（2026年10月18日）

専用バケットで実行し合格した。[公開集計](../../evidence-public/object-lock-governance-lab.json)。実際の主体はcommunityのmy-ssm-roleとdmのOwrM1RecoveryReader。STSでアカウント・ロールを確認し、環境変数や既存AWS設定の長期キーは使用していない。S3設定を事前に読み取り、Object Lock/Versioning有効、デフォルト保持なし、Lifecycle/bucket policyなしを確認した。

| 試験 | 実測結果 |
| --- | --- |
| 保持なし固定版の削除 | 成功。事前にdmから取得・照合済み |
| Governance 24時間保持の設定 | 成功。dmでモード・期限を読み戻し |
| 保持中の固定版削除 | AccessDenied、同じ固定版の内容一致 |
| 保持を1時間へ短縮 | AccessDenied、元の期限が不変 |
| bypassヘッダー付き削除 | AccessDenied。試験用IAMの明示Denyによるbypass禁止を別途確認 |
| Version IDなしの削除 | 成功し削除マーカー作成。保護中の固定版は取得可能 |
| 同じキーへの別内容の保存 | 新しいVersion IDを作成。保護中の旧版も内容一致 |

保持なしの削除に成功する同じ主体・同じプレフィックスで、保持中の固定版は削除できなかった。単なるDeleteObjectVersion権限不足による拒否と区別できる。各拒否後にdmで同じVersion ID・サイズ・SHA-256を照合した。GetObjectRetentionでも保持期限が変わらないことを確認した。

保持期限は **2026年10月19日 12:17:35 JST**（UTC: 2026-10-19T03:17:35+00:00）。期限前の解除やbypass権限追加は行わない。期限到来だけでは自動削除されない。

初回は保持なしに対するNoSuchObjectLockConfiguration応答の判定不足で停止。2回目は削除成功後のGETがAccessDeniedであったため停止した。判定を修正した3回目で完走した。各原本は非公開領域へ保存してあり、失敗した試行を成功に書き換えていない。削除後のAccessDeniedだけを不存在の証明とせず、削除APIの成功応答と区別して記録した。

初回の保持なしファイル、成功回の保護版・削除マーカー・上書き新版等は残っている。自動削除の予約はしていない。既存の復旧バケット・業務バケットには触れず、バケット設定やEC2ロールの付替えも行っていない。

### 次のコンソール操作

試験が終わったため、利用者のコンソールで追加した **OwrObjectLockLabWriterTest**（my-ssm-role）と **OwrObjectLockLabReaderTest**（OwrM1RecoveryReader）の2つだけを取り外す。試験終了時点では取り外し未確認であり、APIで変更していない。元からあるポリシーは維持する。後日の片付けは管理者が専用バケットの全バージョンと削除マーカーを確認し、保持期限を過ぎたものだけを削除する。

### 公開判定

専用環境で「Governance保持とbypass禁止を組み合わせれば、削除許可を持つ保存側からも保持中の固定版を守り、復旧側が取得できる」を実証した。既存バックアップはこの専用バケットへ移行・保護していない。Governance bypassを許された管理者、ロール以外の資格情報、AWSアカウント全体の侵害に対する保証ではない。CR01の全条件の合格にはしない。

### 試験権限の取り外し確認

利用者が試験用ポリシー2件の削除を報告した。2026-10-18T03:21:21Z、communityとdmの現在のEC2ロールで専用バケットの既知の固定版GETを再実行し、両方がAccessDeniedとなることを確認した。書込み・削除の試行やバケット設定変更はしていない。IAM一覧のAPI再取得は行っていないため、ポリシー削除自体は利用者確認、読取り拒否は実測として区別する。非公開原本は `.local/object-lock-lab-20261018/policy-removal-check.json`。

試験権限の取り外しは確認済み。S3の試験用オブジェクト版と削除マーカーは残っており、保持期限後のデータ整理は未実施である。
