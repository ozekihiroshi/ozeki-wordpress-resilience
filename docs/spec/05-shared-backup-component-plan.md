# 共通バックアップ部品への移行計画

2026年10月18日。採用方針はADR 0004。以下は実装計画であり、M1完了後に追加する作業である。

| 順序 | 作業 | 完了条件 |
| --- | --- | --- |
| 1 | 共通部品の入出力契約を定義 | DBダンプ・転送・取得の成功/失敗、サイズ、ハッシュ、固定Version ID、ストリーム所有権と一時ファイル破棄の責任を明文化 |
| 2 | 既存実装とM1実装を同じ契約で検査 | WordPressなしの契約試験で差分を特定。既存の正常系・再試行・大容量対応を失わない範囲を決める |
| 3 | 小さい単位から共通部品へ抽出 | 共通ソースと固定版を用意し、既存プラグインの内部パス・起動処理に依存せず実行できる。対応PHP/AWS SDK版を明示 |
| 4 | Resilienceへ組み込み | 共通部品を同梱した配布物で収集・固定版取得が動き、別プラグイン不要。既存M1とは別記録で復元試験に合格 |
| 5 | 既存製品へ段階導入 | 互換性と変更範囲を報告し、既存の設定・履歴・CLI・保存形式を保った回帰試験に合格 |
| 6 | 形式の互換読込み・移行 | 既存の資産を検査して利用可能/不足を判定。元資産を保持し、保持削除との整合を確認 |
| 7 | 単独導入・併用対策を検証 | クリーン環境で各製品を単独導入可能。二重実行と異なる共通部品版の衝突を検知・制御できる |

## 最初の抽出候補

DBダンパーはすでに再利用しているため、既存コードから独立させる際の依存範囲を調べる。S3転送は既存S3StorageとM1 VersionedAssetStoreの比較から始める。関数名が似ていても、対象サイズ、再試行、条件付き保存、Version ID、チェックサム、ダウンロードの上書き防止などが異なるため、片方を単純コピーして標準とはしない。

メディアの個別ファイル形式とtar形式は、現時点で一方へ統一しない。まず資産記録の契約を共有し、一覧・完全性検証・取得の共通部分を抽出する。サイト全体の整合点と組合せはResilienceが判断する。

## M1初版公開との関係

GitHub初版はM1研究・開発版として保存する。共通化の完了を初版の実績として記載しない。公開範囲・ライセンス、環境固有設定、公開用証拠、ローカル準備スクリプトを含む再現手順を整える。初版の証拠は固定し、共通化後のコード・証拠と区別する。

共通化のために現在のS3資産を書き換えたり、既存Recovery Set IDを再利用したりしない。公開先GitHub remoteは未設定で、公開操作はまだ実施していない。
