# 保守技術者の3場面：机上ウォークスルー

> 設計経緯の文書です。配置・検証の選択肢は[最新の初期仕様](selectable-recovery-spec-jp.md)で具体化しています。提案が異なる場合は初期仕様を優先します。いずれも現行の実装動作を変更するものではありません。

[English](maintainer-tabletop.md) | 日本語

2026年10月22日。[運用設計案](maintainer-operating-model-jp.md)を、既存仕様と照合した設計上の机上検討です。実ユーザー参加、実操作、障害注入、7日間運転、時間計測は行っていません。「自動化案」は実装済みを意味しません。現行の承認・期限・失効検査を変更しません。

## 共通の前提と数え方

対象は技術者1名と代替担当が保守する、単一WordPress・既知の更新経路・ローカル資産・外部キューなしのサイト。例として日次取得、35日保持を置きますが、利用者の要求として確定した値ではありません。通常週はまず1サイト、反復負担を見るため5サイトへ展開します。業務停止上限、実効権限、予算、復旧目標は導入時に合意が必要です。

「判断」は方針・復旧点・例外・公開の選択。「作業」は設定、照合、転記、コマンド実行です。1判断に何回も操作が必要な場合があります。時間は未測定のため合計工数やRTOを算出しません。待機時間、手を動かす時間、外部承認待ちを今後別々に測ります。

比較は公開検証済みBackup for S3 0.4.0を基準とします。製品単体で足りることと、技術者がコード・構成・保管保護・復元手順を別途用意すれば足りることを区別します。両製品の併用や自動取込みは前提にしません。

## 場面A：導入から正常な1週間

想定入力：新規サイトを登録。期間中に構成変更、通知失敗、容量超過、侵害兆候はない。初期受入に失敗したら正常週へ進めません。

| 順序 | 人の判断・操作 | 自動化案 | 現在の到達点／詰まり |
|---|---|---|---|
| A1 資産を決める | 所有者がDB・files・外部依存・除外を確認。技術者は更新元を照合 | 棚卸しと非対応項目の抽出 | プロファイル・SSH棚卸し・導入前検査を再利用可能。不存在や未登録更新元を自動で完全証明できない |
| A2 運用方針を決める | 停止窓・最大停止・許容損失・保持・予算・担当／代替・通知を承認 | 一つの設定案と権限案を生成 | 個別仕様はあるが、取得から復旧までの統合導入は未提供 |
| A3 外部権限と配置 | 正規の管理経路で保管・復旧・署名権限を分離。導入計画を承認 | 対応構成へ配置、権限・接続・readbackを検査 | 設定生成は主に棚卸し／報告系。鍵、systemd、取得backend等の手作業が残る |
| A4 初回受入 | 検査結果と代替担当の独立アクセスを確認し、有効化を判断 | 取得→解除→固定版保存→独立検証→隔離復元を一つの試行として実行 | 部品と専用試験はある。限定SSH実取得、収集切断時解除、汎用導入は未確認。ここで現製品の無支援導入は詰まる |
| A5 1～6日目 | 正常なら操作しないことを目標とする | 日次検査・取得・保存・証跡・報告。安全な再試行のみ自動 | 日次機構は再利用可能。ただし現行はセット承認と短期台帳の手動運用が残り、無操作にはならない |
| A6 復元試験と7日目 | 週次要約の例外・目標との差を判断 | 合意頻度で隔離復元、全サイト要約、期限・容量傾向の表示 | 復元worker／報告はあるが、無人の統合試験・横断要約・新しい署名方針は未完成 |

導入の判断を4束にまとめます：(1)資産と対応範囲、(2)サービス目標・費用、(3)権限・信頼・担当、(4)初回受入と有効化。これで4クリックになるわけではありません。実際の証拠確認と管理者への依頼は必要です。

**正常週の反復負担（条件付きの算数）**：毎日1セットを新たに承認する運用なら1サイト7件、5サイト35件のセット承認が生じます。現行案の台帳確認を1日2回採用すると管理対象一式につき週14回の確認・配布機会です。1ホストあたりinspect→validate→apply→inspectの4段階なので、対象Hホストなら週56H段階の処理になります。バッチ化できても、現行文書では人の確認を必要とします。台帳を共有する場合もあるため14回を自動的にサイト数倍しません。7日期限の担当者確認がこの週に切れるなら別途再確認が必要で、数は期限配置に依存します。障害調査・USB・初回設定・復元試験の操作はこの算数に含めていません。

設計目標は通常週のセットごとの人作業0、全体で週1回の要約確認です。前案の「5サイト10分以内」は未検証の目標のままです。達成には、独立した自動検査証跡、新しい承認方針、認証された台帳配布、統合表示が必要です。35件を一括で承認するボタンだけでは、判断負担を解決しません。

Backup for S3だけで足りる条件：DB/mediaを対象に技術者が構成・ソフトウェアと手動復元を管理でき、媒体取得の周期・更新停止を自分で調整できること。標準の日次設定はDB用で、uploadsの一般向け自動定期化やRecovery Setの一般向け作成は未提供です。「入れるだけで毎日サイト全体」という比較はしません。Resilience案の差は、その調整と復旧準備まで継続運用として引き受ける点です。

判定：現状は開発者支援付きで部品を評価できる段階。提案後の無操作週は条件付きで成立し得るが、未実証です。手動承認を減らす契約を決めないまま導入UIだけ作っても目標には届きません。

## 場面B：保存元喪失

想定入力：昨日の復元検証済み候補があり、今朝、保存元へ接続できない。外部保管・独立管理元・復旧担当のアクセスは生きている。ただし、単なる故障か侵害かは最初から断定しません。

| 順序 | 人の判断・操作 | 自動化案 | 現在の到達点／詰まり |
|---|---|---|---|
| B1 検知・一次判断 | 影響と侵害兆候を確認。担当を割り当てる。疑いがあれば場面Cへ | 古い報告を正常扱いせず警報。最後の候補・時刻・失われ得る更新を提示 | watchdog・鮮度・永続通知を再利用可能。元WPがなくても見る統合入口は未完成 |
| B2 進行中の取得を照合 | 保存元が本当に消失したのか、接続だけ切れたのか確認 | 部分取得を成功にしない。PUTの結果は読戻しで照合し、不明なら保持 | unknownと重複抑制はある。実限定SSHの切断後解除は未確認。保存元が生きている場合は保存元自身で解除が必要 |
| B3 復旧点を選ぶ | 候補の取得時刻、許容損失、失効・保持・検査結果を見て選択 | 最新取得と最新の利用可能候補を区別し、復旧条件を検査 | 固定版・署名・台帳検査は再利用可能。保存が昨日でも最後の承認済みが3日前なら損失評価は後者が基準 |
| B4 隔離再構築 | 必要な資格情報の交換・外部依存を確認 | 元サイトを参照せず取得・展開・再構築・基本試験・結果登録 | 専用fixtureでは確認済み。一般向け復旧入口、必要コード／構成の再現、実対象向け隔離は未完了 |
| B5 再公開 | 技術者が内容を検査し、サイト責任者が公開可否と業務上の損失を承認 | 検査報告と切替案を準備。DNS・通信・副作用の再開は承認前に行わない | 手順はあるが統合された本番切替機能ではない |

判断は少なくとも4束：(1)事故分類・担当、(2)復旧点と許容損失、(3)構成・資格情報の扱い、(4)業務確認と再公開。例外があれば増えます。自動化は転送・照合・構築・記録の反復を減らしますが、内容確認や顧客承認の時間は消せません。RTOは未計測で、データ量・環境準備・独立管理元待ち・人の承認を別に測る必要があります。

対照分岐：収集側だけが停止し保存元が動いている場合、復元より停止解除・サービス継続を優先します。収集側のfinallyが動くことを前提にしません。解除未確認の取得は採用せず、結果照合前に同じ取得を再実行しません。

Backup for S3だけで足りる条件：独立したS3アクセスと資産識別情報があり、別途保管したソフトウェア／構成とDB/mediaから技術者が復元できること。WordPress内の履歴だけを頼りにしていた場合は不足します。0.4.0の専用復元試験は一般向け復元UIの完成ではありません。Resilience案はこれらの散在した準備と操作を統合し、元サイト不要を受入条件にすることに価値があります。

判定：既存の復旧部品は有用。ただし「元サイトに接続せず、別担当者が一つの入口から進める」という提供形態は未完了です。S3から読めたという試験だけではこの場面を合格にできません。

## 場面C：侵害疑いと管理元不通

想定入力：サイトに不審な変更。直近取得も汚染の可能性がある。S3の過去資産と復旧ホストは読めるが、独立した信頼管理元に接続できない。ローカル台帳は期限切れか、今回の事象より前の状態で、未反映の失効がないと確認できない。「管理元不通」と「管理元侵害」を区別し、理由不明ならどちらも除外しません。

| 順序 | 人の判断・操作 | 自動化案 | 現在の到達点／詰まり |
|---|---|---|---|
| C1 対応範囲を決める | 元サイト、収集・署名鍵、管理元のどこまで疑うか判断。証拠保全と封じ込めを承認 | 通知をまとめ、履歴を保持。疑わしい新取得を自動で「安全」としない | 通知・台帳はある。侵害判定や全鍵の失効・資格情報交換は自動実装済みではない |
| C2 過去資産を守る | 信頼できる経路から保管権限・保持状態を確認 | 自動削除を進めず、候補・試行・不明状態を保全 | 原則を再利用。保持は実効権限次第で、全管理アカウント侵害への保証ではない |
| C3 現在の権威を確認 | 別経路・代替担当で管理元へ到達可能か確認。管理元自体の侵害なら再確立へ | 不通・期限切れ・失効確定を分けて表示。署名期限や台帳を延長しない | 期限切れ台帳では現行復旧入口はGET前に停止。署名が正しくても通れない |
| C4 分岐を決める | A:信頼管理を復旧して通常手順へ。B:事前設計された独立オフライン手順。C:安全に判断できず保留 | 現状はAを支援できる部品のみ。Bの代行はしない | Bは未設計・未実装。古いUSBだけで最新失効を知ることはできない。最悪時には復旧期限を約束できない |
| C5 復旧点を調べる | 侵害時期・影響・鍵を調査し候補を選ぶ。業務責任者が再公開を判断 | 適切な隔離で検査し、差分と根拠を提示 | 無感染判定はできない。管理元が復旧しても最新セットを自動選択してはいけない |

この場面の判断は少なくとも5束で、調査の分岐により増えます。操作時間の上限は出せません。自動化できるのは記録保全、候補一覧、通信診断、認証された照合、検査報告です。「現在の失効情報がない」という欠落を自動化では埋められません。

期限内のローカル台帳があれば現行実装で通る場合もありますが、管理元の最新状態と一致することや、侵害後に安全であることの証明にはなりません。この机上例は期限切れで停止する分岐を通しています。安全なオフライン調査が必要なら、現行GET前検査の回避として扱わず、証拠取得・実行・再公開の各権限と隔離条件を別途定義する必要があります。

Backup for S3だけの場合：独立アクセスと必要資産があれば、技術者は台帳サービスの期限に依存せず手動復元を試みられることがあります。しかし、取得可能なことは正常世代・改ざんなし・失効なしの証明ではありません。Resilienceのゲートは古い権威での復旧を防ぐ一方、管理元不通時の復旧可能性を下げ得ます。**ゲートが厳しいだけでは、全体としてレジリエンスが高いとは限りません。** 保護できるものと失う可用性を明示して選ぶ必要があります。

判定：本設計の中心的な未決事項。Bのオフライン権威を構成するか、独立管理元の復旧・冗長化で対応するか、復旧待ちを契約として許容するかを決めない限り「侵害時にも必ず復旧できる」とは説明できません。どの案も今回採用・実装はしていません。

## 3場面から得られた設計上の結論

| 優先して決めること | 理由 | 既存機能の使い方 |
|---|---|---|
| 自動検査証跡と人の承認の責任 | 場面Aの反復負担と、場面Bの利用可能候補の古さに直結 | ハッシュ・固定版・日次台帳を流用。署名の意味は新たに定義 |
| 管理元不通時の復旧契約 | 場面Cで実際に停止する | 現行台帳検査を維持し、別経路・オフライン方針を先に設計 |
| 一つの対応構成と外部復旧入口 | 全場面で個別ツールを組み立てる負担が残る | preflight、復元worker、通知、結果登録を統合する案 |
| 限定SSH取得・保存元自身の解除 | 導入受入と切断分岐で未確認 | 既存の取得・リース試験を再利用した限定検証が必要 |

機能追加の順番をまだ確定しません。まず「正常な週に人を呼ぶ理由」と「管理元不通でも何を許せるか」を仕様として選び、その後に上記3場面を第三者の保守技術者と紙上で確認します。計測項目は判断束・入力／コマンド数・支援依頼・実作業時間・待機時間・復旧結果です。第三者の確認を済ませたとは記録しません。

Backup for S3で十分な運用を無理に置換しません。日常バックアップ／手動復旧の正しさは同製品の改善としても扱えます。Resilienceは、独立した保護・状態把握・復旧の一連の仕事を引き受け、その追加コストより利用者の負担と復旧リスクを減らせる場合に選ぶ製品として評価します。
