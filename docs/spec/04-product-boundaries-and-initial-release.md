# 既存バックアップ製品との責任分担と初版の位置づけ

2026年10月18日。利用者の合意により採用した製品構成方針。共通部品への抽出や単独導入パッケージの実装はこれから行う。

## 採用する関係

Ozeki Database Backup for S3はバックアップに目的を絞った製品として維持する。Ozeki WordPress Resilienceはバックアップ機能を内包し、サイト全体の復旧準備・独立復元・検証まで提供する。両製品は別プラグインのインストール・有効化を必須とせず、それぞれ単独で導入できる配布物を目指す。DBダンプ・圧縮・転送・照合などの共通処理は、版を固定した共通部品として各配布物へ組み込む。利用者による共通部品の追加インストールは不要とする。

通常バックアップだけを必要とする利用者は既存製品だけを使える。Resilienceの平常時の収集・設定はWordPress側、障害時の復元はWordPress外のツールが担う。復元は元プラグインの稼働や内部履歴に依存させない。現在のM1は既存プラグインの固定コミットとローカル依存物を利用しており、この単独導入構成はまだ実装されていない。

## 実装の現状

| 対象 | 現状 | 採用する責任分担 |
| --- | --- | --- |
| DBダンプ | M1は既存PhpMySqlDumperを直接利用 | 共通部品へ抽出し、両製品から同じ契約で利用する |
| メディア収集 | 既存製品は個別ファイルのインベントリと転送。M1はtarで別収集 | 列挙・読取り・照合の共通化を検討し、格納形式と整合性方針は製品側で選ぶ。既存形式の読込みは互換アダプターで扱う |
| S3 PUT・ハッシュ照合 | 両方に実装あり | 共通転送部品を定義し、既存側の互換性を保ちながら重複を減らす |
| 固定Version ID GET | M1側に必須検証付き取得を実装 | WordPress外でも使える転送部品として整理。共通化の単位は契約試験後に決定 |
| Recovery Set | 既存側は主にDB・メディアの収集単位。M1側はコード・構成・実行環境まで含むサイト全体の組合せ | 別階層として定義し、既存セットID・原文ハッシュ・固定版を上位RAMから参照。既存形式を無断変更しない |
| 観測・Evidence | 既存側にもRecoveryObservationがある。M1はE1/E2/E3を記録 | 保存側の申告と外部観測・実復元を区別し、証拠の形式と所有者を整理 |
| Bootstrap・独立復元・機能検査 | M1で実装・2回検証 | Resilienceの中核 |
| 権限分離・信頼の起点・復旧評価 | Resilienceが仕様を持つが一部未達 | Resilienceが設計・検証を担当 |

根拠：docs/m1/01-existing-backup-capabilities.md、lab/m1/fixture/capture-database.php、tools/capture-m1-assets.py、src/VersionedAssetStore.php、tools/run-independent-recovery.py。既存製品の調査基準はコミット627e47c2b31527ef1486e582b79fd5dba875843f。

既存製品にもRecoveryCollector、RecoveryPipeline、RecoveryPublisher、RecoveryObservationが存在するため、「既存は保存だけ、新製品だけが復旧を扱う」という説明では実態を表せない。役割の境界を製品名だけでなく、実行主体・対象資産・公開契約で確定する必要がある。

## 連携契約で決めること

共通部品が生成する資産記録について、種別、サイズ、SHA-256、bucket/key/Version ID、取得期間、整合性、完了・失敗状態の契約を定める。両製品は同じ資産記録を利用できるが、成功の判定条件は各製品が持つ。Resilienceは全必須資産の組合せを検査してサイト全体のRAMを固定する。null版や未完了の収集を復旧準備完了と扱わない。旧形式の互換読込みは別途アダプターで実装し、既存バックアップ全てを自動で復旧可能とは扱わない。

既存製品の現在の内部クラスをそのまま安定APIと宣言しない。まず共通部品の入出力契約と契約試験を用意し、既存実装とM1実装の差を整理する。必要な既存側改修は別の変更として互換性と責任範囲を説明する。

保持・削除も境界になる。上位セットが参照している固定版を、下位の保持処理が消してよいかを決める必要がある。単にVersion IDを返すだけでは連携は完成しない。

## 初版の位置づけ

GitHub上の別リポジトリozeki-wordpress-resilienceに、v0.1.0-alpha相当のM1研究・開発版として記録する。インストール可能な完成版WordPressプラグイン、既存バックアップ製品の後継、全攻撃への耐性を実証した製品とは表現しない。

初版の成果は、固定版の外部資産を使い、元アプリ停止後に新規ボリュームへ2回復元し、動作を検証できたこと。共有IAMロール、同じWSLホスト、署名未実装、環境固有設定という制限をREADMEに明記する。

初版公開時に以下を整備した。公開先はhttps://github.com/ozekihiroshi/ozeki-wordpress-resilience、M1タグはv0.1.0-alpha。将来の配布版でも以下を継続して管理する。

- リポジトリの公開範囲とライセンス、依存物の扱いを確定する。
- AWSアカウント・バケット・インスタンス・SSH接続名などの環境固有値を設定へ分離し、公開用サンプルを用意する。
- 実測証拠の原本は保持し、公開する記録から実環境の識別情報を除いた別の公開版を作る。原本のハッシュや値を置換して元の証拠と称しない。
- 現在.local内にある梱包準備処理を含め、別の開発者が依存取得・梱包・試験できる入口を整える。現状はクローンだけではM1を再現できない。
- 重複している収集・転送処理を暫定M1実装として明記し、共通部品への移行課題を登録する。

リポジトリを分けることと、同じ機能を二重保守することは別である。初版では実証成果を保存し、その後は共通バックアップ部品への抽出を優先する。共通コードの保守元は一つとし、配布時には各製品へ固定版を組み込む。共通部品のリポジトリ・パッケージ名は未決で、既存製品を廃止する決定はしていない。
## 同時利用と移行

初期の推奨運用は同一サイトでどちらか一方を選ぶこと。二重スケジュール・保存先の競合・保持削除の衝突を避けるため、将来の配布版には併用検知と明示的な移行案内を設ける。自動で相手をインストール・有効化・停止・削除しない。既存設定・バックアップの移行は、元データを保持して検証する別機能として扱う。

共通部品を両方が同梱した場合のクラス名衝突や異なる版の混在も、配布前の検証項目とする。片方が先に読み込んだ版へ暗黙に依存する設計にはしない。
