# 通知先・対象警報の設定と、通知機能自身の監視

版：2026-10-19。通知先を利用者が選択できることを製品要件とする。Pushoverは初期アダプターであり必須契約ではない。community、dm、特定のAWS/Googleアカウントは検証事例であり、製品の前提にしない。

## 利用者が設定する内容

WordPress管理画面に「Resilience → 通知」を設ける案とする。初期画面を専用環境で実装済み。設定候補の保存と、外部側で初回反映した配送状態の表示までを扱う。[実装範囲](../guides/wordpress-notification-admin-lab.md)。

|設定|内容・初期方針|
|---|---|
|通知先|表示名、方式、宛先、利用状態。複数登録可能。内部では変更しない宛先IDを使う|
|方式|実装済みの方式だけ選択可能にする。現在の専用環境はSMTP/Pushover。LINE・Slack・PagerDutyは今後のアダプター|
|対象警報|宛先ごとに選択。初期案は詳細・履歴をメール、重要警報をプッシュ。発生と解消を対で扱う|
|確認を求めるか|確認機能を持つ方式のみ設定可能。メールの受付を人の確認と表示しない|
|再通知|間隔と期限。方式側の制限に合わせて検証。夜間抑制は重要警報の取り扱いも明示|
|通知障害の連絡先|通常配送と別の監視・配送経路。通知失敗を同じ失敗中のキューだけへ送らない|
|試験|利用者が明示してテスト送信。送信受付と端末での受信・人の確認を分けて表示|
|運用状態|最後に処理が完了した時刻、配送待ち、失敗・結果不明、確認待ち・期限切れ、外部監視の接続状況|

資格情報は保存後に再表示せず、置換・失効を扱う。送信元の秘密値、受信者の個人情報、Pushover User Key等を診断レポートへ含めない。設定変更は権限を持つ管理者だけが実施し、変更者・時刻・設定版を記録する。一般利用者からの設定変更や試験送信を許さない。外部監視の秘密値をWordPressへ配布する設計にはしない。初期管理画面は管理者権限・nonceを検証し、秘密値を保存せず外部接続設定名を保持する。秘密値の登録支援と設定版移行は今後の作業。

設定画面で「保存済み」「試験済み」「有効」を区別する。保存だけで配信可能と表示しない。重要警報の宛先がなくなる設定には明確な警告を出す。すべての通知を無効にする場合は、利用者がその状態を理解して選べるようにし、健全な監視構成とは表示しない。

## 警報の分類と初期配送

|利用者向け表示|内部の種類|初期案|
|---|---|---|
|バックアップ未取得|backup_missing|プッシュ＋メール|
|バックアップ失敗・結果不明|backup_failed / backup_unknown|プッシュ＋メール|
|署名承認待ち|approval_pending|メール|
|承認期限切れ|approval_expired|プッシュ＋メール|
|復元試験失敗・未完了|restore_failed / restore_incomplete|プッシュ＋メール|
|監視元の読み取り失敗|source_unreadable|プッシュ＋メール|
|監視停止・生存記録不正|monitor_stopped / heartbeat_invalid|独立watchdogの経路|
|通知機能の異常|notification_delivery_failed|独立watchdogの経路。詳細には下記の原因を表示|

解消通知は発生時の宛先と事件の対応を保持する。送信取消は既に届いた通知の削除ではなく、サービス側での繰返し通知の停止。確認操作と、障害解消、署名承認、復元の許可は別々の状態として扱う。

## 失敗を見落とさない判定

|状態|判定と扱い|
|---|---|
|宛先の初期化・認証設定読み取りに失敗|channel_configuration_failed。送信待ちが0件でも異常|
|配送拒否|delivery_rejected。即時に異常として残す|
|配送結果が不明|delivery_unknown。応答喪失等。重複送信を避け自動再送しない。照合が必要|
|配送待ち・再試行が長期化|delivery_backlog。初期300秒。再起動しても待ち時間をリセットしない|
|確認照会・取消に失敗|receipt_check_failed。警報が止まった、確認されたとは扱わない|
|人の確認が期限内にない|ack_overdue。初期300秒。配送失敗とは別の原因として表示|
|サービスの再通知期限が終了|ack_expired。未確認を正常終了と扱わない|
|配送処理が完了しない・停止した|最後の正常完了記録が初期900秒途絶えたら独立watchdogが検知|

配送の「accepted」はサービス受付。人の確認があるサービスのみ「acknowledged」を表示する。元の事件が解消された場合、過去の確認期限切れは履歴に残し、現在の未対応として警報し続けない。一方、結果不明や配送拒否は解消通知を送れたことだけで消さず、照合・対応の記録を必要とする。

## 監視経路と循環防止

配送ワーカー → 秘密値を含まない健全性レポートと生存記録 → 独立watchdog → 別の配送経路、という構造にする。WordPressの画面に警告を出すだけでは、サイト停止時に気付けない。通常配送の状態DBとwatchdogの事件・配送DBを分け、通知失敗を通常outboxへ戻して無限に警報を作らない。

専用環境では既存watchdogのheartbeat契約を使う。`undelivered`には「未配送数」ではなく「未解消の通知健全性条件数」を渡し、`notification_delivery_failed`で通知機能の異常を表す。原因別詳細は`delivery-health.json`に保持する。外部へ渡す完了時刻は転送時刻に置換しない。

健全性ファイルの生成は配送処理が一巡した後だけ。入力台帳の読み取り失敗、設定不整合、プロセス異常終了では新しい正常完了時刻を作らない。watchdogは欠落・古い記録・不正な記録を異常として扱う。

独立watchdog側の送信失敗もその専用outboxに保持し、再試行する。watchdog自身の停止や両経路同時障害を検知するには、さらに外部の生存監視が必要。今回はその外部サービスの配置や接続はしていない。同一ホストの専用環境試験を、実ホスト障害に対する独立性の証明とは扱わない。

## 設定変更と未配送記録

製品版は設定版を管理し、過去の事件の宛先、未配送記録、receiptを保持したまま変更する。宛先の追加で過去の全事件を無断再送しない。宛先削除時にも、未確認の緊急通知や取消処理の扱いを確定する。既存の設定版で発生した処理を新しい資格情報・別宛先へ黙って付け替えない。

現在の専用環境は設定を固定し、変更を検出すると停止する。設定を変えるために状態DBを削除しない。今回追加する健全性用テーブルは既存の配送記録とreceiptを保存したまま作成する。旧記録に取得できない開始時刻がある場合、最初に健全性監視した時刻から猶予を測る。unknown/rejected/expiredはその初回から検知する。

## 実装範囲

今回：設定値検証（対応済み方式、宛先IDの重複、対象警報名、空の選択、閾値）、宛先別の健全性レポート、生存記録、既存独立watchdogとの連携試験、停止・復帰・監視側配送失敗の永続化試験。

管理画面は初期版を実装済み。引き続き未実装：設定版の移行UI、unknownの照合操作、LINE/Slack/PagerDutyアダプター、当番・多人数へのエスカレーション、実ホストへの配置・定期起動・外部サービスによるwatchdog監視。新しい実通知は送信していない。

利用者の選択肢を増やす際は方式ごとの能力（送信、確認、取消、引継ぎ）を表示し、ない能力を擬似的に成功扱いしない。電気設備監視に展開する場合は、設備・顧客ごとの宛先分離と権限・当番・監査・送信量を別の要件として追加する。

## 稼働設定切替・テスト送信の実装（2026-10-19）

[仕様と手順](../guides/notification-live-switch.md)。切替前のイベント・旧経路・認証情報コピーを保持し、新規警報だけ新経路へ送る。解消は旧経路にも戻し、確認・取消を継続する。設定保存と外部の明示適用を分離。管理画面のテストは識別子のみを要求し、外部で設定版・有効宛先・期限・頻度を再検証して通常優先度で送る。過去のテスト結果を新版の成功と扱わない。版移行の外部CLIとテスト要求UIは実装済み。自動移行UI、外部ホスト間の要求・レポート転送、本番配置、旧経路整理、本人による受信確認は引き続き対象外。

## 外部ホスト間のテスト要求・結果転送（2026-10-19）

[受渡し仕様](../guides/notification-transfer.md)を専用環境で実装。転送受領とサービス受付を分ける。要求の同期保存後にID・ハッシュを応答し、応答喪失時は元要求を残す。再送は同一性を照合し、処理済み要求の再取込みを防ぐ。受信ユーザーはワーカーの鍵・配送DBを読書きできず、公開用結果も書換え不可。ホスト鍵固定・専用SSH鍵・固定コマンド・入力上限を使用する。結果の完了時刻を転送時刻へ更新しない。本番の鍵割当て・タイマー・転送停止監視・台帳整理は残る。

## 定期実行・停止監視（2026-10-19）

[実装仕様](../guides/notification-runtime.md)。成功した転送時刻を次のSSH交換で保持・転送する。ワーカーは取込異常でも通常処理を継続し、周期の完了時刻と異常を区別する。外部watchdogはrole別の永続台帳で停止・復帰を判定し、独立したPushover等の配送状態を持つ。初期値は60秒周期（監視30秒）、停止判定300秒。専用環境では1秒周期・8秒判定で試験。systemdサービス・タイマーは構文検証のみ、本番常設化とさらに別ホストからのwatchdog監視は未配置。
