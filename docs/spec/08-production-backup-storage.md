# 実バックアップの保管・保持・管理権限仕様

版数：0.1 / 更新日：2026年10月18日
状態：初期設計。AWSへの適用・本番移行は未実施。利用者が初期案として毎日1回・35日保持を選択した。これは初期設計の基準であり、本番への適用は別途行う。

## 1. 対象と保護の範囲

保存元のWordPress管理者権限、プラグイン、保存元EC2のロール資格情報が侵害されても、保持中の既存固定版と独立した承認記録を失わず、別環境から復旧候補を取得できることを初期要件とする。

専用Object Lock試験で、削除Allowを持つ保存側からのGovernance保持版の削除・保持短縮を拒否し、通常削除のマーカー作成や上書き後もdmから元の固定版を取得できた。ただし試験用の特定キー・ポリシー・主体での実証であり、実運用への適用完了ではない。

署名は承認記録の真正性・完全性を確認する。感染前の状態であること、長期潜伏を発見できること、漏えいを取り消せることを保証しない。Governanceを回避できる管理者、署名端末、AWSアカウント全体の侵害は初期の保護範囲外として表示する。ホスト上の別資格情報や他ホストへのSSH経路も移行前に点検する。

## 2. 保管先

| 項目 | 初期方針 |
| --- | --- |
| 資産の保管 | 東京リージョンの新しい実バックアップ専用S3汎用バケット |
| 既存バケット | ceri-link-resilienceはM1実証記録として維持。Object Lock試験バケットも実バックアップへ転用しない |
| バケット名・所有アカウント | 運用環境を決める段階で確定。既存AWSアカウントを利用する方針を利用者が選択済み。別アカウントでの保管と同等の分離とは表示しない |
| 基本設定 | Versioning・Object Lock有効、ACL無効、全パブリックアクセス遮断、TLS必須 |
| 暗号化 | 初期案はSSE-S3。顧客管理KMS鍵を使う場合は鍵の保護・独立した復号権限・削除防止も追加要件 |
| キー構成 | sites/<site-id>/sets/<unique-set-id>/配下へ新規保存。同名の最新版を復元起点にしない |
| 固定情報 | bucket・region・key・Version ID・サイズ・SHA-256・保持モード・保持期限を資産ごとに記録 |
| 信頼の起点 | 保存元/復旧先とは別の端末で署名。独立配布する公開鍵・失効状態・承認ハッシュ/世代を復旧先で管理 |

セットはDB、コード、テーマ、プラグイン、メディア、必要な構成、復旧手順と実行環境の定義を含む。RAM・Recovery Set・Bootstrap・証拠も保護対象とする。旧環境の本番資格情報を復元環境へそのまま持ち込まない。

初期版はセット単位で必要な資産が揃う構成とし、保持期限の異なる共有資産・差分バックアップへの依存は導入しない。共通化・重複排除を導入する場合は、参照している全セットより先に共有資産が失効/削除されない契約と試験を追加する。

## 3. 頻度と保持

| 項目 | 暫定案／要件 |
| --- | --- |
| 定期取得 | 毎日1回。時刻・タイムゾーンは対象サイトの運用に合わせて設定 |
| 最低保持 | H=35日。利用者が初期案として選択。各オブジェクト版の保存時から保持する |
| 追加取得 | 重要な更新・移行前に別セットを取得。通常取得を置き換えない |
| 保持モード | 初期方式はGovernance。保存側と復旧側にbypassを明示禁止 |
| 保持開始 | 本番ではバケットのデフォルト保持を使用し、保存完了後に後付けする無保護時間を作らない |
| 個別上書き | 保存側のPutObjectRetention/PutObjectLegalHoldを禁止し、明示的な短い保持指定によるデフォルト設定の上書きを拒否する試験を行う |
| セットの利用期限 | 全必須資産・メタデータの保持期限の最小値。最後に保存したファイルの期限だけでセット全体を評価しない |
| 長期保管 | 月次・年次保管は初期確定範囲外。必要なら別の保持クラスと費用を定義 |

H日保持は「H日前まで必ず正常な復旧点がある」という意味ではない。各取得の成功・承認・復元可能性を別に確認する。取得失敗で世代が欠けた場合は不足を表示する。実際の失われ得る更新時間は、選んだ復旧点の整合した取得時刻から障害時刻までであり、毎日実行するだけでRPO24時間達成とは扱わない。

バケットの保持日数変更は既存版の保持を自動調整する仕様にしない。延長が必要な既存版は、独立した保管管理者が対象と理由を確認して操作し、再取得した保持状態を記録する。標準の自動運用では短縮・bypass・Legal hold解除を行わない。Compliance方式へ切り替える場合は、解除できない保持期間・費用・誤設定への対応を別途決定し試験する。

## 4. 権限の分離

実運用の名前は候補。既存のmy-ssm-roleの他業務ポリシーを流用・削除して組み替えるのではなく、実運用環境に必要な役割を定義して移行する。EC2のロール付替えはSSM等の既存運用への影響確認後に行う。

| 役割 | 許可すること | 禁止・分離すること |
| --- | --- | --- |
| 保存側（OwrBackupWriter候補） | 対象サイト配下への新規PutObject、必要最小のmultipart操作、必要な設定読取り | 通常/版削除、保持・Legal hold変更、bypass、バケット設定変更、IAM変更、復旧/管理ロール取得 |
| 独立した確認・復旧側（OwrRecoveryReader候補） | 承認した固定Version IDのGetObjectVersion、保持状態確認、必要範囲の設定読取り | 書込み・削除・保持変更・bypass・IAM/バケット管理。本番WPの資格情報は持たない |
| 保管管理者 | バケット設定、保持延長、期限後の管理された整理 | 資格情報を保存元/復旧サーバーに置かない。通常運用にbypassを含めない |
| 署名担当 | 独立検証結果のレビュー・承認、署名鍵/失効/承認世代管理 | 秘密鍵をWordPress、community、dm、復旧アーカイブへ保存しない |
| 緊急管理 | 管理者による障害対応・設定修復 | MFA付きの独立ログインを使用し、通常ロールから取得不可。例外操作は理由・対象・影響を記録 |

保存側・復旧側のオブジェクト削除やbypassは、identity policyに加えてbucket policyでも対象Principalを限定して明示Denyする方針とする。バケット管理者自身が変更できるため、これをアカウント管理者侵害への保護とは説明しない。

ポリシーはActionだけでなくResource・Condition・信頼ポリシーを確認する。SSM、EC2 instance profile、IAM PassRole、Parameter Store、SSH鍵などを介して別主体の権限を得る経路を含む。Permissions boundaryは権限を付与するものではない。必要なら上限として設計するが、単独で独立性を認定しない。

保存側には実験時と異なり、S3固定版の読取りを必須にしない。転送の受付と独立側の再取得・ハッシュ照合を分離する。版指定なしGETを復旧経路に使わない。

## 5. 保護・承認・復旧の状態

1. 保存受付：各資産を新規キーへ保存しVersion IDを記録する。
2. 保護確認：独立側で各版のサイズ・SHA-256・保持モード・期限を確認する。不足や保護未適用は「保護済み」と表示しない。
3. セット成立：必須資産と整合性が揃い、参照固定版が取得できることを確認する。途中失敗セットは復旧候補に自動採用しない。
4. 独立承認：署名担当が対象セット・期限・世代・検査範囲を確認して署名する。汚染検査未実施なら明記する。
5. 復旧検査：独立配置したツールで署名・失効・期限・世代・対象と実際に使うBootstrapを検証し、隔離した新規環境へ復元・機能確認する。
6. 再公開判定：侵入原因、資格情報/セッションの更新、健全性と事業機能を確認して承認する。復元成功だけで自動公開しない。

保持期限と承認期限は別物である。M1で使った7日有効の署名を、35日/90日の保管仕様へそのまま流用しない。運用上の承認有効期間は別に設定し、資産の利用可能期限を超える利用保証をしない。期限切れ時は検証を省略せず、独立した記録から再評価・再承認し、新しい世代を配布する。

手元PCでの署名は初期の運用候補であり、毎日の自動承認は未実装。PCが停止していても保存・保持は継続できる構成とするが、未承認セットを承認済みと表示しない。初期パイロットでは担当者が日次レビューを行う。自動化する際は独立した署名サービスと管理責任を設計し、保存元へ秘密鍵を移さない。

## 6. 期限後の整理と監視

初期パイロットでは削除Lifecycleを設定せず、独立管理者による一覧・参照関係確認と承認で期限後の版を整理する。保持終了だけで自動削除されるとは扱わない。削除マーカー・未完了multipart・未成立セットも管理対象とする。後日のLifecycle導入は、固定版参照と最新の正常候補を壊さない試験後に設定する。

侵害調査中は整理を停止し、必要な版の保持を期限前に延長する。すでに削除された版は保持延長で戻らない。正常候補を特定できない場合は復旧可能と表示しない。

保存元と独立した監視で、取得遅延・欠落、期限/保持不足、ポリシー・ロール・バケット設定の変更、容量/費用の増大、削除・bypassの試行を検出する。CloudTrailデータイベント等の対象・費用・通知先は導入時に決定する。保存元が侵害されると大量保存による費用増加も可能なので、予算通知・容量変動・頻度制限を設ける。

費用は1セットの圧縮後容量S、日次回数F、保管日数H、未整理/失敗分、実行環境アーカイブ、API/検証取得を実測して見積もる。全量方式の概算容量はS×F×Hだが、初期の手動整理ではH日以降も増える。保持済みデータを費用都合で途中削除できる前提にはしない。価格の確定見積もりは今回行っていない。

## 7. 実運用へ移す受入条件

- 運用バケット名・所有アカウント・対象サイト・H日・頻度・担当者・費用上限を決定する。
- 保存と同時にデフォルト保持が付くこと、短い個別指定が拒否されること、全必須版の保持状態を確認する。
- 保存側/復旧側から通常削除・版削除・保持短縮・bypassを拒否し、独立側から固定版を取得できることを専用canaryで確認する。
- バケット設定・IAM・他ホストへの権限取得経路をレビューし、保存側から保護を解除できないことを確認する。
- 秘密鍵の独立保管、USB復旧、鍵更新/失効・承認更新、担当者不在時の引継ぎを試験する。
- 保存元停止後の完全復元と事業機能確認を行い、測定範囲付きのRPO/RTO評価を記録する。
- 取得失敗、署名期限切れ、Object Lock未適用を表示・通知でき、初心者が未達を安全と誤認しないことを確認する。

古いM1セットは既存保管状態のまま証拠として残す。移行では新しいセットを専用バケットへ保存し、固定版取得・保持・承認・復元の成功を確認してから新方式を運用開始する。既存バックアップを先に削除しない。
