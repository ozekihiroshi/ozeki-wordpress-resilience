# サイバー侵害を想定した製品コンセプトと公開判定

> Release preparation (2026-10-26): [current distribution scope](../releases/wordpress-org-preparation.md) supersedes earlier research gates and draft-only recovery claims. Recovery now preserves saved post status; network exposure is controlled by the target operator. Historical test results below describe their original builds.

更新日：2026年10月19日
状態：公開前レビューに署名ゲート経由の実復元結果を反映。包括的な侵害耐性の合格記録ではない。

## 提供する価値

Ozeki WordPress Resilienceは、侵害や障害によって本番WordPressが利用不能になっても、復旧資産と復旧手段を残し、信頼を確認した環境で必要な事業機能を再建するための製品を目指す。

「たとえやられても、立て直す能力を失わない」を設計目標とする。停止ゼロ、データ損失ゼロ、あらゆる感染の除去、情報流出の取り消し、無条件の復旧保証を意味しない。対象脅威、保管期間、復旧点、権限境界、復旧時間と失われ得る更新を明示する。

感染予防も必要である。更新、認証、権限、ホスティング側の対策と組み合わせる。Resilienceの中心は、侵害後も復旧能力を保持し、再感染の原因を残したまま再公開しないことである。独自の万能なマルウェア検出・自動除去エンジンは現段階の提供範囲に含めない。

依頼サイトで見かける除去依頼は需要を調べるきっかけにはなるが、感染率・市場規模の根拠として扱わない。

## 今回確認した実装と限界

初回レビュー後、dmの復旧専用ロール切替・固定版取得と専用canaryの書込み/削除拒否、手元PCの署名鍵と暗号化USBコピー、必須署名ゲートを通したWSL実復元を追加確認した。各試験は対象・権限・範囲を限定する。続いて実サイト候補のS3固定版・35日保持・独立署名・隔離復元・USB公開信頼情報の読戻しまで確認した。実マルウェアと間接的な権限昇格は未検証。

| 確認項目 | 現在の状態と根拠 | 公開時に説明できる範囲 |
| --- | --- | --- |
| 元サイトなしの復元 | M1は元アプリ・DB停止で復元。実サイト候補は保存元に接続せずS3固定版から新規隔離復元 | 模擬・実サイト候補の基本復元を実証。保存元ホストや担当者の喪失を含む全手順の独立性は未証明 |

## 製品公開の受入条件

以下はサイバー侵害からの復旧を製品能力として訴求するための条件である。ソースを研究・開発版として公開することとは区別する。各項目を実装しただけで合格にせず、対象コミット・環境・攻撃者権限・期待結果・実結果・証拠を記録する。

| ID | 想定・試験 | 合格条件 | 現時点 |
| --- | --- | --- | --- |
| CR01 | 本番WP管理者と保存元の資格情報を攻撃者が持つ | 保護対象の過去版・信頼情報を削除・置換できず、保持を短縮できず、復旧用権限も取得できない。独立担当者は固定版を取得可能 | 一部実証・総合未達：正式バケットのcanaryで両ロールの削除・保持短縮・bypassを拒否。全権限取得経路・別管理主体の検証は未完了 |
| CR02 | RAM・期待ハッシュ・Bootstrap・検証ツールの差替え、古い証拠の再提示 | 本番から独立した信頼の起点で検証し、不一致・期限切れ・失効・未検証を拒否する。鍵更新・紛失時の復旧手順も試験 | 一部実証：必須ゲート・USB読み戻し・実復元は合格。鍵更新/失効運用・別端末復旧は未完了 |
| CR03 | 最新バックアップが汚染され、一定期間発見されない | 複数世代から復旧点を選び、その選定根拠と残る不確実性を提示。汚染前の候補がなければ復旧可能と認定しない | 未達 |
| CR04 | コード、DB、アップロードに無害な疑似改ざん・不正ユーザーを混入 | 信頼できる配布物からコードを再構築し、独自コード・DB・メディアは検査・承認を経る。不審な状態を自動で公開しない。ハッシュ・署名・スキャン単独で無感染認定しない | 未達 |
| CR05 | 復元先から外部接続、メール送信、ジョブ実行を試みる | 独立した検疫環境で必要通信だけを許可し、本番資格情報を持ち込まない。再公開判定まで利用者や外部サービスに影響しない | 一部実証：実サイト候補のloのみの隔離、外部TCP/HTTP・メール遮断とcron停止を確認。悪性コード専用環境としての評価は未完了 |
| CR06 | 元サイト・元ホスト・元担当者を使わず復旧する | 別ホスト・別担当者が独立保管された手順と権限で復旧し、事業機能・目標時間・復旧点を確認できる | 一部実証 |
| CR07 | 復元後の再公開を判定する | 侵入原因の修正、関連資格情報・セッションの失効と交換、検査、機能確認、担当者の承認を記録。不明な条件が残れば再公開を保留 | 未達 |
| CR08 | 設定不備、取得失敗、証拠期限切れ、変更後の未再試験 | UI・CLI・READMEの評価が一致し、未確認を安全表示しない。WP停止時にも独立した経路で状態を確認できる | 未達 |

AWSアカウント全体の管理権限喪失、復旧担当者の端末侵害、署名鍵侵害、長期潜伏で全保持世代が汚染されるケースは、本番WP侵害とは別の脅威として扱う。対応を主張する場合は別アカウント・別管理主体等の境界を設計し試験する。対象外のままなら公開文面に明示する。

復旧資産を持たない状態、独立した信頼の起点を失った状態、信頼できる復旧候補がない状態で「復旧可能」と判定しない。データ漏えいへの対応は復元とは別に残る。

## 予防面で製品が担う範囲

まずは本製品自身の安全性と、運用上の危険の見える化を優先する。以下は製品化要件であり、現在すべて実装済みという意味ではない。

- 管理操作の権限・リクエスト検証、秘密情報の非露出、安全な一時ファイル、復元入力の検証、依存物の更新管理を確認する。
- WordPress・テーマ・プラグイン等の更新状態、権限の過大付与、バックアップと本番の権限共有を診断する。認証強化など外部機能の状態を確認できない場合は未確認とする。
- 外部のWAF、認証強化、マルウェア検査、ホスティング保護と併用できる設計とする。導入されているだけで安全と認定しない。
- 不備は影響と手順を添えて案内する。稼働中サイトの権限・更新設定を無断で変更しない。

平常時の更新を止めることは推奨しない。M1復元環境での自動更新・外部通信の停止は、隔離した検証のための設定であり、本番運用の推奨設定ではない。

## 公開説明と利用者理解の検証

現時点で使用する説明例：

> 侵害や障害が起きても、WordPressを立て直すための資産と手順を残すことを目指す開発版です。模擬資産と実サイトの取得データについて、S3固定版・保持・独立署名を確認した隔離復元と基本動作を実証しました。保存元侵害時の資産保持、感染後の安全な復旧、汚染したバックアップの判定は今後の検証対象です。

「感染しても必ず復旧」「入れるだけで安全」「署名済みなので無感染」「CI合格なので攻撃耐性も検証済み」と説明しない。CI合格、復元成功、侵害耐性の合格は別々に表示する。

本番向け公開前に、開発に参加していない利用者がREADMEと導入画面だけを読み、次を説明・実行できるか確認する。誤解があれば文章や導線を修正して再試験する。この理解度試験はまだ実施していない。

1. 何を守り、何を保証しない製品か説明できる。
2. 必要な外部保管・独立権限を理解し、未設定を未達と認識できる。
3. WP停止時に復旧入口と担当者へ到達できる。
4. 最新バックアップが安全とは限らず、復元成功も無感染証明ではないと理解できる。
5. 再公開には侵入原因の修正と健全性確認が必要だと理解できる。

## 次に進める順序

1. 脅威モデルと独立権限・信頼の起点を確定する（CR01・CR02）。
2. 専用の使い捨て資産で、破壊耐性と汚染世代の選定を試験する（CR03）。
3. 検疫復元・再構築・再公開の判定を実装する（CR04・CR05・CR07）。
4. 別ホスト・別担当者の演習と初心者の理解度試験を行う（CR06・CR08）。

共通部品の拡張は、この条件を満たすために必要な範囲で進める。研究版の公開を製品完成と扱わず、コンセプトの実証を次マイルストーンの優先事項とする。

[2026年10月18日の試験記録](../guides/signed-gate-recovery-test.md)で、署名検証・新規ボリュームへの復元・基準16項目・HTTP14項目の合格を確認した。CR02の部分実証を進めたが、CR01〜CR08を全面合格にしたものではない。本番向け公開の判定は保留し、研究・開発版として実証範囲を明記する。


## 保存側の直接削除試験

[専用canaryでの実測](../guides/writer-deletion-resilience.md)では、保存側からの通常削除・固定版削除はAccessDeniedで、dmから同じ固定版を再取得して内容一致を確認した。Object Lock未設定、Lifecycleなし。IAM/bucket policyの読取りはAccessDeniedのため、設定変更・他主体への権限経路は未評価。CR01の総合判定は未達を維持する。

GetBucketPolicy閲覧権限追加後の再確認ではNoSuchBucketPolicyとなり、bucket policy未設定を確認した。バケットポリシーの閲覧不能は解消。IAM全ポリシー・境界の確認と設定変更経路の評価は引き続き未完了であり、CR01の判定は変えない。


## 専用Object Lock比較試験の追加結果

[Governance保持の実測](../guides/object-lock-lab.md)では、削除権限を持つ保存側が保持なし版を削除できる一方、24時間保持中の固定版削除・保持短縮は拒否された。通常削除のマーカー作成・上書き後もdmで保護版を取得して一致を確認。bypassは試験用ポリシーで明示禁止した。CR01の保持機構の部分実証は進んだが、既存バックアップへの保持適用・全権限経路の遮断・管理主体の分離は未完了のため総合判定は未達を維持する。
