# Ozeki WordPress Resilience 基本仕様

版数：0.2  
更新日：2026年10月18日  
状態：M1実証後の製品構成方針を反映。共通部品と単独導入パッケージは未実装。

## 目的と対象

WordPressを利用する小規模企業、スタートアップ、個人事業者が、サーバ侵入、データ破壊、ランサムウェア、障害によって本番環境を失っても、事業に必要な情報資産と復旧能力を維持できるようにする。

「たとえやられても、立て直す能力を失わない」体制を技術と運用の両面から構築する。一度の侵害が全資産・全復旧手段の喪失につながらないよう設計し、実効性を試験する。絶対的な生存保証ではなく、定義した脅威と条件に対する能力を明示する。

## 基本原則

- 本番環境の侵害・完全喪失を想定する。
- 復旧資産、復旧権限、復旧入口、証拠の信頼の起点を本番WordPressの管理権限から分離する。
- バックアップの存在、取得可能性、復元可能性、事業機能の回復を区別する。
- 証拠が存在すること、信頼できること、復旧できることを区別する。
- 試験の対象・条件・範囲を明示し、未実施の検証を成功として扱わない。
- AIの推定や提案を、観測・復元試験の証拠として扱わない。
- 小規模事業者が継続できる費用と運用負荷を重視する。

## 既存バックアップ製品との関係

Ozeki Database Backup for S3は独立した製品として維持する。Ozeki WordPress Resilienceもバックアップ機能を内包して単独導入できる製品とし、別プラグインのインストール・有効化を必須にしない。共通するバックアップ処理と保存形式を共有し、各配布物へ共通部品の固定版を組み込む。詳細は04-product-boundaries-and-initial-release.mdとADR 0004を参照する。

| 担当 | 責任 |
| --- | --- |
| 共通バックアップ部品 | DBダンプ・圧縮・転送・完全性照合など、共通する処理を提供する |
| Ozeki Database Backup for S3 | バックアップに絞った設定・実行・運用を提供する |
| Ozeki WordPress Resilience | 復旧資産の充足、資産の固定、保管と権限の独立性、復旧手順、外部検証、証拠、目標評価を扱う |

既存機能は再利用し、統合や重複実装を避ける。公開済み機能を無断で変更しない。改修が必要な場合は、理由、対象箇所、互換性への影響を文書化して改修前に報告する。

DB・メディアの形式、S3オブジェクト管理、チェックサム、履歴、WP-CLI、保持・削除処理をソースと出力から確認してから連携方法を決める。復旧は元WordPressの管理画面や内部履歴に依存させない。

## 構成要素

| 要素 | 役割 |
| --- | --- |
| RAM | Recovery Asset Manifest。復旧に必要な資産、取得先、完全性情報、依存関係を記述する |
| Recovery Set | 一緒に復元するDB・ファイル・コード・構成の組み合わせを固定する |
| Recovery Bootstrap | 元環境なしでRAM、手順、復旧権限の取得方法へ到達する入口 |
| 復旧手順とツール | 外部資産から独立環境を構築・復元する |
| Evidence | 申告、外部観測、独立復旧試験の結果を区別して記録する |
| Trust Model | 発行主体、対象、権限、真正性、失効、適用範囲を評価する条件 |
| PEM | Policy Evaluation Model。証拠と事業要件を照合し、不足と改善行動を示す |

平常時の収集・設定はWordPress側、障害時の復元は外部ツールに分ける。共通部品の配布方法・対応ランタイムは抽出時に確定する。復旧の中核はWordPressが停止していても利用できることを必須とする。

## 段階的な実証

M1では、正常な資産を使った完全喪失からの独立復旧を実証する。

後続段階では、バックアップ削除・汚染、資格情報や署名鍵の侵害、証拠改ざん等に対する耐性を検証する。さらに事業要件、費用、検証結果を結びつけ、継続的な改善へつなげる。後続段階の詳細な範囲と合格基準は別途確定する。

M1の成功を、汚染バックアップからの安全な復旧やランサムウェア全般への耐性の証明とは扱わない。
