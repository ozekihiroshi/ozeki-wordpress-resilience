# 独立署名承認付きS3再構築キット（試作）

主仕様は[英語版](rbr-signed-kit.md)です。専用入口 `tools/rbr-approved-kit.py` は、独立配置した公開鍵・承認文書・署名・ルート受領票と、既存の最新世代／失効台帳を要求します。署名なしのS3取得CLIは閉じました。低水準関数と専用試験ランナーは試験部品であり、管理者によるコード改変まで防ぐものではありません。

承認には、S3のバケット・キー・固定Version ID・サイズ・ハッシュを含むルート受領票全体、サイト、セット、世代、用途、有効期間（最大7日）、自動公開しない条件を結び付けます。既存のRSA-SHA256と最新台帳の検証を再利用し、従来のRestore承認条件は変更しません。承認期限は自動延長しません。

S3取得前、取得したプランナーの実行前、再構築前に署名・公開鍵固定・期限・世代・失効を確認します。途中で最新台帳が変われば停止します。取得後のコード・定義・入力・イメージ一覧・計画も再検査します。途中失敗したWordPress環境は自動再開しません。完全に取得済みの素材は `--received` で署名・参照を再検査して再利用できますが、復元先は必ず新規です。

運用は「保管担当が受領票を渡す → 別の承認担当が対象と期限を確認して署名 → 公開鍵固定と最新台帳を独立配置 → 読取り権限だけで取得・隔離再構築 → 結果を確認」です。秘密鍵は取得・実行側へ渡しません。既存の台帳更新手順を用い、失効情報を復旧キット自身から信用する構成にはしません。

今回は試験鍵をrootだけが読める領域へ置き、取得・再構築は別の一般ユーザーで行います。同一試験ホスト内の権限分離であり、ホスト全体の侵害に対する物理的独立を実証するものではありません。試験台帳は専用マウント名前空間内だけに配置し、既存の/etcや本番台帳を変更しません。

署名は承認対象と完全性の確認であり、無侵害の証明ではありません。信頼する取得ツール・公開鍵・最新台帳・互換するDocker環境の準備は必要です。汎用導入画面、任意のテーマやフォーム、本番適用・自動公開は未対応です。結果は[検証記録](../../evidence-public/rbr-signed-kit.json)に整理します。

## 今回判明した問題の区分

- 試験基盤：専用overlayの`/etc`が0700になり、最新台帳を読めずS3取得前に停止しました。専用名前空間内だけ0755へ修正し、ホスト側は変更していません。
- プラグインの実行制御：初回の成功時にPythonが比較器のバイトコードキャッシュを生成し、再利用の厳密なコード一覧検査が拒否しました。`python3 -B`で起動するよう修正し、検査は緩めず、既存キャッシュはコード領域外へ証拠として退避しました。
- 環境：従来どおり互換するDocker保存方式と専用ブリッジ内の通信設定が必要です。一時許可規則は試験終了後に撤去します。
- 試験鍵は再構築ユーザーから読めず、台帳も専用名前空間だけに配置します。別の物理署名ホストを用いた実証ではありません。

最終結果はPASSです。承認後に実S3の75固定版を取得して2回再構築し、最終コードでも取得済み一式を再検査して新しい2環境を構築しました。いずれもQに一致しました。署名関連15ケース、実台帳とファイル差替え10ケース、旧署名なしCLIの拒否を確認しました。S3への追加保存・本番変更・自動公開はありません。一時通信規則は撤去し、専用実行環境は停止しました。

一時通信ヘルパーにもネットワーク撤去と一覧取得の競合があり、規則を撤去して終了しました。消えたネットワークの検査を次の巡回へ戻すよう試験基盤を修正し、再構築を重複起動せずヘルパーだけ再開しました。最終結果はこの中断からの回復も含みます。
