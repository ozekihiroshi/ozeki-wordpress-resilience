# 最初に対応するサイト構成と取得方式

2026-10-20。収集アダプターの初期仕様。設定検査と専用Docker接続による取得を実装・検証済み。専用fixtureの実装済み機能と、任意サイト向けの未実装機能を区別する。本書の作成では実サイトを停止・取得・変更しない。

## 対応範囲

最初の対応構成は、Linux上の単一WordPress（マルチサイトなし）、単一MariaDB/MySQLデータベース、単一ホスト内のローカルサイトファイルとする。最初の実装・試験対象は既存のWSL Ubuntu＋Docker＋WordPress/MariaDB構成。MySQL各版の互換性は未検証であり、対応版はアダプターの試験結果から明示する。プラグイン本体はPHP8.1以上。Web・DB・ジョブを個別に停止・確認できる管理経路が必要。

利用者が選択済みの最初の適用候補はwp.ceri.link。現行構成がこのプロファイルへ適合するかは再調査が必要で、適合済みとはしない。停止時間帯、最大停止時間、許容データ損失、復旧目標時間、代替担当は適用前の入力必須事項。これらが未設定なら定期取得を有効にしない。毎日1回・35日保持は既定方針として維持し、今回の試験の03:00を本番時刻には流用しない。

|資産・経路|最初の対応条件|外れる場合|
|---|---|---|
|DB|対象DB・テーブル一覧・エンジンを列挙。初期対象はInnoDB。DDLと直接DB書込みも制御|非対応エンジン、複数DB、列挙不能はunverified。対象を黙って省略しない|
|ファイル|WordPress本体、テーマ、プラグイン、MUプラグイン、uploads、復旧に必要な設定を明示|外部mount、シンボリックリンク、外部メディアは初期対象外。参照先を含められなければunverified|
|秘密情報|wp-config等を含む場合は秘密を含む復旧資産としてアクセス制限。復旧時の資格情報交換を別工程にする|Git・管理画面・公開検証結果・通知本文へ秘密を出さない|
|一時ファイル|再生成可能なキャッシュ、ログ、一時領域は所有者が除外一覧を承認|パス名だけで除外しない。復旧に必要か不明なら除外を確定しない|
|HTTP/PHP|GETを含め受付を止め、実行中処理・終了時処理の完了を待つ|メンテナンス表示だけでは停止確認にしない|
|Cron/CLI/SSH|WP-Cron、外部Cron、WP-CLI、更新、デプロイ、直接編集の全入口を登録・制御|未登録ユーザーやroot操作のバイパスを許す運用では整合性を断定しない|
|キュー|最小構成は外部キューなし。DB内ジョブも書込み元として棚卸し|外部キューありは保留。対応アダプターの停止・排出・状態取得・再配送契約を追加してから対応|

キューなしでも「不存在を確認した範囲と根拠」を記録する。空のキュー資産を捏造して三資産試験と同一扱いしない。新規取得結果はdatabase/filesの二資産とqueue.state=absentを記録する。既存の三資産日次fixtureはそのまま維持する。別の二資産契約では、キューなし取得結果からS3固定版・保持証拠・独立試験署名・隔離復元・日次結果登録まで実装し、専用生成環境で検証済み。任意サイト向け本番アダプターの提供とは区別する。Redis等のセッション、外部注文・決済、メール、別ストレージにしかない状態も資産調査の対象。未対応依存が見つかった場合は適用を止める。

## アダプターに渡す運用設定

設定にはsite_id、DB/サイトパスの識別情報、対象・除外一覧、必要ランタイムと取得元、全書込み元と制御担当、停止順と解除順、停止上限、外部作業領域と容量上限、保管先とwriter/reader参照、署名担当と独立ピンの入手先を持たせる。秘密の値は別の権限制限済み設定から参照する。運用設定の版とハッシュを試行へ結び付け、収集側が対象や必須更新元を自動縮小できないようにする。

上記の初期設定検査と専用生成環境向け設定例を追加した。[実装と使用方法](../guides/first-site-capture-lab.md)を参照。本番用の導入・取得コマンドは提供していない。既存labコマンドにサイトURLを渡して代用しない。

## 停止窓とストリーム取得

[取得整合性契約](11-capture-consistency-contract.md)を実サイト向けに次の順で適用する。

1. 事前確認：対象・空き容量・DBエンジン・更新元・解除手段・権限を検査。同一サイトの未完了試行と結果不明の送信があれば新規取得を止める。
2. 停止：所有トークン付きで新規受付とジョブを停止し、進行中処理、子プロセス、DB書込みの完了を待つ。排出上限超過なら取得しない。
3. 取得：DBスナップショットとサイトファイルを同じ停止窓内で取得。保存元に巨大な圧縮ファイルを置かず、外部作業領域へストリームする。パイプ全段の終了コードを検査する。
4. 検証：DB/ファイルの試行ID・設定版、前後一覧、内容ハッシュ、出力サイズ、停止継続、DB参照との整合性を検査。通常WordPressの添付メディア参照とDB再読込みは専用生成環境で検証済み。独自プラグインの参照や任意サイトへの適用は未検証。fixtureの独自ハッシュ列をそのまま製品仕様にしない。
5. 解除：自分が取得した停止だけを解除し、元の運転状態へ戻ったことを確認。独立した期限監視・手動解除手段を用意する。期限で自動解除された取得は不合格。
6. 保管：取得検証と解除の確認後に外部作業領域からS3へ保存する。S3送信待ちのために停止窓を延ばさない。外部領域も秘密情報を含むためアクセス制限し、削除は保存・証拠・再試行状態を照合して別途行う。

外部容量不足や接続断ならcapture_failed。停止範囲・DB確認不足や停止喪失はunverified。途中変更はinconsistent。解除失敗は取得の判定と別に記録し、試行全体を成功表示しない。consistentだけでは保存成功・承認済み・復元確認済みを意味しない。保存先侵害や取得元の虚偽報告、既に混入したマルウェアをこの整合性検査だけでは判別できない。

## 次の実装受入条件

|対象|専用環境で確認すること|
|---|---|
|収集設定|未登録更新元・外部依存・不明な除外を拒否。設定版を証拠へ固定|
|実WordPressの取得|通常投稿・uploads・テーマ等を対象にDB参照と取得ファイルを照合。キューなしを明示|
|障害・解除|排出期限、転送途中断、外部容量不足、制御プロセス停止、リース喪失、解除失敗を別結果で残す|
|保管接続|保存元の停止解除後に固定Version IDと保持証拠を確定。unknownを自動再送しない|
|復旧|保存元へ接続せず独立ピンとreaderで取得し、隔離先へ復元。秘密情報や外部配送を持ち込まない|

設定検査と専用構成での取得・解除・障害・通常添付参照・DB再読込みは[今回の検証](../guides/first-site-capture-lab.md)で確認した。二資産のS3保管・独立試験署名・隔離復元は[専用環境で検証済み](../guides/first-site-s3-recovery-lab.md)。[日次処理](../guides/first-site-daily.md)・[結果登録](../guides/first-site-auto-recovery.md)も接続済み。汎用サイトの本番復旧は未達。専用fixtureの既存結果は[初版検証記録](../releases/initial-release-verification.md)を参照。
