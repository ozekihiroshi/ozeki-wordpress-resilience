# S3先行保存のWordPress編集画面（明示的に有効化する試作）

対象3固定ページの「固定ページ → 編集」から、タイトル・スラッグ・プレーンテキストの段落を編集する専用画面へ進めます。既存APIの設定に加え `Owr\RbrWordPressEditor::boot($ids)` を明示的に呼び出す専用配置です。通常の管理プラグインZIPからは有効になりません。Gutenberg全般に対応したものではありません。

## 操作

- **S3へ保存して反映**：現在のページを変更し、残る2ページの本文・固定画像・関係を引き継いだ世代を保存します。S3確定とDBの一括反映を確認するまで公開内容を更新しません。
- **同じ保存を再開**：未完了なら内容を変更せず再開します。要求全体をサーバーへ先に記録するため、画面を閉じても再取得できます。別の対象ページから再開しても、記録した3ページ一式を再開します。
- **最新状態を読み直す**：競合時は古い内容で上書きせず、最新状態を取得して編集し直します。未保存の入力を捨てる場合は確認を表示します。

保存中・未完了・S3確定済み反映待ち・競合/別経路の変更・入力不適合・反映完了・状態取得不能を表示します。通信断では成否不明とし、同じ要求で照合します。反映完了の表示には保存応答と状態再取得の両方の成功が必要です。自動再送・署名承認・期限延長・自動公開は追加しません。

## 範囲と制限

状態取得APIはローカル台帳だけを読み、S3へアクセスしません。3ページすべての編集権限と公開権限、Cookie認証・nonceが必要です。秘密情報・パスは返しません。対象ページの従来フォームによる直接POSTは409で拒否し、コアRESTの変更拒否も維持します。無関係なページの編集は変更しません。

登録時の本文は単純な `<p>テキスト</p>` のみとし、対応外のHTMLを黙って削除しません。新規画像・通常投稿・Markdown・任意ブロック・保存フック・リビジョン・永続キャッシュは未対応です。任意プラグイン、XML-RPC、admin-ajax、一括操作、直接SQLなど全経路を封じたとは主張しません。別経路の変更は次の検査で拒否します。旧形式の台帳には自動移行やリセットを行わず、編集用原文がない場合は画面を利用不可にします。未解決操作の取消し・台帳整理も未対応です。

## 検証

実Chromium・WordPress HTTP・MariaDBと永続S3模擬ストアで、保存失敗時の公開内容保持、画面再読込み後の再開、別編集画面との競合、古い画面の拒否、S3確定後の中断・再開、権限・nonce・フォーム迂回拒否を確認します。[確定した検証結果](../../evidence-public/rbr-wordpress-editor.json)を参照してください。前回の実S3 API試験とは別で、今回を実S3の再試験と扱いません。

最初のSelenium起動タイムアウトは編集画面に到達する前に発生しました。同じ版のChromeDriverを直接起動すると進みましたが、仲介部のタイムアウト原因は未確定です。次の試行では試験コードがtextarea値を属性として読んでいたため、プロパティの読取りへ修正しました。これらの失敗記録は試験基盤のものとして残し、プラグインの不具合と混同しません。本番変更・クラウド書込み・自動公開はありません。

## 実S3とのブラウザ接続試験

`tools/run-rbr-wordpress-editor-s3-lab.py` は既存の編集画面シナリオとAPI試験の限定S3通信処理を再利用します。新しい専用出力先、対応するローカルComposer vendor、新しい `--case api-...` 保存範囲を指定し、読取り専用の一覧で未使用と確認できた場合だけ保存します。WordPressとブラウザは外部通信・公開ポートのないネットワーク内で動かし、試験用Unixソケットを介して既存の分離ロールでS3へ接続します。本番の資格情報配置や応答時間の保証ではありません。

実S3試験は3世代に絞ります。確定前の保存失敗と同じ要求の再開、別編集者の成功と古い編集の拒否、S3確定後の処理停止と同じ固定版からの再開です。応答喪失などのUI単独ケースは既存のオフライン証拠を利用します。503は意図的な障害注入で、AWSの実障害ではありません。失敗前に保存された原本は保持し、台帳やS3資産を削除しません。署名承認・保持条件は変更しません。
