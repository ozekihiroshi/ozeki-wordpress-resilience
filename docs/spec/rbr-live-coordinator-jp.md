# 実S3の世代確定コーディネーター接続（試作版）

開発キットのCLIで、既存の世代確定処理を実験用S3へ接続します。WordPress編集画面の保存フックや自動公開の実装ではありません。

入力原本と操作要求 → 原本・操作記録の条件付き保存 → 一つの世代枠の条件付き確定 → 確定参照をそのままキット入口へ渡す → 独立署名承認待ち → 既存の署名・最新信頼情報検査 → 隔離再構築、という流れです。試験用コードで世代マニフェストを作り直しません。

## 入口

`tools/rbr-coordinate-s3-lab.php --job=JOB --case=CASE --work=PRIVATE_DIRECTORY --execute-generated-lab` を使います。PHP/Composer・Python・既存SSH別名community/dm・実験限定権限が前提です。対象は生成データのcorporate-testのみです。並行処理では個別の非公開作業ディレクトリを使い、失敗時の台帳も残してください。同じ台帳を複数処理で同時に使用しません。

論理サイトIDと物理保存範囲を分けます。追加の最新版読取り・一覧権限は新しい実験範囲だけです。HEADの403単独では未作成扱いせず、成功した範囲限定一覧で存在しないことを確認します。内容の取得は固定Version IDで行います。汎用的な本番認証・設定画面は未実装です。

## 保持

実測では、バケットはObject Lock有効・デフォルト保持ルールなしで、試験前後とも同じ設定でした。以前の説明にあった「既定35日」は、従来の保存時の個別保持指定との混同でした。バケット設定は変更していません。新しい保存モードでは、新規PUTの版だけに36日GOVERNANCE保持を指定して実際の保持を読み戻します。世代の約束は従来どおり「確定期限＋35日」です。従来モードの36日デフォルト要件は維持します。既存原本の保持が不足する場合は新しい保持付きコピーを作り、古い版の保持変更・削除・保護回避は行いません。

## 検証の範囲

実行結果は完了後に `evidence-public/rbr-live-coordinator.json` へ記録します。同時編集、保存直前失敗からの再開、確定応答喪失後の同一版照合、保持不足拒否と保持付きコピーを確認します。確定した世代は独立署名検証を経て新しい隔離WordPress二つへ再構築し、Qと比較します。

失敗は実S3要求の前後に注入したものです。AWS自体で障害が起きたという証拠ではありません。試験鍵はroot専用、信頼台帳は一時マウント名前空間のみで、物理的な署名ホスト分離の実証ではありません。既存の専用Docker格納領域を再利用し、cold-cache再試験ではありません。本番変更、自動承認延長、自動公開、新EC2、ZIP作成・リリースは含みません。

## 実測結果

合格：実S3で確定は1処理だけ。保存失敗から再開し、応答喪失後の再実行ではPUTを行わず同一版へ復帰しました。保持不足は拒否し、新しい保持付きコピー作成後も旧版の保持は不変でした。確定参照をそのまま署名付きキットへ渡し、隔離WordPress二つの論理状態がQに一致しました。ハッシュ・件数・範囲は証拠JSONを参照してください。
