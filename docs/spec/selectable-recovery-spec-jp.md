# 選べる検証構成と復旧版：初期仕様

[English（主文書）](selectable-recovery-spec.md) | 日本語

2026年10月22日。**設計案。未実装であり、本番適用・既存承認条件の変更は行わない。** PR #9後の試作版を基準とし、[運用モデル](maintainer-operating-model-jp.md)と[机上検討](maintainer-tabletop-jp.md)を具体化する。Backup for S3との必須連携や共通部品の変更は含めない。

## 1. 目的と対象

WordPressの保守技術者が、正常時に毎日のバックアップを手動承認せず、確認できた範囲が明確な復旧版を蓄積できるようにする。復旧専用EC2の常時稼働は要求しない。

同一サーバーでの検証も成果として扱う。「独立検証がないから0点」とせず、検証内容と障害・侵害からの独立性を分ける。初期の取得対象は、既知の更新経路とローカル資産を持つ単一WordPress構成。あらゆるホスティングへの対応を約束しない。

## 2. 利用者が選ぶ構成

| 構成 | 確認できること | 残る限界 |
|---|---|---|
| 同一サーバーの内容検査 | 必要資産・固定版・ハッシュ・メタデータ | 復元・起動は未確認 |
| 同一サーバーの別DB・別ファイル領域への隔離復元 | 実復元・起動・指定機能 | ホスト喪失・管理者侵害の影響を共有 |
| 同一サーバーの使い捨て環境でキットから構築 | キットの不足・構築手順 | カーネル・資格情報・隠れた依存の共有があり得る |
| 既存の別サーバー | 元ホストを使わない構築・復元 | 実際の管理権限やストレージの分離範囲に依存 |
| 必要時だけ起動する一時環境 | 復旧用常設サーバーなしの構築・復元 | 起動権限・容量・依存資産の確保が必要 |

同一サーバー、既存別ホスト、一時環境から選択できるようにする。通常は同一サーバー、重要変更時だけ別環境という組合せも認める。

独立検証の欠如だけでは復旧を禁止しない。ただし、不整合・必要資産欠落・利用保留・失効は別の拒否理由である。これは将来仕様であり、現行入口を緩和するものではない。

同一サーバー試験も別DB・別ファイル・限定権限・容量/負荷制限・通信制御を必須とする。メール・Cron・決済などの外部副作用を防止する。分離できなければ復元試験を開始せず、完了した軽量検査だけ表示する。本番上書きを試験に使わない。

## 3. 検証済み復旧版

意味は「特定の固定版が、明示した検査に合格した」。無感染・万能な復旧保証ではない。S3にあること、名前、タグだけでは証明にならない。

記録するもの：復旧版ID、資産範囲、DB/ファイルの対応、S3固定Version IDとハッシュ、保持証拠、キット/実行環境/依存資産の版、検査方針・時刻・結果・未確認/スキップ、検証主体と配置、署名・信頼情報の参照。現在の利用可否は別記録とする。

表示する軸を分離する。

- 保存：処理中／完了／失敗／結果不明
- 検証：未検証／内容検査合格／隔離復元合格／キット構築合格／失敗。配置と検査範囲を併記
- 利用可否：利用可能／確認待ち／侵害疑いによる保留／失効。理由と判断世代を併記
- 情報の鮮度・管理元：最新／古い／確認不能

過去の検査成功は利用保留後も履歴として残す。古い正常世代へ戻れるよう複数世代を保持し、最新だけを復旧可能にしない。

保存元の権限で「独立検証済み」や正式な利用可否を発行できないようにする。同一ホストの結果は有用だが、ホスト管理者侵害時には操作され得る。署名だけで独立性は増えない。

将来の自動検査証跡は、人の署名承認とは別形式・別権限とする。既存署名の自動延長や読み替えを行わない。移行方法は未設計。

## 4. 侵害疑い・凍結・隔離保管

| 状態 | 事前合意した範囲の自動動作 | 人の判断 |
|---|---|---|
| 正常 | 取得・検査・候補登録 | 方針と重要変更 |
| 要注意 | 根拠保存、新しい候補への昇格保留 | 一時障害か侵害疑いか |
| 侵害疑い | 候補を保留、更新・外部送信の凍結要求、後続取得は隔離 | 停止範囲、影響、調査 |
| 調査 | 過去証拠の維持、別途許可した隔離検査・復元 | 影響期間、復旧点、資格情報交換 |
| 再開 | 承認後、新しい構成・方針世代で取得再開 | 凍結解除と再公開 |

通信失敗だけで侵害確定とはしない。信号、停止対象、通知・判断担当を導入時に定める。無関係なサイトやAWS全体まで停止しない。

更新経路は管理画面・REST・Cron・SSH・キューなど。現行試作版で本番の全経路を制御できるとは確認されていない。「凍結要求済み／停止確認済み／停止確認不能」を区別する。侵害された保存元自身の返答だけを独立した停止証明にしない。

**取得時の短時間停止と、侵害時の凍結は別の理由・所有者で管理する。取得停止のタイムアウト解除で侵害凍結を解除してはならない。** 収集側喪失時の安全な取得停止解除は未確認の接続部分である。

発見時刻と侵害開始時刻は違う。発見後の取得を除外するだけでなく、調査により過去の版にも利用保留を付ける。元データや検証証拠は削除・改変しない。

隔離保管は別バケット等の権限境界を用い、通常の復旧権限では取得できないようにする。名前だけの区分にしない。既存の保持版は元の場所に残して利用保留を反映できる設計とし、移動完了まで保留を待たない。振分け結果が不明なら信頼済み側へ代替保存・昇格しない。証拠採取のための取得も任意・制限付きとし、凍結を破らない。

保留版の通常復旧・自動再公開を止める。疑わしい版の調査用取得は別の限定された入口とし、利用可能と偽装しない。影響外の過去版は調査判断後に選択可能とする。再公開は明示承認を必要とする。

## 5. 必要時に構築する復旧環境

別管理のS3に復旧キットと索引を保管する。別バケットだけではAWS管理アカウント全体の侵害から独立しないため、配置ごとの権限・アカウント境界を説明する。

キット：版固定の復旧プログラム、実行環境の構築手順と必要資産、バックアップ索引、検査証跡、世代・凍結・保留・失効情報、依存関係と資格情報の参照、構築・復元・後片付け手順。長期秘密鍵を同梱しない。

事故前に、元サイト・通常管理元の外へ準備するもの：
- 保管先へのアクセス、必要な復号・環境作成の手段
- キットと同じ場所から初めて信用するのではない、鍵指紋等の信頼の起点
- 主担当・代替担当と非常時の方針

手順：信頼できる端末で認証→キットと利用可否を検証→一時環境を構築→版を選択→固定版取得→隔離復元→人の確認→再公開。不要資源は終了後に削除する。元ホストの設定を裏で借りて「キットだけで復旧成功」としない。

通常の取得・検査・記録更新には実行場所が必要だが、復旧専用VMの常設は不要とする。S3保管だけですべての実行や費用がなくなるとはしない。

## 6. 管理元不通と復旧不能リスク

平常時から、凍結・失効記録を独立した復旧保管へ発行し、読戻し確認する。発行失敗は障害であり、記録がないことを「保留なし」の証明にしない。古い索引では後から発生した失効の不存在を証明できない。可能な場合は独立保持した最低世代と照合し、時計や古い情報への再署名で最新性を作らない。

- 最新の信頼情報・有効な許可がある：通常の隔離復元。
- 管理元不通：最後の確認時刻・世代・未確認事項を表示。事前に限定した非常時方針と担当者の確認で隔離構築を許す案。
- 既知の失効や署名主体侵害：その証明では進めない。他の独立確認済み版や再構築を検討。
- S3アクセス・復号手段欠落：前提を回復するまで取得できない。

非常時の隔離復元は再公開許可ではない。代替担当、対象版、判断理由、残余リスクを記録して再公開を判断する。隔離データの自動再利用はしない。**非常時入口は未実装で、現行の期限切れ・欠落台帳は引き続きGET前に拒否する。**

最新確認の全面必須は古い失効情報で進む危険を抑えるが、正常な版の復旧も止め得る。無条件オフライン復旧は失効版を使う危険がある。本案は不確実性を表示した限定隔離作業と、再公開の判断を分ける。

## 7. 自動・低コストの実証

仮の開始頻度でありSLAではない：
- 毎回：保存内容の軽量検査
- 週1回程度・重要変更時：選択した構成で隔離復元
- 月1回程度・キット更新時：キットから構築。必要なら一時的な別ホストを使用

利用者は費用・規模・リスクに合わせて変更できる。EC2必須ではない。時間・費用を実測して予算を決める。予定設定だけでは検証済みにならない。

構築→キット取得→検証→復元→試験→結果保存→後片付けを自動化する。全工程試験の初期入力は宣言した認証・信頼情報に限定し、キャッシュや外部取得依存を記録する。

重複起動、同時数、資源サイズ、時間、再試行を制限する。不明な結果は照合してから再試行する。所有資源を識別し、試験本体と別の期限超過回収を用意する。予算警報だけを費用上限とはしない。実データを使う場合も、移送先と隔離条件は別途許可された範囲に限る。

表示は検査種類別の最終成功・対象版、最新失敗、情報の古さ、実行漏れ、管理元の確認状態、費用、資源残り。実証失敗・未実行だけで侵害と判定しない。

## 8. 再利用と変更の区分

| 要件 | 既存の再利用候補 | 変更・未確認部分 |
|---|---|---|
| 検証済み復旧版 | S3固定版・ハッシュ・保持証拠・署名・隔離復元・結果登録 | 復旧版の統一形式、検証配置の表示、自動証跡の権限 |
| 同一サーバー選択 | 専用隔離試験と復元部品 | 利用者向け導入、分離・資源検査、本番を傷めない操作 |
| 凍結と利用可否 | 世代・失効検査、取得判定、状態報告 | サイト全体の侵害状態、過去版の保留、統合画面 |
| 更新停止と隔離保管 | 書込み調整部品、保管アダプター | 全更新経路、取得停止と凍結の分離、限定SSH取得、振分けと権限 |
| 必要時の環境構築 | 復旧キット配布物、設定案、SSH配置部品 | 自立した構築入口、元サイト不要の操作、索引配布、資源作成 |
| 管理元不通 | 現行の独立ローカル台帳、原子的更新、読戻し・巻戻し拒否 | 非常時許可と段階別取得権限。現行に迂回路はない |
| 自動実証 | 復元結果、日次記録、報告、timer、通知 | 全工程の定期実行、費用制御、独立した後片付け |
| 承認負担軽減 | 技術検査と独立署名の部品 | 方針に基づく自動証跡、期限の意味、移行と画面 |

再利用できることと製品として確認済みであることは違う。本仕様の実機試験は行っていない。過去の短縮観測は68時間28分24秒・空白2件で終了済みで、本仕様の実証や72時間合格ではない。

環境の制約（容量・通信・権限）、試験基盤の問題（fixture・ブラウザ起動等）、上表の製品課題は別々に報告する。

## 9. 実装承認前の確認事項

- 同一サーバーの成功を評価しつつ、独立性を誤表示しないか。
- 配置を問わず不整合・欠落・保留を拒否し、履歴を保持するか。
- 凍結要求・実停止・振分け失敗を区別できるか。
- 取得停止の自動解除が侵害凍結を解除しないか。
- 元サイト・通常管理元なしで、宣言した初期入力だけで構築できるか。
- 管理元不通を勝手に「最新」とみなさないか。
- 不明なクラウド処理を照合し、残存資源を制限できるか。
- 既存署名の自動延長なしで、正常時の日次手作業をなくせるか。

実装前に決めるのは、対応する隔離方式、凍結の信号と自動停止範囲、利用可否の管理主体と非常時許可、隔離保管の権限境界、データの扱い、実測に基づく予算・頻度。現時点では本番の設定値として確定しない。
