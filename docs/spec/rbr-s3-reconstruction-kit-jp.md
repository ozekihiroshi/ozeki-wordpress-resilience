# 固定版S3キットからのWordPress再構築

現在は[独立署名承認の入口](rbr-signed-kit-jp.md)を追加しています。以下は署名接続前の検証記録であり、署名なしの取得CLIは現在無効です。

試作CLIの専用実験です。[英語仕様](rbr-s3-reconstruction-kit.md)を主文書とします。本番変更・自動公開・既存承認条件の変更は行いません。

本文・画像・ページ間関係のA、規則R、環境E、定義D、比較器C、期待結果Qに加えて、再構築コードと実際のWordPress/PHP・MariaDBイメージを実験用S3へ保存します。大きなイメージは8 MiBずつ分割し、順序・全体ハッシュ・各固定Version IDをEに結び付けます。参照先の変更は新しいマニフェストとして保存します。

既存の実験用バケットと分離ロール、S3転送処理を再利用します。SSHで認証するスクリプトは一時実行だけで、既存サーバのファイル、IAM、バケット設定は変更しません。送信台帳に結果不明のPUTがあれば自動再送しません。

復旧は、別途保管したルート受領票（Version ID・ハッシュ・サイズ）と、読取り権限・信頼する取得ツールから開始します。取得する各オブジェクトの固定版・ハッシュ・暗号化・35日保持の証拠を検査し、元のPをコピーせず取得済みDからPを作り直します。S3キーがあるだけで正当性を保証する設計ではなく、この新キット用の独立署名承認は今回未実装です。

手元の既存イメージに頼らないことを、空の専用Dockerデータ領域から確認します。S3から取得したイメージを読み込み、送信元の作業フォルダを参照せず、取得したコードと入力だけで新規WordPressを構築します。2つのDB・uploadsを分離し、実DBとHTTP応答からそれぞれQとの一致を確認します。

下書き・認証付きプレビュー、外向き既定経路なし、公開ポートなし、メール/HTTP遮断、Cron停止を維持します。合格しても公開しません。試験で固定したソフトウェア版を本番推奨とするものでもありません。

結果は[検証記録](../../evidence-public/rbr-s3-reconstruction-kit.json)に記載します。実験用S3の保持中オブジェクトは削除せず残し、通常の保管費用が発生します。汎用導入UI、途中失敗からのWP再開、任意テーマ/フォーム、独立署名によるルート承認などは別の未完了事項です。

## 今回確認した互換条件

最初の空のDocker 29環境はcontainerd方式、保存側はclassic overlay2方式でした。同じ取得済みMariaDBアーカイブでも、前者では別のマニフェストIDとして見えるため、固定ID照合で停止しました。IDの置換や検査の緩和はせず、保存側と同じclassic overlay2方式の、もう一つの空の専用デーモンで同じ取得済みアーカイブを読み込みます。既存Docker設定の変更やS3再送はありません。

環境差として原因を確認した一方、製品側でも「任意のDocker保存方式を自動判定・変換する機能は未対応」という制限です。現状は互換する保存方式・アーキテクチャの準備が必要です。Eの固定ID検査は不一致を止めますが、ホスト側互換プロファイルの十分な定義は今後の課題です。最初の失敗は成功記録に混ぜません。

## 結果

75オブジェクト・412,585,057バイトを固定版として保存・取得し、ハッシュと保持証拠を確認しました。元フォルダを別名・権限000で参照不能にした間に、空だった独立Docker領域へ取得済みイメージを読み込み、2回の新規WordPress再構築がともにQへ一致しました。4つのコンテナの読取り専用マウント先が、取得済みコードと入力だけであることも確認しました。検証後は元フォルダの権限を0700へ戻し、資料は`.sealed`名で保持しています。

専用ブリッジのDNSとDB起動は正常でしたが、ホストの転送制御でTCP通信が止まりました。ローカル試験ブリッジ内だけを対象とする一時許可2規則を使い、終了後に削除を確認しました。完全に別のネットワーク名前空間ではDocker自体が起動時panicになりましたが、根本原因は未確定で、失敗した試験基盤の記録として残します。既存の本番サーバ・既存規則の緩和は行っていません。

タグなしイメージの一覧確認と、コンテナ撤去時の監視競合も試験基盤側で修正しました。これらの対応でS3へ再送していません。回帰試験16実行（S3制御7項目、比較器9項目など）も通過しました。専用コンテナ・デーモンは停止撤去済みで、保持中のS3オブジェクトは残しています。
