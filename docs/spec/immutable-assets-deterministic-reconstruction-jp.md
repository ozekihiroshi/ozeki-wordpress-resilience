# Immutable Assets, Deterministic Reconstruction

**不変の情報資産による決定的な再構築**

2026年10月22日採用の設計原則。[英語版](immutable-assets-deterministic-reconstruction.md)。今回は文書化のみで、追加実装・試験は行っていません。

> Ozeki WordPress Resilienceは、個別に保存された不変の情報資産、バージョン固定された再構築規則、および明示的に定義された実行環境を入力として、事業に必要なWordPressの論理状態を再生成する。
>
> 元のWordPressデータベースや実行環境は、再構築時の必須入力としない。
>
> 同じ入力から同じ論理的結果が得られることを、反復実験によって検証する。

これは今後の到達条件で、現行実装がすでに新しいWordPressを再構築できるという意味ではありません。S3先行原本を正常とする前提、常設別EC2不要の構成を維持します。

## W = F(A, R, E) の意味

| 入力 | 固定するもの |
|---|---|
| A：情報資産 | 選択したサイト世代、本文・画像・関係・必要情報。独立ID、固定版、ハッシュで参照先を閉じる |
| R：規則 | 変換、ID対応、リンク再構成、必要情報、代替表示、欠落の扱い、比較・正規化規則。名前だけでなく内容のハッシュを固定 |
| E：環境 | WP、テーマ、許可プラグイン、再構築エンジンF、PHP・拡張、DB・文字コード・照合順序、言語・タイムゾーンなど。実行物の版とハッシュ、取得方法を固定 |
| W：結果 | 事業に必要なページ・文章・画像・関係・動作。DBの全バイト列ではない |

F自身の実装が変われば結果も変わり得るため、エンジンのビルドもEに含めます。実行物が取得できない場合に、黙って最新版へ差し替えません。修正版への更新は、新しいEによる新しい再構築として扱います。

現在の素材入力は型付きJSON・プレーンテキストとJPEG/PNGです。この原則を掲げただけでMarkdownやPDFが対応済みになるわけではありません。

## 純粋な計画と、書込みを伴う実行を分ける

まずA/R/Eだけから再構築計画Pを作ります。この計画生成では旧DB・旧ファイル、現在時刻、外部API、ホストの暗黙設定に頼りません。その後、実行器が新しい環境へ計画を反映します。

WordPressを動かす処理全体が厳密な純粋関数になるわけではありません。**論理結果の決定性を契約とし、副作用のある実行部分を分ける**という設計です。

移行先URL・保存パス・新規認証情報・運用上の生成日時は「配置時の値」として明示的に渡し、秘密情報を除いて実行記録に残します。これらが事業情報や動作を変えるなら、単なる環境差として無視せずR/Eの入力に含めます。

WPのDBは普段どおり使います。ただし保護対象の編集は先に新しいS3原本へ反映し、DBをその投影として更新します。未対応の直接書込みまで保護したとは扱いません。

## 守る四つの規律

1. 原本は上書きせず、新版を追加する。保持付きコピーは原本の論理ID・内容・由来を変えない。
2. 規則と比較方法を版管理する。規則が変わったものを同じ入力と呼ばない。
3. 環境とエンジンを固定する。古い脆弱な版を使い続けることは要求せず、更新時は新しい入力として評価する。
4. 再構築中のメール・外部API・決済・Cronを止める。アプリ設定だけでなく実行環境や通信制限でも抑える。固定パッケージの準備と、入力を閉じた再構築実行を分ける。公開・外部連携の再開は別判断とする。

## 最初の「同じ論理状態」の判定

比較対象は会社案内・サービス・連絡先の役割、タイトル、本文と順序、公開状態、必要な連絡先、画像の原本ハッシュと使用位置、リンク先、関係、ナビゲーション順です。対応範囲が広がった際には代替文・説明・アンカー・必要機能も契約に追加します。

正規化してよいのは、独立資産IDへ対応付けたDB内部ID、明示した移行先ドメイン・配置パス、事業上の意味を持たない運用時刻です。本文の公開日など意味のある日付は勝手に除きません。URLのクエリーやフラグメントを一律に削除して、壊れたリンクを一致扱いにしません。

比較規則は結果を見る前に決めます。不一致が出るたびに比較から除外することを禁止します。

## 新しい中核試験の合格条件

- 小さな生成データのA/R/Eと、独立した期待結果を先に固定する。
- 元WordPress・DB・ファイルへ接続できない状態にする。
- 別々に準備した空の環境へ2回再構築する。一方の生成物やキャッシュを他方に流用しない。
- 移行先URLやDB内部IDだけを意図的に変え、明示した対応付けが働くことを確認する。
- **正規化した結果1＝結果2＝独立した期待結果**であることを確認する。2回とも同じ誤りなら不合格。
- ページ・画像の不足、未解決リンク、旧環境への隠れた依存、禁止したメール等の副作用があれば不合格。
- 入力・エンジン・比較器のハッシュ、環境、結果、差分、欠落を保存する。自動公開はしない。

これは再現性を確認する目的の反復で、日数を決めた長期観測を再開することではありません。既存のS3競合・再開・保持試験は保存の前提条件として残し、再構築の証拠に読み替えません。

## 現在地と次の単位

| 部分 | 状況 |
|---|---|
| Aの原本保存・固定版・世代管理 | 最小PHP実装とローカル試験あり。実AWS/IAMは未検証 |
| 本文・画像・関係の独立化 | 小さな型付きパッケージあり。WPの全形式には未対応 |
| Rの固定と依存関係 | 未実装。現在のProfileは役割対応のみで、完全な規則定義ではない |
| EとFの固定・実行物の確保 | 未実装。既存の試験イメージを一般的な環境契約とは扱わない |
| 計画生成・新WPへの投入 | 未実装 |
| 論理状態の抽出・比較・2回再構築 | 未実装・未実施 |
| 通常編集から投影を更新する入口 | 未実装 |

次の中心は、**既存のAに固定したR/Eを結び付ける再構築定義と、論理状態の比較契約**です。その後、3ページと画像の計画生成・再投入を実装し、上記の中核試験へ進みます。監視や通知をさらに広げることは、この原則の達成条件にしません。
