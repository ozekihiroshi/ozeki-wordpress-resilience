# DBとファイルの取得整合性契約 v0.1

更新：2026年10月19日。状態：初期仕様とローカル模擬試験。MariaDB/WordPress実環境への取得制御は未統合。

## 目的と判定の境界

DBだけのトランザクションスナップショットは、メディア・テーマ・プラグイン等のファイルを同時点に揃えるものではない。各ファイルのハッシュが正しくても、DBが参照する内容と同じ世代とは限らない。

初期方式は **書込み停止・進行中処理の完了・停止維持を確認した窓の中でDBとファイルを取得する方式** とする。無停止整合性は初期仕様に含めない。取得の開始・終了前後でハッシュが同じ、HTTP入口が閉じている、cronが止まっている、ダンプが成功した、という条件だけでは成功としない。

整合性合格、S3保存、保持確認、署名、本番再公開は別の状態である。今回は整合性判定契約を追加する。署名された2026年10月18日の既存候補を再署名したり、整合性確認済みへ書き換えたりしない。

## 書込み元の棚卸し

制御する書込み元の一覧は収集プログラム自身が都合よく減らせないよう、運用設定として別に渡す。最低限、HTTP/PHP処理、wp-cron/システムcron、キュー・外部連携、WP-CLI/SSH/デプロイ、自動更新、DBへ直接接続する利用者、ファイル共有・外部ストレージを点検する。未把握の経路や制御できない経路があればunverified。

読み取り専用に見えるアクセスもセッションやキャッシュを書き込む場合がある。初期実装で確実に全経路を制御できなければ、短時間のアプリ・ジョブ停止を選ぶ。実サイトの停止時間帯と最大許容停止時間は未決定。今回サイトの停止・書込み制限は行わない。

## 取得の手順と証拠

1. fence：新規書込みを拒否し、試行ID・対象サイト・停止の所有トークンを発行する。
2. drain：全書込み元が停止を確認し、進行中の処理がゼロになったことを確認する。未完了トランザクションやファイル更新の途中で進めない。
3. snapshot：スキーマ変更も停止した状態でDBスナップショットを作る。対象テーブル・エンジンの対応を点検し、未対応があれば不明扱い。MariaDB用の具体的制御は別途実装・試験する。
4. copy：停止を維持したまま全対象ファイルを取得する。DBとファイルの生成順は固定する。大きなアーカイブを保存元へ置かず外部作業領域へストリーム転送する。
5. verify：出力サイズ・ハッシュ、全生成処理の終了コード、停止トークン継続、書込み世代、前後ファイル一覧、対象固有のDB参照を検査する。
6. release：自分が所有する停止だけを解除し、解除できたことを確認して試行を終了する。

全期間を囲う強制的な停止が中心要件。ファイル一覧と世代番号の検査は補助であり、全経路を観測できる実装が必要。世代番号が変わらないという自己申告だけで強制停止を証明しない。停止から解除までの時刻・最大継続時間・所有者・解除結果を実アダプターで記録する。模擬コードのphase配列は実環境の時間計測を代替しない。

## 状態

| 状態 | 条件 | 後続処理 |
| --- | --- | --- |
| capture_failed | DB/ファイル生成の失敗・途中終了・空出力、解除未確認 | 自動成功表示・整合性合格としての発行を禁止。解除未確認は運用復帰の対応が必要 |
| inconsistent | 世代/ファイルの変化、DB参照と取得ファイルの不一致 | 新しい試行IDで再取得。異なる試行の資産を混ぜない |
| unverified | 停止範囲不明、停止未確認、進行中処理あり、トークン喪失、DB/スキーマ確認不足、証拠欠落 | 収集物を調査用に保存できても、整合した復旧点とは表示しない |
| consistent | 全必須条件が確認できた | 整合性の受入候補。保管・保持・独立検証・署名・再公開は別途必要 |

停止解除失敗時に整合性だけ成功しても、試行全体は成功と表示しない。取得失敗時はfinallyで解除を試み、解除失敗と取得失敗を別々に残す。プロセス停止・ホスト障害時の期限付きリース/監視・手動復帰は実アダプターの必須事項。自動解除した場合は途中取得を合格にしない。

## 実装範囲

`tools/capture-consistency.py` は `owr-capture-consistency-v1` の観測と独立した期待書込み元一覧から状態を返す純粋な判定器。明示的な条件分岐を使い、Python最適化で重要な拒否条件が消えない。未知・欠落した必須証拠は不合格。観測の真正性や侵害されたホストの虚偽報告は判定できない。

`tools/simulate-capture-consistency.py` は標準ライブラリのSQLiteと実ファイルを一時ディレクトリに生成する。DB backup APIでスナップショットを取り、メディアのハッシュ参照を照合する。並行書込み試験はthreadとmutexで書込み拒否を確認する。更新競合・ABAはスナップショット後の決まった位置にバイパス書込みを挿入するため、タイミング依存ではない。

SQLiteの試験はMariaDBのロック、WordPress全経路、S3転送中の停止維持を実証するものではない。途中失敗・停止喪失・解除失敗は故障注入であり、実OS障害試験ではない。ファイル一覧は模擬image.binだけ。現実の対象範囲・シンボリックリンク・外部メディアは実アダプターで扱う。

DB参照検査は模擬DBに格納したファイルハッシュとの照合である。通常のWordPress DBに同じハッシュがあるわけではなく、添付メディア・派生ファイル等の具体的な参照契約は未実装。既存の署名候補の発行器へこの判定を必須にする統合も未完了。従来の整合性未確認パイロットを自動実行しない。

## 模擬試験

正常停止、並行書込み拒否、停止なしで偶然一致、DBとファイルの間の更新、更新後に元へ戻るABA、未知の書込み元、進行中処理、DB生成失敗、ファイル生成失敗、停止リース喪失、解除失敗、スキーマ変更の12ケースを検査する。

```bash
python3 tools/simulate-capture-consistency.py --output .local/consistency-lab-new.json
python3 tools/capture-consistency.py --record OBSERVATION.json --writer web --writer cron --writer cli
```

出力先は新規ファイルのみ。シミュレーター出力のcases[].observationが判定器の入力で、全体レポートをそのまま渡さない。判定器はconsistentのみ終了コード0、他は1。オフラインで動き、実サイト・AWS・Docker・資格情報に触れない。

## 次の受入

本仕様と模擬試験の後、MariaDB＋WordPressの専用模擬環境で、実際のHTTP/cron/CLI書込み・DDL・失敗・タイムアウトを制御するアダプターを実装する。その結果を踏まえ、停止時間帯と上限を決めて初回実サイトへ適用する。まだ日次運用の整合性保証は開始しない。

## 初回試験結果

[12ケースの公開集計](../../evidence-public/capture-consistency-lab.json)。正常停止と並行書込み拒否の2ケースのみconsistent。他10ケースは不整合・未確認・取得失敗として拒否した。DB取得後にファイルを更新すると、実際にDB参照ハッシュとの不一致を再現できた。ABAでは前後ファイル・参照ハッシュが一致しても世代変更により拒否した。模擬作業領域・ロックは各ケース終了時に解放した。

追加確認：出力ごとのsite_id/attempt_idも照合し、異なる試行の混在を拒否する。取得前後に加え、コピー先ファイル一覧の全ハッシュ一致も要求する。参照されたメディアだけが一致しても受け入れない。全Python契約80件と、最適化実行での整合性テスト9件に合格した。

## WordPress / MariaDB 実アダプター試験（2026-10-19）

専用環境の協調更新入口で、実際の書込み停止・処理排出・DB読取りロック・取得・解除を実装した。10ケースと既存Python契約80件に合格。ダンプを空DBへ復元し、取得済みメディアとの参照一致を確認。HTTP/CLI拒否、直接DB更新の待機タイムアウト、取得失敗・排出期限・リース期限・制御切断時の解除を確認した。[手順と適用範囲](../guides/wordpress-consistency-lab.md)、[実測](../../evidence-public/wordpress-consistency-lab.json)。任意のWordPress更新経路を制御する本番アダプターや、強制終了後の独立監視は未統合。実サイト全体の整合性合格へ読み替えない。

## 実更新経路と判定器の接続（2026-10-19）

専用環境でPHPのWordPress読込み前に受付を制御し、管理画面フォーム、標準REST投稿・メディア、標準Ajax、wp-cron、PHPファイル実行と終了コールバックの排出を実測した。先行分を含む19ケースに合格。サイト全体の取得前後/tar内ハッシュとDB復元後のメディア参照を確認し、既存判定器で試験構成内のconsistentを得た。停止中はGETも503。直接ファイル変更はinconsistent、未登録更新元・停止範囲未確認・リース喪失はunverified。[構成・範囲・再実行](../guides/wordpress-route-consistency.md)、[実測](../../evidence-public/wordpress-route-consistency.json)。php -r等の管理者バイパス、外部キュー、任意子プロセス、SSH/デプロイは未網羅であり、本番のscope_completeへ転用しない。

## SSH・外部キュー・子プロセスの専用試験（2026-10-19）

制限されたSSH運用ユーザーと別コンテナのHTTP/SQLiteキュー・単一ワーカーを専用実行サービスへ接続した。固定ジョブとその子が終了するまで共有ロックを保持し、停止中はSSH受付を拒否、キューはACKせず保留する。先行分を含む29ケースとPython契約80件に合格。キュー再起動・重複配送・停止後再開・期限切れ・ワーカー確認欠落も検証。[実装範囲と再実行](../guides/wordpress-external-writers.md)、[実測](../../evidence-public/wordpress-external-writers.json)。取得したDB/全ファイルは拡張した期待更新元でconsistent。本番のroot/Docker管理者、任意デプロイ、未登録ワーカー、外部ストレージは未網羅であり、キュー自体の復旧・再配送方針も別途必要。

## キュー資産の整合復旧（専用環境）

キューを独立した復旧資産としてDB・ファイルと共通チェックポイントに束ねる。世代違い、資産破損、未対応ハンドラーを復旧前に拒否し、復元後は完了記録とDB・ファイルの対応を確認して配送を再開する。ACK喪失は同じIDで再配送、効果の衝突・実行失敗は隔離。取得後の投入は別途照合が必要でRPOゼロとはしない。[詳細仕様](../guides/queue-recovery.md)。

## 三資産の固定版と独立署名

共通取得記録を三資産のVersion ID・保持証拠と同一署名文書に含める。署名・信頼ピン・鮮度・三資産を全て検証してから復元へ渡す。[専用環境の新形式](../guides/protected-queue-set.md)。既存セットの承認範囲は変更しない。S3部分は模擬であり実AWSの保持強制の実測とは区別する。
