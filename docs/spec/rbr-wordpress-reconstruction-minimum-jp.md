# 固定計画Pから新しいWordPressへ再構築する最小実装

試作版の開発キットです。会社案内・サービス・連絡先と装飾画像を、専用の新規WordPressへ投入して比較します。本番向けの導入入口や管理画面、自動公開ではありません。[英語仕様](rbr-wordpress-reconstruction-minimum.md)を主文書とします。

## 今回一続きにしたこと

既存のA・Rから計画Pを作り、実WordPress/PHP/DBと専用テーマを固定したEの下で、画像登録→下書きページ作成→本文・画像・リンク投入→非公開プレビュー→実DBとHTTP応答の観測→期待結果Qとの比較を行います。

2つの環境はDB・uploads・設定を別々に新規作成します。同じD/A/R/E/C/Qを使い、URLと内部IDを変えます。元WordPressや旧DBは参照しません。期待結果を投入処理から作らず、独立に定義したQとそれぞれ比較します。本文1文字・段落順・リンク先の変更、画像削除を実際の対象へ加え、比較または必須HTTP取得検査が失敗することも確認します。

## 固定と隔離の意味

Eは計画用ダミーから、実際にキャッシュされているOCIイメージの完全なIDとテーマの固定ソースへ差し替えます。実際の起動イメージも照合します。実行・観測・比較・試験環境準備のコードも固定ビルドに含めます。これはローカルに存在する固定依存物による実証であり、実行イメージのS3保管や別PCでの入手性の実証ではありません。試験で使ったソフトウェア版を本番推奨とするものでもありません。

外部向け既定経路のない内部Dockerネットワーク、公開ポートなし、メール/WordPress HTTPの遮断・試行記録、Cron無効化を使います。新規インストール時の通知試行は遮断し別記録に残します。再構築・観測中の試行は0を合格条件とします。匿名アクセスでは下書き本文を表示せず、WordPress認証を使うプレビューで検査します。常設の別EC2は不要です。

## 境界と残る課題

- 実験用Aの保存は既存のローカルS3契約ダブルを再利用。今回はAWSへ接続していません。
- 既存の承認条件を変更しません。Pの `execution_authorized: false` も維持し、明示した専用実験の実行だけを許可します。
- 同じ対象への再投入は拒否します。途中失敗した対象を再開する仕組みは未実装で、新規環境でやり直します。
- 最初の実証は3ページ・装飾PNG1枚・連続した関連ナビゲーション位置。一般的なブロック、フォーム、説明付き画像、任意テーマ/プラグイン、疎なナビゲーション位置の再現は未確認です。
- 管理画面・本番導入・自動公開・イメージの独立保管は今回の対象外です。Qとの一致は公開承認や侵害されていない証明を意味しません。

## 問題の区別

環境問題はDockerの自動サブネット割当枠不足でした。既存ネットワークを変えず、重複のない専用内部サブネットを使用します。

試験基盤では初期コピー完了待ち、PHP文字列生成、WP_INSTALLING、数値optionの型、DB_COLLATEの指定方法を修正しました。失敗した試験は成功として数えません。

今回の実装では、補助関数 `checked()` がWordPress標準関数と衝突していました。固有名 `rbr_checked()` へ修正しました。

結果は[検証記録](../../evidence-public/rbr-wordpress-reconstruction.json)に記載します。本番・既存の承認処理・終了済み観測は変更しません。
