## 再開順序と完了条件

- [ ] バックアップ製品の現行mainとPR差分を再確認し、以後の修正との競合・仕様差をレビューする。
- [ ] 共通部品の固定版・ライセンス・ハッシュを確認する。出自を記録するUPSTREAM.jsonと、同梱版を固定するdistribution.jsonを混同しない。可変ブランチURLに加え、採用する正本のコミットを更新記録に残す。
- [ ] 最終採用コードで旧API互換、native/PHPの取得・復元・強制終了後の再開、ビルドZIP内の同梱ハッシュ・WordPressでの読込みを確認する。過去試験を再実行済みと表示しない。
- [ ] PRをレビュー可能にして、採用判断後にマージする。延期する場合は理由と再開条件をPRに残す。
- [ ] 既存0.3.0候補を上書きせず、次の配布版・変更履歴・戻し方を確定する。WordPress.orgへの公開は別のリリース作業とする。

過去の回帰試験は[共通化時の記録](shared-core-development.md)を参照。今回新しく実行したのは同梱ハッシュの照合のみであり、全回帰試験の再実施ではない。

## 保守責任と範囲

正本の修正はResilienceのpackages/backup-coreで行い、バックアップ製品側のlibsを手修正しない。更新PRには正本の版・コミット・同梱ハッシュ・両製品の検証結果をそろえ、各製品の配布版は独立して決める。取り込みまで既存の固定版を維持する。

現在共有しているのはPHP DBダンプと書込み補助。S3転送、gzip、メディア全体、保持・署名・復旧判断を共有済みとはしない。別プラグインの自動インストールは不要。Resilienceの現在の日次CLI取得を、このPHP部品へ統合済みとも扱わない。

この残作業はバックアップ製品への採用・配布管理の課題であり、環境の待機タイムアウト調査や3日間の観測終了を待つ課題ではない。今回の整理では実行コード、稼働サイト、既存公開候補を変更していない。
