Thank you for reviewing Ozeki Resilience. I have uploaded 0.3.3 rc.3 to the existing application and would appreciate clarification on two points.

The recovery feature reconstructs a site from the administrator's own trusted Baseline, independently preserved content and confirmed history in their S3 storage. It is not a code-entry editor or a developer-hosted update channel. Recovery requires explicit administrator action and checks fixed object versions, hashes and destination paths; it respects WordPress file-modification restrictions. Hash checks establish integrity, not whether code is trustworthy. May archived theme/plugin restoration remain as part of this recovery workflow?

Declarations now use the OzekiResilience\M1 namespace. Existing owr_ option/meta names and hooks are retained to preserve saved state and integrations. May these existing identifiers remain, or is migration required before approval?

Markdown originals are validated as archival text and are not executed or directly output as HTML. Stripping markup would destroy legitimate source/code examples. Rendered URL changes now use WordPress's HTML Tag Processor to escape changed attributes without stripping unrelated shortcode output.

Source and validation: https://github.com/ozekihiroshi/ozeki-wordpress-resilience/releases/tag/wporg-0.3.3-rc.3
