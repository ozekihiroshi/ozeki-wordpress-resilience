# WP-Members 適用契約の開発用検証

この検証は、原本から契約上必要な内容を取り出し、製品の適用内容と復旧先の読み戻し結果を比較する。原本の保存処理、製品の実行経路、配布ZIPには組み込まない。製品側の適用結果から期待値を作ってはいけない。

## 構成

- `MemberApplicationContract.php`: 検証の基準となる契約。項目型ごとの必要な定義、対応設定、会員属性・値、比較方法を定める。原本は変更しない。
- `MemberContractReadback.php`: 製品のcapture/project処理を呼ばず、WordPress APIから復旧先を観測する。元IDとの対応、subscriber権限、旧セッション等の不在、人数、ページ参照、記事・固定ページの制限設定も確認する。
- `member-contract-test.php`: 製品の適用結果と独立した期待内容を比較する。実画面由来の定義と、契約の全設定を含むデータを使う。各末端項目を一つずつ取り除き、不合格になることも確認する。
- `member-contract-check.php`: 別のWordPress起動で復旧先を照合するCLI。正常は終了コード0、不一致・実行失敗は1、使い方の誤りは2。

今回の契約版は `wp-members-application-1`、実環境の確認版はWP-Members 3.5.8.1。契約と実装が同じ誤認を持つことを避けるため、実画面から採取した試験データと実環境の利用確認を併用する。

## 契約の範囲と判定

会員情報、対応項目の定義と値、認識された設定を比較する。値はWordPressのメタデータ表現を保持して比較し、型・値・空欄・未設定を勝手に揃えない。表示フラグのみ、明示したtrue/falseと0/1の表現を同等として比較する。選択肢、区切り文字、チェック値、入力条件は独立した必須比較項目になる。

契約は入力フォームの業務バリデーションを新たに実装するものではない。会員メタデータの値は、対応キーに属する配列内の単純値として型を確認し、原本からの欠落・変更を検出する。全ての項目設定の組合せや業務上の整合性を検証済みという意味ではない。

- `missing`: 必要な値・定義が欠落。不合格。
- `changed`: 値や型が契約上同等でない。不合格。
- `unexpected`: 適用内容へ契約外の情報が加わった。不合格。
- `invalid-source`: 正常な対応データとして期待内容を作れない。不合格。原本はそのまま残る。
- `excluded`: 原本に保持するが、この契約では適用対象外の項目。正常な対応値の欠落とは区別する。

結果には項目パスと理由だけを出し、会員値・パスワードハッシュは出力しない。

## 実行

リポジトリのルートから、既存の契約試験と同じPHP環境で実行する。

```sh
php tools/testing/member-contract-test.php packages/markdown-m1
```

CIの既存contractsジョブにも登録している。CIへの登録と、GitHub上でその実行が完了したことは別である。

別プロセスでの実環境照合は、専用の隔離サイトで次のように実行する。

```sh
php tools/testing/member-contract-check.php /isolated/site/wp-load.php /private/expected.json
```

`expected.json`は以下の構造で、検証済みS3原本からBaselineと対象履歴を組み立てた、**適用前**の状態を入れる。

```text
raw: membership、tables.posts、tables.postmetaを含む適用前の状態
source_url: その原本の元サイトURL
trusted_defaults:
  version: 別の新規隔離サイトへ導入したWP-Membersの版
  settings: その導入直後のwpmembers_settings
```

入力ファイルには秘密情報が含まれるため、Web公開領域外に権限0600で置き、リポジトリへ入れない。S3原本の検証・履歴の組立て・この入力の作成は呼び出し側の責任である。CLIは入力の出所を認証するツールではない。

標準設定は、信頼できる同じ版を別の空の隔離サイトで有効化して取得する。`wpmem_install_settings()`は設定を書き戻すので、検証対象から標準設定を得る目的で呼んではいけない。保存された認識済み設定と、別途得た標準設定を分けた上で期待内容を構成する。

復旧直後、利用者のログイン前に実行する。ログイン後に新しく作られたセッションを「旧セッションの持ち込み」と混同しない。WordPress起動にはプラグインの処理も伴うので、隔離環境で確認前後の状態も比較する。

## 既存の仕組みと追加した仕組み

保存・履歴・Baseline・Checkpoint・製品の適用処理は既存のまま使う。会員項目を修正するたびに人が目視で追う代わりに、適用前データから期待内容を作る処理と、結果の欠落を検出する比較を追加した。

今回の契約は開発用の独立した基準であり、製品の適用規則を生成するものではない。両者の変更が食い違えば、契約試験の代表データ・宣言した設定について差を検出する。新しい正常な保存表現が実プラグインで生じた場合には、実データの採取と契約更新が必要であり、自動的に未知の全表現を網羅するものではない。

## 2026年11月11日の確認

- PHP 8.3.36、隔離WordPress 7.1.3、WP-Members 3.5.8.1。
- 正常な製品適用結果は合格。契約試験の166箇所を個別に欠落させ、全件検出。
- 実S3の適用前データでも正常は合格。会員定義・値の280箇所を個別に欠落させ、全件検出。欠落はメモリ上の比較用コピーにだけ作り、S3や会員DBを破損させていない。
- 実際に隔離サイトへ復旧後、別リクエストで会員・定義・標準設定と8件の記事・固定ページの制限状態を照合して合格。
- 最終CLIを2回実行し、設定・会員・会員メタデータ・投稿メタデータの前後ハッシュが一致。
- 実S3の原本・履歴の個別ハッシュと、組立てた復旧状態が復旧前後で一致。
- 初期の検証コードでは標準設定取得に副作用のある初期化関数を使い、隔離先の設定を変えてしまった。別サイトで標準設定を取得する方式へ修正し、隔離先を元のS3資産から再復旧して上記の最終確認を行った。製品コードやS3保存処理への変更はない。

前回の会員項目修正で実施したログイン・編集・再保存・再復旧の結果は保持する。今回その利用試験一式を繰り返したわけではなく、契約による欠落検出と読み戻し照合を追加した。これだけで公開準備全体の完了とはしない。

### 最終レビューとURL判定の修正

過去の実装を隔離環境で照合し、表示フラグの型不一致、選択肢・入力条件など33項目の欠落、起動に必要な標準設定9項目の欠落を検出した。定義の欠落を確認する際は、先に発生する型エラーを避けるため、比較用コピーのフラグだけを有効な旧表現0/1にした。標準設定の欠落はトランザクション内で確認してロールバックし、対象データの前後一致を確認した。

レビューでは、検証側のURL変換が似た名前の外部ホストまで置換する問題を発見した。元サイトそのもの、または `/` で区切られた子パスのみを対象に修正した。製品の変換関数から期待値を作らず、固定した期待値でサイト内URL・似た外部ホスト・似たパス・末尾スラッシュ・数値ページIDなど10ケースを確認して合格した。既存166項目の欠落検出と、隔離復旧先の別リクエスト照合（制限8件）も合格した。

この結果はWP-Membersの開発用検証を取り込む判断の根拠であり、他アダプターの確認完了や新しい配布版の公開判断を意味しない。提出済みrc.10のZIPとタグは変更していない。
