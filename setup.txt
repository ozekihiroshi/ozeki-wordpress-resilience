# Setup and current release scope — 0.2.0

This is an operator-managed integration. The plugin ZIP contains WordPress UI,
request handling and projection code. It does not contain an AWS SDK or silently
install an external worker. The matching operator kit/source revision is required.
Source and release location: https://github.com/ozekihiroshi/ozeki-wordpress-resilience
During submission preparation the branch is `release/wordpress-org`. Pin the exact
commit supplied with the distribution rather than following a moving branch.

## Source editing

Use a dedicated enrolled WordPress with PHP >= 8.1, DOM, and InnoDB tables.
The Linux/POSIX worker needs Python 3 (fcntl support), PHP and the dependencies
specified in the kit. Create a private bridge with `requests` and `reports`
directories, writable/readable only by the designated WordPress and worker users.
Keep it outside the public document root. Back up configuration and journals
outside the replaceable plugin/runtime directory.

Explicit source enrollment requires `OWR_RBR_DISPOSABLE=1` in the PHP process
environment and `define('OWR_SITE_MATERIALS_BRIDGE', '/private/bridge');` in
wp-config.php. This legacy opt-in name is retained; no environment is enrolled
merely by installing/updating the plugin. Initial `owr_site_editor` state must
contain the verified material site and receipt, and its projection must match.
The kit's `tools/run-site-editor-lab.py` documents a generated-data example;
it is a test harness, not an existing-site migration tool. Do not import an
unverified receipt or use the harness on an existing production site.

The existing worker configuration contains `transport`, `work`, `bridge` and
`prefix`. Run `python3 tools/site-editor-worker.py --config /private/editor.json`.
Use one designated writer host; preserve its journal. `filesystem-lab` is a test
double, not cloud protection. `experimental-s3` is the supplied dedicated adapter:
`tools/rbr-s3-kit.py`, `tools/queue-s3-adapter.py` and `tools/lab-s3-request.py`
contain its SSH aliases, scoped bucket/region/roles and permitted keys. It requires
operator-provisioned matching signing hosts (`community` writer, `dm` reader).
The included experimental identifiers are not portable account defaults or
credentials. There is no generic AWS enrollment UI or automatic IAM provisioning.
Operators without that compatible external environment cannot enable live S3
protection using the plugin ZIP alone. This boundary is disclosed in readme.txt.

## Recovery target

Prepare a separate WordPress installation with InnoDB and no existing posts,
pages or attachments (including installation samples). The projection rejects an
unrelated populated target. Set its URL, administrator and web-server access
controls before reconstruction; the plugin does not prepare the hosting service.

The recovery configuration reuses the writer's `transport`, `work`, `bridge` and
`prefix`, and adds:

```json
{
  "target_mode": "wordpress",
  "target_label": "Operator-prepared recovery site",
  "wordpress_path": "/srv/recovery/wordpress",
  "target_url": "https://recovery.example.invalid",
  "wordpress_user": 1,
  "php_binary": "php",
  "recovery_work": "/private/recovery"
}
```

These are illustrative values, not a complete storage configuration. The worker
must have local access to that WordPress path. Run
`python3 tools/site-reconstruction-worker.py --config /private/recovery.json`.
It validates the configured target URL and administrator and uses fixed-version
retrieval, retention/integrity verification and request-derived comparison.
Select a generation in **S3先行編集 → 素材世代から再構築**. A repeated identical
request does not create a second job. Failed/interrupted jobs need operator review.

Saved post status is restored, including `publish`. On a reachable destination,
these posts can become publicly visible immediately. DNS, TLS, access controls,
mail/Cron effects and any independent publication approval are operator concerns.
There is no claim that every target is automatically private or side-effect-free.
The optional `docker-lab` target and content-snapshot viewer are retained research
paths; they are not prerequisites for the configured WordPress target.

## Limits and removal

Basic static blocks, administrator editing and PNG/JPEG are supported. See
readme.txt for unsupported editors/content and size bounds. Ordinary existing
sites and legacy three-page state are not automatically converted. A failed
source save retains prior projected content; an unknown S3 result needs journal
reconciliation rather than blind retries. Source apply requires the browser or
explicit resume/apply action after worker confirmation.

Deactivation/removal retains settings, history and external journals. Deactivate
the protected source only as an operator decision: subsequent ordinary WordPress
writes will not be S3-first. Removing the plugin does not delete retained cloud
objects or stop separately managed workers. Stop those services explicitly if
retiring the workflow, and follow the configured retention policy.

## Switching from the GitHub preview directory

The directory slug is now `ozeki-resilience`, approved by the owner for directory
submission. The existing PHP entry filename is retained inside that directory.
Deactivate the old `ozeki-wordpress-resilience` preview before activating the new
ZIP; never run both together. Check settings/history and external worker paths,
then remove only the old plugin code. No option names, journals or material IDs
are renamed. Use a maintenance window for an enrolled source so ordinary writes
do not bypass protection while the old plugin is inactive.
