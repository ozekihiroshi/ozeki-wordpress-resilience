# Flamingoを通常登録で再構築する実装・確認（2026-11-28）

## 結論

Flamingo 2.6.4を変更せず、CF7自身も実受信で呼ぶ既存の `Flamingo_Inbound_Message::add()` を使う再構築入口を実装した。通常受信・迷惑判定付き受信・正式履歴から追加された受信の計3件では、項目・件名・送信者・受信日時・状態・同意・付随情報・ハッシュ・CF7チャンネルを保持し、新IDで登録、管理画面で閲覧できた。

ただし、バックスラッシュを含む保存値では、同じ通常登録へそのまま渡すと値が変わるケースが1件あった。失敗として記録し、内部補正や再書込みは行っていない。したがって、すべての受信がこの実装で成立したという結論ではない。

## 通常機能の意味

Flamingoには受信の取込み管理画面やREST登録機能はない。既存の公開登録メソッドをWordPressが起動済みのCLIから呼ぶ。CF7連携にもともとある `wpcf7_flamingo_add_channel()` でチャンネルを取得・作成する。プラグインのprivateメソッド、初期化、インストール処理は呼ばない。

新しいCF7フォームは先行の通常REST登録で用意し、旧フォームID→新フォームIDの明示対応を渡す。新環境で既存のCF7チャンネル指定があればそれを読み、それ以外はCF7の通常受信時と同じく新フォームのslug/titleでチャンネルを取得する。ResilienceからCF7の `_flamingo` メタを直接書き込まない。通常のチャンネル取得を再度呼んでも同じチャンネルになることを確認した。新規問い合わせ送信そのものは確認していない。

## 素材の扱い

- 初回保存と正式履歴は既存SiteSnapshotの読取り・履歴適用で選択し、原本を変更しない。
- 保存された `_fields` の項目名と `_field_*` の実値を、Flamingo自身の読取り規則と同じ意味で組み合わせる。欠けた値や名前衝突は推測で埋めず保留。
- 保存時のチャンネル関係とCF7の既存チャンネル指定、またはフォームslugを照合する。対応フォームが一意に決まらなければ保留。
- 件名・送信者・受信状態・フィールド・付随情報・同意・迷惑情報・受信日時・posted_data_hashを通常登録引数に渡す。
- 受信当時のmeta内URL・投稿IDは履歴情報として保持する。新環境の実行設定や現行ページ参照と誤認して書き換えない。
- 新IDと新チャンネルは通常登録から受け取る。旧DB行・投稿ID・メタ・チャンネル台帳を直接配置しない。
- 迷惑判定の管理用 `_spam_meta_time` は通常登録が新規生成する。受信日時とは異なり、旧判定時刻を復元する処理は追加しない。

## 実装と失敗の記録

`SiteSnapshot::flamingoRegistrationPlan()` → `FlamingoReconstruction::plan()` で入力を整理し、`FlamingoReconstruction::run()` が既存登録メソッドを実行する。

`tools/reconstruct-flamingo.php` はWP-CLI専用入口。適切な既存管理者を `--user` で指定し、計画JSON、CF7の新ID対応JSON、新規の私的な進行記録、isolated指定を渡す。同じ保存元への適用、権限不足、必要プラグイン未準備は拒否する。再構築処理はプラグインをインストールしない。

登録直後にFlamingo自身の読取りとWordPressの読取りAPIで値を比較する。異なれば、新IDと不一致項目を進行記録に残す。値を修正して成功扱いにはしない。登録済みの不完全な受信を自動削除することもしない。今回の不完全な受信は使い捨て隔離環境内だけに作成され、環境とともに撤去された。

進行記録が既存なら無条件に再実行しない。failedがあれば `completed_with_failures`。held/failedが残った結果を「完全復旧」と扱わない。

## 隔離確認

WordPress 7.1.5 / CF7 6.2.5 / Flamingo 2.6.4 / PHP8.3 / MariaDB10.11。dmの専用内部Dockerネットワーク、使い捨てDBとvolume、外部公開ポートなし。PHPメモリ256MiB、コンテナ各512MiB。S3接続・メール送信なし。既存試験用配布物はコピーだけで使用。

合成データを通常のCF7 REST登録とFlamingo addで作成。初回保存と1件の正式履歴を既存シリアライズ/read/replayへ渡した。履歴レコードはFormHistory形式で合成し、輸送はメモリ内オブジェクトを使用した。日常保存フックや実S3への送信を試験したものではない。

- 通常受信2件と迷惑判定付き1件の厳密な読戻し照合。
- 配列、複数行、日本語、文字列0、空文字、同意情報等を確認。
- 認証済みのFlamingo受信詳細画面のHTTPを取得し、項目の表示テキストを確認。匿名アクセスでは受信値を取得できないことを確認。
- 新CF7 ID、新受信ID、通常機能での同一チャンネル再取得を確認。
- 対応する新CF7フォームがない合成受信は、登録せず理由付き保留。
- CF7フォーム・準備済み設定・保存素材・両プラグイン全ファイルの不変を確認。
- バックスラッシュを含む受信の不一致を検出し、補正せず記録。

実ブラウザのクリックやJavaScript、再保存・再復旧、実問い合わせ送信、Flamingoアドレス帳、添付実体、ゴミ箱状態、外部サービスは今回の確認範囲外。

## バックスラッシュの不一致

通常の登録関数の経路で、受信項目を `update_post_meta()` へ渡している。WordPressのメタ保存ではスラッシュ解除が行われるため、保存済み値をそのまま再入力した場合、既存のバックスラッシュが減るケースがある。今回のテストは元の受信を読み取った値と、新規登録後の値を厳密比較して検出した。

これは現状の入力をそのまま渡す実装の制限であり、Flamingo全体が通常登録で再構築不能と断定する根拠ではない。一方、無条件にエスケープ追加や内部メタ再書込みを行って解決済みともしていない。入力契約の確認と次の判断が必要である。今回の依頼に従い補正は行わず、具体的な前後値は合成データの結果JSONに記録した。
