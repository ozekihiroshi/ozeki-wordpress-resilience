# 構築時記録による通常操作の統合確認（2026-11-28）

## 原則と今回の実装境界

構築した時点で入力・操作順・先行対象への参照を記録し、同じ通常処理を同じ順に実行する。構築後のDB状態から過去の操作や順序を推測しない。参照は構築時に明示し、再構築時には通常処理で発行された新ID・URLを使う。

今回追加した `tools/construction-record.py` は、S3を使わない開発用のローカル実装である。通常管理画面の任意の操作を自動捕捉する製品機能ではない。既存のS3形式、正式履歴、初回保存、製品の復旧UIは変更していない。従来の個別復旧エントリを製品内で置き換え終えたという意味ではない。

この実験では、合成サイトを構築する各操作を記録処理から呼び出す。入力は操作前に永続化し、通常処理の成功確認後に確定記録を追記する。原文や通常入力を保存済みの出力から逆算しない。

## 記録と実行

- 操作名と入力、およびその時点で宣言した先行操作への参照を `attempt` に保存する。
- 成功を確認すると、結果の識別子を `confirmed` に保存する。
- 再構築前に全記録の順序・対応・参照整合を確認する。
- 再構築は同じ通常操作の実行関数を使う。後から順序を組み替えない。
- 新IDの対応は対象生成の結果から得る。既存の対象を名前などで推測して採用しない。
- 未確定操作が残る場合は、再実行を始めない。結果不明の操作を自動再試行しない。
- nonce、Cookie、管理者資格情報、会員パスワードは構築記録に格納しない。会員は標準パスワード再設定で利用する。

ローカル形式名は `owr-local-construction-experiment-1`。公開用保存形式ではない。既存記録の移行、同時実行、汎用入力検証、実運用の機密情報管理を済ませた仕様として扱わない。

## 使う通常操作

| 対象 | 構築元と再構築先で共通に使う処理 |
|---|---|
| 投稿・固定ページ・カテゴリー | WordPress REST登録・更新 |
| 画像 | `media_handle_sideload()` |
| メニュー | `wp_create_nav_menu()` / `wp_update_nav_menu_item()` |
| Markdown Documents | 既存の取込み画面と保存画面 |
| TablePress | 既存の取込みと編集保存 |
| Contact Form 7 | 既存のフォーム登録REST |
| WP-Members | 通常設定画面、会員項目画面、記事の制限欄、WordPress会員登録・プロフィール画面 |
| ACF無料版 | `acf_import_field_group()` と記事編集画面での値保存 |
| Flamingo連携 | 合成CF7フォームへ通常送信し、通常のCF7→Flamingo登録結果を確認 |

Flamingoについて、この統合実験は元の通常送信も含めた経路を繰り返す。外部メールは試験用フィルターで遮断・捕捉する。実製品が問い合わせを再送信してよいという設計決定ではない。既存の `ReceiptInputs` で捕捉する登録入力を共通記録へ接続し、再送信を伴わない通常登録を統合する作業は別途必要である。

## 構築順序で見つかった条件

最初の実行は、元の合成サイトのWP-Membersページ指定で停止した。下書きのログイン・プロフィールページを指定したため、通常画面で選択状態を確認できなかった。

配布版3.5.8.3の `includes/admin/tabs/class-wp-members-admin-tab-options.php` の `page_list()` は `get_pages()` を使用する。通常画面の公開済みページ候補に合わせ、元の構築操作を「ページ登録→ログイン・プロフィールページ公開→通常設定で指定」に修正した。この順序をそのまま記録して再構築する。保存済みの設定値を後で直接書き換える補正はしていない。

資料ページは下書きで作成し、通常の閲覧制限を設定した後で公開する。ログインページの公開と、会員資料の公開は同じ条件ではない。

2回目は試験の比較条件で停止した。CF7のフォーム送信入力 `PLC C:\technical\manual 日本語` に対し、元の通常処理でもFlamingoの保存値は `PLC C:technicalmanual 日本語` になった。入力と出力を直接同一視する判定は、この再構築方式の合格基準ではない。入力を一切修正せず記録し、元の通常処理の出力と再構築側の通常処理の出力が一致することを比較する。対象プラグインの通常処理自体の挙動をResilienceで修復したという報告はしない。

3回目は元サイトの画像HTTP取得が403で停止した。CLI経由の標準APIもWebと同じOSユーザー（`www-data`）で呼ぶ試験構成に揃えた。4回目はそのユーザーが試験用WP-CLIを読めず停止したため、試験開始前のツール読取り権限を整えた。登録後の画像や復旧先データへの権限補正は追加していない。これらの失敗結果も保存し、成功結果だけで経緯を置き換えない。

## 確認範囲と残る接続

最終の[機械出力](construction-record-integration-20261128-results.json)では全判定が通過した。専用Dockerの準備と片付けを含め107.81秒、S3未使用。3個の小さな記録処理試験も通過（0.043秒）。

| 確認 | 結果 |
|---|---|
| 元の構築 | 操作時に26操作を記録・確定 |
| 別サイトへの再構築 | 26操作を記録順に実行、同じ通常利用を確認 |
| 通常編集・再保存 | 投稿タイトルの編集・再保存、Markdown・表・ACFの再保存の5操作を追記 |
| 再再構築 | 追記を含む31操作を別サイトで実行、編集後タイトルも保持 |
| 3サイト共通の利用確認 | 標準パスワード再設定後の会員ログイン、Markdown・表の表示、非会員遮断、画像HTTP取得、ACF値、プロフィール項目、Flamingo管理画面閲覧がすべて成功 |
| 参照 | 資料ページのIDは3サイトで異なる。操作結果の新IDを使って参照 |
| 通常送信の結果 | CF7→Flamingoの項目値は3サイトで一致。入力・出力を補正せず |
| 保全 | プラグインファイルのハッシュ、元の構築記録のハッシュが不変 |
| 初期化 | 観測開始後にWP-Members `includes/install.php` の読込みなし |
| 片付け | 専用コンテナ・ボリューム・ネットワークの削除エラーなし |

成功時記録は `D:/workspace/wp-rescue/release-readiness/construction-record-integration-20261128/construction-record-1795866525-{source,target,again}.jsonl`。最初の4回の停止結果は同じ領域の `first-result.json` ～ `fourth-result.json` と操作記録に残している。すべて合成データであり、公開物としてアップロードしていない。

**判定：構築時の記録を同じ通常操作で実行する統合経路は、この合成ケースで成立した。製品全体の保存・復旧をこの方式へ移行し終えたとは判定しない。**

個別検証の結果は通常操作が使える根拠として継承する。ただし、それだけで統合成立とは判定しない。

今回の対象は、記録経由の合成構築、記録順の再構築、通常ログイン・閲覧、編集・再保存、その追記記録を使う再再構築。公開画像、公開記事、会員制限した埋込みページ、単純な表、フォーム、会員項目、ACFテキスト項目を組み合わせる。すべてのフィールド型・制限方式を再検証したものではない。

製品への統一に残るもの：

1. 実際の管理画面操作時の入力捕捉と成功確定を、対応操作ごとに共通記録へ接続する。
2. CF7→Flamingoの登録入力を同じ記録へ接続し、復旧時の送信副作用を発生させない。
3. 導入前のサイトを扱う初回保存は過去の操作記録ではない。通常再構築に使える素材との関係と、記録開始後の操作列との接続を明示する。既存DBから過去操作を捏造しない。
4. 保存形式を正式に変更する前に、既存原本・履歴との互換性と公開前データの扱いを報告する。

本番、既存S3原本・履歴、ZIP、タグには触れていない。申請・メール返信・push・マージは行っていない。
