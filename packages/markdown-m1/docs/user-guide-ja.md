# 利用ガイド — 導入から復旧まで

[English](user-guide.md) · [AWS設定と完全なポリシーJSON](aws-setup-ja.md)

公開済み[GitHub Pre-release v0.3.1-pre.2](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/releases/tag/v0.3.1-pre.2)の案内です。WordPress管理者向け試験版であり、運用代行サービスではありません。日常操作はWordPress管理者が行い、最初のAWS・サーバ設定は担当者の協力が必要になることがあります。プラグインにAWS秘密鍵を入力しません。このガイドは検証済みのEC2ロール構成を主経路とします。共有レンタルサーバ等はSDK標準認証を実行環境に用意できるか、別途確認が必要です。

**未公開候補の条件付き依存：** `ozeki-wordpress-resilience-0.3.1-optional-markdown.zip` では、Markdown未使用の通常投稿サイトのBaseline作成・復旧にMarkdown Documentsは不要です。有効な場合は収録し、文書・原文が残るのに無効なら保存前に停止します。Markdown復旧時は記録した互換版を事前に導入・有効化してください（確認版0.1.1）。公開済みpre.2は不変で、管理画面のBaseline作成には従来どおり必要です。[候補の検証記録](optional-markdown-verification.md)。

## 1. 何をするのか

最初に信頼できる現在のサイトを **Baseline（初期復旧点）** として保存します。その後、対応する通常編集から独立した原本と正式履歴をS3へ保存します。**Checkpoint** はその保存資産から、対応範囲を再構築する一式を作ります。必要になったら別のWordPressを準備し、選んだ復旧点と正式履歴から復旧します。保存するたびに復旧先が更新される仕組みではありません。

まず管理できる小さなサイトで使い始め、[対応表](../RAADME-jp.md#supported-content-and-plugins)を確認してください。Posts・Pages、ローカル画像、標準コメント、Markdown Documents、CF7・Flamingo、WP-Members基本会員、TablePress基本機能にはそれぞれ制限があります。任意の拡張、外部・CDN資源、追跡対象外の設定変更は自動保護されません。自分のサイトの対応範囲を復旧確認するまでは、既存のバックアップ運用も残してください。

元サイトのWordPress・PHP・プラグインの版とAWS設定表を控えます。宣言上の最低版はWordPress 6.4／PHP 8.1ですが、全組合せの保証ではありません。検証したCF7 6.2.3にはPHP 8.3以上が必要です。InnoDB、ZipArchive、書込み可能なパスが必要で、復旧には非公開の一時領域と互換性のあるWordPressリリース系列・同等以上の保守版を使います。[導入詳細](install-update.md)も参照してください。

## 2. AWSを準備し、プラグインを導入する

未公開候補は別途提供する `ozeki-wordpress-resilience-0.3.1-optional-markdown.zip` と同名の `.sha256` を使います。下記pre.2のハッシュ・容量を候補に流用せず、候補の実サイズと送信分を考慮してアップロード上限を確認してください。プラグイン表示版は0.3.1のままなのでファイル名とハッシュで区別します。

1. [AWS設定手順](aws-setup-ja.md)を実施します。最初は削除不可の **source-no-delete** ポリシー、バージョニング済みの専用prefix、自動削除オフで開始します。複数サイトから同じprefixへ書き込まないでください。
2. 公開済み版を使う場合は、リリースページのAssetsから `ozeki-wordpress-resilience-0.3.1-pre.2.zip` と `.sha256` を取得します。Source code (zip)は導入用ではありません。SHA-256は以下です。
   `109f0db79f1e5b0886b11d6ebcb2df0f4728912baa1217f977de91760b0b3d0a`
3. アップロード前に、PHPの `upload_max_filesize`・`post_max_size` とWebサーバの要求サイズ上限が、7,455,881バイトのZIPと送信時の付加情報を収容できることを確認します。不足時はサーバ担当者が対象環境の上限を調整し、ZIPは変更しません。[アップロード条件](install-update.md)も参照してください。WordPressの **プラグイン→新規プラグインを追加→プラグインのアップロード** でZIPを選び、インストール・有効化します。更新時は[既存の注意点](install-update.md)に従い、更新のためにアンインストールしないでください。設定を控え、可能なら未確定操作を先に解消します。
4. **ツール→Resilience** を開きます。現行画面の操作名は英語なので、以下にそのまま記載します。
5. **Storage and optional scheduling settings** で `bucket`・`region`・末尾 `/` の `prefix`・12桁AWSアカウントIDの `owner` を入力します。最初は **Protect supported operations**、GFSの **Enabled**、自動削除をオフにします。製品から削除ロックを要求しない構成を選んだ場合、**Optional S3 deletion protection in days** は `0` にして **Save settings** を押します。

設定保存だけでは接続・保護成功の証明になりません。次のBaseline成功と、その後の正式履歴で確認します。エラー解消のために他サイトのprefixへ切り替えないでください。

## 3. 最初のBaselineを作る

1. 元サイトが信頼できることを判断し、編集を一時停止して未確定履歴を解消します。未公開の条件付き依存候補ではMarkdown未使用なら追加導入不要です。有効なら収録し、文書や `_ozmd_source` 原文が残っているのに無効なら有効化してから取得します。回避のために原文を削除しないでください。公開済みpre.2は通常投稿だけでもMD導入・有効化が必要です。確認版は0.1.1。他の対応プラグインはコンテンツに応じて有効化します。
2. **Site-wide recovery — primary workflow** で **I trust the whole current site and have paused editing.** にチェックし、**Create complete initial snapshot** を押します。対応する現在のDB情報・ファイルを読み取る操作です。侵害の疑いがあるサイトを、エラーを消す目的で新基点にしないでください。
3. 結果を待ち、成功表示と確定した復旧点が一覧に現れることを確認します。送信できたことだけを成功としません。全資源の保存・固定版照合後にマニフェストが確定します。失敗や結果不明なら理由を記録し、停止して調べます。
4. **Protect supported operations (one writer per prefix)** を有効にして設定保存後、通常編集を再開します。

Baseline自体で復旧できます。初期取得をもう一度行うのは、新たな信頼判断に基づく別Baselineです。対して **Create complete Checkpoint** は既存復旧点とその後の正式履歴をS3から使い、未記録の稼働サイト変更を取り込みません。[三原則の詳細](site-snapshot-ja.md)を参照してください。

## 4. 日常編集と保存失敗

通常のWordPressや対応プラグインの編集画面を使います。代表的な保存の後に **Save protection status** を確認します。「保護設定が有効」は設定状態であり、最後の確定番号・未確定操作・エラーが保存の実態です。本文と付随情報が別の正式履歴になることがあるため、一件の確定だけで関連操作すべてが確定したと考えないでください。

対応する本文保存はS3原本保存後にWordPressへ反映します。コメントや一部の連携・詳細操作は成功直後のデータを取得するため、画面上の変更が未確定のことがあります。現在の新規保存資源は固定版から再取得・照合して履歴確定しますが、状態表示のたびに過去の原本すべてを再監査するわけではありません。

| 表示・状況 | 操作 | 完了の目安 |
|---|---|---|
| キュー登録前の原本保存失敗 | 保存先・権限などの原因を解消し、通常編集画面で再保存。登録されていない要求はResume historyでは戻せない | 意図した内容が保存され正式履歴が確定 |
| 未確定操作・履歴保存失敗 | 理由を調べ、保存先回復後に **Resume history** | 未確定が解消し、対象履歴が確定 |
| 確定前に元サーバを喪失 | 確定済みの境界までを復旧する | 最後の未確定変更を復旧可能と数えない |
| 結果不明・エラー | 理由を控え、連打や成功扱いをせず調べる | 原因を把握してから再実行を判断 |

[履歴再開手順](save-resume.md)。テーマ、メニュー、実行プラグインなど通常履歴が追跡しない変更は、編集停止後に新しい信頼済みBaselineが必要になる場合があります。通常Checkpointでは発見できません。[既存の変更別対応表](start-here-ja.md)を参照してください。

## 5. Checkpointの日時・保持を設定する

画面のタイムゾーンを確認します。例えば週次は日曜02:00・2週間、月次は1日02:00・3か月、年次は1月1日02:00・1年と設定できます。例示であり必須設定・容量検証済みの推奨値ではありません。日付と時刻が重なると一式を一回作って複数区分を付け、一つでも有効な区分があれば残します。更新がなくても独立一式を取得します。同じサーバの複数サイトでは時刻をずらせます。

**Detailed history recovery window in days** は詳細履歴を残す期間と境界の復旧点を決めます。`0` は最新Checkpointと必要な後続履歴であり、全資源を消す意味ではありません。過去のGFS基点は途中の全履歴がなくても残せます。**Optional S3 deletion protection** は別のAWS削除ロックで、`0` に変えても既存ロックは解除されません。[GFS詳細](gfs-checkpoints-ja.md)。

設定後は **Next complete-site Checkpoint (UTC)** を確認します。サーバ担当者と定期的な起動機会を用意してください。WP-Cronは厳密な時計ではありません。実行後は今回の成功・失敗と次回予約を確認します。取得失敗時には削除を行わず、前回の削除成功記録が過去の時刻付きで残る場合があります。

最初は削除しない **Preview complete-site retention** を使い、残す点・必要資源・候補・保留理由を見ます。復旧確認後に[AWSの削除用ポリシー](aws-setup-ja.md)へ変更すると、確認チェックと **Delete expired complete-site resources** で候補を削除できます。定期削除は別のチェックボックスで、定期取得成功後だけ動きます。任意の保持中復旧点を強制削除する機能や初期化ボタンではありません。S3 Lifecycleの経過日数による削除を代わりに設定しないでください。

## 6. 別のWordPressへ復旧する

1. クリーンな専用復旧先に互換性のあるWordPress、製品ZIP、必要なプラグインを用意し、管理者ログインを確認します。WP-Membersが承認を要求する場合、復旧先管理者を別途有効化します。元管理者の認証情報は復旧しません。他用途で稼働中のサイトを復旧先にしません。
2. AWS認証には **recovery-read-only** を使い、Resilienceへ元と同じbucket・region・prefix・ownerを設定します。保護・定期取得・削除はすべてオフ。復旧先でBaselineを作りません。未解決のローカル未確定操作がない復旧環境を用意します。
3. **Site-wide recovery — primary workflow** の **Checkpoint** でBaselineまたはCheckpointを選び、**Formal history end** で適用終了番号を指定します。その番号を含めて復旧します。基点の `through` と同じ番号なら基点だけ、後の番号なら間の必要な正式履歴・資源が必要です。番号は必ずしも編集一回の境界ではありません。
4. 復旧先の置換を確認して **Restore complete site** を実行します。復旧先コンテンツを置換します。ローカル退避があっても自動巻戻しの保証ではありません。S3の復旧資源は残します。
5. 成功・失敗、使用Checkpoint、要求・適用履歴番号、件数を確認します。調査には詳細JSONを残します。失敗なら停止し、原因を確認して復旧先を整え直し、再実行を判断します。失敗したから無変更とは限りません。
6. 再ログインし、代表的な本文・画像・リンクと必要な会員制限・表・フォームの動作を確認します。元の `publish` はそのまま再現します。DNS・ネットワーク公開は管理者の別判断であり、メール再送は復旧機能に含めません。

## 7. 制限と問い合わせ

無害化の証明・無条件復旧の保証ではありません。AccessDenied、認証情報の取得不能、PHP拡張の不足、一時領域への書込み不能、非互換ランタイムは環境条件として原因を調べ、確定条件を弱めて回避しません。問い合わせには版・タグ、操作、エラー、確定番号、必要な環境版を添え、秘密鍵・トークン・個人情報・非公開原本は除いてください。

[残る確認事項](remaining-confirmations.md)にHTTP起動・長期運用・削除途中停止を確認済み機能と分けて記録しています。[初回導入の検証](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/main/docs/releases/user-guide-onboarding.md)では、不足していたMarkdown Documentsの必須前提を補い、ブラウザZIP導入・Baseline・通常投稿更新・正式履歴・別の隔離WordPressへの復旧を確認しました。既存EC2ロールを再利用したため、完全版IAM JSONの新規適用とその権限だけでの導入は未検証です。ビジュアル編集や全対応プラグインの組合せを再試験したものではありません。公開済みZIPは変更せず、新しい案内はオンラインで参照します。
