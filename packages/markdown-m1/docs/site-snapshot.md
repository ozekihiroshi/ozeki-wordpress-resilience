# Complete site baseline and reconstruction

The goal is the same site's content, appearance, navigation and supported behavior on a new WordPress, not merely a readable Markdown document. `SiteSnapshot` supplements the Markdown original/history path.

An administrator-trusted initial capture stores native posts (including pages, revisions, templates, navigation and global styles), metadata, taxonomies, comments, presentation options, raw Markdown, upload files, the active theme/parent and explicitly selected runtime plugin code. Content records are portable JSON, Markdown remains raw `.md`, media remains individual files, and software is a ZIP with per-file hashes. This is not an SQL/database-image restore. Source login credentials, WordPress configuration, AWS configuration, cron queues and SMTP credentials are not imported.

`site-snapshots/<identity>/manifest.json` is written last and pins every resource by VersionId and SHA-256. A Checkpoint copies the complete baseline into its own resource prefix and applies later successful Markdown history, including new documents. It does not require the initial snapshot's resources during recovery. Missing history or damaged resources blocks reconstruction. Later ordinary page, media, template and plugin changes do not yet have S3-first history adapters: capture a newly trusted baseline for those changes; do not claim automatic protection of them. No live-source data is silently adopted during Checkpoint creation. Existing periodic Markdown scheduling is unchanged; automatic whole-site scheduling is deferred.

Tools → Resilience provides complete initial capture, Checkpoint and destination replacement controls. The current UI dependency selection is Markdown Documents plus the active theme. Additional runtime plugin adapters/settings require explicit coverage work; admin-only Backup for S3 and Plugin Check are excluded and recorded. Mail delivery and external portal authentication remain external services, not fabricated successes.

Recovery requires a separate destination URL, write protection disabled, InnoDB content tables, ZipArchive, writable resource directories and the recorded WordPress release line (same or newer maintenance patch). S3 is read-only at the destination. All resources are downloaded and verified before content replacement. The destination's existing content, presentation options and changed files are backed up in a private temporary directory outside the web root. Native IDs are retained within the replaced content set so block/menu/template references stay intact; source users are represented by non-privileged author display identities, never copied passwords. Destination administrative users remain.

Local URL references are rebased recursively, including serialized metadata. Raw Markdown bytes remain unchanged; rendered links are rebased. Existing identical software files are hash-verified and reused. Failed writes roll back touched files and transactional content; process-kill recovery/automatic rollback is not yet an accepted guarantee. A new request loads the recorded theme and plugin code. Do not overwrite active code during concurrent use; perform recovery on a designated destination.

2026-10-24 real acceptance: wp.ceri.link → existing wp-backup.ceri.link using default EC2 role authentication and S3 only for recovery input. 73 post records, 9 raw Markdown files including revision originals, 23 media files and 558 theme/Markdown program files matched. Both public pages, menu navigation, local PDF and three original images were checked. Source WordPress 7.1.2; destination maintenance patch 7.1.3. Source 39-record baseline remained unchanged. The new Resilience code was then deployed on source and its admin controls inspected; source content and scheduling configuration remained unchanged. This is a manual whole-site acceptance, not a periodic execution acceptance or universal plugin compatibility claim.
