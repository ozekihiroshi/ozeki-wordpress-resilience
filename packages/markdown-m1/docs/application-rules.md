# Recovery attribute and setting rules

Status: included in application-rules-final candidate after PR #41, verified with the limits below. The older separated-assets-final ZIP does not contain these rules; no release.

## Boundary

`RecoveryRules::project()` runs in complete-site restoration **after** loading the selected snapshot and replaying the selected confirmed history, **before** destination files or content are replaced. Initial snapshots and subsequent history therefore use the same final application rules. Capture, original storage, Checkpoint generation and S3 resources are unchanged. Projection operates on an in-memory copy; unknown captured information remains in the selected S3 resources. A subsequent Checkpoint is never built from this filtered destination projection.

The existing adapters declare their recognized metadata/settings. Known values with invalid types stop recovery before replacement. Unrecognized keys are withheld and reported by path/reason, without copying their values into the report. Result `application_report` records the rules version, omitted paths and count; the admin result displays them with the existing detailed JSON. A failed/latest attempt does not present an earlier successful omission report as current.

## Rules in this first implementation

| Area | Automatically applied | Preserved in originals but withheld |
|---|---|---|
| Core and Markdown | Body/source unchanged; core article identity/details through existing replay; known image/attachment, featured-image, page-template, menu, trash and recovery identity metadata; known core options | Unrecognized post/term/comment metadata. Markdown source hash is regenerated by the existing renderer, not imported. Core comment trash state is retained |
| CF7 | Form definition, locale/hash, recognized mail-template fields and messages; core `skip_mail`, `demo_mode`, `acceptance_as_validation`, `subscribers_only` directives | Unknown nested mail settings, other additional directives and extension metadata. Recovery does not replay mail |
| Flamingo | Submitted fields, subject/sender, submission status, consent/hash, spam timestamp; post state/channels via existing replay | Other metadata, including third-party analysis payloads; no attachment/address-book extension |
| WP-Members | Existing subscriber/identity checks, approval/restriction, recognized basic settings, core registration-field definitions and values, dialogs/terms | Unrecognized setting keys or field types; session/privilege metadata remains excluded. Only existing captured resources can be retained; this does not add capture of previously excluded credentials |
| TablePress | Table content/IDs, recognized visibility, headers, sorting/search/pagination controls and registry/version settings | Custom DataTables commands, custom CSS/module/extension and editor-notice settings. Custom CSS and modules are disabled in the destination projection |
| Theme/widget settings | Menu locations, custom logo and basic background/header text colours | Other theme-specific settings and all widget option payloads in this first rule set |

Definitions are in FormHistory, MemberHistory and TableHistory; common core metadata is in RecoveryRules. Structured submitted content is retained as data; this is not a content sanitizer or a proof that HTML/Markdown is harmless. CF7 form text and body content are not reparsed into a new security language. Supporting a plugin does not certify arbitrary extensions.

## Limits

- Withheld presentation/customisation settings can change appearance or behaviour. Do not describe this first set as full visual equivalence for every previously captured site. Inspect the omission report; required customisations need an explicit rule before claiming complete reproduction.
- Software bundle selection/installation/activation is unchanged. This work does not implement a software certification registry or clean-distribution installer.
- The supplementary individual text-recovery path already applies its limited attributes; this new report belongs to complete-site restoration.
- Results are local administration records, not a replacement for S3 history. Unknown values remain in S3, not in a new local export or database quarantine. The rules do not preserve unrelated destination content.
- No automatic continuation, new rollback, S3 deletion, IAM change or infrastructure was added.

## Verification

`tests/application-rules.php` verifies known CF7/Flamingo/TablePress/member values, unknown withholding, source immutability, baseline and form-history equivalence, invalid known-type rejection, serialization-looking Markdown preservation, comment trash metadata and escaped/value-free result display. Existing form/member/table/recovery-result/recovery-errors/selected-point contracts pass. These are local fixtures, not AWS or browser acceptance.

Existing dm Docker/WordPress and the earlier separated-assets trial namespace were reused. A stored memory-S3 fixture Checkpoint restored seven post records through history 1 with body, Markdown, image, comment, table and inquiry values preserved. Unknown nested metadata and an unrecognized trial table option were not applied; the product admin renderer showed paths and reasons. The original fixture hash and existing shared-site probe were unchanged; mail attempts zero, no cron or AWS calls. The final core-setting/text adjustment was verified in a second isolated restore. A later small addition retaining core comment-trash metadata and allowing the normal member excerpt-length type was covered by contracts, not another full restore.

New-code correction: CF7 additional-setting filtering initially validated but returned the unfiltered string; corrected before acceptance. Harness issue: a reused contract left its simulated write-failure switch enabled; reset in the test. Existing duplicate DISABLE_WP_CRON warning belongs to the probe bootstrap. These are separate findings.

## Existing real-S3 acceptance (2026-10-25)

Work: verification of implemented rules; status: verified with limits. The existing separated-assets experimental Checkpoint and dm isolated target were reused. No capture, new S3 assets, source environment access or product correction was needed. SDK default EC2-role authentication was used with a test-only read-method guard (not an authentication helper).

Restoration through history 1 succeeded for seven post records. All 24 restoration GetObject requests specified VersionId and stayed inside the Checkpoint directory. HTML and Markdown (including Mermaid/math/code), title/slug/publish state, selected core settings, image, comment, table cells and Flamingo submitted fields matched. Unknown nested metadata remained in the S3 original but was absent from the destination. The unsupported fixture table option `paging` was withheld. The application report contained 21 paths/reasons; the actual administration renderer showed them without copying unknown values.

Before/after hashes of the loaded original resources and the dedicated S3 current-object inventory matched. The existing shared-site probe also matched. Mail attempts were zero; cron disabled; S3 writes/deletes and formal release were not performed. The target was the previously dedicated trial namespace, not the shared site's database tables.

Limits: this fixture does not exercise all recognized CF7, WP-Members or TablePress settings/runtime functions. Those rule cases retain their earlier contract-test evidence, not new AWS functional acceptance. This was an administration-renderer check, not browser interaction. No new ZIP install/update test was performed; the frozen PR #41 ZIP does not contain these rules. The earlier baseline/history common-rule tests remain separate from this Checkpoint-only real-S3 restore.

Harness issue: the first attempt tried to JSON-encode a file collection containing binary image bytes for comparison and stopped before restoration. Its comparison was changed to binary-safe serialization and the verification then passed. No product code change was needed. The existing duplicate DISABLE_WP_CRON warning remains a probe-environment issue.
