# CF7 → Flamingo 入力原本の保全と通常登録による再構築

2026-11-28。開発作業ツリー `codex/native-wordpress-reconstruction`。未公開・未マージ。

## 今回の契約

CF7 が Flamingo の通常登録に渡した引数を、その時点の値のまま保全する。保存済みDB値を入力とみなし直したり、再構築時だけ `wp_slash()` を施したりしない。Flamingo 自身が通常行う既定値の補完と変換は、元の登録と再構築の双方で同じように行われる。

1. CF7 の `wpcf7_flamingo_inbound_message_parameters` で入力JSONとSHA-256、操作UUID、フォームIDをローカルのResilience専用記録へ保存する。フィルターは受け取った配列を変更せず返す。
2. `flamingo_add_inbound` では、Flamingoが既定値を補った後の引数も別のJSONとして記録する。これも変更して返さない。
3. `wpcf7_after_flamingo` の成功IDを確認し、Flamingoの通常の読み出し結果と、その時点の素材・関係を記録する。入力JSONは書き換えない。
4. 共通キューへ同じ操作UUIDで登録し、原本の書込み・読み戻し・正式履歴の確定を経て confirmed にする。S3送信に失敗した登録成功分は registered のまま残す。
5. 初回保存・Checkpointには confirmed の入力原本も含める。登録結果が未確認の入力をDB値から推定して昇格させない。

ローカルの段階は `staged → registered → confirmed`。正式履歴の新しい種類は `owr_form_input`、原本内の契約は `owr-flamingo-input-1`。入力原本を含むサイト保存は `owr-separated-assets-flamingo-input-1` として旧リーダーに拒否させる。既存の原本・履歴を書き換える移行は行わない。

## 再構築

`FlamingoReconstruction` は新しいCF7フォームへの対応表を使い、CF7既存の通常チャネル登録により関係を設定する。入力原本のコピーではチャネル参照だけを新しいものへ置き換え、`Flamingo_Inbound_Message::add()` に渡す。入力原本自体は不変。登録後の投稿・メタデータ・キャッシュの直接補正は行わない。プラグインの変更、再インストール、初期化も行わない。

比較対象は「入力文字列とDB出力の一致」ではなく、「元の通常登録結果と再構築の通常登録結果の一致」。受信日時・フィールド・付随情報も照合する。今回のCF7は timestamp を渡しているため日時も一致した。

Flamingo 2.6.4 の通常登録では、バックスラッシュが失われる例がある。**今回の修正はその第三者プラグインの挙動を補正しない。** バックスラッシュを含む入力原本は完全に残り、再構築結果は元の通常登録結果と一致する。「送信した文字列がFlamingo画面でも無変換で表示される」とは主張しない。

## 中断・再試行

- 正式履歴の書込み応答を失っても、同じ操作ID・原本・履歴を再確認する。新しい正式履歴を重複作成しない。
- 書込み障害後は登録済みの凍結記録を再送する。Flamingoの登録をもう一度呼ばない。
- 成功IDを記録できなかった中断は staged として残る。似た受信がDBにあるという理由で自動確定しない。この未解決状態では新しい初回保存を停止し、注意を表示する。
- 再構築にはプラン・対応表・復旧先に結び付いた排他ジャーナルを使う。登録済みIDは再読取りで確認し、二重登録しない。
- 登録を始めたがIDを記録できなかった復旧処理は、結果不明として保留する。自動再登録しない。ジャーナルを失った場合まで exactly-once を保証するものではない。

未確定入力の管理者による解決UIは今回追加していない。登録結果不明のものを自動判定で解消する仕組みも追加していない。

## 旧形式・登録後の変更

旧形式の保存素材は読み取れる。ただし入力原本がない受信は「保存結果のみ」として新方式の再構築対象から保留する。失われた入力を逆算したり、現DBから入力原本を捏造したりしない。

入力記録後に受信の内容・メタデータ・迷惑メール状態が変わったものも、最初の入力だけでその後の変更を再現できたことにしない。既存の受信状態記録は維持し、新方式では理由を示して保留する。別途、通常の後続操作をどう扱うかを判断する必要がある。

## 隔離確認結果

dmの専用Docker、使い捨てDB、合成データで実施。本番のマウントなし、公開ポートなし、内部ネットワーク。WordPress 7.1.5 / PHP 8.3 / CF7 6.2.5 / Flamingo 2.6.4。通常の匿名CF7 HTTP送信を使用。メール配送のみ試験用フックで抑止した。

S3は使わず、実際の Store / CommentHistory / FormHistory / ReceiptInputs を、ファイルで永続化する試験用オブジェクト転送層で動かした。正式履歴の組み立て、ハッシュ検証、読み戻しは製品コード。Pluginの設定取得部分は試験用の保護オン/オフ実装を使用した。AWS IAM・S3通信・製品の起動移行・管理画面全体の統合試験を行ったという意味ではない。

| 確認 | 結果 |
|---|---|
| バックスラッシュ、JSON風文字列、改行、日本語、選択肢配列を実CF7送信 | 入力原本の値を保持 |
| 成功した受信3件を正式履歴化 | 成功後のみ確定 |
| 保存先書込み失敗 → 新しいPHPリクエストで再試行 | registered を維持し、後で確定 |
| 履歴書込み応答消失 → 再試行 | 正式履歴を重複作成しない |

| 新CF7フォームへ3件を通常登録 | 新ID、元の登録結果と一致 |
| Flamingoの認証済み管理画面HTML | 件名・受信内容を閲覧可能 |

最終実行は環境作成・破棄込み46.12秒。全コンテナ・試験ボリューム・専用ネットワークの後片付けに失敗なし。最初の照合実装で通常の読み出し表現と生メタ値を混同した過剰保留を検出し、登録時と現在の生メタ値同士の照合に修正してから再実行した。
