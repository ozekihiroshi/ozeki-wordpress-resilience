# 導入案内：配布物・保護範囲・復旧

[English](start-here.md) | 日本語

状態：0.3.1のWordPress.org申請候補。まだ申請・承認されていません。[利用ガイド](user-guide-ja.md)と[AWS設定](aws-setup-ja.md)からお読みください。

## 1. 導入する配布物

[ozeki-resilience-0.3.1.zip](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/releases/tag/wporg-0.3.1-rc.1)と `SHA256SUMS`・マニフェストで識別します。表示版0.3.1だけでは配布物を特定できません。

[検証範囲と制限](site-checkpoint-verification.md)で実S3成功・試験用失敗注入・ZIP導入更新を区別しています。既存資産と公開済み配布物は変更していません。GitHubのソースアーカイブや旧研究版を導入しないでください。

[GFSの取得・保存設定とZIP検証](gfs-checkpoints-ja.md)を参照してください。

## 2. 保護するもの

信頼した初期スナップショットまたは完全Checkpointと、S3正式履歴から**対応範囲内のサイト状態**を再構築します。「サイト全体」は、すべてのWordPress拡張機能や、その後の全設定変更への対応という意味ではありません。

通常操作の対応対象はPosts／Pages、参照されるローカル画像、標準コメント、Ozeki Markdown Documents、Contact Form 7、Flamingo、WP-Membersの基本購読者機能、TablePressの基本機能です。[README](../RAADME-jp.md)の対応一覧・除外事項・確認済みバージョンを参照してください。Markdown未使用なら追加導入は不要です。Markdown文書・原文が存在する場合はMarkdown Documentsを有効化します。[利用ガイドの前提](user-guide-ja.md)を確認し、その他の任意プラグインは必要なコンテンツに応じて導入します。

初期状態の信頼性は管理者が判断します。その後の完全CheckpointはS3の基準状態と正式履歴から作り、未追跡の現サイト変更を取り込みません。未確定操作は復旧対象外です。保存済みの公開状態を再現し、外部公開・DNSは管理者が判断します。レプリケーション、無侵害の証明、サーバ自動構築ではありません。

Baselineは最初の独立した完全復旧点です。通常CheckpointはS3資産と正式履歴だけから作り、現在のWordPressの再取得は別操作の新しいBaselineです。[操作と依存関係](site-snapshot-ja.md)を参照してください。旧Markdown資産単位の経路とは区別します。

## 3. 変更後に管理者が行うこと

| 変更内容 | 対応 |
|---|---|
| 対応する本文・画像・コメント・連携プラグイン操作 | 通常の画面を使い、正式履歴への確定を確認。保存元が残っている場合、表示された未確定操作を解消します。 |
| テーマ／親テーマの変更・選択、メニュー、テンプレート、ナビゲーション、グローバルスタイル、取得対象の表示設定 | 変更後、編集を止めて**新しい信頼済みの完全初期スナップショット**を作成。通常のS3由来Checkpointでは取り込めません。 |
| 実行プラグインの更新、履歴対象外だが初期取得対象の設定、分類の全体管理、通常アップロード以外のファイル変更 | 初期取得に含まれる資産か確認し、含まれる場合は新しい信頼済み初期スナップショットを作成。過去の互換性試験は更新版を保証しません。 |
| 未取得のプラグイン専用テーブル・設定、外部／CDNファイル、外部サービス・秘密情報 | 新しいスナップショットだけで対応可能にはなりません。別の保全・設定手順を用意するか、復旧保証の対象外とします。 |

侵害が疑われる保存元の新規取得を、信頼済み復旧地点の代わりにしてはいけません。新基準には管理者の信頼判断が必要です。以前の復旧資源は保持方針に従って残します。この手順は削除を許可するものではありません。未追跡変更の全件自動検出や、新基準作成の自動通知は現行機能にはありません。

## 4. 保存側・復旧側の最小構成

| 項目 | 保存側WordPress | 復旧側WordPress |
|---|---|---|
| 環境 | 通常運用するサイト | 異なるURLの新しい専用WordPress。常設不要 |
| ソフトウェア | 製品ZIPと保護対象に必要なプラグイン | 製品ZIP、互換のWordPressリリース系列、復旧検査が要求する記録済み依存プラグイン |
| 実行条件 | 管理対象テーブルのInnoDB、ZipArchive、書込み可能な資産配置先、依存プラグインに適合するPHP | 左記に加えWebルート外の非公開・書込み可能な作業領域 |
| AWS認証 | AWS SDK標準認証。利用可能ならEC2ロール | SDK標準認証。復旧用の読取り専用アクセスでよい |
| S3 | バージョニング有効のバケット、末尾`/`の専用prefix。同じprefixの書込み元は1サイト | 同じバケット・リージョン・prefix。保護を無効化し、ローカル未確定操作を残さない |
| 権限 | 範囲を限定したListBucket・GetObject・GetObjectVersion・PutObject。保持設定に応じPutObjectRetention | 範囲を限定したListBucket・GetObject・GetObjectVersion。復旧に書込み・削除権限は不要 |

製品の宣言はWP6.4以上／PHP8.1以上ですが、全組合せの検証ではありません。確認済みCF7 6.2.3はPHP8.3以上が必要です。[README](../RAADME-jp.md)の依存版を参照してください。復旧先は記録済みWordPressと同じリリース系列・同等以上の保守パッチが必要です。元環境喪失前に依存版も記録してください。IAM・バケット・KMS等の個別条件により追加要件があり、万能なIAMポリシーを示すものではありません。Object Lock保持には対応バケットと権限が必要です。通常保存・復旧に削除・保持回避権限は不要で、保持プレビューの全バージョン一覧権限とは区別します。

常設の別EC2、Pythonワーカー、SSH認証補助、共有bridge、Dockerは製品の必須条件ではありません。Dockerは環境準備の選択肢です。管理者認証・AWS認証・メール送信設定は別途準備し、元環境の資格情報から復元しません。

## 5. 利用の順序

1. [導入・更新手順](install-update.md)に従い、上記ファイルとハッシュを確認して導入します。
2. 「ツール → Resilience」で保存先と適用する保持条件を設定。未確定履歴を解消し、編集を停止、管理者が信頼を確認して完全初期スナップショットを作成。通常操作の保護を有効にします。
3. 確定履歴・未確定操作を確認し、必要時に完全Checkpointを手動作成。定期設定・保持規則に従う削除は[現在の利用ガイド](user-guide-ja.md)を参照。専用実S3範囲で確認済みで、制限を明記しています。
4. 復旧時は専用WordPress、管理者ログイン（必要ならWP-Membersの有効化確認）、依存プラグイン、S3読取り設定を用意。復旧先の保護は無効のままにします。
5. 完全Checkpointと正式履歴の終了番号を選択し、復旧先の置換を確認して実行。1履歴が編集操作全体とは限らない点に注意します。
6. 結果と復旧内容・必要な動作を確認。失敗なら停止し、原因を調べた後、再実行を別に判断します。自動続行しません。外部公開は管理者の別判断です。
