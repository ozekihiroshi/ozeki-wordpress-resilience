# Markdown Documentsを変更しない通常登録での再構築

2026-11-28。第一段階のWordPress標準再構築に続く、Markdown用の開発実装。作業ブランチは `codex/native-wordpress-reconstruction`。本番、既存の原本/履歴、ZIP/タグは変更していない。申請・メール返信は保留。

## 実装した経路

1. `SiteSnapshot::markdownRegistrationPlan()` が既存の初回保存と正式履歴の読取りを使い、指定した時点の素材を選ぶ。
2. `MarkdownReconstruction::plan()` が公開/非公開の正式なMarkdown本文、保存済みファイル名、必要な画像、埋込みページを取り出す。原本は変更しない。
3. `tools/reconstruct-markdown.py` が復旧先へ通常ログインし、WordPress標準RESTで画像をアップロードする。
4. 復旧先へ渡すMarkdownのコピーに対して、認識した画像参照を新しい画像URLへ置き換える。コード例中のURLと他の本文は維持する。
5. Markdown Documentsの通常の「取込み」フォームへファイルを送信する。フォームのnonceと、実際のアップロードを使用。取込み成功通知の編集リンクから新IDを取得する。
6. 取り込んだ下書きを通常のエクスポートで照合し、通常の編集フォームでタイトル・公開状態・著者・日時・本文を保存する。もう一度エクスポートと編集画面で照合する。
7. 文書が登録された後、認識した埋込みショートコードのIDを新IDに置き換え、通常のWordPress RESTでページを作成する。

**Markdown Documentsの内部クラスや保存関数を直接呼び出していない。** `_ozmd_source`、ハッシュ、描画HTML、キャッシュ、リビジョン等の内部メタを復旧先へ配置・修復する処理はない。nonceの生成を代行したり、アップロード判定を迂回する処理もない。派生状態はプラグインが自身の通常処理で生成する。

原文の保存形式・日常保存処理は変更していない。読取り処理は素材側の既存のメタを参照するが、それを復旧先の内部状態として書き込むわけではない。保存済み原本と、画像URLを接続し直した適用用コピーを区別する。

## 今回の成立範囲

- `.md` / `.markdown` の通常取込み。正式履歴で追記した本文と、初回保存以降未編集の本文。
- 新しい文書ID・画像ID。通常のMarkdown画像記法による、保存された公開画像原本のURL接続。
- 直接表示とページ埋込み、通常編集・再保存、エクスポート原文の照合。
- 日本語、CRLF、バックスラッシュ、コード例。画像URLの変更箇所以外はバイト単位で照合する。
- 非公開文書が匿名閲覧で表示されないこと。下書き/公開停止した文書は登録しないこと。
- 元の文書が登録されなかった場合、埋込みページを公開しないこと。
- 元ファイル名がある場合、その名前を通常の取込みへ渡す。`.markdown` のエクスポート名はプラグイン自身の既存規則に従い、内部メタで補正しない。

著者は明示した新旧アカウント対応を使用する。公開日時を通常の編集フォームで設定するため、保存元と復旧先のタイムゾーンが一致しない場合は先に準備を求める。復旧処理が復旧先の設定を書き換えることはしない。

## 補正せず保留したもの

|項目|結果・理由|
|---|---|
|初回保存後に作成した新規文書の元ファイル名|今回の正式履歴素材には含まれない。本文は存在するが、元の名前での自動取込みはできない。取込み名の明示が必要で、推測による命名や内部メタ補充は行わない|
|保存された公開画像に対応しない画像参照|画像原本の不足、閲覧条件の不足、未対応のURL形式を区別して保留。外部画像を勝手にダウンロードしない|
|公開停止した文書への埋込み|対象文書が登録されないため、埋込みページを公開しない|
|会員条件・親子関係の接続が必要な文書等|会員/全体の再構築段階と接続するまで保留。公開扱いへ緩めない|
|複雑な画像記法、HTML img、文書位置に依存する相対画像URL|今回の参照変換範囲外。推測で本文を変えない|

ファイル名不足は、実際の `Plugin::beforeSave` 相当の属性作成（`Plugin.php` の title/slug/status/date/origin と `UpdateContract::capture`）にも元ファイル名が含まれず、`Store::prepare()` が本文を `source.md` として保全することと整合する。初回保存には `_ozmd_original_filename` が含まれるので、それ以前からある文書の名前は取得できる。

これはMarkdownプラグインの改造や特殊な内部処理が必要という意味ではない。取込み用の名前を通常の操作として指定すれば原文の登録は可能だが、保存素材から元の名前を保証することとは別である。今回は保存側の追加修正は行っていない。

## 確認方法

dm上の専用内部Dockerネットワークに、保存元と復旧先のWordPressを別コンテナ/ボリューム/DBプレフィックスで用意。公開ポートなし、S3なし、Cronと外部HTTPを無効化。WordPress 7.1.5、PHP 8.3、公開済みMarkdown Documents 0.1.3を使用。Resilienceの公開ZIPは導入せず、作業コピーの素材選択処理とHTTPクライアントを実行。

保存元のMarkdownも通常の取込み・編集フォームで作成した。初回保存は現行の取得コードから生成。正式履歴は現在の属性構造を用いて、メモリ上のStoreへprepare/commitした。AWSのネットワークI/Oだけをメモリに置き換えており、既存の原本・履歴を使って書換え試験を行っていない。

独立した期待値と比較した項目：

- 初回保存時点と履歴3までで、選ばれる本文が異なること。
- 追記文書と未編集文書の原文、画像URL以外の完全一致。エクスポート名、画像のHTTP取得バイト一致。
- 同じコード例に含まれる画像URLは書き換えられないこと。
- 文書の直接表示、複数文書のページ埋込み、繰り返し表示、通常の編集・再保存後の表示。
- 新ID、タイトル、投稿日時、公開状態、著者。非公開文書の匿名閲覧拒否。
- 対象外/保留の文書や埋込みが公開されないこと。
- 保存元素材のハッシュ、保存元のエクスポート本文、両サイトのMarkdown Documents全ファイルのハッシュが変わらないこと。
- 復旧先の準備済み独自設定が維持されること。

HTTPによる通常管理画面フォームの操作であり、ブラウザのクリック操作やMermaid等のJavaScript描画の確認を行ったという意味ではない。

最終結果：18項目の確認に合格。文書3件（追記済み・未編集・非公開）、画像1件、埋込みページ1件を新IDで登録。初稿下書きと公開停止の2件は除外。元ファイル名不足、意図的な画像不足、そのままでは成立しない埋込みの3件は保留理由を記録した。これは全素材の無条件な復旧成功という判定ではない。

環境構築・撤去を含む試験全体は41.75秒、撤去エラー0。初回実行では使い捨て環境のuploads親ディレクトリの所有者がWebプロセスと異なり、通常のメディアアップロードが失敗した。隔離環境の所有者設定だけを修正し、プラグインや登録処理での迂回はしていない。

## 運用入口と次の区切り

専用CLI開発入口であり、既存の管理画面の復旧ボタンへの接続やmainへの取り込みはまだ行っていない。元の初回保存・正式履歴から得た計画JSONと著者対応JSONを渡し、通常のWordPress認証で実行する。認証情報は計画や進行記録に保存しない。

処理済みIDと保留理由はローカルの専用進行記録に残す。既存の記録がある場合は無条件に再実行しない。`state=completed` はこの処理の終了を表し、保留ゼロを意味しない。今回の意図的な不足ケースも保留一覧に残る。

全体のWordPress再構築との一括導線、既存の新ID対応表の共有、途中停止からの再開、復旧先からの再保全・再復旧、会員連携、複雑な参照記法は次段階。今回の成立範囲を越えた保証はしない。

コード：`src/MarkdownReconstruction.php`、`tools/reconstruct-markdown.py`。確認：`tests/markdown-reconstruction.php`、`tests/markdown-reconstruction-run.py`。数値と最終ソースのハッシュは同名の結果JSONに記録する。
