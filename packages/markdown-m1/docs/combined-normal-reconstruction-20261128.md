# 通常登録による再構築の組合せ確認

2026-11-28。S3なし・合成データ・dm専用Dockerによる確認。**一通りの再構築は未成立。** 個別の登録方法が成立しても、それらを結ぶ統合段階は完成していない。

## 確認方法

同一の保存元と同一の再構築先へ、ACF無料版6.8.10、CF7 6.2.5、Flamingo 2.6.4、Markdown Documents 0.1.3、TablePress 3.4.1、WP-Members 3.5.8.3を事前導入した。WP-Membersの通常オンボーディングも先に完了した。

保存元には公開ページ・投稿・画像・カテゴリー・メニュー、画像入りMarkdown、TablePressの表、CF7フォーム、実際にCF7を通して登録したFlamingo受信内容、会員1名、ログイン／プロフィールページ、Markdownと表を同じページに埋め込んだ会員資料、ACF項目を用意した。

保存元の会員ログイン、Markdown・表の表示、非会員への本文制限は成功した。したがって、もともと使えないサイトを入力にした結果ではない。

既存 `SiteSnapshot::data()` で初回素材を取得し、ACFの通常編集後の素材を既存 `AcfHistory::replay()` で反映した。S3の確定キューは使用せず、ローカル素材と合成正式履歴1件を用いた。Flamingoは既存の入力捕捉処理とローカルStore試験用代替を使用し、CF7から通常登録へ渡った入力を保全した。実メール送信は捕捉して外部へ送っていない。

実行順はWordPress標準→Markdown→TablePress→CF7→会員→ACF→Flamingo。各既存処理が実際に返したIDだけを共通対応表へ集めた。素材から会員情報を除く、対象を登録済みと偽る、試験側で代わりのページを作る、非公開条件を外す、といった補正は行っていない。

## 結果

| 対象 | 観測した結果 |
|---|---|
| WordPress標準 | 会員情報の存在により公開ページ・投稿・画像・ログインページ等が保留。投稿ID対応表は空。カテゴリーとメニューの一部を作成した後、メニュー参照先不足で停止 |
| Markdown | 文書と埋込みページが会員段階待ちで保留。文書0件、画像0件、ページ0件の登録 |
| TablePress | 表は新IDへ通常登録でき、管理画面経路の編集・再保存に成功。埋込みページは保留 |
| CF7 | フォームは新IDへ通常登録でき、管理画面経路の編集・再保存に成功。問い合わせページは保留 |
| WP-Members | 新しいプロフィールページの対応がなく停止。会員の新規登録・再設定・再構築先ログインには到達せず |
| ACF | 新しい所有投稿IDがなく、取込み前に停止 |
| Flamingo | 新CF7フォームへの参照をつないで通常登録成功。受信内容を管理画面で閲覧できた |

表・フォーム・Flamingoの単体データは使えるが、再構築サイトで一般利用者・会員が一通り利用できるという合格には達していない。未到達の表示・会員ログイン・投稿編集・再保存を成功扱いしていない。

## 原因の根拠

`NativeReconstruction.php`、`MarkdownReconstruction.php`、`TableReconstruction.php`、`ContactFormReconstruction.php` には、個々の対象が非公開かどうかだけでなく、**素材に `membership` が存在するだけで登録を保留する条件**がある。個別実装で将来の統合段階を待つために置かれた条件が、そのまま残っている。

一方、`reconstruct-members.py::save_settings()` は新しいログイン／プロフィールページの対応を前提とし、`reconstruct-acf.py::rebuild()` は新しい所有投稿を前提とする。

このため「ページは会員段階を待つ」「会員段階は新しいページを待つ」という循環が発生した。単なる実行順の入替えでは、現在の入口同士を接続できない。

メニュー停止も同じ不足から派生した。参照先ページが保留されているのにメニュー作成段階へ進み、`Menu reference unavailable` となった。隔離環境内ではカテゴリー・空のメニュー等の部分登録が生じており、全処理が書込み前に停止したわけではない。

また、Markdown・表・CF7の実行記録には `state: completed` と未適用の `held` が同時に残った。これは処理ループの終了であり、必要な情報の再構築完了ではない。今回の判定は状態文字列ではなく、作成件数・保留理由・参照対応・利用結果を基にした。

同一ページに複数プラグインの埋込みがある場合、各単独処理は自分の埋込み以外を保留する境界もある。この点はコード上確認したが、今回の実行はその手前の会員条件で止まっており、独立した実行不具合としては数えていない。

## 今回の判断

通常の登録・設定を使う方式そのものが不可能になった、という証拠ではない。表・フォーム・受信内容では同居環境でも成立した。ただし、**個別実装を組み合わせればサイト全体ができる状態にはなっていなかった**ことは確認できた。

次に必要なのは、各プラグインの内部補正ではなく、共通の新ID対応と登録段階の設計である。

1. 投稿等の登録担当を一つにし、下書き／非公開の新規登録と公開を分離する。
2. 共通ID対応を各通常登録処理へ渡し、文書・表・フォーム・会員・ACFの参照を設定する。
3. ページの閲覧条件とファイルの閲覧条件を別々に確定し、依存先不足では公開しない。
4. 必要な登録・関係・条件が揃ってから公開する。保留を含む結果を全体成功としない。

これは次の設計候補であり、今回実装して通したものではない。

## 試験上の切り分け・限界

初回試行では、合成フォームのメール本文が任意入力タグだけで構成され、CF7自身の「空になり得る本文」の警告も発生した。通常の固定説明を含む本文にした別の新規合成サイトでも同じ統合停止が起きるか再確認した。既存の保全素材を後から書き換えたのではない。

最終の合成サイトではACF表示を公開説明ページへ配置した。通常テーマが明示的に `get_fields()` を表示する構成であり、テーマが閲覧制限の外で会員情報を表示する試験構成にはしない。

HTTPによる実際のフォーム／REST経路と生成HTMLを確認した。JavaScriptを含む実ブラウザ操作、実メール配送、S3アクセスは対象外。再構築先での会員ログイン以降はページ未登録のため未確認。

製品コードを修正して制限を回避していない。保存元の素材とプラグイン本体はハッシュ不変。専用Dockerは試験後に削除。本番・既存原本・履歴・ZIP・タグは保全し、公開申請・メール返信は保留した。

証拠：`combined-normal-reconstruction-20261128-results.json`、`combined-normal-reconstruction-20261128-first-results.json`、`../tests/combined-normal-reconstruction/`。

## 追跡確認：個別成功と統合停止の条件差

ユーザーからの「構築順序がデータとして保持されていないのではないか」という指摘について、既存コードと試験記録を照合した。追加試験・製品コード変更は行っていない。

| 対象 | 個別確認の前提 | 統合確認との差 |
|---|---|---|
| WP-Members | `tests/members-normal-registration/run.py` がログイン・プロフィール・資料ページを通常RESTで先に作り、`mapping` を組み立てて渡していた。さらに制限対象をその対応表にあるページへ絞っていた | ページ準備を標準再構築へ任せると、会員情報があるため全体保留となり、対応表を作れない |
| ACF | `tests/acf-reconstruction-implementation/run.py` が対象の下書きページを先に作り、そのIDを渡していた | 同じページ準備を再構築自身に任せると所有投稿IDがなく、値の登録以前に停止 |
| WordPress標準／Markdown／TablePress／CF7 | 各個別試験の保存元にはWP-Members全体の保存状態を同居させていなかった。制限ページを明示的に保留する試験は別途あった | 統合素材には `membership` が存在し、個々のページの公開条件に関係なく保留する分岐へ入った |
| CF7→Flamingo | CF7の登録結果から新フォームIDを明示的に渡す | 統合試験でも実際の新フォームIDを渡せたため成功した |

したがって「個別に確認した通常APIの動作が、同居によって壊れた」とは確認されていない。**個別試験では試験側が満たしていた前提を、統合時に実装が満たせなかった。** 個別確認の成功は「準備済みの対象へ登録できる」という範囲であり、前提の準備まで自動再構築できることの証明ではなかった。

### 保存されている順序と、保存されていない順序

- `Store` の正式履歴には `sequence` があり、`SiteSnapshot::replay()` がその順番で素材の状態へ反映する。ただし、その結果は選択時点の状態であり、各通常登録操作を履歴順に実行するものではない。
- 初回保存には、取得時点のデータ・設定がある。初回保存以前に管理者が実行した作成・設定操作の時系列全体は残っていない。
- プラグイン一覧・版情報はあるが、一覧順が「資料・ページ・会員設定を作った順序」を表す契約にはなっていない。`dependencies` という名前の情報も、CF7／Flamingoでは主に必要なプラグイン版情報であり、全登録操作の先行関係ではない。
- `wpmembers_settings.user_pages`、埋込みID、ACFの所有投稿・フィールドキー、Flamingoの `form_origin_id`、親ページ等の参照関係は残っている。このため、今回必要だった参照先を一切特定できないという状態ではない。
- 一方、その関係から全体の通常構築手順を定め、各登録処理を実行して共通IDへ接続する契約・実行機構はない。Native内の `dependencies` は局所的な参照検証であり、アダプター横断の順序管理ではない。

**構築操作全体の順序を保存・再現する設計がないという懸念は該当する。ただし今回の停止を「順序データだけを保存すれば直る」とは判断できない。** 既にある参照情報を使う前に停止する条件と、個別試験が代行した準備の未実装も直接の原因である。

既存素材だけから元の操作順を完全に復元できるとは主張しない。実際に成立した通常構築操作と保存情報を対応付け、順序を確定できる箇所・未記録で確定できない箇所を区別する必要がある。推測した順序で同じ結果になることを前提に、新しい処理を実装してはいない。
