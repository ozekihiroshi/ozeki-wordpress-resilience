## 対象と保全

## 変更

- `FileScope`に初回保存と復旧で共通するファイル選択を置いた。通常のメディア登録、標準の保存場所、添付情報、親投稿の公開状態を確認する。専用ディレクトリ、未知の添付メタデータ、未知の投稿型によるファイル参照、非公開・パスワード付き・会員制限付きの親投稿を持つ添付は自動配置しない。生成画像・元画像も一緒に扱う。同じパスの公開／非公開登録が競合したら非公開側を優先する。
- 未対応ファイルは容量確認前に除外する。対応対象のファイルの容量超過は引き続き明示的に停止し、成功扱いにしない。保存時に祖先ディレクトリの`.htaccess`があるファイルも公開用に選択しない。
- 保存からの除外と、保存済み原本から復旧先への適用除外を区別して表示する。保存から除外したファイルを「S3に保存済み」と案内しない。
- 未保存の`WPLANG=false`をWordPress標準英語として扱う。復旧準備だけでなく、適用時も空文字へ正規化する。保存済み原本内の値は変更しない。

## 互換性と確認範囲

原本の既存形式は変更せず、保存対象外一覧を新規manifestの任意項目として追加した。既存の原本・履歴は書き換えない。古い復旧点にも新しい選択規則を適用するため、以前は無条件に配置されたファイルが対象外になることがある。復旧には修正版の読取り処理を使用する。旧版の読取り処理そのものを安全に変える変更ではない。

復旧先は従来どおり新しく用意したサイトが前提。以前の旧版復旧で既に公開されているファイルを自動削除する処理ではない。

今回確認したのは記録された投稿・添付・ファイル領域から判断できる範囲。任意の未対応プラグインが独自テーブルや外部サービスだけで行うアクセス制御を自動判定する仕組みではない。そのような構成は別途確認が必要で、全プラグインの非公開制御を検証済みとはしない。この節までの試験は実S3通信、全管理画面操作、全プラグイン組合せの試験ではない。実S3の追加結果は次節に記録する。

## 実S3での追加確認と最終レビュー

communityの本番WordPressとは別のDockerコンテナ4台・試験用DB・ネットワークを新設し、既存の試験バケット`ceri-link-resilience-lock-lab-121426368082`の未使用prefixで実施した。AWS SDKのハンドラー置換は行わず、EC2ロール`my-ssm-role`の標準認証で実S3を使用。アクセスキーの配布・IAM変更・本番バケットの利用はしていない。定期実行・メール送信・自動削除は無効。

環境はWordPress 7.1.3 / PHP 8.3.31。初期の試験用DockerイメージはWordPress 7.0でCF7の要件を満たさなかったため、試験コンテナに限り前回と同じ7.1.3の本体を用意してやり直した。本番WordPressは変更していない。
