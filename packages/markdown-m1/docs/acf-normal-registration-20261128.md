# ACF無料版：保全素材を通常の取込み・投稿保存で再登録する確認

2026-11-28。開発用の隔離確認。公開判定・本番への反映は行っていない。

## 結論

今回確認した基本15種類・16項目では、既存の保存処理が保全する素材から、ACFを変更・初期化せず通常のJSON取込みと投稿編集画面の保存によって再構築できた。定義・値・フィールドキーの対応が一致し、新しいDB IDで表示・編集・再保存が成立した。内部DBの配置、保存後のメタデータ補正、キャッシュ修復は行っていない。

目的は旧DBの複製ではなく、保存素材を使って新しいWordPressへもう一度登録すること。フィールドキーはACFの取込みで使う論理識別子として保持し、投稿・グループ・フィールドのDB IDは新しく割り当てられる。

## 既存素材との照合

`src/AcfHistory.php` の現行 `baseline()` / `capture()` / `replay()` を使用した。

| 素材 | 保存されているもの | 今回の使用方法 |
|---|---|---|
| `acf_definitions` | グループ、項目名・型・キー、選択肢、説明、表示条件等 | ACF自身の通常エクスポート準備処理を通し、通常JSON取込みへ渡す |
| `acf_values` | 対応項目の保存値。配列は配列、文字列は文字列 | 単一保存値を取り出し、キーに対応する通常投稿編集フォームへ渡す |
| `acf_references` | 項目名とフィールドキーの関係 | 投稿フォームの `acf[field_...]` に対応付ける |
| 投稿の識別・型 | 値を持つ投稿／固定ページ | 新しく登録したページへ対応付ける |
| `raw_meta` | 生の付随情報 | 登録後の補正には使わない |

定義の保存素材には旧DB ID等も含まれる。そのままインポートすると既存IDを参照する可能性があるため、生の定義を無条件に渡す方式は採らない。ACFの通常エクスポートと同じ `acf_prepare_internal_post_type_for_export(..., 'acf-field-group')` を、保存素材のコピーに適用する。これはACF自身がID・parent等を取り除く通常処理であり、Resilience独自の修復処理ではない。元の保存素材は変更しない。

根拠となるACF 6.8.10の配布ソース：

- `includes/admin/tools/class-acf-admin-tool-export.php`：通常エクスポートも上記関数を使用。
- `includes/post-types/class-acf-field-group.php::prepare_post_for_export()`：グループの内部属性を除き、通常のフィールドエクスポート準備へ渡す。
- `includes/acf-field-functions.php::acf_prepare_field_for_export()`：ID・parent等を除く。
- `includes/admin/tools/class-acf-admin-tool-import.php::submit()`：通常JSON取込みからACFの登録処理へ渡す。
- `includes/forms/form-post.php::save_post()`：投稿編集画面のnonce・検証を経て通常の値保存を行う。

今回の素材に不足は見つからなかった。ただし全実サイトの原本を調べたという意味ではない。現行保存処理で合成データを保全し、既存形式・既存履歴再生との対応を確認した。

## 確認手順と結果

証拠：`acf-normal-registration-20261128-results.json`、`../tests/acf-normal-registration/`。

dm上の専用・使い捨てDockerで、WordPress 7.1.5、ACF無料版6.8.10、PHP 8.3、PHPメモリ256MiBを使用。ネットワークは外部接続なし、ポート非公開、DBは試験専用。S3は使用していない。

1. 両環境にACFを事前導入する。以後の再構築では導入・初期化を呼ばない。
2. 保存元で通常JSON取込みから定義を登録し、通常の投稿編集フォームから値を保存する。
3. 現行 `AcfHistory::baseline()` で初回素材を取得。通常編集後の値を `capture()` で取得し、既存 `replay()` で初回素材へ適用する。
4. 選んだ保存定義をACFの通常エクスポート準備処理へ渡す。再構築先では管理画面のJSON取込みフォームへ送信する。
5. 新しく作成した固定ページの通常投稿編集フォームから保存値を登録する。実際の画面から取得したnonceを使用する。
6. 定義・値・参照関係を読み取り比較し、通常のテーマ表示、編集画面、再保存を確認する。
7. 文字列の変更、複数選択の変更・解除を通常編集で行い、表示と再保存後の値を確認する。

| 観点 | 結果 |
|---|---|
| 基本15種類＋複数選択select | 16項目の定義・値・参照を再構築 |
| text / textarea | 日本語、バックスラッシュ、`&`、シリアライズ形式に似た文字列 `a:0:{}` を維持 |
| number / range / true_false | 数値0を含め一致 |
| email / url | 通常フォームで登録・再保存できる |
| select / checkbox / radio / button_group | 選択値・複数値の順序が一致 |
| date_picker / date_time_picker / time_picker / color_picker | 保存値と通常の整形表示が一致 |
| 説明・条件付き表示の定義 | 可搬定義全体が一致。説明は編集画面にも存在 |
| 新ID | ページ23→30、グループ6→31、フィールドのDB IDもすべて異なる |
| 無編集の再保存 | 値を維持 |
| 編集・再保存 | 文字列変更、checkbox変更、複数select解除を維持 |
| ACF本体 | 両環境でファイルハッシュ不変 |
| 初回素材 | ハッシュ不変 |

ACFは項目の値をテーマへ自動表示する製品ではない。今回は両環境に事前配置した小さな通常テーマが `get_fields()` の結果をエスケープ表示し、表示結果を比較した。テーマはACFの値保存やメタデータ補正には介入していない。

## 限界と次の判断

- 実際の管理画面HTTP経路と生成HTMLを確認した。ブラウザでのJavaScript操作・日付選択UI・条件付き表示の動的切替は今回の確認外。
- 正式履歴の再生は、通常保存後の素材から合成した1件を既存 `replay()` へ渡して確認した。S3保存・正式確定キューの試験ではない。
- PRO、画像・投稿・ユーザー等の参照型、入れ子、Options、PHP／Local JSON定義は今回の対象外。基本型だけの結果をそれらへ拡張しない。
- 既存グループと同じキーを取込むとACFの通常仕様で更新され得る。今回は空のACFへ新規登録した。準備済み定義との衝突を勝手に上書きする運用は認めていない。
- 任意の未知設定・外部アドオンの定義を自動適用して安全だと証明したものではない。今回の合成定義は内容を限定している。
- 今回は方式の成立確認と素材照合まで。再構築ツールの製品UIへの接続・公開対応範囲の確定は未実施。従来の直接適用経路は今回変更していない。

本番・既存原本・履歴・ZIP・タグを変更していない。保存形式も変更していない。GitHubへのpush、公開申請、審査メール返信は行っていない。
