## 環境と判定方法

dm上の専用WordPress 3サイト、専用DB・ボリューム、外部公開ポートのない内部Dockerネットワークを使用。WordPress 7.1.3 / PHP 8.3.36、WP-Members有効。メール、Cron、外向きWordPress HTTPを停止。S3 SDKのローカル代替ストレージを使用し、実S3にはアクセスしていない。

単体回帰確認を先に追加し、修正前は「Page restrictions are not file restrictions」で不合格になった。往復の独立した判定も、修正前の保存済み結果を「Condition-only change missing from formal history」として不合格にする。

合格判定は、操作の返却値だけでなく、匿名・会員のHTTP表示、ファイルURLのHTTP状態、固定した試験画像のSHA-256、記事への追記、二度目の復旧結果、確定待ちの有無を用いた。各復旧の前後で代替ストレージの全オブジェクトのSHA-256集合が一致した。

## 試験中の不備と修正

追加試験で、uploadsの退避先が別ファイルシステムだったため試験用初期化が失敗した。製品は既存の公開ファイルと保留対象の衝突を検出して復旧を拒否しており、試験側がこの操作失敗を即時検出していなかった。退避先を同一ボリュームへ変更し、全操作の`operation_failed`を即不合格にした。

旧サイトの会員を、別サイト由来の会員が既にある試験DBへ復旧しようとした際も、製品の会員衝突検出が作動した。互換性確認の対象ごとに空のDB接頭辞を用意し直した。失敗を回避するために製品の衝突検出を緩めてはいない。最終の通常4ケースと追加確認は修正した試験手順で合格した。

SSH終了で試験用Dockerが停止しても途中結果を失わないよう、試験DBを専用ボリュームへ変更した。終了後、この作業で作成した12コンテナと対応するボリューム・ネットワークだけを削除し、原本を含む試験証跡は残した。
