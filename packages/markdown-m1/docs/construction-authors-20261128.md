# 投稿者登録材料の保存と通常登録（2026-11-28）

## 結果

保存元の `get_userdata()` でログイン名・メールアドレスを取得できる。表示名・スラッグと合わせた4項目を新しい初回保存の実験用付随資料へ保持し、独立した復旧先で `wp_insert_user()` により登録できた。試験から投稿者ID対応表を渡していない。

前回の試験が渡していた旧投稿者→準備済み管理者の対応は、保存素材だけで再構築する証拠として無効だった。今回の結果と区別する。

## 実装

- `ConstructionAuthors::capture()`：正式対象の投稿・固定ページ・添付・Markdown文書から投稿者を選び、通常登録用の4項目を取得。
- `ConstructionOperations::initialSaveWithAuthors()`：新しい初回保存と一緒に `construction/authors.json` を作り、ハッシュと操作到達点に含める。既存の原本・初回保存・正式履歴は変更しない。
- `ConstructionReadiness`：新資料を読取り、従来の投稿者材料不足を解消。資料がない旧保存は推測で補わない。
- `ConstructionAuthors::register()`：同名・同メールの既存ユーザーを暗黙に採用せず、登録前に衝突を拒否。登録結果の新IDを記録する。未確定登録が残った場合は再作成しない。
- `ConstructionCapture`：通常REST・管理画面操作の実行者IDを操作時に記録。投稿者を省略した入力について、後から復旧先管理者を元の実行者と仮定しないための材料。

パスワード・ハッシュ・管理者権限・セッションは保存しない。通常ユーザー登録に必要な新しいランダムパスワードを発行するが、保存元のパスワード復元ではない。今回の投稿者登録では権限を付与せず、メール通知も発行しない。会員設定・権限の通常設定との統合は別途残る。

[隔離結果](construction-authors-20261128-results.json)。dmの専用Docker、合成データ、実S3なし。準備・片付け込み66.08秒。

- 保存元の管理者 `operator` と復旧先の `destination-admin` を別にし、名前や旧IDの偶然の一致で試験を通さない。
- 実初回保存、操作23までの到達点、以降の自動記録1件を保存・転送。
- 4項目を保持した新IDでの通常登録を確認。
- 保存元の管理者権限を持ち込まず、復旧先管理者のログイン名・パスワードハッシュ・権限も不変。
- 再試行でユーザー重複なし。
- 衝突を与えた負例ではユーザー数が増えず拒否。
- 登録材料を持たない旧形式は保留。
- 保存中断、応答消失、読取り改変の拒否、既存保存オブジェクト不変も確認。

その後に追加した実行者IDの捕捉は `tests/construction-operations.php` で確認した。PHP 8.3のネットワークなしコンテナで構文確認および既存記録契約試験も通過。結合結果JSONは実行者ID追加前の結果であり、全体結合を再確認したと解釈しない。

## 未完了の範囲

これは投稿者の材料不足と通常登録の解消であり、サイト全体の再構築完了ではない。初回保存の全対象を通常登録する実行器、登録結果の新IDによるプラグイン間参照と後続操作の接続、製品の通常保全キューへの統合は残っている。結果JSONの `ready_for_registration` は限定した材料点検の通過であり、全体の利用可能性を示さない。

新しい登録資料は個人情報を含むため、旧資料へ後付けしたり公開したりしない。この変更は隔離用の開発経路のみ。既存公開版・本番・原本・履歴・ZIP・タグは変更せず、申請とメール返信も実施していない。
