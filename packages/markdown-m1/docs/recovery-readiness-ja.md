## 削除途中の失敗と復旧

既存の削除検証専用範囲の下に、現行オブジェクト・旧版・削除マーカーが存在しない子prefixを確認して使用しました。community/dmの既存コンテナを再利用し、DB接頭辞とコンテンツディレクトリを分離しました。認証は既存EC2ロールによるSDK標準認証です。試験領域のメール・自動更新・WordPress Cronは停止しました。

Baseline、履歴1、履歴1までの独立Checkpoint、後続履歴2を用意しました。製品のプレビュー結果は33版、削除候補16版、保持資源17版でした。不要になった履歴の固定版1件を実S3から削除し、2件目のDeleteObjectを試験用ラッパーで**送信前に遮断**しました。製品は `ok:false`、削除済み1件、失敗・結果不明の対象と理由を記録して停止し、その後の削除は行いませんでした。残存32版、削除マーカー0件で、保持する17資源のハッシュはすべて一致しました。

続いてdmの既存復旧ロールを使い、別の試験領域へCheckpointと履歴2から復旧しました。本文・タイトル・公開状態・画像ハッシュ・移し替えたリンクが一致し、元DBや祖先資源は使用していません。これは実削除と障害注入を組み合わせた確認です。実AWS障害、AWS側で結果が不明になるタイムアウト、ブラウザ中断、自動再開の検証ではありません。再開・巻戻し機能は追加していません。

## 運用条件

導入時の起動方式の基準は、検証済みの標準 `wp-cron.php` をサーバから起動する方式とします。期限到来イベントの実行、更新なしの独立Checkpoint、次回予約、定期削除、障害注入時の削除抑止は[既存の受入記録](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/main/docs/releases/cleanup-browser-scheduled-acceptance.md)で確認済みです。今回は本番の定期起動を追加せず、同じ試験も繰り返していません。HTTPループバックや年単位の自然期限経過は、この証拠には含みません。

保存側ロールは専用範囲の全バージョン一覧とロック状態を取得できました。バケットはObject Lock有効・既定保持規則なしです。当初の保持期限設定は、許可先が別prefixだったため拒否されました。その後、管理者が専用子prefixの `s3:PutObjectRetention` だけを許可する一時インラインポリシーを追加しました。既存の保存側ポリシーとdmの権限は変更していません。

2026-10-26 13:13:40 JSTに、不要になった専用試験資産の固定版1件へ、2026-10-27 13:13:37 JSTまでのGOVERNANCE保護を設定し、モード・期限の読取り一致を確認しました。製品は当該版と同じ旧Checkpointの資産を削除候補から除外しました。候補13件から0件、削除不可15件となり、全32版の識別情報と対象原本のバイト列は不変でした。PutObjectRetentionは1回、PutObjectとDeleteObjectは0回です。実保持期限と候補除外の検証であり、Legal Hold ON、保護中の実削除拒否、自然な期限満了の検証ではありません。

先行するdm復旧の呼出しはGetObject 18回とListObjectsV2 1回でした。全バージョン一覧・ロック管理・IAM調査の拒否を、この復旧経路の失敗として扱いません。その後、先の一時ポリシー `OwrTemporaryRetentionTest` と `OwrTemporaryIamInspection` を撤去し、再読込みしたコンソールで不在を確認しました。既存write-policyは不変です。
