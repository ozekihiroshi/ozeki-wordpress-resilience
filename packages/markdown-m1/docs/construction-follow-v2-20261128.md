# 保存時の契約から順番どおりに追随する改修（2026-11-28）

## 方針の修正

再構築時に操作の意味や参照先を推測して補うのをやめ、操作を行う時点でその情報を保存する。初回保存の登録と、その後の操作追随を分ける。初回保存から得た実際の登録結果だけを、追随の開始時のID対応とする。

以前の種類別に組んだ統合試験は、保存素材から代表構成を組める証拠であって、構築過程に追随できる証拠ではなかった。その試験結果を新方式の合格根拠として流用しない。

## 保存側に戻して修正した不足

| 起きていた問題・不足 | 操作時に取得・保存すべき情報 | 今回の扱い |
|---|---|---|
| 投稿者を試験側で対応付けていた | 初回保存の通常ユーザー登録素材、操作時の実行者と省略時の投稿者 | 前回の投稿者素材を維持。新規投稿の通常デフォルト投稿者を、入力原文とは別の実行引数に記録 |
| 数字の意味を復旧時に解釈していた | 対象と参照の型、入力内の位置、保存元の識別子 | `user`、`post`、`category`、`tag` と、参照値の入力パスを保存 |
| 順序を種類別に組み替えていた | 確定順序と直前操作番号 | `sequence` と `previous` を保存。並替えず追随。欠番・入替えは拒否 |
| 登録結果を試験から渡していた | 通常処理が返した対象IDと型 | 成功応答から `outputs` を記録。参照対応は追随先の通常登録結果からのみ作る |
| 返却値の型を保存し損ねていた | postイベント種別と実際のpost_typeを別フィールドで保存 | `ConstructionCapture` の配列結合でtypeが隠れる問題を修正し、`post_type` を別に記録 |
| 記録があれば再実行可能と見なしていた | その操作を追随するための項目が揃っているか | `coverage` と `reasons` を保存。記録不足は通常処理成功と区別し、追随前に拒否 |
| 応答・確定結果を検証できない | 入力・契約・確定結果それぞれの整合確認 | 各ハッシュを記録。未確定・改変結果からは追随しない |

`input` は取得した原文のまま保持する。型付きの実行引数・参照・通常デフォルト値は `contract` に分離する。再構築の都合に合わせて原文を書き換えない。

## 実装と互換性

- `ConstructionContract`：通常ハンドラーの実行前に入力契約を作る。
- `ConstructionOperations`：入力と契約を先に記録し、成功結果・型付き出力をその後に確定する。
- `ConstructionFollow`：初回保存の登録結果から始め、保存された順序で参照を結んで通常APIを呼ぶ。種類別ソート、参照の推測、不確定な登録の再試行はしない。
- `construction-api.php`：通常WordPress RESTへの呼出しを提供する。復旧先の準備済み管理者を明示して実行する。
- `reconstruct-kit.py`：初回保存後の独自のroute/body解釈を削除し、記録契約の追随処理へ接続した。

開発用optionは `ozeki_resilience_construction_experiment_v2`、記録schemaは `owr-observed-construction-experiment-2`、初回保存への接続schemaもv2へ分離した。旧optionや既存原本・履歴は変換・削除しない。旧形式を読み、後から不足する型情報を推測して新形式とする処理はない。

この変更は隔離実験用であり、製品の通常保存キュー・本番の保存形式を更新したものではない。

## 今回確認した範囲

**投稿・固定ページのREST登録・更新を起点に、保存側と追随側の共通部分をやり直した段階。全対応プラグインの型定義は未完了。**

現状、埋込み・URL・ブロックを含む本文、未定義の入力項目、プラグイン固有操作などは、原入力を記録しても契約を `incomplete` とする。追随側は補って実行しない。通常操作自体の成功記録と、追随可能性を区別するためであり、これらを対応範囲外へ無断で変更したという意味ではない。

## 軽量確認

`tests/construction-follow.php` はWordPress・DB・S3・HTTPなしで動く。100組の異なるIDで、登録→依存登録→更新→参照解除、順序違反、参照不足、結果改変、未完成契約の拒否を確認した。601はアサーション数であり、601種類の操作や網羅性を意味しない。

実WordPressでは、通常RESTで親ページを公開登録し、子ページ登録、タイトル更新、親参照の解除を行った。自動捕捉された4操作だけを別のWordPressへ渡し、通常登録が返した新IDで同じ順に実行した。元サイトの構築レシピや試験用ID対応表を追随側へ渡していない。

この実WordPress確認の初回保存部分は**実在する初期投稿者の登録素材に限定**した確認であり、全SiteSnapshot・全プラグインの結合試験ではない。以前の全体試験の代わりに済ませたものではなく、記録と追随の不具合を短時間で検出するために分離した。

専用ラベル・内部ネットワークのDockerを使い、再利用時は専用コンテナのラベルを検証してから、合成データだけのseedへ戻す。実S3・本番へは接続しない。実行は `run.py --keep`、続いて `run.py --reuse`。2回目終了時に専用コンテナ・ボリューム・ネットワークを片付け、エラーなし。DB初期化による本番への影響はない。

## 次に残る保存側の仕事

1. Markdown・TablePress・CF7・Flamingo・WP-Members・ACF各操作について、通常入力、対象・参照位置、生成ID、完了通知を操作時の型定義へ揃える。今は未定義として明示している。
2. 埋込み・画像URL等の参照を操作時に記録する。単なる文字列だからと、再構築側で解釈して帳尻を合わせない。
3. 参照の削除・操作失敗・同時実行・途中中断と、公開／未公開の境界を確定契約へ含める。
4. 全プラグインの統合経路でv2を確認する。今回差し替えた全体実行器からの呼出し自体は、まだ全体結合で再確認していない。

本番・既存原本と履歴・ZIP・タグは不変更。GitHubへのpush、申請、メール返信も実施していない。
