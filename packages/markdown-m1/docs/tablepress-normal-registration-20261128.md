# TablePressを通常の取込み・保存で再構築する実装と確認（2026-11-28）

## 結論

未改造のTablePress 3.4.1で、初回保存と正式履歴から選んだ表を、通常のJSON取込み、編集保存、エクスポートで再構築する開発用入口を実装した。表の内部投稿、メタ、ID台帳、キャッシュを復旧先に直接配置・補正する処理はない。復旧処理によるプラグインのインストール・初期化もない。

本番・既存の原本と履歴・既存ZIP・タグは変更していない。mainへの取り込み・push・新しいZIP・申請・審査メール返信は行っていない。先行のWordPress/Markdown再構築実装は保持した。

## 素材と通常登録の対応

|保存素材|今回の処理|
|---|---|
|初回保存と正式履歴|既存SiteSnapshotの読取り・履歴適用で指定時点の論理素材を選択する。元オブジェクトを書き換えない|
|tablepress_tableの表名・説明・セルJSON|通常JSON取込みのname/description/dataへ組み替える|
|表ごとのoptions/visibility|型・寸法・対応項目を検査し、そのまま通常取込みへ渡す。正常値をHTML変換しない|
|旧表IDの対応|選択した保存素材内でのみ参照し、取込み成功時に返された新表IDとの対応を記録する|
|通常の[table id=… /]埋込み|新表IDへ参照を置き換え、WordPress標準RESTでページを新規登録する|
|last_editor、旧作者、旧ID台帳|持ち込まない。通常のTablePress登録・保存が新環境で生成する|
|TablePress全体設定|復旧先の準備済み設定を維持する。保存元の全体設定を書き込まない|

既存の保存形式は変更していない。データを取込み用JSONに組み替えることと、復旧先の内部状態を補正することを区別している。

## 実行経路

1. SiteSnapshot::tablepressRegistrationPlan()で保存素材を選択する。
2. reconstruct-tablepress.pyが通常の管理者ログインを行い、管理画面が発行したnonceを取得する。
3. TablePressの通常取込みフォーム（admin-post.php / tablepress_import、JSONテキストの追加取込み）で新規表を作る。
4. 成功通知の新表IDを記録し、通常エクスポートでセル・説明・表示条件・指定した設定を比較する。
5. 通常編集画面のnonceとAJAX保存経路（tablepress_save_table）で保存し、再び通常エクスポートで比較する。
6. 登録できた表だけページの既知の埋込みへ接続し、WordPress標準のページ登録・読取りで確認する。

プラグインのprivateモデルやインポーターを直接呼び出さない。nonceを生成・偽造しない。通常保存が値を変えた場合は失敗と記録し、メタやキャッシュを書き戻して帳尻を合わせない。通信は同一オリジンに限定する。

開発用CLIは --isolated、計画JSON、著者の明示対応JSON、新規の進行記録パスを必要とする。既存の進行記録がある場合は再実行しない。作成した新IDと保留理由を記録する。completedは処理終了であり、保留ゼロではない。

## 今回成立した範囲

S3を使わないdmの専用内部Dockerネットワーク上に、合成データの保存元と新規復旧先を作成した。既存サービスへのポート公開やアクセスはない。WordPress 7.1.5、TablePress 3.4.1、PHP 8.3、MariaDB 10.11。PHPメモリ256MiB、各コンテナ512MiB。定期処理・外部HTTPは停止。準備段階で管理者がTablePressを通常インストールし、その後の再構築ではインストールしない。

- 表3件：正式履歴で追記された表、初回保存後未編集の表、初回保存後に追加した表。
- 正式履歴による削除で対象外になった表は再登録しない。
- セル文字列、日本語、引用符、アンパサンド、空文字、文字列の0、バックスラッシュ、表名・説明を保持。
- 行と列の非表示、表ごとの設定を通常エクスポートで比較。非表示値が表示HTMLに出ないことを確認。
- 通常埋込みページと非公開ページを新IDで作り、匿名閲覧条件を確認。
- 表を通常編集してセル変更・行追加、再保存後も値と表示が維持されることを確認。
- ページの通常編集・保存後も表が表示されることを確認。
- 復旧先の準備済み表・全体設定・独自設定、保存元素材、TablePress全ファイルが変わらないことを確認。

初回保存のシリアライズと正式履歴のprepare/commit/read/replayは既存コードを使い、オブジェクトの輸送部分のみメモリ内に置換した。合成履歴はTableHistoryの記録形式で組み立てたため、この試験は日常保存フックからの自動送信を再確認したものではない。表示はHTTP応答、編集保存は通常フォーム/AJAX/RESTで確認した。実ブラウザのクリック操作、DataTablesのJavaScriptによる検索・並べ替えは今回の確認に含まない。

## 補正せず保留・対象外とするもの

|内容|扱いと理由|
|削除済み・未登録の表へのページ参照|ページを保留。存在しない表を推測で作らない|
|文字参照化された埋込み|保留として明示。一律に文字参照を解除して実行可能にしない|
|初稿下書きのページ|正式対象外|
|セル・表名・説明のHTMLまたはショートコード様の内容|今回の限定入口では保留。内容を削る・無害化して成功扱いにはしない。通常取込み自体の能力不足を意味しない|
|独自JavaScript命令、未知の拡張設定|保留。保存されていることを理由に実行しない|
|欠けた表示条件、異常な寸法や型|保留。デフォルト値で欠落を隠さない|
|セル内画像・リンクの新環境への参照対応|今回未接続。通常の表データの成立確認を超える。必要なものはWordPress側の素材・新ID対応と統合して別途判断する|
|会員連携、親ページ、複雑なページ/ブロック|この入口では保留。全体再構築との統合前に推測で適用しない|

したがって「TablePress全機能の再構築が完了」とはしていない。今回の通常の情報表では成立し、内部補正を要した項目はない。上記の保留は、普通の取込みで技術的に不可能と実証したものと混同しない。

## 次の接続範囲

既存の復旧ボタンやmainにはまだ接続していない。WordPress/Markdownの再構築と共通のページ登録・参照対応を使う統合、途中失敗からの再開、実データの複雑な埋込み、再保全からの再復旧は今回の確認範囲外である。

コード：src/TableReconstruction.php、tools/reconstruct-tablepress.py、SiteSnapshotの新しい読取り入口。HTTP認証等だけ先行のreconstruct-markdown.pyを再利用するが、Markdown Documentsの処理を呼ばない。

試験：tests/tablepress-reconstruction.php、tests/tablepress-reconstruction-run.py。
