# Independent Markdown snapshots and Checkpoints

> **設計・検証資料（過去の版を含みます） / Technical and historical reference.** 現行の導入案内ではありません。Use the [current user guide](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/main/packages/markdown-m1/docs/user-guide.md) / [現行導入ガイド](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/main/packages/markdown-m1/docs/user-guide-ja.md) and [配布状況 / distribution status](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/main/packages/markdown-m1/docs/wordpress-org-candidate.md).

This guide covers the supplementary asset-level path, not complete site recovery. For articles with images, themes, menus and site relationships, use [site-wide recovery](site-snapshot.md), the primary workflow. The asset restore button is **Restore assets from Checkpoint + later history**. A trusted baseline plus confirmed S3 formal history defines the recovery state; pending operations are excluded if the source is lost. An unconfirmed new article is absent; an unconfirmed update leaves the previous confirmed version.

Initial snapshots and subsequent Checkpoints use the same builder, complete-file format and restore path. Initial capture uses published Markdown documents explicitly trusted by the administrator; pause editing during capture. Later Checkpoints use the previous snapshot and confirmed S3 history, never the live WordPress contents. Coverage is M1 Markdown documents and their attributes/links, not every WordPress asset.

Each snapshot contains `assets/<logical-id>/source.md`, `metadata.json`, an immutable attempt plan and a final manifest. Raw Markdown is independently readable. Every retained document is copied, including unchanged documents. All references in the manifest point inside this snapshot and pin S3 Version IDs and hashes. The manifest is published only after copied files are read back. Failed attempts are not listed; retry reuses the same plan and retention deadline. Initial capture can be retried without creating another baseline; a changed baseline cannot silently replace it.

Normal edits still store only the edited document and successful history. Recovery reads a selected snapshot and contiguous later history. Missing history or content fails recovery. Original bytes are preserved; rendered document links are remapped on the new WordPress. Publication status is preserved. The database is not used to discover snapshot contents or history.

## Operation

Tools → Resilience: configure bucket/prefix/region, protection and an optional Checkpoint interval in days. Zero means manual; there is no fixed daily default. WP-Cron requires traffic or an existing scheduler. Initial capture requires an unused stream and explicit administrator acceptance. Existing confirmed M1 history can instead create its first Checkpoint from S3. Use Create Checkpoint now or the scheduled event; use Restore Checkpoint + later history on the target. Pending formal history must be resolved first. If there are no new operations, keep the existing complete snapshot rather than copy it again.

## Retention and deletion

Object Lock minimum retention and application recovery-point retention are separate. The newest verified complete Checkpoint is always retained. Other Checkpoints within the configured recovery-point age window are also retained, together with every later successful history record and its complete originals. Expiry alone never authorizes removal of a required resource.

Tools → Resilience offers **Preview expired versions** and **Delete previewed versions**. Both manual execution and optional automatic cleanup use the same plan. The default recovery-point window is 90 days; zero keeps the latest baseline and its required tail. This is a cleanup policy, not the Checkpoint creation interval. Automatic cleanup is disabled by default and, if enabled, runs only after a successful scheduled Checkpoint check. A nonzero Checkpoint interval is required. Nothing is enabled by upgrading.

Preview reads S3 only. It verifies retained snapshot contents and continuous subsequent history, inventories exact versions, and checks retention and Legal Hold explicitly. Execution repeats that inspection under the same writer lock as normal saves and rejects a stale preview. Pending formal history prevents cleanup. An active lock/hold on any candidate stops the entire run before deletion. S3 still enforces any protection added after inspection; a refusal or lost response stops the remaining deletes and is reported. There is no bypass or hold-removal request.

Only recognized expired snapshot files, covered history records, and unreferenced old originals are eligible. Unfinished/unadopted originals can be reclaimed only when old enough and no pending save exists. Unknown paths are retained. Multiple versions of one managed key or delete markers stop cleanup for separate review; the product writes immutable single-version keys. Deletes always specify VersionId, never a prefix or delete-marker-only operation. Old manifests/history are retired before data. After interruption, regenerate a preview from S3; already removed versions are absent and orphaned eligible old data can be reclaimed. No local deletion ledger is required to resume. One writing WordPress per prefix remains a requirement; external mutation/lifecycle jobs must not independently prune these assets.

### Permissions and validation boundary

Cleanup needs the normal read permissions plus prefix-scoped `s3:ListBucketVersions`, `s3:DeleteObjectVersion`, bucket `s3:GetBucketObjectLockConfiguration`, and, for Object Lock buckets, `s3:GetObjectRetention` / `s3:GetObjectLegalHold`. Missing read permissions stop planning; delete denial stops execution. Existing IAM has not been changed. See [AWS operation permissions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-policy-actions.html) and [HEAD lock-header visibility](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html).

The cleanup candidate was exercised with an in-memory versioned S3 double and actual WordPress re-registration in the existing dm Docker environment. Age windows, latest-baseline protection, tail preservation, holds, stale plans, interruption/resume and ambiguous version inventories were tested. The scheduled callback was exercised directly; real elapsed scheduler execution and AWS-side deletion enforcement are not thereby proven. No real S3 asset was deleted and the new deletion code is not deployed to the running source or recovery plugin. Source UI snapshot creation and real-S3 Checkpoint-plus-tail recovery passed separately; elapsed scheduled execution remains deferred; no fixed daily policy is implied.
