# 復旧方式に関するよくある疑問

[English](recovery-faq.md) · [利用ガイド](user-guide-ja.md) · [復旧仕様](site-snapshot-ja.md)

Ozeki Resilienceは、保全した原本・Baseline／Checkpoint・正式履歴から対応範囲の状態を再構築します。別の稼働サイトへ任意のレコードを合流させる汎用インポーターではありません。以下では**設計上の対策・既存の確認結果・利用条件**を区別します。攻撃後に元環境を再利用せず業務を再開するための[役割と保証範囲の説明](../RAADME-jp.md#攻撃の後もサイトを再開するために)を先に確認してください。このFAQ作成のための追加試験は行っていません。

主な説明対象は、**専用の復旧先へのサイト全体復旧**です。旧Markdown個別復旧は別の操作であり、サイト全体の関係再現の保証をそのまま適用しません。この0.3.1申請候補はMarkdown未使用なら追加導入不要です。Markdown文書・原文がある場合の条件は利用ガイドに従ってください。

## 1. 自動採番でIDが変わり、関係が壊れませんか？

**設計上の対策：** サイト全体復旧では対象コンテンツテーブルを置換し、元のIDを明示して保存行を挿入します。投稿ID・Term IDをインポート順に新規採番する方式ではありません。再構築するデータ内の投稿とカテゴリー、アイキャッチ、親子参照などのID上の対応を維持します。ユーザーは別処理で、元の著者・対応する会員を復旧先ユーザーへ対応付け、対応範囲の投稿著者・コメントユーザー参照を調整します。

**確認済みの動作：** 復旧試験でアイキャッチのID・原本バイト、カテゴリー／タグID、削除結果を照合しています。WP-Membersでは対応会員のログインと閲覧制限を確認しています。[通常投稿の関係の検証](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/main/docs/releases/native-details-final-m1-031.md)・[会員の検証](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/main/docs/releases/members-m1-031.md)。

**利用条件：** クリーンな専用復旧先を用意し、コンテンツを置換します。別サイトの投稿との合流ではありません。任意のカスタムフィールドをすべて解釈・対応付けする機能ではなく、認識した属性はアダプターの規則で適用し、取得済みの未知情報はS3に残して未適用として報告します。元から壊れた参照をID保持で修復できるわけではなく、すべての参照の組合せを検証済みともしていません。[適用規則](application-rules.md)を参照してください。

## 2. URL変更や日本語でシリアライズされた設定が壊れませんか？

**設計上の対策：** 認識したシリアライズ属性は値へ復号し、必要な変換後に再シリアライズします。URL変更時に、文字列長の情報を残したまま保存文字列を直接置換する方式ではありません。新しい長さはPHPが計算します。JSONもエラーを検出して復号・符号化します。分離原本形式は送信フィールドを再構成し、必要な場合は標準的な再シリアライズ結果と異なる元の表現も保持します。オブジェクト型の設定を自動的に実体化して移植設定として適用しません。

**確認済みの動作：** 既存の分離試験には、日本語・改行を含む送信フィールド、欠落のない再結合、未知フィールドの保持が含まれます。適用規則試験ではCF7の認識した入れ子属性も確認しています。[分離保存の検証](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/main/docs/releases/separated-assets-m1.md)・[分離処理の実装](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/main/packages/markdown-m1/src/AssetFormat.php)。

**利用条件：** 一般的な単純置換による文字列長の破損を避ける方式ですが、壊れた元データの修復や任意プラグインの符号化の解釈を約束するものではありません。認識した属性の不正なシリアライズは拒否します。取得済みの未知項目は無造作に適用せずS3に残します。絵文字・文字コード・入れ子・URL形式の全組合せを実証したわけではありません。エラー時は保護原本を書き換えて回避せず、原因を確認してください。

## 3. WordPressやプラグインの版が違っても大丈夫ですか？

**設計上の対策：** 復旧はデータ構造を自動移行する機能ではありません。WordPressは記録したリリース系列で同等以上の保守版を要求します。収録テーマ・選択したプラグインファイルはハッシュで固定します。アダプターごとに確認内容は異なり、WP-Membersは導入版と記録版、フォーム履歴は記録した依存、TablePress履歴は収録版との整合を検査します。任意プラグインに共通の版変換機構ではありません。

**確認済みの動作：** 検証記録には使用したWordPress・PHP・プラグイン版を明記しています。互換性のある実行環境を準備して確認しており、任意の旧版から新版への互換性を実証したものではありません。[検証索引](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/main/docs/releases/product-evidence-index.md)と[README](../RAADME-jp.md)から個別記録を参照してください。

**利用条件：** 版を記録し、必要な互換プラグインを復旧前に準備します。Markdown復旧はMarkdown Documents 0.1.1を事前に利用可能・有効化した環境で確認しています。コードが収録されていても、実行中のPHP要求ですでにロードしたクラスを別版へ置き換えられる保証ではありません。履歴で追跡しない実行環境の変更後は、新しい信頼済みBaselineが必要です。通常Checkpointは新しい稼働コードを取り込みません。依存不一致なら強制インポートせず、記録した環境を準備してください。[導入条件](install-update.md)。

## 4. データだけ戻り、テーマや独自動作を失いませんか？

**設計上の対策：** 信頼したBaselineには、コンテンツ・アップロード資産に加え、選択した子／親テーマと対応する有効な依存プラグインを、ハッシュ確認するソフトウェア書庫として収録します。取得対象テーマの `functions.php` が一律に省かれるわけではありません。通常Checkpointは保全したS3資産と正式履歴を使い、未記録の稼働ファイルは取り込みません。

**確認済みの動作：** サイト全体試験では本文・画像・対応プラグインの動作を確認しています。直近の条件付きMarkdown試験はプラグイン収録とソフトウェアのハッシュを確認しましたが、復旧先には同一ソフトウェアが存在したため、空ディスクへの展開試験ではありません。[その検証範囲](optional-markdown-verification.md)。

**利用条件：** ルートの `.htaccess`、Webサーバ・PHP設定、DNS、外部API、秘密情報、任意の対象外プラグインまで環境全体を再現する約束ではありません。管理者が別途用意します。テーマ内のコードが外部サービスに依存する場合もあります。コードは保存時のハッシュとの一致を検査して復旧します。この検査は不正コードの検知・除去ではないため、初期Baselineに含めるコードの信頼性を管理者が確認します。追跡対象外の変更は新しい信頼済みBaselineへ取り込みます。[BaselineとCheckpointの責任範囲](site-snapshot-ja.md)。

## 5. WordPress保存後にS3の履歴確定が失敗したらどうなりますか？

**設計上の対策：** WordPressとS3を一つの原子的トランザクションにはしていません。対応する本文保存はWordPress反映前にS3へ原本を保存し、コメントや一部の連携・付随情報は操作成功後のデータを取得します。新規保存資源は固定版から再取得・照合して正式履歴を書き込みます。未確定・エラーは確定履歴と区別します。サイト全体Checkpointは正式S3履歴を使い、履歴の欠落では停止します。未確定の変更を稼働DBから黙って追加しません。

**確認済みの動作：** 既存の失敗注入・再開試験で、未確定と失敗理由の表示、後の履歴確定を確認しています。原本照合の失敗時は確定しません。これらの限定試験は、あらゆる実AWS障害や強制終了の瞬間を検証した証拠ではありません。[保存・再開の検証](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/main/docs/releases/save-resume-acceptance.md)・[原本照合の検証](https://github.com/ozekihiroshi/ozeki-wordpress-resilience/blob/main/docs/releases/save-verification-final-m1-031.md)。

**利用条件：** 保護設定のチェックやWordPress画面の更新だけでは保護の確定を意味しません。最後の確定履歴と未確定・エラーを確認します。原因解消後、キューにある操作は履歴再開、キュー登録前の失敗は再保存します。正式確定前に元サーバを失った操作は復旧対象外です。復旧処理自体が失敗した場合は停止し、自動継続や無条件の巻戻しは約束しません。[保存失敗からの手順](save-resume.md)。

## 復旧でエラーが出たとき

選択したCheckpoint、履歴終了番号、製品・プラグイン版、記録されたエラーを控えます。失敗した最新試行と詳細を確認し、以前の成功表示で代用しません。S3資源を保全し、原因を特定して復旧先を整え、再実行を判断します。問い合わせに認証情報や非公開原本を添えないでください。環境の準備不足や対応範囲外と、必要資源の喪失や成功の誤表示は区別して扱います。
