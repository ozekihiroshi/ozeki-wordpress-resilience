# 初回保存・自動記録だけを渡す接続確認（2026-11-28）

## 結論

3点の統合は未完了。実際の初回保存と自動記録の固定版を独立した復旧先へ渡し、読み取るところまでは確認した。保存素材だけによる通常登録・新ID参照接続・利用確認までは成立を確認していない。

以前の結合試験では、復旧先でも試験用の構築手順を使い、投稿者の旧ID 1を準備済み管理者ID 1へ対応付けていた。今回、その手順・ID対応表を渡さずに既存の初回保存素材を点検すると、投稿者情報は `display_name` と `user_nicename` だけだった。ログイン名・メールアドレスを保存していないため、同一人物として通常のアカウント登録を行う根拠がない。

これは投稿者情報を維持した自動再構築の不足であり、WordPressが記事を登録できないという意味ではない。管理者へ無断で付け替える、表示名からログイン名を推測する、メールアドレスを生成する処理は追加しなかった。今回の専用試験は登録前で保留し、復旧先を変更していない。

さらに、全対応操作の通常登録実行器そのものの統合も未完了である。この材料不足だけを直せば全自動再構築が完成する、とは評価しない。

## 今回の追加

- `ConstructionTransfer`：既存の `Store::put/get` を使い、初回保存素材・自動記録入力・登録結果・確定参照を別の実験用名前空間へ保存。固定版とハッシュを読み戻してから、選択した範囲の確定参照を発行する。
- `ConstructionReadiness`：渡された素材だけで投稿者の通常登録材料、添付原本、後続操作の参照先不足を検出する。復旧先の同名管理者を暗黙に採用しない。これは限定的な材料点検であり、完全な再構築計画器ではない。
- `kit-operation.php`：Reflectionで取り出した簡略データではなく、実際の `SiteSnapshot::capture()` と `load()` で初回保存を作る。
- `run-kit.py`：合成サイトの通常構築と自動記録後、別の復旧先へ保存オブジェクトと確定参照だけを渡す。元サイトで使った手順や実行中のID対応表を復旧先の点検へ渡さない。

既存の初回保存・正式履歴形式を上書きしていない。`construction-experiment/` 以下の開発用接続であり、既存の製品UI・正式履歴キューに統合済みとはしない。通常リクエストからの自動転送・再開も未統合。

構文確認と既存の `tests/construction-operations.php` もネットワークなしのPHP 8.3コンテナで通過。操作前入力、未確定結果、初回保存の到達点、前半記録の変更拒否、保存中の変更、資格情報の除外、書込み後の失敗を確認した。

## 3点の残り

| 接続 | 現在の状態 | 残ること |
|---|---|---|
| 自動記録だけから通常登録を実行 | 自動記録の固定版転送・読取りまで確認 | 全対応操作の引数・参照の明示的な解決と通常登録実行器の統合。試験用手順による代行を廃止 |
| 初回保存からの新ID接続 | 実初回保存との到達点接続と材料不足検出を確認 | 投稿者の材料・扱いを明確にし、通常登録が返すIDで後続操作を接続 |
| 保存・確定・中断再試行 | 実験用ストリームで固定版の確定と保存再試行を確認 | 製品の通常保全処理への接続。登録処理側の中断再開との一体確認。未確定操作は推測して成功扱いにしない |

次に必要なのは、管理者の資格情報を復元することではなく、投稿者として必要な識別・通常登録用素材をどこで確定するかの整理である。既存の原本にない情報を後から捏造しない。復旧先管理者へ割り当てる運用を採る場合も明示的な利用者判断であり、自動的な補正にしない。

本番・既存原本と履歴・ZIP・タグは変更なし。研究側の未コミット変更も変更なし。GitHubへのpush、申請、メール返信は行っていない。
