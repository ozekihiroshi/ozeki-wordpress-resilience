# Ozeki WordPress Resilience

[English](README.md) | 日本語

**失えば取り戻せない情報を守り、失われた、あるいは信頼できないWordPressだけに、情報を取り戻す手段を依存させない。**

## 1. Why — 従来のバックアップだけでは解決できない問題

バックアップは、誤操作や障害の前の状態へサイトを戻すために役立ちます。しかし侵害後には、別の問いが生じます。**そのバックアップに含まれるWordPressのDBやシステム状態を、そのまま復元してよいのでしょうか。** 復元が成功したことだけでは、戻した状態を信頼できるとは判断できません。

問題は、バックアップの有無だけではありません。重要な記事・文書・画像・業務記録が、それを管理するアプリケーションや設定、実行される処理と結び付いていると、システムを失ったときや信用できなくなったとき、情報の救出までシステムの復旧に依存してしまいます。

Ozeki WordPress Resilienceが重視するのは、この依存を減らすことです。情報が作成・確定される段階で独立した原本を確保し、再構築の根拠を残します。通常のバックアップの価値は変わりません。Ozeki Database Backup for S3は別製品であり、本製品の依存先ではありません。

## 2. Philosophy — システムより情報資産を優先する思想

**復旧資源を失うことには不可逆性があります。一方、再構築処理は原則としてやり直せます。** そのため、あらゆる復旧失敗を自動修復することより、情報を確実に残すことを優先します。

目指すのは、元のWordPressやこの復旧エンジンがなくても、原本自体を理解し利用できる構成です。完全なMarkdown・HTMLの本文、メディアファイル、読める構造化データを保存し、解釈に必要な属性や関係を別に持ちます。更新版はそれぞれ完全な資産であり、ファイル内容の差分ではありません。情報を保存することと、新しいシステムへ自動適用することは分けて考えます。

再構築では、既知の型と明示した規則を使います。その規則では適用できない取得済み情報も、適用できないという理由だけで捨てません。同時に、保存されているからというだけで設定を無条件に取り込むこともしません。

**これは設計上の規律であり、データの無害性の保証ではありません。** 管理者が信頼する初期状態と、保存時点で受け入れた入力を前提とします。分離保存・版の固定・ハッシュによって、マルウェアを排除したり、入力が無害だと証明したりはできません。以下に現在の実装と限界を示します。設計上の目標と、現時点の対応範囲は同一ではありません。

## 3. Architecture — 独立原本・確定履歴・Checkpoint・選択的再構築

1. **信頼する初期スナップショットを作る。** 管理者が既存サイトを適切と判断し、編集を止めて取得します。対応するサイト状態の出発点となる資源です。
2. **独立原本を確保する。** 対応する操作では、実データと付随情報を分離し、資産の完全な各版をS3へ保存します。通常更新では対象資産を保存し、毎回サイト全体の目録は作りません。
3. **履歴を確定する。** S3の正式履歴には成立した操作を順序付きで記録します。現在の履歴確定処理では、操作の原本と参照画像を固定Version IDから再取得・照合してから履歴を書きます。原本が存在するだけ、WordPressへの反映が成功しただけでは確定としません。
4. **独立したCheckpointを作る。** サイト全体のCheckpointは、信頼したS3上の基点と確定履歴から必要な資源をコピーします。古い世代を指す目録だけではありません。選択したCheckpointと後続履歴に必要な資源を保持します。
5. **準備したWordPressへ選択的に再構築する。** Checkpointと履歴の終了番号を選び、対応する状態を再現します。認識した属性・設定はアダプターの規則で適用し、未知の取得済み情報はS3に残します。未適用項目と理由を報告します。元サーバ・旧DB・ローカル未確定キューは復旧の必須入力ではありません。

保護対象の記事本文は、WordPressへの反映前にS3へ保存します。一方、コメント、記事の付随情報・削除、対応する外部プラグインのアダプターは、成立した操作のデータを取得します。この場合、履歴が未確定でも元サイトへの変更は表示されていることがあります。本文と関連操作は別々に確定する場合があり、WordPressとS3をまたぐ一つの原子的トランザクションではありません。

確定前に元環境を失った場合、その操作は復旧対象外です。未確定の新規記事は存在しないものとし、未確定の更新は直前の確定版までを対象にします。サイト全体の再構築は復旧先の対応状態を置き換えるため、専用の復旧環境を準備します。個別の本文復旧は補助機能であり、サイト全体の再構築を代替しません。

`publish`を含む保存された公開状態を再現します。サーバの準備、外部への公開、DNSの判断は管理者の責任です。常設の別EC2は必要ありません。必要時の再構築であり、常時レプリケーションではありません。

## 5. Scope and Limitations — 現時点で約束できないこと

- **原本保全は無害化ではありません。** 完全なマルウェア排除や無条件の復旧成功を保証しません。本文は本文のまま保持され、型やハッシュの確認は無害性の証明ではありません。
- **現在の基点保存は、ソフトウェアをクリーンに入れ直す仕組みではありません。** 選択したテーマ・プラグインのコードやコンテンツテーブルの記録もファイル・JSONとして含みます。すべてを信頼できる配布元から新規取得する方式ではありません。情報自体の取出しと、サイト動作の再現は異なり、後者には互換性のあるWordPress・プラグイン・解釈規則が必要です。
- **対応範囲は限定されています。** 任意のプラグイン・拡張機能、全メタデータ、下書き・予約状態の完全再現、外部・CDN資源には対応しません。追跡対象外のテーマ・メニュー・テンプレート・実行ソフトウェアの変更には、管理者が信頼する新しい基点が必要です。未知項目を残す規則も、もともと取得対象外の情報を保存可能にするものではありません。
- **選択的な適用により、外観や動作が変わる場合があります。** 未知の取得済み項目は保存されますが、無条件には取り込みません。現行規則ではウィジェット設定、未認識のテーマ設定、TablePressの独自CSS・モジュール・コマンド等を自動適用しません。プラグインへの対応は、全拡張・全設定の認定ではありません。
- **保持とアクセスが前提です。** S3の版管理、適切な権限、prefixごとに一つの保存元、必要な固定版の保持が必要です。外部からの任意削除やアクセス喪失後まで保証しません。本文は5 MiB、対応する画像は1ファイル32 MiBが上限です。大規模サイトでの処理性能は確立していません。
- **確定には境界があります。** 元環境喪失後に未確定操作は復旧できません。旧履歴の遡及認定や、状態表示時の全原本監査は行いません。新しいcheckpoint-verification候補では、初期スナップショット／Checkpointの全資源も固定版から再取得・照合してからマニフェストを書きます。公開済みv0.3.1-pre.1にはこの変更を含みません。DB障害・強制終了では失敗診断を残せない場合があります。
- **運用自動化には未確認部分があります。** 実時間での定期実行、サイト全体の実削除の受入確認は保留です。保持プレビューは削除の許可ではなく、旧資産単位の削除処理はサイト全体用ではありません。復旧の自動継続、インフラ構築、DNS切替、メール再送は保証しません。

必要な依存バージョン・権限・細かな対象外事項は、導入手順と各アダプターの仕様を確認してください。ブラウザ表示やコンテナのメモリ不足等の試験環境の事象は、製品不具合と分けて記録し、製品の復旧目的を変更する理由にはしません。
