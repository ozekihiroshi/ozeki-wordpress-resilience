# Ozeki WordPress Resilience — Markdown M1

## 通常編集・画像の確認済み範囲（2026-10-24）

通常のPages・Postsの作成・公開・更新・ゴミ箱への移動と復帰を、WordPress標準編集画面から行います。対象画像は登録前にS3へ保存し、本文で参照する原寸画像・縮小版を成功した記事の版へ結び付けます。通常本文は完全なHTMLファイルであり、DBダンプや内容差分ではありません。全サイト基準スナップショットと後続のS3正式履歴から、公開状態を含めて復旧します。

試験記事でブラウザからの画像追加・差替えと別WordPressへの復旧を確認しました。Chromeのビジュアル挿入とReplace/メディア選択で成功し、コードエディタは使用していません（履歴25・26）。アプリ内ブラウザではblobの編集iframeが空白でしたが、同じサイト・ユーザー・記事がChromeでは無変更で動作しました。ブラウザ環境の制限として区別し、内部原因は未確定です。この操作にはChromeを利用してください。Resilienceの保存・復旧不具合と断定する根拠はありません。

アイキャッチ変更、未使用メディア、外部/CDN資産、任意のメタ情報・分類変更、外部ツールによるバイナリ上書き、完全削除、予約公開の保証は対象外です。画像はJPEG/PNG/GIF/WebP/AVIF、1ファイル32 MiB、本文は5 MiBまでです。復旧は明示実行であり自動同期ではありません。実時間による定期実行確認は後回しです。任意の整理機能は初期状態で無効で、実S3削除の受入完了は主張しません。

最終ZIPの導入・更新結果は同梱外の検証報告に記録します。試験コード・認証補助はZIPへ入れず、AWS SDK標準認証を使用します。ファイル更新で設定や履歴を消す移行処理は行いません。正式履歴はS3にあります。切戻し用コピーを残し、更新時に保存先prefixを削除しないでください。


**サイト全体の再構築：** [全体初期スナップショット・Checkpoint](docs/site-snapshot-ja.md)で固定ページ・メディア・テーマ・メニュー・表示設定を保存する経路を追加しました。対応範囲と後日の変更取得に残る制限を参照してください。以下のMarkdown限定の説明は従来M1経路のものです。

Markdownの完全原本と成功履歴をS3へ独立保存し、元サーバ・旧DBを使わず新しいWordPressへ文書を再登録します。

製品経路はWordPressプラグイン＋Ozeki Markdown Documents＋S3です。旧研究用Pythonワーカー・SSH署名ヘルパー・共有bridge・Docker・専用本文編集画面は必須にしません。受入試験のDockerや認証補助は製品ZIPに含めません。

## 利用手順

1. PHP 8.1以上、posts/postmeta/optionsがInnoDBのWordPressに、両プラグインを導入・有効化します。
2. AWS SDK標準の認証供給方法（サーバのロールや環境変数等）を設定します。秘密情報はWordPress設定に保存しません。
3. **ツール → Resilience**でbucket、region、専用prefix（末尾 `/`）、任意のアカウント所有者・保持日数を指定します。S3 Versioningが必要です。保持日数を指定する場合は既存のObject Lock対応bucketが必要です。プラグインはIAM・bucket設定・既存版の保持期限を変更しません。
4. prefixに限定した一覧・原本読取り・版読取り・新規保存権限を設定します。保持付き保存にはPutObjectRetentionも必要です。保存・復旧には削除権限は不要です。任意の整理機能には別途確認した版削除・保持情報読取り権限が必要です（docs/checkpoints-ja.md）。保持回避権限は使用しません。一つのprefixの書込み元は一つのWordPressとします。
5. 保護を有効化し、通常の**Markdown Documentsの編集画面**で公開・更新します。

各版は `originals/<文書UUID>/<操作UUID>/source.md` と付随情報です。成功操作だけを `history/<確定順>.json` に記録します。毎回の全サイト目録・本文差分は作りません。S3から原文の固定VersionIdを指定して通常のMarkdownとして直接取得できます。

## 失敗と復旧

- S3原本保存失敗：WordPressの確定反映前に停止。編集画面に戻って再試行します。
- WordPress反映・照合失敗：DBトランザクションを戻し、正式履歴には採用しません。
- WordPress反映成功後の履歴保存失敗：「履歴確定待ち」を表示。**Resume history**で反映内容を照合し、同じ履歴キーへ再送します。修復まで次の保護対象編集を待機させます。対象外の下書き・予約操作は通常どおり利用できます。
- 正式履歴がS3に残る前に元サーバを失った場合、その未確定操作を成功と推定しません。確定済み履歴までを復旧対象にします。WordPressとS3間の完全な同時コミットは保証しません。
- 新しいWordPressに両プラグインを入れ、同じS3保存先を設定します。履歴から文書ごとに一つの版を選び、**Restore selected versions**を実行します。元DB・ローカル台帳から復旧候補を探しません。新しいID・採用順・hash・状態を結果表示します。
- 元がpublishならpublishへ戻します。ネットワーク公開・DNSの判断はシステム管理者の責任です。

原文は通常編集画面から受け取ったバイト列を保持します。ブラウザtextareaによる改行の変換は区別します。記録済みの文書の正規URLへのリンクを表示時だけ新URLへ対応付け、原文を書き換えません。参照先も一緒に復旧してください。任意のURL・外部資産・埋込みshortcode・相対URL・外部プラグイン固有関係の汎用移行は対象外です。

## 保持と保証範囲

各操作の原文・付随情報・履歴には同一の任意保持期限を指定します。必要な版を消すLifecycle設定にしないでください。保持延長は対象外です。追加のCheckpoint・任意の削除機能はdocs/checkpoints-ja.mdを参照してください。自動削除は初期状態で無効です。原文上限は5 MiB、NULを含まないUTF-8です。履歴一覧は小規模向けのprefix走査です。複数WordPressから同一prefixへの同時書込みは対象外です。

認証済みMarkdown編集と、標準の固定ページ・投稿の保存をS3先行保存・正式履歴へ接続しました。通常のブロック本文は完全なsource.html、Markdownはsource.mdとして保存します。保護済み資産または公開済み資産のゴミ箱移動・復元も状態変更として記録し、全体Checkpointと後続履歴から再現します。復旧先の常時自動同期ではなく、復旧は明示的に実行します。

今回の追加対象は本文・タイトル・スラッグ・公開状態・日時・抜粋・親/順序・コメント設定です。画像upload/sideloadではWordPress登録前に原本をS3へ保存します。通常投稿・固定ページの公開/更新では本文が参照するローカル画像の原寸・生成サイズ・添付情報・代替テキストを成功した版に結び付け、全体復旧時にS3から取り出して内部URLを復旧先へ置換します。画像差替えは別の画像を選ぶ操作であり、外部プラグインによる同一ファイル上書きは対象外です。未使用メディアライブラリ、外部/CDN画像、アイキャッチ画像変更、分類変更、独自メタデータ、任意の動的ブロック依存は含みません。初期保存済み資産は引き続き利用します。完全削除/ゴミ箱を空にする操作の追随、未公開下書きの完全復旧、予約状態・予約公開時の自動保護は今回の受入対象外です。古い編集画面の拒否はMarkdown全文編集で提供し、通常投稿はWordPress標準の編集制御を利用します。

標準投稿/固定ページの全面対応、添付資産の再構築、業務CSV/Excel、任意プラグイン、全サイト構築、ネットワーク切替、旧研究移行、高度監視、常設復旧サーバは対象外です。保存フック内の外部副作用や独自COMMITはDBロールバックの対象になりません。試験外のobject cacheとの互換性は別途確認が必要です。

ZIPは既存AWS SDK for PHPを同梱し、試験補助は含めません。Markdown Documentsは別途必要です。実測結果と未達条件は受入報告で区別します。このREADME自体は合格証明ではありません。
